# Notifications, Reminders, and Push Delivery

## Purpose and Scope

This module owns household notification records, bell/history presentation, per-user read/dismiss state, FCM subscription and delivery, foreground/background handling, and deep-link navigation. Feature modules own the events and due calculations that create records.

## User-Facing Capabilities

- View recent active notifications from the header bell, grouped into Today, This week and Earlier. The bell is named "Notifications" (with the unread count), rings briefly and pops its badge when a new unread notification arrives (the badge's number ticks to the new count with `NumberTicker`; "9+" above nine), and shows an "All caught up" illustration when empty.
- Open seven-day history at `/notifications`, grouped into Today, This week and Earlier. Cards show the title, message, age, a plain-language source ("Home maintenance", "Warranty", "Chore assignment", "New member"...) and who dismissed or completed it; internal source names and expiry stamps are never shown.
- An empty Unread filter shows the shared `EmptyState` (notifications illustration, "All caught up" with a friendly line that stays the same all day); other empty filters offer "Show all".
- On a hovering pointer, a card's dismiss button appears on hover or when the card has keyboard focus. On touch screens (touch, or a pen on a coarse-pointer device) the dismiss button is always shown and swiping a card left dismisses it; a mouse drag does nothing. Only the card's visual layer slides; the card and its link stay in place, so taps land where they were aimed. With reduced motion nothing slides: the dismiss hint fades in over the card and a completed swipe dismisses it in place.
- Every dismissal (swipe, button, Dismiss visible, Dismiss all) shows a toast with Undo for 10 seconds (the shared `UNDO_WINDOW_MS`); Undo removes the member's own dismissal. Only one dismissal toast shows at a time (a newer dismissal replaces the older toast at once through the toast `group` `notification-dismiss`; other toasts may show beside it), so dismissals made within 10 seconds of each other accumulate: the newest toast counts them all ("2 notifications dismissed") and its Undo restores them all. The window runs from the latest dismissal (`src/app/notifications/undo-batch.ts`, one batch per household and member shared by the bell and the center).
- Pushes show the app icon (`/icons/icon-192.png`), a monochrome house badge for the Android status bar (`/icons/badge-96.png`), and, when the notification is about a pet or a product with a photo stored in the household, that photo as the large image.
- Filter unread, all, dismissed, and feature categories. The Unread filter shows the unread count (a `NumberTicker`, same visibility rules as the list). Each group's cards enter staggered (`Stagger`, replayed when the filter changes, instant under reduced motion).
- On a hovering pointer, resting on a Notification Center card (or focusing its link from the keyboard) for 400 ms shows a peek card (`PeekCard`, H26) with the exact time, where the link opens (`notificationDestination`) and who completed it. The peek wraps the whole card, so the card and its link keep their own structure and hit targets; touch never shows it.
- Mark a notification read by opening it.
- Dismiss one or all active notifications without deleting history.
- Follow supported deep links to source pages.
- Enable/disable browser push notifications from Profile.
- See the unread count as a badge on the installed app's home-screen or taskbar icon where the browser supports the Badging API.

## Architecture and Data Flow

Feature code creates household notification documents with `buildNotificationDocument`. Bell and center queries parse legacy/current shapes, merge duplicate semantic identities for presentation, filter per-user target/read/dismiss state, and write only the current UID's map entries. Swipe handling lives in `src/app/notifications/swipe-dismiss.ts` (`useSwipeDismiss` plus pure helpers, shared by the bell and the center). Its pointer handlers sit on the card wrapper, which never moves; only the `data-swipe-visual` layer inside the link is translated. Cards keep vertical pan (`touch-pan-y`), capture the pointer only after 6 px of horizontal travel (so a tap still opens the link), swallow the click that ends a swipe (so a swipe that starts on the dismiss button, which sits where a left swipe naturally starts, does not also press it; a tap still does), and dismiss when released at least 70 px left (200 ms slide-out). Action entries (`readBy.<uid>`, `dismissedBy.<uid>`, maintenance `resolvedBy`) are built by `createNotificationAction` and hold `at`, `uid` and `displayName` only: every member who can read the notification sees them, so they no longer carry the email. Older entries may still have one; the center never shows it (who completed or dismissed something is the display name, else "Household member"). Dismissals go through `useDismissNotifications` (`src/app/notifications/use-dismiss-notifications.tsx`): one batch sets `dismissedBy.<own uid>`, wrapped in `awaitWriteUnlessOffline`, then a 10-second toast offers Undo, which deletes the same key with `deleteField()`. Both writes change only the caller's own key, which the existing rules allow.

Audience queries: every client list query of notifications carries `where('audience', 'array-contains-any', [uid, '*'])` (`audienceConstraint` in `src/app/notifications/notification-query.ts`): the bell, center and dashboard tile through `notificationWindowQuery`, and Maintenance Center's two reminder resolvers through `notificationsBySourceQuery`. A document whose `audience` names neither the member nor everyone, or that has no `audience` at all, is not returned, and the read rule refuses any list query that lacks this filter (see Authentication, Roles, and Security).

Category queries: for a member who cannot see every module, the bell, center and dashboard tile also put the category filter in the Firestore query (`where('category', 'in', viewable)` with `system` and `general` always included; `src/app/notifications/notification-query.ts`), so the bell's 30-item cap counts only notifications they can see and a busy hidden category cannot push theirs out. Full-access members keep the unfiltered query. Stored categories are always one of the seven known values. Composite indexes in `firestore.indexes.json`: (`audience` array-contains, `createdAt` DESC) for the full-access window, (`audience` array-contains, `category` ASC, `createdAt` DESC) for the category-filtered one, (`audience` array-contains, `sourceType` ASC) for a deleted asset's or vehicle's reminders and (`audience` array-contains, `sourceType` ASC, `sourceId` ASC) for one schedule's reminders. The older (`category` ASC, `createdAt` DESC) index is no longer used by the app.

Category visibility (`functions/src/shared/push-audience.ts`, shared by the push sender, bell, center and dashboard tile): notifications in a module category need that module's view permission (`chores` → `chores.view`, `pets` → `pets.view`, `shopping` → `shopping.view`, `maintenance` → `maintenance.view`, `automation` → `automation.view`); `system` and `general` need none. In the app this uses the member's effective permissions; on the server `memberCanView` mirrors the rules (owner always, explicit override wins, then the role default; a unit test checks it against `getEffectivePermissions` for every role). A member who lacks the permission sees none of that category in the bell, center or unread tile and gets no push for it, not even text.

The bell's active list is `activeBellNotifications` (not expired, visible to the member, allowed by category permission when the caller passes `canView`, unresolved, not dismissed by them, at most 10), applied after `deduplicateNotifications`; the dashboard's unread tile uses the same two steps, so duplicate legacy copies are counted once and a read or dismissal on either copy applies to both. Presentation helpers in `src/lib/dashboard/notification-display.ts` also group items by local day (`today` since local midnight, `week` for the six days before, `earlier`) and map `sourceType` values to plain labels (unknown values show nothing rather than the raw name). Bell ring and badge pop are CSS animations from `src/components/dashboard/dashboard.module.css`, keyed so they replay only when the unread count increases after the first load; both are removed under reduced motion. Load failures in the center show `friendlyError` text; dismiss failures use `toastError`.

A Firestore create trigger resolves recipients, sends FCM, and removes invalid registration tokens. Foreground messages become toasts. `/api/sw` serves HomeHub's single service worker: Firebase Messaging background display and deep-link clicks, plus the offline app shell owned by [Application Shell and Dashboard](../application-shell/README.md). Production builds register it on every page load through `PushNotificationManager`; `PushNotificationSettings` registers the same URL and scope (`src/lib/service-worker.ts`) on push opt-in and so receives the same registration for `getToken`. Background display: when a payload carries a `notification` block, the Messaging SDK shows it itself (with the server's icon, badge, image and tag); the worker's `onBackgroundMessage` then shows the same notification with the same `tag`, which replaces the SDK's copy instead of stacking a second one, and routes clicks to the worker's own handler. That display uses `icon` and `image` from `payload.notification` and `badge` and `tag` from `payload.data`, re-checked in the worker: icons and badges only from this origin's `/icons/`, images only as https Firebase Storage download URLs under `households/` in the configured bucket or image paths on this origin, falling back to `/icons/icon-192.png` and `/icons/badge-96.png`. `notificationclick` opens only `/`-relative in-app paths; anything else opens `/`. The check is `safePushLink` in `functions/src/shared/push-link.ts`, the same function the push function uses as `safeDeepLink` for `fcmOptions.link`; the route imports it through `src/app/api/sw/push-link.ts` and embeds its source in the worker (`safePushLink.toString()`). It is self-contained and ASCII-only with no named inner functions, because build tools may wrap those in helpers the worker lacks (tsx's `__name`); the production build's minified copy was checked to run correctly. Beyond the old rule (one leading slash, no `//`) it refuses control characters (URL parsing drops tabs and newlines, so `/<tab>/evil.com` would open as `//evil.com`), backslashes and `.`/`..` segments, raw or percent-encoded, malformed percent-encoding, and anything that does not resolve to the same origin. `tests/unit/notifications-push-link.test.ts` runs one hostile-input table against `safeDeepLink`, the module the route imports and the function embedded in the served worker. If the Firebase scripts cannot be imported (CDN blocked or offline at install), the worker still installs without push and retries on its next update.

`NotificationBell` passes its unread count to `useAppBadge`, which calls `navigator.setAppBadge(count)` (or `clearAppBadge()` at zero) when the Badging API exists. The badge is left unchanged while notifications are loading or failed to load, and cleared when the bell unmounts (sign-out, or loss of `notifications.view`). The badge updates only while HomeHub is open; push messages received in the background do not change it.

## Data Model and Persistence

- Notifications: `households/{householdId}/notifications/{notificationId}`.
- Push tokens: `users/{email}/private/push` `{ fcmTokens: string[], updatedAt }`, owner-only. `registerPushOnThisDevice` (`src/lib/push-registration.ts`, called by `PushNotificationSettings` on opt-in and by the silent registration below) gets the device token with `getToken`, checks that the account is still the signed-in one, reads that document, computes the new list with `nextPushTokens` (stored tokens oldest first, then legacy profile tokens, then this device last, de-duplicated; when that would exceed the rules' cap of 20 the oldest tokens are dropped, so subscribing never fails on the cap), and writes it in one batch (through `awaitWriteUnlessOffline`) that also deletes the legacy profile field. Two devices of the same person subscribing at the same instant can overwrite each other's token; that device re-registers on its next subscribe. A failed subscribe from the Profile card shows the component's own wording for an unsupported browser, a missing VAPID key ("not set up yet", the variable name only in the console) or no token; any other error goes through `friendlyError`, never raw text.
- This device's registration: `localStorage["homehub.push-device"]` `{ v: 1, token, email, at }`, written after every successful registration (`email` is the account whose private document holds `token`, `at` the time it was last confirmed with FCM). It exists so sign-out can remove the token without asking FCM for it. It is never sent anywhere and holds nothing the browser's own FCM storage does not hold. An empty `email` marks a sign-out that could not finish removing the registration; when no token was remembered at that point the placeholder token `"unknown"` is stored with it.
- Sign-out (`logout`, see [Identity and Profile](../identity-profile/README.md)): before anything else `logout` closes the sign-out gate (`pushSignOutGate.begin()`), then runs `runPushSignOut` while still signed in. The whole push cleanup, including downloading `src/lib/push-registration.ts` and Firebase Messaging, shares one 2 s budget (`settleWithin`); it never throws and never holds sign-out up longer, and logs a console warning on failure or timeout.
  - Nothing is loaded when this device has no device record, no registration in flight and no browser push subscription (`hasPushSubscription`): never subscribed, unsupported browser such as an iOS Safari tab, or no service worker.
  - Otherwise `unregisterPushOnThisDevice` first waits for registrations in flight (`pushSignOutGate.drain()`), then removes the remembered token from the signed-in account's document with `arrayRemove` (only if the record names that account) and, in parallel, revokes the device registration: Firebase Messaging `deleteToken`, then the service worker's push subscription is unsubscribed directly if it is still there, so the old token cannot deliver to this browser even when FCM could not be told. This also runs when a subscription exists without a device record (a device subscribed before the record existed, or an interrupted registration); that token stays in the account's document until a push to it fails and the push function removes it. `deleteToken` is pointed at HomeHub's existing worker registration (`navigator.serviceWorker.getRegistration('/')`), because without one the SDK would try to register its default worker file, which HomeHub does not serve; no `getToken` runs at sign-out.
  - When everything succeeded the device record is deleted. Otherwise (failure, the budget ran out, or the browser is offline, in which case the network work is skipped) the record is kept with an empty `email`, or the `"unknown"` placeholder is written when there was no record, so the next sign-in revokes the device registration before registering.
  - Registrations racing sign-out: every registration (Profile opt-in or silent) takes a pass from the gate when it starts and checks it after `getToken`, after reading the token document and after the write (`pushRegistrationStep`). Once sign-out has begun, a pass taken earlier is never valid again and no new registration starts until sign-out is over. A token that arrives after sign-out began is not stored and the device registration is revoked; if the token was already written, it is removed from the account again (`arrayRemove`, possible only while still signed in) and revoked, and if either step fails the token is kept in the device record with an empty `email`. The gate reopens when a sign-out ends without a page reload (emulator mode, or Firestore could not be stopped); after a reload the module state is new. The gate is per tab: a registration running in another tab of the same browser is not stopped by this tab's sign-out.
- Silent registration after sign-in (`syncPushForSignedInUser`, run by `PushForegroundListener` once per signed-in account after the page is idle): browser permission stays "granted" after sign-out, so `pushSignInAction` decides without prompting. Permission not granted, or nobody signed in: nothing. Permission granted and no device record (after a sign-out, or a device that subscribed before the record existed): register a token for the signed-in account. Record for this account older than 7 days: register again, which confirms the token and, if FCM changed it, replaces the old one in the list. Record for another account or with an empty `email`: revoke the device registration first (as on sign-out), then register, so the new account gets a token the previous account never held; if the old push subscription cannot be removed, nothing is registered and the next page load tries again. A token is only ever written for the account that is signed in at the moment of the write. Failures log a console warning; offline, the step is skipped.
- Legacy push tokens: `users/{email}.fcmTokens`. Approved housemates can read the whole profile, so tokens no longer go there; the rules let the field only shrink or be removed. `scripts/ops/migrate-push-tokens.mjs --project <id>` (dry run, counts only) and `--apply` move the remaining ones, one transaction per profile. Until it has run, the push function reads both places.
- `users/{email}/notifications/{notificationId}` is a legacy inbox: its owner may read, update and delete it, and rules deny creation by anyone.

`Notification`, `NotificationCategory`, `NotificationUserAction`, and `NotificationUserActionMap` define categories, source/deep-link fields, optional `stateKey`, targeting, UID-keyed `readBy`/`dismissedBy`, and optional resolution metadata. `expiresAt` defaults to seven days after `createdAt`; parsing supplies that fallback for older records.

Targeting: the web app's `buildNotificationDocument` takes `targetUser: { uid }` and writes `targetUserUid` only, and upkeep's chore reminders no longer write `targetUserEmail` either: the field named the target's email to every member who can read the document. Every reader (bell, center, dashboard, AI overview, push sender, audience derivation) already prefers `targetUserUid`; documents with only `targetUserEmail` (older ones, and the rules' legacy create path) keep working.

`audience` (list of strings) names who a notification is for: `[targetUserUid]` when it targets one member, `['*']` when it is household-wide. It is written at creation by every producer, the web app builder included, each through `notificationAudience` in `functions/src/shared/notification-audience.ts` (shared by the Functions code and the app, like `push-audience.ts`):

- the web app's `buildNotificationDocument` (chore assignment in the Chores page and quick add);
- the upkeep function (`functions/src/reminders.ts`): maintenance and pet medication reminders are `['*']`, chore reminders `[uid]`. A refresh leaves the stored value alone and a reopen writes it again; both add it to a reminder written before the field existed;
- the household server actions (`src/lib/server/household-membership.ts`): the new-member and member-left notices, one per approver, `[approver uid]`; the ownership-transfer notice and the daily pending-member reminder, `['*']`;
- the e2e seed (`scripts/e2e/seed.mjs`).

Every current producer knows the target's uid. For a legacy email-only target the derivation gives the member's uid when the caller can look it up and `[]` (nobody) when it cannot; it never falls back to `['*']`.

Consumers decide from `audience`. The client queries filter on it and the read rule enforces it (see audience queries above). Behind them, one check, `isAddressedToMember` in `functions/src/shared/notification-audience.ts`, decides who a document is for in the bell and center (`isNotificationVisibleToUser`, kept as defence in depth), the dashboard tile, the AI overview and the push sender: a stored `audience` decides on its own (it names the member's uid or `'*'`; `[]` is nobody); a document without it falls back to `targetUserUid`, then `targetUserEmail` (case-insensitive), then everyone. Documents written before the field existed (they expire within seven days) get it from `scripts/ops/backfill-notification-audience.mjs --project <id>` (dry run, counts only) and `--apply`: `[targetUserUid]`, else the uid of the household member with the legacy target email, else `['*']` for an untargeted document, else `[]`. It updates only that field in batches of at most 400, skips documents that already have it or were deleted meanwhile, and is safe to re-run. Documents it has not reached are missing from the client queries and unreadable by clients; server code (Admin SDK: upkeep, push, AI overview, household actions) still reads them.

## Authentication, Roles, and Security

A member with `notifications.view` may get or list a household notification only when its `audience` names them or everyone (`resource.data.audience.hasAny([request.auth.uid, '*'])`); owners and admins are no exception. A single-document read of a notification aimed at someone else, of one with an empty `audience`, or of one without the field is refused, and a list query is accepted only when it is constrained by `audience` `array-contains-any [uid, '*']` (or `array-contains` of either value). Updates need the same audience: only a member the document is addressed to may change it, and only the caller UID key in `readBy` and `dismissedBy` (with `notifications.dismiss`), or, for a maintenance document, `resolvedAt`/`resolvedBy` (with `maintenance.edit`). Deletion is denied. The rules do not inspect the action values; the app stopped writing emails into them without a rules change. Admin SDK code is not subject to rules.

`notifications.view` controls navigation and reads; `notifications.dismiss` is checked by the rules for read/dismiss state but not by the notification UI. Action-map keys are UID-restricted, but rules do not validate email/display-name values inside the action object.

Creation rules require an approved sender, the household's own `householdId`, Timestamp `createdAt`/`expiresAt`, a known category, bounded title/message, an allow-listed set of fields, a `/`-relative `deepLink` (no scheme, no `//`), and targets that belong to the household (a `targetUserUid` membership record; a `targetUserEmail` profile pointing at the household). The push function independently re-validates targets and links.

`audience` is required on every client create and must be exactly `[targetUserUid]` on a document with a `targetUserUid` (a member of the household) and `['*']` on an untargeted one, the derivation of `notificationAudience`. A client may not create a notification with only a `targetUserEmail` (it could name nobody), and anything else (missing, another uid, extra entries, an empty or non-list value) is denied, so a client cached from before the field existed can no longer create notifications. Clients cannot add, change or remove it afterwards: the two permitted updates touch only `readBy`/`dismissedBy` or `resolvedAt`/`resolvedBy`. The departure-notice create rule (a legacy client path; departures are written by the server action) requires `['*']`.

## Integrations and Background Processing

- FCM web config uses `NEXT_PUBLIC_FIREBASE_*` and `NEXT_PUBLIC_FIREBASE_VAPID_KEY`.
- Cloud Function `sendPushOnNewNotification` runs on notification creation. It reads each recipient's tokens with the Admin SDK from `users/{email}/private/push` and from the legacy `users/{email}.fcmTokens` field, de-duplicated, and removes an invalid or unregistered token from every document that holds it.
- The push function re-validates every document: it ignores documents whose `householdId` does not match their path, loads the household's membership records, and pushes only to approved active members. An `audience` uid or `targetUserUid`/`targetUserEmail` that is not an approved member receives nothing; untargeted notifications go to approved members only (never pending joiners). Recipients are then limited to members who hold the category's view permission (see category visibility above). Links are reduced to `/`-relative in-app paths by the shared `safePushLink` check (see the service worker above), and title/body are bounded (`functions/src/push-policy.ts`, tested in `tests/server/push-policy.test.ts`).
- Push artwork (`functions/src/shared/push-media.ts`): every push sets `webpush.notification.icon` `/icons/icon-192.png`, `badge` `/icons/badge-96.png` (the house glyph from the app icon on transparency) and `tag` (the notification ID); `webpush.data` repeats `tag` and `badge` for the worker. A rich `image` is added only when the notification names a household record with a photo, read with the Admin SDK only under `households/{householdId}` from the trigger path (and only when the document's `householdId` matches it):
  - category `pets`, `sourceType` `pet` or starting `pet-`/`pet_` (for feeding and medication reminders, for example `pet_feeding`): `sourceId` is the pet ID, optionally followed by `:` or `|` and a state key; uses the pet's `photoUrl`.
  - category `shopping`, `sourceType` `shopping_item`: `sourceId` is `listId:itemId`; uses the item's `imageUrl`, else its barcode's library `imageUrl`.
  - category `shopping`, `sourceType` `barcode_library` or `product`: `sourceId` is the barcode; uses the library item's `imageUrl`.
  - The URL is used only if it is an https `firebasestorage.googleapis.com` media download URL for this project's default bucket whose object path is `households/{householdId}/pets/...` (pets) or `households/{householdId}/barcode-library/...` (shopping), with no credentials, port or path tricks, or an image path on the app origin. Placeholders, Open Food Facts and any other host, other buckets, other households and other folders are dropped, as are malformed IDs; any read failure means no image.
  - Recipients who could not open the record in the app (no `pets.view` / `shopping.view`) already get no push for that category; the image check is kept as a second guard and would send such a recipient the push without the image, as a separate multicast. Title and body are unchanged, so a push never reveals more than the notification text plus a picture the recipient can already see.
  - Pet medication reminders (below) use this contract; no generator writes shopping-item notifications yet. Tested in `tests/unit/notifications-push-media.test.ts` and against the emulator in `tests/server/push-media.test.ts`.
- Reminders are never written by browser code: there is no per-minute timer on Chores and no synchronization when Maintenance opens. Opening Chores does call the server-side `syncHouseholdUpkeep` action, which runs the full upkeep step (recurring chores, retention, maintenance and chore reminders) on demand. Direct Temporary Task creation writes one deterministic targeted assignment notification in the same batch as its chore.
- Pending-member reminders: when someone with `household.manageMembers` opens Household Manager and a pending person has not been reminded about for 24 hours, the page calls the `remindPendingMembersAction` server action, which stamps `lastNewUserReminderAt` and writes one household-wide `system` notification per person and day (deterministic ID, `audience: ['*']`). See [Household Governance](../household-governance/README.md).
- Medication reminders: hourly upkeep (`householdUpkeep`, and `syncHouseholdUpkeep` when Chores opens) reads every pet and all of its `medication-logs` and applies the countdown rule of `nextMedication` / `useMedicationCountdownLogs` (`functions/src/shared/medication-reminders.ts`): entries are grouped by trimmed, lower-cased medication name, the most recent entry with a readable `date` decides, and a later dose without a valid `nextDueDate` cancels the countdown. When the due day is today or past in the household time zone, it writes one household-wide (untargeted, like maintenance) `pets` notification, which only members with `pets.view` see or are pushed per countdown state: `sourceType` `pet_medication`, `sourceId` `<petId>:<medication key>`, `stateKey` `due|<day>` or `overdue|<day>`, deterministic ID from `deterministicNotificationId`, title "Maple's flea prevention is due today" / "... is overdue", deep link `/pets/<petId>?tab=medication`. Re-runs create nothing; still-open reminders get the usual refresh before expiry. An open reminder is resolved (`resolvedAt`, no `resolvedBy`) once its countdown (medication and due day) is no longer pending: a newer dose was logged, or the pet was deleted. The resolve transaction re-reads the pet and all its medication entries and resolves only if the countdown is still not pending, so a run working from stale entries never hides a reminder that an overlapping run reopened. If the countdown becomes pending again (the newer dose is deleted), the same reminder is reopened (see reopening below). The push carries the pet's photo when it is stored in the household's Storage folder (see push artwork above).
- Reopening: when upkeep finds a reminder actionable again whose deterministic document is resolved (medication: the dose that resolved it was deleted; maintenance: resolved in the app but the schedule is still due with the same state, for example the schedule write failed), it reopens that document: `resolvedAt` and `resolvedBy` become `null`, title, message and link are rewritten, and `createdAt`/`expiresAt` move as on a refresh, so it is listed again. Read and dismissed state are kept. It reopens only if the document was last written before the run started reading its sources (Firestore `updateTime` against the run's wall-clock start), so a resolution written while a run is in flight is never undone by that run's older reads. A reopen is an update, so it sends no push: members already got one for this same reminder. Chore reminders share this path but are never resolved.
- Maintenance and chore reminders are scheduled server-side. The hourly `householdUpkeep` Cloud Function (`functions/src/index.ts` → `functions/src/reminders.ts`) runs the same idempotent step for every household; the Chores page also runs it on demand through `syncHouseholdUpkeep` (`src/app/chores/actions.ts`, authorized by `chores.view`) on each load so a new recurring assignment appears immediately. Maintenance Center computes its due/overdue list locally from the same shared rules (`functions/src/shared/maintenance-reminders.ts`) for display only and writes no reminder notifications.
- Snoozed maintenance reminders are not notified: a schedule snoozed in the Maintenance Center carries `snoozedUntil` equal to its new due date, and `actionableReminders` skips the reminder while it is upcoming or due soon. It notifies again on the due day, or at once if a vehicle service becomes due by mileage (see [Maintenance Center](../maintenance-center/README.md)).
- Physical expiration: a Firestore TTL policy on collection group `notifications`, field `expiresAt`, deletes documents after they expire (Firestore usually acts within a day). It is versioned in `firestore.indexes.json` (`fieldOverrides`, `ttl: true`, with the field's default single-field indexes) and deployed by the release workflow. Nothing visible is lost: `expiresAt` is seven days after `createdAt`, and the bell and center only list the last seven days by `createdAt`. Still-overdue maintenance reminders are re-surfaced by hourly upkeep before they expire. Legacy `users/{email}/notifications` documents have no `expiresAt` and are not affected.

## Cross-Module Dependencies

The homepage overview counts only active notifications addressed to the verified user (`audience` when present, otherwise UID/email targeting; `isAddressedToMember`), expiration, dismissal, resolution, and read state. It sends at most five bounded maintenance/system titles to the optional narrative.

- [Chores](../chores/README.md), [Maintenance Center](../maintenance-center/README.md), and [Household Governance](../household-governance/README.md) create records.
- [Identity and Profile](../identity-profile/README.md) stores FCM tokens.
- [Application Shell and Dashboard](../application-shell/README.md) mounts bell/foreground handlers and owns the offline half of the shared service worker.
- [Firebase Platform](../firebase-platform/README.md) owns Functions and rules.

## Invariants and Failure Behavior

- Notification UI never displays `sourceType`, `stateKey` or `expiresAt` values directly.

- Bell queries the last seven days, reads at most 30 records (for a member who cannot see every module, the 30 are counted after the category filter, which is part of the query), and displays up to 10 active unresolved/undismissed items.
- Center hides expired records and supports system/general records under broad filters, but has no dedicated system/general category filter.
- Dismissal is per user and does not delete the record.
- Deterministic maintenance identity is `(sourceType, sourceId, stateKey)`; `stateKey` changes only for a meaningful due-state/date/mileage cycle change.
- Deleting a maintenance asset or vehicle resolves its active schedule and expiration reminders from a fresh notification snapshot; unrelated notification history remains intact.
- Bell and center presentation deduplicate legacy documents with the same semantic source while merging read, dismiss, and resolution history.
- Reminders appear without anyone opening a page; IDs are deterministic, so overlapping runs never duplicate.
- Push recipients come from the household's membership records: a `[uid]` audience goes only to that approved member, `['*']` to every approved member, `[]` to nobody; a document without `audience` falls back to `targetUserUid` (or `targetUserEmail`) for one approved member, else every approved member. Never pending or former members. Each recipient's profile is then read directly by email (`users/{email}`) for its FCM tokens; no `users.uid` query is involved, so profiles without a stored `uid` still receive pushes.
- New-member approval notifications are targeted at each active owner/admin.
- Signing out stops pushes to that browser for the account that signed out; the next account to sign in there (or the same one) is registered again without a prompt when browser permission is still granted. If sign-out could not reach the server, the account's document may still list the old token until the next push to it fails and the push function removes it, or the next sign-in on that device replaces it; if the browser was offline, the push subscription itself also stays until that next sign-in.
- The Profile card's "active" text reflects browser permission. It is accurate once the silent registration has run (shortly after page load); it is not if that registration fails (for example a missing VAPID key), which is logged in the console.

## Validation

- Run `npm.cmd run lint`, `npm.cmd run typecheck`, and relevant functions lint/build after implementation changes.
- Run `npm.cmd run test:e2e:local` for deterministic read, unread, dismissed, system, shopping, and maintenance notification fixtures in desktop/mobile views.
- `tests/unit/notifications-push-device.test.ts` covers the device record, the sign-out plan (no token, own account, another account, offline), the unfinished marker, the silent sign-in decision, the token list after a refresh at the cap, the time bound (`settleWithin`), the sign-out gate (a registration in flight when sign-out begins is discarded or undone, and sign-out waits for it), `runPushSignOut` (nothing loaded when there is nothing to remove; a module load or cleanup that stalls, fails or reports leftovers lets sign-out proceed and leaves the device marked), and that `logout` closes the gate first and removes push before the cache flush and Auth sign-out. - Manually test in a production build with real FCM: subscribe, sign out (the token leaves `users/{email}/private/push`, `localStorage["homehub.push-device"]` is gone, a push to that account no longer shows in that browser), then sign in as another account (a new token appears in that account's document without a prompt).
- Manually test own-UID read/dismiss updates, dismiss-all scope, seven-day filtering, deep links, foreground/background delivery, denied permission, invalid-token cleanup, and target/broadcast recipients.
