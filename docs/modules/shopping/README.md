# Shopping Lists

## Purpose and Scope

This module owns shopping-list metadata, list categories, needed/purchased items, barcode-assisted entry, and purchasing handoffs. Pantry inventory and barcode mappings are separate modules even though they share the `/shopping` experience.

## User-Facing Capabilities

- Use the Shopping Lists tab at `/shopping`. The route skeleton, the page while the household loads and the tab before its first snapshot draw one shared shape (tabs, a Create New List row and three list cards), so loading does not shift the layout (SH-25a). The open list is in the URL (`/shopping?list=<listId>`; the pantry tab is `?tab=pantry`), so refresh keeps your place, Back returns to the overview and a list can be linked; a link to a missing list falls back to the overview with a "List not found" toast.
- See each list as a card with its tinted icon, "n to buy, n in the cart" (live counts: the shared `NumberTicker` with `animateOnMount={false}`, whose only text node is always the final value, so labels such as "Purchased (2)" read exactly that) and a trip progress bar. Cards enter with the shared `Stagger`. Hovering (fine pointer) or keyboard-focusing **Open List** for 400 ms shows a peek card (H26) with the list's type, counts, progress and description.
- Opening a list morphs its card into the open list, and **Back to all lists** morphs it back (H12 shared element, View Transitions): the list is in the URL on the same route, so `useInPageMorph` (`src/components/shopping/use-in-page-morph.ts`) gives the card and the open list the same `view-transition-name` only while morphing and holds the old snapshot until the new view renders (at most 800 ms). Reduced motion, a browser without View Transitions or a modified click just switch. The open list's rows enter with a stagger on first load (≤ 30 ms apart, ≤ 400 ms total, in store-walk order; rows added later do not stagger), and the Needed and Purchased counts tick.
- **Add Item** shows its keyboard shortcut in a tooltip on hover or keyboard focus ("Add an item from anywhere  A", H28) and carries `aria-keyshortcuts="A"`, through the shared `ShortcutHint` (`src/components/ui/shortcut-hint.tsx`), which reads the keys from the global shortcut map (`src/lib/dashboard/shortcuts.ts`). `A` itself opens the command palette's quick-add, as everywhere. An item's saved-link button has a peek card with the item, quantity, category and the link's host.
- Create, edit, and delete Grocery, Auto, Hardware, Pets, and Custom lists. Lists pick an icon and one of eight palette tints (or Automatic). **Delete** (needs a connection and `shopping.delete`) really removes the list, its items and its categories for everyone ("This permanently deletes the list, its items and its categories for everyone in the household").
- Everything is live across devices (SH-1): the cards and their counts, the open list's items and categories and the pantry follow other members' adds, ticks, deletes and list changes without a reload. A list deleted on another device while it is open here shows "This list was deleted" with **Back to all lists** and no write controls (no checkboxes, quick-add, Add Item, Manage Categories or delete buttons).
- Customize per-list categories (duplicate or empty names are explained inline under the field).
- Shop in store order: needed items are grouped by aisle in the order of a supermarket walk (Produce, Bakery, Meat, Dairy, Frozen, Pantry, Snacks, Drinks, Household), then the list's custom categories, then categories only found on items, then Other. Items in a category removed from the list's configuration still show.
- Tick an item by tapping anywhere on its row (S3, SH-13a): the whole row is the tick target (a label for the 24 px circle, at least 44 px tall and 48 px on touch), or on touch devices by swiping the row right (with a haptic tick when Haptics is on). The name is struck through as it leaves Needed, a copy of the name drops into the cart icon in the list header (**into the cart**, H07), the cart then wobbles and counts up, and "Milk is in the cart" offers **Undo** for 10 seconds. Ticking never leaves the list. Focus moves to the next row of the same section (else the previous one, else the cart), never to the page (SH-26a).
- Each row shows who added it, "Sam added · 2d" (SH-28b, "You added" for yourself): the name comes from the household's member records (`useMemberNames`, `src/lib/shopping/member-names.ts`; display names only, first name, never an email; an unknown or unnamed member reads "Member"); items without `addedByUid` (older clients) show nothing.
- Edit an item (SH-8a/b) from the trailing **Edit {item}** control (a 48 px chevron) or a long-press on touch (500 ms without moving; the click that ends it does not tick): the edit sheet (`src/components/shopping/item-edit-sheet.tsx`) changes the name, the quantity (−/+ or typed, 1 to 999) and the category, and **Save** writes only the fields the member changed from what the sheet showed when it opened (the opening snapshot, `editBaseline`; never compared to the live item, so a field someone else changed meanwhile and the member did not touch is not written back) (`planItemEdit`, `src/lib/shopping/edit.ts`: a rename also sets `nameKey`, a new category sets `categorySource: 'manual'`) plus `editedByUid` (the signed-in uid) and `editedAt` (server time). It opens with focus in the name field and works with the keyboard alone; Save, Escape and Close return focus to that row's Edit control (found again by row id, `data-edit-control`; the cart if the row is gone), a delete to the next row. Each open is a session (`nextEditOpening` / `saveMayComplete`): a slow save that completes after the sheet was closed, or reopened for another item, neither closes that later sheet nor clears its spinner. The fields stay editable while a save waits (for acknowledgement or its 4 s timeout); when it completes, the sheet closes only if the draft is still the one submitted (`settleItemSave`). If the member changed a field meanwhile, the sheet stays open with that newer input and the saved values become its baseline, so the next Save writes only the later change; a failed save keeps the sheet and its baseline. **Delete** lives in the sheet (SH-13b: no trash button beside each row).
- Add several items at once with the quick-add field pinned to the bottom of an open list: `milk, eggs, 2 bread` (also `bread x2`, `2x bread`). Submitting clears the field at once: the parsed entries are the submission, and anything typed while it saves is new input. One save runs at a time (another Enter is ignored and the text stays; an empty Enter shows an inline hint only when nothing is saving). Each entry is saved on its own; when the save finishes, saved entries are reported and shown, and only the failed ones are put back in front of whatever is in the field now, with an inline message naming them, so pressing Add again never adds anything twice. The field is keyed per list; if the list or page changes mid-save, failed entries are reported in a toast instead. Every add is saved at once: nothing waits for AI (QA-6). Each entry's write is classified honestly (SH-4, `src/lib/shopping/save-status.ts`): **saved** (the server answered), **Saved, will sync** (not answered, but the durable cache shows it, so it survives a reload), **Still sending…** (not answered and not known to be durable: memory cache, unknown persistence, or not in the cache yet), **Checking…** (a merge transaction that has not answered in about 4 s; it may still commit), or failed. The spinner waits at most about 4 s (not at all offline); entries still sending or checking then show in a chip under the field and the field is free for more adds; when they settle the chip goes, and any that finally failed go back into the field with the inline message. A second Enter while a submission is saving is ignored. A name already on the list as needed (ignoring case and spacing) raises that item's quantity instead of adding a duplicate; the same applies to the Add Item dialog. Typed all-lower-case names are capitalized ("milk" becomes "Milk"). An empty entry shows an inline error under the field.
- Delete an item from its edit sheet, with 10 seconds to undo; focus then goes to the next row.
- **Undo** (SH-15a/b, UNDO-10s): one 10-second window (the shared `UNDO_WINDOW_MS` from `src/lib/undo-window.ts`, re-exported by `src/lib/shopping/undo.ts`), one Undo per group (the latest tick and the latest delete; a newer one of the same group replaces the older). While a list is open the Undo is a bottom snackbar directly above the quick-add bar (`src/components/shopping/undo-snackbar.tsx`, rendered in the quick-add bar's sticky dock), near the thumb on phones; on the overview or a deleted list's screen it floats above the phone tab bar. The app's toasts are top-placed and show one at a time, so the snackbar is separate from them and a later "Item added" toast cannot hide an Undo. Each Undo is also journaled in `localStorage` (`homehub.shopping.undo.v1`, scoped by user, household and list; every access in `try/catch`), so a reload re-offers what is left of its window.
- Categories without waiting (QA-6 / SH-16): a new item gets the member's pick, else the category remembered for that name (from the list's items whose category a person or the AI chose, plus answers seen this session), else the local keyword map (`src/lib/shopping/local-categories.ts`: "orange juice" is Drinks, "coconut milk" Pantry), else `Other`. Then one batched AI call per submission (up to 40 names) sorts the names nothing else knew; the rows move when the answer lands. If the call fails, a toast says why: "Item saved to Other" only for items whose write the server had confirmed by then (`peekSettled`, `categorizationNotice`); an item still unconfirmed (a write slower than the 4 s wait, which may yet fail) is only said not to have been sorted ("Automatic sorting failed"), and one that already failed is left to its own failure toast.
- A scan adds one package (BL-1): the product's package size is shown as a note on the row ("450 g") and kept as `size`/`sizeUnit`; a second scan of a needed item adds 1.
- Finish a trip: ticking the last needed item prints a receipt (online, once a server count query confirms nothing is still needed, so an item another member added keeps the trip open; the check runs once the tick is acknowledged, also when that answer arrives after the 4 s timeout on a weak connection, and never twice (`tickFollowUp`, `once`); offline, from this device's cached list) (list, time, items and totals) that offers **Add to pantry** (Grocery lists) and **Clear purchased**.
- Clear purchased items and optionally remove an emptied list. Clear needs a connection (offline it explains that and does nothing): it runs a transaction that deletes, of the purchased items shown when Clear was pressed (captured then with the household and list they came from, so the live list changing under the open dialog changes nothing; the confirmation closes and its ids are dropped whenever the open list changes, and ids captured on another household or list are refused (`clearIdsFor`), so a dialog left over from list A never clears list B), only those still purchased on the server (an item ticked meanwhile, or un-ticked by someone else, stays), and the "Delete Empty List?" prompt appears only when a server count query confirms the list is empty (never offline). On Grocery lists, Clear offers **Add to pantry, then clear**, which clears exactly the items listed in the pantry dialog (those still purchased) in the same transaction as the pantry writes, so the two succeed or fail together and a retry never adds the purchases to the pantry twice.
- Send purchased Grocery items to the pantry in one batch: every item starts ticked with a shelf guessed from its category (Dairy goes to the Fridge, Frozen to the Freezer) and can be unticked or moved before confirming.
- Scan a barcode while adding an item.
- Open the household barcode catalog from the `Barcode Library` inventory action.
- Share a recipe link, product page or text into the installed app (`/share`), pick a list, and confirm to add it as an item, optionally keeping the link.
- Open lists and tick items with no connection; ticks sync when the connection returns.
- Launch the "Add to shopping" home-screen shortcut (`/shopping?quickAdd=1`) to open the add-item dialog directly.

## Architecture and Data Flow

`ShoppingCenterClient` coordinates the Shopping Lists and Pantry Inventory tabs. The open tab, list and quick-add request are derived on every render from `useSearchParams()` (`parseShoppingUrlState` in `src/lib/shopping/url-state.ts`), never read once, so browser Back/Forward, Next.js `<Link>` navigation (the header and phone tab bar "Shopping" links) and its own shallow `history.pushState`/`replaceState` updates all keep the screen and address bar in step. Opening a list pushes an entry; leaving it steps back when that entry was pushed here, otherwise replaces; switching tabs replaces. The page wraps it in `Suspense` for `useSearchParams`. Both tabs stay mounted (`forceMount`, the inactive one `hidden`), so switching tabs keeps their listeners and state and re-reads nothing (SH-25b). Their dialogs, menus and peek cards render through portals outside the hidden panel, so each tab is wrapped in `TabActivity` (`src/components/shopping/tab-activity.tsx`): when a tab stops being the shown one (a tab click or browser Back/Forward changing `?tab=`), it closes every overlay it owns, the item edit sheet included, in that same render (`useOnTabDeactivate`; card and shelf menus are `TabDropdownMenu`, peek cards are not rendered while hidden), so nothing stays on screen or traps focus over the other tab. Nested overlays follow too: the pantry item dialog's scanner (a sibling dialog) closes on deactivation and whenever the item dialog closes, the Add Item scanner never outlives Add Item, and calendar and select popovers live inside their dialog's content, so they unmount with it. `BarcodeScanner` stops every camera track on unmount, on top of react-zxing's reader reset, so a hidden tab never keeps the camera on. The listeners keep running. `ShoppingListClient` receives the list id, subscribes to the lists, the open list's items and categories and the card counts (`src/lib/shopping/live.ts`), writes Firestore records, and treats the OpenAI-backed grocery categorization server action as optional enrichment for new items. The client sends a Firebase ID token; the action verifies household membership and `shopping.edit` before requesting a model.

Ticking an item only changes its status: it never switches tabs or opens a form. The pantry handoff is opt-in and batched: from the trip receipt, from **Add to pantry, then clear** in the Clear dialog, or (for members who can edit but not delete) an **Add to pantry** button next to Purchased. It is offered only for Grocery lists, to members with `shopping.edit`, and only while online. Reverting an item to needed does not subtract pantry inventory.

**Live data (SH-1).** The lists, the open list's items, its `config/categories` and the pantry are `onSnapshot` listeners with `includeMetadataChanges`, so the screen knows when it shows the cache (`fromCache`) or unsent writes (`hasPendingWrites`; the open list carries both as `data-from-cache` / `data-pending-writes`). Firestore applies this device's own writes to the listener at once, offline too, and rolls a rejected write back in the listener, so there is no optimistic local copy and no re-read after a write: a tick no longer re-reads the whole list (SH-27a). Each listener's state is keyed by household and list (`liveKey`, `stateFor`), so a list switch or household change shows loading, never another list's items. `keepListening` keeps a listener alive: after an error it retries with bounded backoff (1 s doubling to 30 s, reset only by a snapshot the server confirmed (`!fromCache`), so a refused listener that answers each resubscribe from the cache before the denial still backs off; nothing scheduled while the page is hidden; the card-count listeners follow the same rule), coming back `online` or showing the page reopens a failed listener at once, and a listener hidden for 30 s or more is renewed when the page is shown (a wall tablet that slept); a renewal starts the new listener before stopping the old one, so the target never leaves Firestore's cache. A failed listener keeps its last value on screen and shows one `toastError`: a cached snapshot keeps the error, only a server-confirmed one clears it, and a retry failing with the same Firestore `code` keeps the first error object (`sameListenerError`), so a retry loop raises one toast. Before the first lists snapshot the tab shows the shared skeleton; later snapshots never bring it back (SH-25c).

**Writes that depend on current state.** The listener can trail the server by a moment, so every such write still checks at write time: merges and clears use transactions, the pantry handoff re-checks its merge targets in a transaction, the trip receipt and the empty-list prompt come from server count queries (`countNeededOnServer`, `countAllOnServer`; one aggregation read each), and ticks, deletes, restores and shelf moves are writes by id of the value the member chose. The Clear dialog and the pantry handoff dialog act on the items they showed when opened, even if the live list changes meanwhile.

**Card counts (SH-27b).** While `/shopping` is mounted, the first 20 lists (in the order shown, `LIVE_COUNT_LIMIT`) get one items listener each for their card counts; lists beyond that use two count queries (`countListItemsOnServer`: all items and purchased ones), refreshed when the view changes (overview ↔ a list), when the page is shown and on a `homehub:data-changed` shopping event. Offline, a fallback card keeps its last count.

**List deletion (SH-9).** **Delete** calls the `deleteShoppingList` server action (`src/app/shopping/actions.ts`) with a Firebase ID token: `authorizeHouseholdAction(..., 'shopping.delete')` verifies the token, the household and the permission, the list id must be a plain document id, and `deleteListTree` (`src/lib/server/shopping-list-delete.ts`) removes `households/{householdId}/shopping-lists/{listId}` with `items/*` and `config/*` (the path is built from the verified household). The list document is deleted first, so from that moment the rules (`shoppingListExists()`) refuse every item and category create or update under it and no member's add can land behind the scan and survive as an orphan; then the subcollections are deleted with the orphan purge plan (`purgeOrphanList`, pages of at most 200 in transactions that re-read the list document) and re-checked, repeating up to 5 passes until nothing is left. If a member re-creates a list under the same id meanwhile, the remaining pages stop and that list and what is under it are left alone (the delete still reports success); if documents are still found after the last pass the action reports `unavailable` ("The list could not be deleted right now") and a retry finishes the job. Deleting a list that is already gone also removes anything left under it, so a retry is safe. Offline it explains that a connection is needed and does nothing. The device that deletes navigates away itself, and its "deleting" marker lasts only until it has left the list and the snapshot no longer holds it (`deletionSettled`), so a list re-created under the same id and deleted elsewhere later is reported normally; on any other device with the list open, the list leaving the lists snapshot (it was seen there before) shows "This list was deleted" (`isOpenListDeleted`). A `?list=` link to a list never seen falls back to the overview with "List not found", decided only from a server-confirmed snapshot (or the cache when offline: `isListLinkMissing`), so a cache that has not seen a new list yet never sends the member back.

**Save path (S2).** Every new item goes through `addItemsToList` (`src/lib/shopping/add-items.ts`), shared by the add-item dialog, quick-add, barcode scans, the command palette, the pantry's "Put on a shopping list" (no merge yet) and the share target (never merges: it may carry a link). Per entry: merge or create (below), the category from `initialCategory` with its `categorySource` (`manual`, `remembered`, `local`, `pending` when one AI call will be asked, `fallback` offline), `addedByUid` = the signed-in uid and `nameKey` = `itemNameKey(name)` (SH-28a; the row shows who added it from S3). Each write goes through `trackWrite`: a queued write (set/update) waits up to 4 s (online only), then counts as `stored-locally` only when `localPersistence` is `durable` and `getDocFromCache` shows the write, else `sending`; a transaction without an answer is `uncertain` and resolves when it settles (a late "not merged" still creates the item; `settleTimedOutMerge` in `save-status.ts` reports every late failure through `onLateError`, a refused merge and also a fallback create that fails at once, for example after the member's permission was revoked, so the caller never silently drops the pending status). A timeout alone is never proof. After the writes, the `pending` items go to one `categorizeGroceryItems` call (serialized per page, 20 s client timeout); each answer is written in a transaction only if `shouldApplyLateCategory` holds on the freshly read item and list: the list still exists, the item exists with the same name key, its source is still `pending` or `local`, the answer is one of the list's categories, and the household and list are still the active ones (on the Shopping screen: the list still open; elsewhere: the same household signed in). The update sets `category` and `categorySource: 'ai'`. The Add Item dialog shares one form across openings, so a save confirmed late (after the 4 s wait) always reports its success but clears the form only while the draft is still the submitted one (no edit since, counted by a form-values subscription) and closes the dialog only if it is the same opening on the same list (`dialogAfterSave` in `save-status.ts`); a draft typed meanwhile, in that dialog or on another list, is never wiped or closed. Item creation uses `buildShoppingListItem` (`src/lib/shopping-items.ts`): document ID `slugify(name)` (a slug plus a random suffix). Before creating, the dialog and quick-add look for a still-needed item with the same `itemNameKey`. Because the live list can still trail the server by a moment, online the merge runs in a transaction (`mergeIntoNeededItem`, `src/lib/shopping/item-transactions.ts`) that re-reads the item and raises its `quantity` with an atomic `increment()` only if it is still needed; if another member bought or deleted it meanwhile, a new needed item is created instead. Offline, transactions cannot run, so there is no merge at all: a new needed item is queued (a duplicate is harmless; folding an addition into an item someone already bought would lose it); purchased items are never merged into, and the share target always creates (it may carry a link). New items have `status: 'needed'`, `createdAt: new Date()`, `nameKey`, `categorySource` and `addedByUid` (when signed in), and optional `imageUrl`, `barcode`, `sourceUrl`, `size` and `sizeUnit` omitted when empty. Undo of a delete re-creates the item as it was read, keeping its original `addedByUid`, and adds `restoredByUid` = the signed-in member and a fresh `restoreOpId` (`restoreItemData`); it does not write back `purchasedByUid`, `purchasedAt`, `editedByUid`, `editedAt`, `undoOpId` or an older `restoreOpId`/`restoredAt` (only their own writer may set those; the rules refuse them on a restore), and adds `restoredAt` at write time. The rules that accept another member's `addedByUid` on such a restore (writer's own `restoredByUid`, adder an existing member) were proposed in rules PR #121; this branch carries them in its own shopping item section (below), which must be deployed with or before this client.

**Tick, edit and Undo (S3, WT-20).** No Undo writes back a copy of the whole item. A tick writes `status: 'purchased'`, `purchasedByUid` (signed-in uid), `purchasedAt` (server time), a fresh `purchaseOpId` and removes `undoOpId` (`tickUpdate`, `src/lib/shopping/item-writes.ts`); un-ticking from Purchased is a new decision, not an Undo (`status: 'needed'`, purchase stamps null). The tick's Undo writes only `{ status: 'needed', undoOpId: <that purchaseOpId>, purchasedByUid: null, purchasedAt: null }` (`undoTickUpdate`), which the rules accept only while the stored `purchaseOpId` is still that id: if anyone ticked it again meanwhile (a new `purchaseOpId`), the Undo is refused and their change stays. A delete's Undo re-creates the item only if it is absent: online in a transaction (`restoreIfAbsent`, `src/lib/shopping/item-writes.ts`: read, and write nothing if the item exists), offline as a queued `setDoc`; either way the document (`restoreDocument`) carries a fresh `restoreOpId` and `restoredAt` (server time), which the rules accept only on a create, so neither a second restore nor a replay of the same one overwrites an item that exists again. Before writing, `planTickUndo` / `planRemoveUndo` check what the screen knows (the open list's listener): a tick whose `purchaseOpId` changed, or an item that is gone, is refused at once; an item already back is left alone; when the item is not on screen (another list open, or not loaded yet after a reload) the write is sent and the rules decide. Both are ordinary queued writes (`trackWrite`, at most ~4 s wait, none offline), so they work offline and after a reload; a refusal by the rules (now or when a queued write reaches the server: `permission-denied` or `not-found`) shows "Changed by someone else — not undone". Edits write only changed fields with `editedByUid`/`editedAt` (`editUpdate`), so another member's change to another field is kept. Limitation: a re-tick by an older client (no `purchaseOpId`) does not change the stored id, so an Undo of the earlier tick can still land over it until every client is on this release.

**Offline.** The listeners serve Firestore's persistent cache when the browser is offline. Ticking an item updates the screen immediately (the listener shows the queued write); the status write is queued by Firestore and syncs on reconnect, even if the page is reloaded in between. Offline, the pantry handoff, Clear and list deletion are not available (they need the server) and a one-time "You are offline" toast explains that ticks sync later; if a queued write is later rejected, an error toast appears and Firestore rolls the write back in the listener, so the screen shows the confirmed state, also when several ticks of one item were queued and rejected together, and also for writes restored from the queue after a reload. `tests/e2e/pwa-share.spec.ts` covers a tick and an untick queued offline, both rejected on reconnect. Items added offline (dialog or quick-add) get a remembered or local category, else `Other` with `categorySource: 'fallback'` (no model is asked), and are confirmed as "Saved, will sync" only when the durable cache shows them, otherwise as still sending; the first offline tick shows its Undo toast with the offline note inside it (SH-7c: "saved on this device" only when the durable cache shows the tick, else "keep HomeHub open until then"); quantity merges and deletes are queued the same way, and a later rejection shows a `toastError`. The `/shopping` page shell itself loads offline from the service worker described in [Application Shell and Dashboard](../application-shell/README.md). Only lists and items this browser has already loaded are available offline.

**Share target.** The manifest declares a GET share target at `/share` with `title`, `text` and `url` parameters. `parseSharedContent` takes the first http(s) URL from `url` or `text` (Android often places it in `text`) and suggests an item name from the title, then the text without the link, then the link's host name, capped at 120 characters. `ShareTargetClient` shows sign-in, no-household, pending-approval and no-permission states; otherwise the member edits the name and quantity, chooses whether to keep the link, and picks a list. Nothing is written until **Add to list** is pressed. Lists show their tinted icon, and the confirmation links straight to the chosen list (`/shopping?list=<listId>`). The save reads the list's category config and items (for remembered categories) and saves through `addItemsToList` like the add-item dialog (never merging); the confirmation says "Added to your list", "Saved, will sync" (durable cache shows it) or "Still sending…" (updates when the write settles; a late failure returns to the form with an error).

**Quick add.** `/shopping?quickAdd=1` (a fresh load or in-app navigation) is consumed once the lists are confirmed (a server snapshot, or the cache when offline: `listsConfirmed`, `quickAddDecision`; cached lists are drawn at once, but a Grocery list deleted elsewhere and still in the cache is never chosen and the request is not lost): the entry is replaced (so Back never reopens the dialog) with the only list, or the first Grocery list, open and the add-item dialog shown; otherwise it shows a "Choose a list" toast.

## Data Model and Persistence

- Lists: `households/{householdId}/shopping-lists/{listId}`.
- Items: `households/{householdId}/shopping-lists/{listId}/items/{itemId}`.
- Categories: `households/{householdId}/shopping-lists/{listId}/config/categories`.
- Deleting a list deletes the document first and then both subcollections (server action, `deleteListTree`), so no child write is accepted while the cleanup runs. Items and categories that older clients left under lists they deleted (they removed only the list document) are purged once by `scripts/ops/purge-orphan-shopping-subcollections.mjs --project <id>`: a dry run by default that prints counts only, `--apply` to delete, `--firebase-tools-login [--firebase-tools-from <dir>]` to authenticate with the `firebase login` account instead of Application Default Credentials. It pages households 400 at a time, finds list references without a document with `listDocuments()` and deletes only what is under them, never a list document. It is safe to run while members use Shopping: list ids derive from the name, so a member can re-create a deleted list under the same id mid-run, and every delete goes through `purgeOrphanList` (`scripts/ops/shopping-orphans.mjs`) in pages of at most 200 documents (deepest first), each page one Firestore transaction that re-reads the list document and deletes nothing if it exists. The transaction's read serializes each page with the re-creation, so no document under an existing list is ever deleted: once a page finds the list, the rest of that list is left alone and counted as re-created. Output stays counts only (lists purged, documents deleted, lists re-created). Everything it deletes is gone, so a stopped run is resumed by running it again. Run it after every client is on this release.
- List `color` now stores a palette tint `tint-1` to `tint-8` (or empty for Automatic). Older lists that stored a hex color, and lists without one, are read with a stable tint derived from the list id; nothing is migrated and the hex value is never rendered. An unknown `icon` name renders the list type's icon (Grocery cart, Auto car, Hardware wrench, Pets paw print, Custom clipboard).
- Barcode lookup dependency: `households/{householdId}/barcode-library/{barcode}`.

`ShoppingList`, `ShoppingListType`, `ShoppingListItem`, and `ShoppingListCategory` are defined in `src/lib/types.ts`. `ShoppingListItem.sourceUrl` (optional) holds an http(s) link saved from the share target; the item row shows an external-link button for it and re-checks the scheme before rendering.

## Authentication, Roles, and Security

The page requires an authenticated user and scopes paths with `householdId`. Navigation uses `shopping.view`. Pending users are blocked.

Firestore rules require `shopping.view` to read lists, items and category config, `shopping.edit` to create or update them, and `shopping.delete` to delete them. They also validate shapes (QA-8): an item may only set `name` (1 to 500 characters, required on create), `quantity` (a number above 0 and at most 100000, checked after `increment()`), `category` (up to 100), `createdAt` (timestamp or string), `status` (`needed` or `purchased`), `imageUrl`, `barcode`, `sourceUrl`, `nameKey` (1 to 500), `addedByUid` (on create only the writer's own uid; never changed or removed afterwards, `shoppingAdderOnCreate` / `shoppingAdderUnchanged`), `categorySource` (`manual`, `remembered`, `local`, `ai`, `fallback` or `pending`), `size` (a number above 0 and at most 100000) and `sizeUnit` (1 to 16 characters); `restoredByUid` (1 to 128; on create the writer's own uid, and then `addedByUid` may name another member of the household or be absent; frozen afterwards); and the S3 stamps (`validShoppingItemStamps`): `purchasedByUid` the writer or null, `purchasedAt` `request.time` or null (a set `purchasedAt` needs the writer as `purchasedByUid`), `purchaseOpId` 1 to 64 characters, `editedByUid` the writer and only together with `editedAt == request.time` (and `editedAt` only with the writer as `editedByUid`), `undoOpId` only on an update back to `needed` that leaves `purchaseOpId` unchanged and only while the stored `purchaseOpId` equals it, and a restore (a create with `restoreOpId`, 1 to 64) must carry `restoredByUid` = the writer and `restoredAt == request.time` and none of `purchasedByUid`, `purchasedAt`, `editedByUid`, `editedAt` or `undoOpId` (a restored item keeps its status and `purchaseOpId`); `restoreOpId` and `restoredAt` are accepted only on a create, and because `restoredAt` resolves to a new time on every write, replaying the same restore onto an item that exists again (perhaps changed since) is a changed key on an update and is refused; once set, `restoreOpId` and `restoredAt` are frozen (`shoppingRestoreStampsKept`: an update may neither change nor remove them), so a second tab holding the same Undo (same `restoreOpId`) is refused even if its payload leaves `restoredAt` out; all new fields are optional, so older clients' items stay valid. **Release order:** these rules must be deployed before a client that writes the new fields; a list only `name` (1 to 100, required on create), `description`, `icon`, `type` and `color`; category config only `list` (at most 200 entries). Items and category config may only be created or updated while the parent list document exists (`shoppingListExists()`, SH-9b), so no tick, add, merge, restore or category edit lands on a list deleted elsewhere (its screen shows "This list was deleted"; a late Undo shows a `toastError`); deletes stay allowed, for cleanup. On update only added or changed keys are checked, so documents with legacy fields stay editable, and undo-after-delete (which re-creates the item as it was read) keeps working. The UI hides what a member cannot do: Create New List, Edit, Manage Categories, Add Item, quick-add, row ticks and swipe, editing an item, the Undo snackbar and the pantry handoff need `shopping.edit` (viewers see a read-only status mark instead of a checkbox); Delete list, Delete item (in the edit sheet, which opens for members with `shopping.edit` or `shopping.delete`) and Clear purchased need `shopping.delete` (the list delete is also checked by the server action). Members without `shopping.view` see an explanation instead of the tabs, and the Barcode Library header link is hidden. Denied writes still fail at the rules and show a `toastError`. The share target checks `shopping.view` and `shopping.edit` (and blocks pending members) before loading lists or offering a save.

## Integrations and Background Processing

- Grocery categorization calls the shared authenticated, batched OpenAI flow (`categorizeGroceryItems`, one call and one quota unit per submission) only for new items whose name has no remembered or local category, and only online. Household item names are serialized as untrusted data under the centralized AI system instruction. Emulator E2E uses the deterministic provider and never calls OpenAI.
- The dashboard overview reads list/item counts only after server verification of `shopping.view`; omitted permission means no Shopping query or overview section.
- Barcode lookup checks the household library, then Open Food Facts; camera capture uses `react-zxing`.
- Live `onSnapshot` listeners (see Live data). The one server action is `deleteShoppingList`; there are no shopping Cloud Functions or scheduled jobs.

## Invariants and Failure Behavior

- A manually selected category bypasses AI. Items are saved before any AI call; AI errors, invalid responses, configuration failures, rate limits or the 20 s client timeout leave them under `Other` (exactly one item each) with a non-blocking toast: "Item saved to Other" for writes the server confirmed, "Automatic sorting failed" (never "saved") for writes still unconfirmed. A late AI answer never overwrites a category a member chose, a renamed item, or an item on a list or household that is no longer the active one.
- "Saved, will sync" is shown only when the write is known to be on the device durably (persistent cache confirmed and the cache shows the write); a timeout alone is never proof. Typed input is kept until a save is known to have succeeded (sending entries stay in a chip; failed ones return to the field or the dialog), and one submission is never sent twice.
- A scan adds one package; package size and unit never become the quantity.
- Loaded custom category sets always include `Other`, so fallback items remain visible even when older category configuration omitted it.
- Optional `imageUrl` and `barcode` fields are omitted from Firestore writes when absent; undefined values are never sent.
- Lists, items, categories and the pantry are live listeners; nothing re-reads a whole list after a write. A screen only shows a listener's data while its household-and-list key matches.
- A tick is never lost offline: local state updates first and the queued write survives reloads. The share target never writes before explicit confirmation.
- `sourceUrl` is stored only when it parses as http(s), and is re-checked before rendering as a link.
- Deleting a list removes the document, its items and its categories (server action); the dialog says exactly that. Writes to a deleted list are refused by the rules.
- Purchase-to-pantry is one Firestore batch, but it is separate from clearing purchased items: "Add to pantry, then clear" clears only after the pantry batch succeeds.
- Undo after a delete re-creates the same document id with the item's previous fields only if it is absent (`restoreOpId`, create-only); undo after a tick writes only the status and purchase stamps, guarded by `undoOpId == purchaseOpId`, always to the item's own list, so neither overwrites a newer change by someone else. If another list has been opened since, the write still lands on the original list but the open list's items are left alone: the screen shows only the listener for the list in the URL. The same holds for undo after a delete (the item is written back to its own list and only re-inserted on screen if that list is still open), clearing purchased items (only the open list is cleared, and a late result never touches another list's screen) and category edits.
- Motion stays in budget and respects reduced motion (system or in-app): row strike-through 150 ms then a 120 ms fade, purchased rows drop in over 220 ms, the cart wobble is 350 ms and skipped under reduced motion; the into-the-cart flight (`useCartFlight`) is a separate fixed, `pointer-events: none`, `aria-hidden` copy of the name that moves from the row to the cart in 420 ms (transform and opacity only), so the row, its checkbox and every existing selector stay where they are; the cart's visible badge waits for the copy to land (a 900 ms safety timer lands it regardless) while its accessible name has the new count at once; the flight is skipped under reduced motion and when the row or the cart is off screen, and it does not touch the write path or the offline contract; the receipt prints in 900 ms and any key or pointer press finishes it (instant under reduced motion). Swipe-to-tick is enabled only for coarse pointers; the checkbox never moves. Every icon control on the shopping screen (row Edit and saved-link buttons, the snackbar's Undo and Dismiss, the list card's actions menu, the cart, quick-add's Add, the add-item and edit-sheet quantity buttons, the category "x" and the edit sheet's own Close) is 44 px, 48 px on touch (D-2); the generic dialog close button and the pantry tab's menu and move handle are outside this change. **Open List** is named "Open List: {list}" so its accessible name starts with its visible label (SH-26b).
- All colors are tokens (list tints use the contrast-tested `--member-N` palette); `tests/unit/shopping-logic.test.ts` fails on raw color literals in the shopping components.
- Errors use `toastError`, so raw Firebase text never reaches users; field problems are inline (`FormMessage` or `FieldError`).
- Barcode lookup failure does not invent product data.
- The `/shopping` header action stacks on narrow screens so its label and controls stay inside the viewport.
