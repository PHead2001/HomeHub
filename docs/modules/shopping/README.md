# Shopping Lists

## Purpose and Scope

This module owns shopping-list metadata, list categories, needed/purchased items, barcode-assisted entry, and purchasing handoffs. Pantry inventory and barcode mappings are separate modules even though they share the `/shopping` experience.

## User-Facing Capabilities

- Use the Shopping Lists tab at `/shopping`. The route skeleton, the page while the household loads and the tab before its first snapshot draw one shared shape (tabs, a Create New List row and three list cards), so loading does not shift the layout (SH-25a). The open list is in the URL (`/shopping?list=<listId>`; the pantry tab is `?tab=pantry`), so refresh keeps your place, Back returns to the overview and a list can be linked; a link to a missing list falls back to the overview with a "List not found" toast.
- See each list as a card with its tinted icon, "n to buy, n in the cart" (live counts: the shared `NumberTicker` with `animateOnMount={false}`, whose only text node is always the final value, so labels such as "Purchased (2)" read exactly that) and a trip progress bar. Cards enter with the shared `Stagger`. Hovering (fine pointer) or keyboard-focusing **Open List** for 400 ms shows a peek card (H26) with the list's type, counts, progress and description.
- Opening a list morphs its card into the open list, and **Back to all lists** morphs it back (H12 shared element, View Transitions): the list is in the URL on the same route, so `useInPageMorph` (`src/components/shopping/use-in-page-morph.ts`) gives the card and the open list the same `view-transition-name` only while morphing and holds the old snapshot until the new view renders (at most 800 ms). Reduced motion, a browser without View Transitions or a modified click just switch. The open list's rows enter with a stagger on first load (≤ 30 ms apart, ≤ 400 ms total, in store-walk order; rows added later do not stagger), and the Needed and Purchased counts tick.
- **Add Item** shows its keyboard shortcut in a tooltip on hover or keyboard focus ("Add an item from anywhere  A", H28) and carries `aria-keyshortcuts="A"`, through the shared `ShortcutHint` (`src/components/ui/shortcut-hint.tsx`), which reads the keys from the global shortcut map (`src/lib/dashboard/shortcuts.ts`). `A` itself opens the command palette's quick-add, as everywhere. An item's saved-link button has a peek card with the item, quantity, category and the link's host.
- Create, edit, and delete Grocery, Auto, Hardware, Pets, and Custom lists. Lists pick an icon and one of eight palette tints (or Automatic). **Delete** (needs a connection and `shopping.delete`) really removes the list, its items and its categories for everyone ("This permanently deletes the list, its items and its categories for everyone in the household").
- Everything is live across devices (SH-1): the cards and their counts, the open list's items and categories and the pantry follow other members' adds, ticks, deletes and list changes without a reload. A list deleted on another device while it is open here shows "This list was deleted" with **Back to all lists** and no write controls (no checkboxes, quick-add, Add Item, Manage Categories or delete buttons).
- Customize per-list categories (duplicate or empty names are explained inline under the field).
- Shop in store order: needed items are grouped by aisle in the order of a supermarket walk (Produce, Bakery, Meat, Dairy, Frozen, Pantry, Snacks, Drinks, Household), then the list's custom categories, then categories only found on items, then Other. Items in a category removed from the list's configuration still show.
- Tick an item with its checkbox, or on touch devices by swiping the row right (with a haptic tick when Haptics is on). The name is struck through as it leaves Needed, a copy of the name drops into the cart icon in the list header (**into the cart**, H07), the cart then wobbles and counts up, and a "Milk is in the cart" toast offers **Undo** for five seconds. Ticking never leaves the list.
- Add several items at once with the quick-add field pinned to the bottom of an open list: `milk, eggs, 2 bread` (also `bread x2`, `2x bread`). Submitting clears the field at once: the parsed entries are the submission, and anything typed while it saves is new input. One save runs at a time (another Enter is ignored and the text stays; an empty Enter shows an inline hint only when nothing is saving). Each entry is saved on its own; when the save finishes, saved entries are reported and shown, and only the failed ones are put back in front of whatever is in the field now, with an inline message naming them, so pressing Add again never adds anything twice. The field is keyed per list; if the list or page changes mid-save, failed entries are reported in a toast instead. Offline entries are queued and count as saved. A name already on the list as needed (ignoring case and spacing) raises that item's quantity instead of adding a duplicate; the same applies to the Add Item dialog. Typed all-lower-case names are capitalized ("milk" becomes "Milk"). An empty entry shows an inline error under the field.
- Delete an item with five seconds to undo (the item is written back as it was).
- Finish a trip: ticking the last needed item prints a receipt (online, once a server count query confirms nothing is still needed, so an item another member added keeps the trip open; offline, from this device's cached list) (list, time, items and totals) that offers **Add to pantry** (Grocery lists) and **Clear purchased**.
- Clear purchased items and optionally remove an emptied list. Clear needs a connection (offline it explains that and does nothing): it runs a transaction that deletes, of the purchased items shown when Clear was pressed (captured then, so the live list changing under the open dialog changes nothing), only those still purchased on the server (an item ticked meanwhile, or un-ticked by someone else, stays), and the "Delete Empty List?" prompt appears only when a server count query confirms the list is empty (never offline). On Grocery lists, Clear offers **Add to pantry, then clear**, which clears exactly the items listed in the pantry dialog (those still purchased) in the same transaction as the pantry writes, so the two succeed or fail together and a retry never adds the purchases to the pantry twice.
- Send purchased Grocery items to the pantry in one batch: every item starts ticked with a shelf guessed from its category (Dairy goes to the Fridge, Frozen to the Freezer) and can be unticked or moved before confirming.
- Scan a barcode while adding an item.
- Open the household barcode catalog from the `Barcode Library` inventory action.
- Share a recipe link, product page or text into the installed app (`/share`), pick a list, and confirm to add it as an item, optionally keeping the link.
- Open lists and tick items with no connection; ticks sync when the connection returns.
- Launch the "Add to shopping" home-screen shortcut (`/shopping?quickAdd=1`) to open the add-item dialog directly.

## Architecture and Data Flow

`ShoppingCenterClient` coordinates the Shopping Lists and Pantry Inventory tabs. The open tab, list and quick-add request are derived on every render from `useSearchParams()` (`parseShoppingUrlState` in `src/lib/shopping/url-state.ts`), never read once, so browser Back/Forward, Next.js `<Link>` navigation (the header and phone tab bar "Shopping" links) and its own shallow `history.pushState`/`replaceState` updates all keep the screen and address bar in step. Opening a list pushes an entry; leaving it steps back when that entry was pushed here, otherwise replaces; switching tabs replaces. The page wraps it in `Suspense` for `useSearchParams`. Both tabs stay mounted (`forceMount`, the inactive one `hidden`), so switching tabs keeps their listeners and state and re-reads nothing (SH-25b). Their dialogs, menus and peek cards render through portals outside the hidden panel, so each tab is wrapped in `TabActivity` (`src/components/shopping/tab-activity.tsx`): when a tab stops being the shown one (a tab click or browser Back/Forward changing `?tab=`), it closes every overlay it owns in that same render (`useOnTabDeactivate`; card and shelf menus are `TabDropdownMenu`, peek cards are not rendered while hidden), so nothing stays on screen or traps focus over the other tab. Nested overlays follow too: the pantry item dialog's scanner (a sibling dialog) closes on deactivation and whenever the item dialog closes, the Add Item scanner never outlives Add Item, and calendar and select popovers live inside their dialog's content, so they unmount with it. `BarcodeScanner` stops every camera track on unmount, on top of react-zxing's reader reset, so a hidden tab never keeps the camera on. The listeners keep running. `ShoppingListClient` receives the list id, subscribes to the lists, the open list's items and categories and the card counts (`src/lib/shopping/live.ts`), writes Firestore records, and treats the OpenAI-backed grocery categorization server action as optional enrichment for new items. The client sends a Firebase ID token; the action verifies household membership and `shopping.edit` before requesting a model.

Ticking an item only changes its status: it never switches tabs or opens a form. The pantry handoff is opt-in and batched: from the trip receipt, from **Add to pantry, then clear** in the Clear dialog, or (for members who can edit but not delete) an **Add to pantry** button next to Purchased. It is offered only for Grocery lists, to members with `shopping.edit`, and only while online. Reverting an item to needed does not subtract pantry inventory.

**Live data (SH-1).** The lists, the open list's items, its `config/categories` and the pantry are `onSnapshot` listeners with `includeMetadataChanges`, so the screen knows when it shows the cache (`fromCache`) or unsent writes (`hasPendingWrites`; the open list carries both as `data-from-cache` / `data-pending-writes`). Firestore applies this device's own writes to the listener at once, offline too, and rolls a rejected write back in the listener, so there is no optimistic local copy and no re-read after a write: a tick no longer re-reads the whole list (SH-27a). Each listener's state is keyed by household and list (`liveKey`, `stateFor`), so a list switch or household change shows loading, never another list's items. `keepListening` keeps a listener alive: after an error it retries with bounded backoff (1 s doubling to 30 s, reset by the next healthy snapshot, nothing scheduled while the page is hidden), coming back `online` or showing the page reopens a failed listener at once, and a listener hidden for 30 s or more is renewed when the page is shown (a wall tablet that slept); a renewal starts the new listener before stopping the old one, so the target never leaves Firestore's cache. A failed listener keeps its last value on screen and shows one `toastError`. Before the first lists snapshot the tab shows the shared skeleton; later snapshots never bring it back (SH-25c).

**Writes that depend on current state.** The listener can trail the server by a moment, so every such write still checks at write time: merges and clears use transactions, the pantry handoff re-checks its merge targets in a transaction, the trip receipt and the empty-list prompt come from server count queries (`countNeededOnServer`, `countAllOnServer`; one aggregation read each), and ticks, deletes, restores and shelf moves are writes by id of the value the member chose. The Clear dialog and the pantry handoff dialog act on the items they showed when opened, even if the live list changes meanwhile.

**Card counts (SH-27b).** While `/shopping` is mounted, the first 20 lists (in the order shown, `LIVE_COUNT_LIMIT`) get one items listener each for their card counts; lists beyond that use two count queries (`countListItemsOnServer`: all items and purchased ones), refreshed when the view changes (overview ↔ a list), when the page is shown and on a `homehub:data-changed` shopping event. Offline, a fallback card keeps its last count.

**List deletion (SH-9).** **Delete** calls the `deleteShoppingList` server action (`src/app/shopping/actions.ts`) with a Firebase ID token: `authorizeHouseholdAction(..., 'shopping.delete')` verifies the token, the household and the permission, the list id must be a plain document id, and the Admin SDK's `recursiveDelete` removes `households/{householdId}/shopping-lists/{listId}` with `items/*` and `config/*` (the path is built from the verified household). Deleting a list that is already gone also removes anything left under it, so a retry is safe. Offline it explains that a connection is needed and does nothing. The device that deletes navigates away itself; on any other device with the list open, the list leaving the lists snapshot (it was seen there before) shows "This list was deleted" (`isOpenListDeleted`). A `?list=` link to a list never seen falls back to the overview with "List not found", decided only from a server-confirmed snapshot (or the cache when offline: `isListLinkMissing`), so a cache that has not seen a new list yet never sends the member back.

Item creation goes through `buildShoppingListItem` (`src/lib/shopping-items.ts`), shared by the add-item dialog, quick-add, the pantry's "Put on a shopping list" and the share target: document ID `slugify(name)` (a slug plus a random suffix). Before creating, the dialog and quick-add look for a still-needed item with the same `itemNameKey`. Because the live list can still trail the server by a moment, online the merge runs in a transaction (`mergeIntoNeededItem`, `src/lib/shopping/item-transactions.ts`) that re-reads the item and raises its `quantity` with an atomic `increment()` only if it is still needed; if another member bought or deleted it meanwhile, a new needed item is created instead. Offline, transactions cannot run, so there is no merge at all: a new needed item is queued (a duplicate is harmless; folding an addition into an item someone already bought would lose it); purchased items are never merged into, and the share target always creates (it may carry a link). New items have `status: 'needed'`, `createdAt: new Date()`, and optional `imageUrl`, `barcode` and `sourceUrl` omitted when empty.

**Offline.** The listeners serve Firestore's persistent cache when the browser is offline. Ticking an item updates the screen immediately (the listener shows the queued write); the status write is queued by Firestore and syncs on reconnect, even if the page is reloaded in between. Offline, the pantry handoff, Clear and list deletion are not available (they need the server) and a one-time "You are offline" toast explains that ticks sync later; if a queued write is later rejected, an error toast appears and Firestore rolls the write back in the listener, so the screen shows the confirmed state, also when several ticks of one item were queued and rejected together, and also for writes restored from the queue after a reload. `tests/e2e/pwa-share.spec.ts` covers a tick and an untick queued offline, both rejected on reconnect. Items added offline (dialog or quick-add) are saved under `Other` without asking the model, unless a category was picked, and confirmed with an "Item Added Offline" toast; quantity merges and deletes are queued the same way, and a later rejection shows a `toastError`. The `/shopping` page shell itself loads offline from the service worker described in [Application Shell and Dashboard](../application-shell/README.md). Only lists and items this browser has already loaded are available offline.

**Share target.** The manifest declares a GET share target at `/share` with `title`, `text` and `url` parameters. `parseSharedContent` takes the first http(s) URL from `url` or `text` (Android often places it in `text`) and suggests an item name from the title, then the text without the link, then the link's host name, capped at 120 characters. `ShareTargetClient` shows sign-in, no-household, pending-approval and no-permission states; otherwise the member edits the name and quantity, chooses whether to keep the link, and picks a list. Nothing is written until **Add to list** is pressed. Lists show their tinted icon, and the confirmation links straight to the chosen list (`/shopping?list=<listId>`). The save reads the list's category config, categorizes like the add-item dialog (Automatic; `Other` immediately when offline), and writes one item; offline it reports "Saved offline".

**Quick add.** `/shopping?quickAdd=1` (a fresh load or in-app navigation) is consumed once the lists are confirmed (a server snapshot, or the cache when offline: `listsConfirmed`, `quickAddDecision`; cached lists are drawn at once, but a Grocery list deleted elsewhere and still in the cache is never chosen and the request is not lost): the entry is replaced (so Back never reopens the dialog) with the only list, or the first Grocery list, open and the add-item dialog shown; otherwise it shows a "Choose a list" toast.

## Data Model and Persistence

- Lists: `households/{householdId}/shopping-lists/{listId}`.
- Items: `households/{householdId}/shopping-lists/{listId}/items/{itemId}`.
- Categories: `households/{householdId}/shopping-lists/{listId}/config/categories`.
- Deleting a list deletes the document and both subcollections (server action, `recursiveDelete`). Items and categories that older clients left under lists they deleted (they removed only the list document) are purged once by `scripts/ops/purge-orphan-shopping-subcollections.mjs --project <id>`: a dry run by default that prints counts only, `--apply` to delete, `--firebase-tools-login [--firebase-tools-from <dir>]` to authenticate with the `firebase login` account instead of Application Default Credentials. It pages households 400 at a time, finds list references without a document with `listDocuments()`, re-checks each just before deleting and then deletes only its subcollections (never a list document, so a list re-created meanwhile under the same id survives). Everything it deletes is gone, so a stopped run is resumed by running it again. Run it after every client is on this release.
- List `color` now stores a palette tint `tint-1` to `tint-8` (or empty for Automatic). Older lists that stored a hex color, and lists without one, are read with a stable tint derived from the list id; nothing is migrated and the hex value is never rendered. An unknown `icon` name renders the list type's icon (Grocery cart, Auto car, Hardware wrench, Pets paw print, Custom clipboard).
- Barcode lookup dependency: `households/{householdId}/barcode-library/{barcode}`.

`ShoppingList`, `ShoppingListType`, `ShoppingListItem`, and `ShoppingListCategory` are defined in `src/lib/types.ts`. `ShoppingListItem.sourceUrl` (optional) holds an http(s) link saved from the share target; the item row shows an external-link button for it and re-checks the scheme before rendering.

## Authentication, Roles, and Security

The page requires an authenticated user and scopes paths with `householdId`. Navigation uses `shopping.view`. Pending users are blocked.

Firestore rules require `shopping.view` to read lists, items and category config, `shopping.edit` to create or update them, and `shopping.delete` to delete them. They also validate shapes (QA-8): an item may only set `name` (1 to 500 characters, required on create), `quantity` (a number above 0 and at most 100000, checked after `increment()`), `category` (up to 100), `createdAt` (timestamp or string), `status` (`needed` or `purchased`), `imageUrl`, `barcode` and `sourceUrl`; a list only `name` (1 to 100, required on create), `description`, `icon`, `type` and `color`; category config only `list` (at most 200 entries). Items and category config may only be created or updated while the parent list document exists (`shoppingListExists()`, SH-9b), so no tick, add, merge, restore or category edit lands on a list deleted elsewhere (its screen shows "This list was deleted"; a late Undo shows a `toastError`); deletes stay allowed, for cleanup. On update only added or changed keys are checked, so documents with legacy fields stay editable, and undo-after-delete (which re-creates the item as it was read) keeps working. The UI hides what a member cannot do: Create New List, Edit, Manage Categories, Add Item, quick-add, the tick checkboxes and swipe, undo-after-delete and the pantry handoff need `shopping.edit` (viewers see a read-only status mark instead of a checkbox); Delete list, Delete item and Clear purchased need `shopping.delete` (the list delete is also checked by the server action). Members without `shopping.view` see an explanation instead of the tabs, and the Barcode Library header link is hidden. Denied writes still fail at the rules and show a `toastError`. The share target checks `shopping.view` and `shopping.edit` (and blocks pending members) before loading lists or offering a save.

## Integrations and Background Processing

- Grocery categorization calls the shared authenticated OpenAI flow only when the user leaves category selection on Automatic. Household item names are serialized as untrusted data under the centralized AI system instruction. Emulator E2E uses the deterministic provider and never calls OpenAI.
- The dashboard overview reads list/item counts only after server verification of `shopping.view`; omitted permission means no Shopping query or overview section.
- Barcode lookup checks the household library, then Open Food Facts; camera capture uses `react-zxing`.
- Live `onSnapshot` listeners (see Live data). The one server action is `deleteShoppingList`; there are no shopping Cloud Functions or scheduled jobs.

## Invariants and Failure Behavior

- A manually selected category bypasses AI. Automatic categorization errors, invalid responses, configuration failures, rate limits, or a five-second client timeout save exactly one item under `Other` and show a non-blocking fallback toast.
- Loaded custom category sets always include `Other`, so fallback items remain visible even when older category configuration omitted it.
- Optional `imageUrl` and `barcode` fields are omitted from Firestore writes when absent; undefined values are never sent.
- Lists, items, categories and the pantry are live listeners; nothing re-reads a whole list after a write. A screen only shows a listener's data while its household-and-list key matches.
- A tick is never lost offline: local state updates first and the queued write survives reloads. The share target never writes before explicit confirmation.
- `sourceUrl` is stored only when it parses as http(s), and is re-checked before rendering as a link.
- Deleting a list removes the document, its items and its categories (server action); the dialog says exactly that. Writes to a deleted list are refused by the rules.
- Purchase-to-pantry is one Firestore batch, but it is separate from clearing purchased items: "Add to pantry, then clear" clears only after the pantry batch succeeds.
- Undo after a delete rewrites the same document id with the item's previous fields; undo after a tick writes the status back through the same offline-aware path, always to the item's own list. If another list has been opened since, the write still lands on the original list but the open list's items are left alone: the screen shows only the listener for the list in the URL. The same holds for undo after a delete (the item is written back to its own list and only re-inserted on screen if that list is still open), clearing purchased items (only the open list is cleared, and a late result never touches another list's screen) and category edits.
- Motion stays in budget and respects reduced motion (system or in-app): row strike-through 150 ms then a 120 ms fade, purchased rows drop in over 220 ms, the cart wobble is 350 ms and skipped under reduced motion; the into-the-cart flight (`useCartFlight`) is a separate fixed, `pointer-events: none`, `aria-hidden` copy of the name that moves from the row to the cart in 420 ms (transform and opacity only), so the row, its checkbox and every existing selector stay where they are; the cart's visible badge waits for the copy to land (a 900 ms safety timer lands it regardless) while its accessible name has the new count at once; the flight is skipped under reduced motion and when the row or the cart is off screen, and it does not touch the write path or the offline contract; the receipt prints in 900 ms and any key or pointer press finishes it (instant under reduced motion). Swipe-to-tick is enabled only for coarse pointers; the checkbox never moves.
- All colors are tokens (list tints use the contrast-tested `--member-N` palette); `tests/unit/shopping-logic.test.ts` fails on raw color literals in the shopping components.
- Errors use `toastError`, so raw Firebase text never reaches users; field problems are inline (`FormMessage` or `FieldError`).
- Barcode lookup failure does not invent product data.
- The `/shopping` header action stacks on narrow screens so its label and controls stay inside the viewport.
