Sections marked **Planned (F3/F4)** describe the contract later pull requests must meet. **Release gate (JC-8):** no rules release containing a device read clause may deploy until the four email scrub scripts report zero remaining work in a production dry run, recorded in the tracker (see Authentication, Roles, and Security).

## Purpose and Scope

This module owns the **device principal**: a wall tablet that joins one household with a single-use device code instead of a Google account, has no permissions of its own, and acts as whoever is standing at it (the selected member, checked by the server on every action). Built today:

- the device credential (Firebase Auth custom tokens for uid `device_<deviceId>`), its verification, and ending it (removal, re-pair, household deletion);
- pairing (device codes, QR setup link with the code in the URL fragment, the `/setup` screen with typed entry and camera scan, redemption) and re-pairing the same record;
- the device record (`households/{h}/devices/{deviceId}`): settings that live with the household, edited from the Devices tab; the heartbeat (truthful last seen and app version);
- the Firestore and Storage **read** rules for tablets (no device client writes anywhere);
- the principal switch: `AuthProvider` tells a tablet session from a personal one before any profile work, and a tablet session shows a minimal "This tablet is set up" screen;
- actors: who may act at a tablet (active owners, admins, members and children, including **kid profiles**: `members/kid_<id>` records with `kind: 'identity'`, no sign-in);
- tablet **PINs**: server-held salted scrypt hashes with a versioned server pepper, the WT-17 authority matrix, verification with lockouts per tablet and per person, and PIN sessions;
- the **device action gate** (`authorizeDeviceAction`) with the capability policy (`src/lib/devices/action-policy.ts`), the transaction hooks every device mutation runs, the server **op ledger** helpers, and the `OperationActor` / `OperationContext` types feature operations take;
- attribution of device writes (`deviceAttribution`) and their activity entries; the household **points-PIN** setting.

It does not own the feature data tablets read (chores, pets, shopping, maintenance keep their own modules and rules; this module adds only the separate device read clauses) nor the feature operations themselves: each feature keeps one server operation that takes an actor and runs this module's hooks (F4 adds the Pets and Chores device actions).

**Planned (F3/F4), not built:** the tablet shell (rail, "Who's here?" row UI, resting/face/PIN states, PIN pad, idle return, ambient, night dimming, keep-awake, protected exit, tablet settings screen), the offline face-action queue and Undo journal, revocation clearing in the shell (F3); device actions for Pets and Chores (feed, dose, complete, take, their Undo) and the 10.4 proofs that let a capability into `UNDO_PROVEN` (F4). Personal accounts are unaffected by all of it.

## Architecture and Data Flow

### Device identity

A tablet's Firebase uid is `device_<deviceId>` (`deviceId` is the record's 20-character auto id; Google uids never contain `_`). Its ID token carries four developer claims and nothing personal: `hh_kind: 'device'`, `hh_household`, `hh_device` (equals the uid suffix), `hh_gen` (the credential generation, an integer). No email, name or picture; `firebase.sign_in_provider == 'custom'`. `mintDeviceCredential(deviceId, householdId, generation)` creates (or re-enables) the Auth user with no email, stores the claims with `setCustomUserClaims` (the copy every newly issued ID token carries) and returns `createCustomToken(uid, claims)`, used once for the sign-in. The server test proves all four claims are present after a refresh-token exchange at the emulator's `securetoken` endpoint and that `hh_gen` arrives as an integer. **Emulator limit:** the Auth emulator does not check `revokeRefreshTokens` on the refresh-token exchange (it refuses only deleted or disabled users), and re-stamps `auth_time` on it, so after a re-pair the tests prove that the device's refresh tokens were revoked (`tokensValidAfterTime` moved past the old sign-in) and that an ID token the emulator still issues from the old refresh token carries the old `hh_gen` and is refused by `verifyDevice` and the rules; refusal at the exchange itself is production Firebase behaviour, to be confirmed live. The session is Firebase Auth's refresh token in the browser's existing persistence (IndexedDB); nothing else credential-like is stored.

`verifyDevice(idToken, householdId)` runs `verifyIdToken(token, true)` and classifies a failure (`classifyVerifyError`, `src/lib/devices/verify-errors.ts`): a revoked token or a disabled or deleted user is `device_revoked`; an invalid or expired token is `unauthenticated`; anything else (network, `auth/internal-error`, quota, timeouts, unknown or missing codes) is a verifier outage, `unavailable`, which the tablet treats as "try again later" and never as the end of its session, checks the claims (`readDeviceClaims`; a personal token is `not_a_device`), that the token's household is the requested one (`wrong_household`), that the household exists without `deletingAt` (`household_deleting`), and that the record is `active` at the token's generation (`device_revoked`).

**Revocation.** New requests are refused as soon as the record's `status` leaves `active` or its `generation` moves past the token's `hh_gen`: the rules compare them on every read, query or listener start, and `verifyDevice` on every server call. After the record's transaction commits, the Auth side follows (`finishRevocationForRecord`): refresh tokens revoked, then the user deleted (`removed`) or disabled (`unpaired`); an `active` record whose Auth user still carries an older `hh_gen` gets its refresh tokens revoked. It is idempotent and re-run by a retry of Remove, by opening the Devices list (`reconcileDeviceSessions`, at most once a minute per household per instance) and by the daily sweep. **Already-open listeners (JC-25):** Firestore does not document re-evaluating an open listener when a document its rules `get()` changes; `tests/server/device-identity.test.ts` holds a listener across a removal and records what it receives: on the Firestore emulator (2026-11-14) the listener got `permission-denied` when the next change to the document arrived after the removal, instead of the new data. That is the emulator; production behaviour is not documented and still needs the live check. Without it, a tampered tablet could keep an open listener until its ID token expires (at most an hour), after which the refresh fails. An honest tablet tears its listeners down as soon as it sees its record change (`set-up-landing.tsx` today; the F3 shell later).

### Pairing and redemption

1. An owner or admin (role) creates a code (`createDeviceCode`): name and room (1–40 characters after trimming), optional sections. One transaction checks the caller's role and the household (not being deleted), refuses an 11th live code (`too_many_codes`), reserves a code never used by a device code or a member invite (`INVITE_CHARS`, `XXXX-XXXX-XX`, about 50 bits, `randomInt`), writes `deviceCodes/{code}` and `device.code_created` (kind, name, room; never the code).
2. The dialog shows `https://<origin>/setup#code=ABCD-EFGH-JK` as a QR code. The code is in the fragment, so it never reaches a server, proxy or log.
3. The tablet (signed out) types or scans the code. `/setup` keeps `{ code, nonce }` in `sessionStorage` (`homehub.device-setup`; nonce = 32 random bytes, base64url) until the sign-in finishes, asks for a limited-use App Check token when App Check runs on the page (`appCheck` exported from `src/lib/firebase.ts`, `getLimitedUseToken`), and calls `redeemDeviceCodeAction` with the code in the request body.
4. The action takes the client address (`clientAddress`, below), then `redeemDeviceCodeGuarded`: server flag, rate limits, App Check (consumed), then `redeemDeviceCode`, one transaction:
   - read the code. Missing: `wrong_kind` when a member invite has that code, else `not_found`. `revokedAt`: `revoked`. Past `min(expiresAt, createTime + 15 min)`: `expired` (a stored `expiresAt` is never trusted further).
   - already used: if `redemptionNonceHash == sha256(nonce)` and the record it created is still `active` at the generation it created, this is the same tablet retrying after an uncertain answer and gets a fresh credential for that record; otherwise `used`.
   - the household exists (`not_found`), is not being deleted (`household_deleting`) and carries no legacy `memberEmails`/`ownerEmail` (`household_needs_upkeep`); the code's creator is still an active owner or admin (`creator_lost_access`, D-T14).
   - `pair`: creates the record (defaults plus the code's name, room and sections, `status: 'active'`, `generation: 1`). `repair`: the target record must not be `removed` (`not_repairable`) and its generation must still equal the code's `targetGeneration` (`superseded`); then `generation + 1`, `status: 'active'`, `pairedAt`, `pairedByUid`, the end fields cleared, settings untouched.
   - marks the code used (`usedAt`, `usedByDeviceId`, `usedDeviceName`, `usedGeneration`, `redemptionNonceHash`), writes `device.paired`/`device.repaired` (actor: the code's creator) and the creator's notification (`device-paired-<deviceId>-<generation>`).
5. After the commit the credential is issued under the device's **issuance lease** (`credentialLease: { holder, generation, until }` on the record, 30 s, taken and released in transactions): one redemption at a time per device, and only while the record is still `active` at the redemption's generation. A redemption superseded while it waited (a newer re-pair or a removal committed after it) gets `superseded` / `not_repairable` and changes nothing in Auth, so it never overwrites a newer generation's claims or ends its session. Under the lease every earlier credential is revoked and the new one minted; the record is then re-read: if it was removed meanwhile (removal does not take the lease) the credential just issued is ended (`not_repairable`); if a newer generation committed meanwhile the redemption is refused (`superseded`) without touching Auth, and that generation's issuance, which waits for the lease, revokes this credential and writes its own claims. A minting failure releases the lease and answers `failed`; the same code and nonce then recover the same record (retry path).
6. `/setup` keeps the pending code and nonce through every outcome a retry can still recover (`keepPendingAfter`, `src/lib/devices/setup-pending.ts`): `failed`, `rate_limited`, `app_check_failed`, `unavailable`, no answer, or a sign-in that did not finish. It drops them only after the sign-in or a refusal no retry can change (`used`, `expired`, `superseded`, …).
7. The tablet clears leftover push state (`clearPushState`: FCM `deleteToken`, then any push subscription of the service worker, then the stored push-device record; failures are logged and retried at the next start), calls `signInWithCustomToken`, and drops the pending nonce.

Two tablets redeeming one code race on the code document: Firestore serializes the transactions, exactly one commits and the others re-run, see `usedAt` with a different nonce hash and get `used`. The record is created inside the winning transaction, so no partial record exists. A re-pair racing a removal or another re-pair loses on the generation check (or on the re-pair code the removal revoked).

**Re-pair codes** (`createDeviceRepairCode`): same authority and limit; the target must be `active` or `unpaired`; older unused re-pair codes of that tablet are revoked (`superseded`) in the same transaction; the code stores `deviceId`, `targetGeneration`, and the record's name and room. **Cancel** (`revokeDeviceCode`): owners and admins, this household's codes only (another household's code is reported as not found), idempotent.

### Principal switch (S4)

`AuthProvider`'s Auth listener first asks `devicePrincipalOf(user)` (`src/lib/devices/principal.ts`): a user with an email is a person at once (no token read); otherwise the ID token's claims decide (`getIdTokenResult`, `readDeviceClaims`). A user with no email and a `device_` uid whose claims cannot be read (offline restore with an expired token) becomes `{ kind: 'device-unresolved', deviceId }`: never the personal flow, never a settled device with an empty household. While unresolved, `retryDeviceClaims` re-reads the claims on reconnect (`online`), on every ID-token change (`onIdTokenChanged`) and every 30 s, one read at a time, until they resolve; the tablet screen shows "HomeHub can't be reached right now" and opens no listener and sends no heartbeat meanwhile, then starts both once the principal resolves. For a tablet, `switchPrincipal` resets membership state, clears the previous person's household data on the device, sets `principal = { kind: 'device', deviceId, householdId, generation }` and returns before any profile work: no `users/{email}` read or creation, no profile listener, no membership listeners, no push sync (`currentUser` stays null, so the push manager never mounts), no member sync, no "No email address found" toast. The provider then renders the lazily loaded `set-up-landing.tsx` instead of the page (so a tablet never sees personal screens or `/setup`). `signInWithGoogle` refuses while the principal is a tablet. Personal sessions are unchanged (`principal = { kind: 'personal' }`).

### Settings, heartbeat, removal

- **Edits** (`updateDeviceSettings`, owners and admins by role): one transaction re-reads the household, the caller's membership and the record; a record not `active` refuses (`device_not_active`); `validateDevicePatch` (shared with the form) checks every named field and writes only fields whose value changes, as dotted paths, with `updatedAt`, `updatedByUid`, `updatedVia: 'devices-list'`. Two people editing different fields both keep their change. A start page in a section that is off is refused (`start_page_section_off`, D-T18); switching off the section that holds the start page resets it to Home in the same write. Admin-field edits write `device.settings_changed` (field names); comfort-only edits are not logged. The tablet listens to its own record, so edits reach it without a reload.
- **Heartbeat** (`recordDeviceHeartbeat`, device token): `verifyDevice`, at most 6 a minute per tablet, then a transaction that writes `lastSeenAt` (the server's clock) and `appVersion` (the running build id if it matches `^[0-9]{8}T[0-9]{9}Z$`, else `unknown`) only when the stored one is at least 60 s old or the version changed. The minimal tablet screen sends it at start, when it becomes visible, on reconnect and every 5 minutes while visible. The Devices list judges Online against the server's time (`reconcileDeviceSessions` returns `serverNow`; the list keeps the offset), never the viewer's clock.
- **Removal** (`removeDevice`, owners and admins): one transaction sets `status: 'removed'`, `generation + 1`, `removedAt`, `removedByUid`, `endedReason: 'removed'`, revokes the tablet's unused codes, writes `device.removed` and one notification per active owner and admin (`device-removed-<deviceId>-<generation>-<uid>`). After the commit, `finishDeviceRevocation` revokes and deletes the Auth user; if that fails the result says `authCleanup: 'pending'` and the record already refuses everything. A retry of Remove on a removed record changes nothing in Firestore and finishes the Auth side. Removed records stay (history) and can never be re-paired. Nobody's account is touched.

### Household deletion (B2)

`deleteHousehold` (`src/lib/server/household-membership.ts`): its first transaction also reads every device record and every device code of the household, marks each device `removed` (`generation + 1`, `endedReason: 'household-deleted'`) and revokes each unused code (`household-deleted`). Immediately after it commits, before any file or data deletion, every tablet of the household has its refresh tokens revoked and its Auth user deleted (3 tries each; failures are logged and left to the daily sweep). Data deletion then removes `devices/**` with the other subcollections, and the final batch deletes the household's `deviceCodes` with its invites. The rules refuse every device read once `deletingAt` is set, even if a later step fails and the household stays frozen.

### Daily sweep

`householdUpkeep` (hourly) calls `sweepDeviceRevocations(db, getAuth(), now)`, which runs in the hour `DEVICE_SWEEP_UTC_HOUR` (03 UTC) only: for every household's device records it runs `finishRevocationForRecord`, then it lists Auth users and deletes every `device_` user whose `hh_household` was not in its household list. The household list is read first, so before deleting such a user it re-reads the household and the device record the user names, and spares the user when either exists now or when the user was created after the sweep started (a household created and a tablet paired during the sweep). A failure counts as a failed household in the upkeep totals; it never blocks household upkeep.

### Actors and kid profiles (6.1, 6.2)

**Who may act at a tablet.** Membership records with `role` owner, admin, member or child and `status: 'active'`: adults with accounts and kid profiles. Never pending people, departing households, removed people, guests (WT-21a) or devices. The F3 "Who's here?" row lists exactly these (adults by name, then children); the gate applies the same rule to every action (`checkActorEligible`), so a stale roster can never credit an ineligible person.

**Kid profiles** (`src/lib/server/child-identities.ts`, JC-9): `households/{h}/members/kid_<20-char auto id>` with `uid`, `kind: 'identity'`, `role: 'child'` (fixed), `status: 'active'`, `displayName` (1-40, never an email), `avatarUrl` (null or a Storage download URL under `households/{h}/members/{kid}/avatar/`), `permissions` (overrides, editable as for any child), `joinedAt`, `createdAt`, `createdByUid`. No contact document, no `users/{email}` profile, no Auth user, no email: a `kid_` uid can never sign in (the server never mints a token for one). Owners and admins (role, active; JC-22) create (name only; the photo is uploaded by the dialog afterwards and set with an update), update (name, photo; the server checks that the URL is in the app's own Storage bucket, `NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET`, under the profile's path, and deletes a replaced photo after the commit; the dialog keeps the id of a profile it created, so pressing Save again after a failed photo step updates that profile instead of creating another) and remove them. Removal is one transaction body shared with `removeMember` (`removeIdentityInTransaction`): open chores and recurring templates assigned to the kid profile are unassigned, completed chores keep their history (stats are keyed by uid, so nothing is folded), the record and its PIN documents are deleted; the photo files go after the commit. Activity: `child.created`, `child.updated` (field names), `child.removed`.

### PINs (7)

**Storage (server only).** `households/{h}/members/{uid}/private/pin`: `{ pinId, hash, salt, params: { alg: 'scrypt', N: 32768, r: 8, p: 1, keyLen: 32, maxmem: 67108864 }, pepperId, pinVersion, setAt, setByUid, setHow: 'self' | 'admin-for-child' }` (`pinId`: a random UUID written with every set, never reused); a clear writes `pinId`, `hash`, `salt`, `params`, `pepperId` null with `clearedAt`, `clearedByUid` and keeps `pinVersion` (bumped). `hash = scrypt(HMAC-SHA256(pepper, pin), salt, 32, { N, r, p, maxmem: 64 MiB })` with the async `crypto.scrypt` (never `scryptSync`), a 16-byte random salt and `timingSafeEqual`. Hashing uses two pools per server instance, so changing PINs can never starve verification: verification has 4 scrypt slots (at most 8 verifications admitted at once, waiting included; `busy` beyond), PIN sets have 2; a slot is held only around the scrypt call itself, never across a transaction. PIN sets (`setMyPin`, `setChildPin`) are limited to 10 a minute per person and to 6 admitted at once per instance, running and waiting together (`PIN_SET_ADMISSION`; `busy` beyond). The PIN value is never logged, returned, put in activity details or kept after hashing. The existing rule on `members/{uid}/private/{docId}` allows a client `get` of `contact` only and no writes, so `pin` and `pinGuard` are unreadable and unwritable by every client (tested for the owner, the member and a tablet).

**Pepper** (JC-10): server secrets `HOMEHUB_PIN_PEPPER_<id>` (at least 32 characters; ids are letters and digits) and `HOMEHUB_PIN_PEPPER_CURRENT` naming the id new hashes use. Rotation: add a new id and make it current, keep the old ones configured; a successful verify against an older `pepperId` re-hashes with the current one in the settle transaction (same `pinVersion`, so sessions survive). Without the needed pepper, setting a PIN and verifying one both **fail closed** (`pin_unavailable`), and a verify fails before anything is counted. Losing a pepper forces every PIN hashed with it to be reset. Production: `HOMEHUB_PIN_PEPPER_CURRENT=V1` and `HOMEHUB_PIN_PEPPER_V1` from secret `homehubPinPepperV1` (`apphosting.yaml`; see [Firebase Platform](../firebase-platform/README.md)).

**Format** (JC-11): 4-6 digits; not the same digit throughout, not a straight run up or down (`1234`, `987654`).

**Authority** (WT-9a/b, WT-17; every action uses `verifyCaller`, so a tablet token is refused):

| Action | Who |
|---|---|
| Set or change your own PIN | Yourself (owner, admin, member, or a child with an account), from your own signed-in session; no old PIN needed. Guests: refused |
| Clear your own PIN | Yourself |
| Clear another person's PIN | An owner or admin (role) for someone of strictly lower rank (`rank()`); never set. Nobody but the owner touches the owner's PIN (WT-17c) |
| Set, change or clear a kid profile's PIN | An owner or admin (role) (WT-17d). Setting a PIN for any account is refused (no known-value reset, WT-17a) |
| Clear a lockout | Yourself, or an owner or admin above your rank |

Each set or clear bumps `pinVersion`, which ends that person's PIN sessions on every tablet at once (WT-17e). Activity: `pin.set` (`details.how`), `pin.cleared`, `pin.lockout_cleared` (actor and target, never the value). `pinStatusAction` tells owners and admins whether each person has a PIN and whether it is hard-locked, and everyone else only about themselves.

**Lockouts** (D-T11, WT-9f; arithmetic in `src/lib/devices/pins.ts`):

- Per tablet and person, `devices/{d}/pinGuards/{memberUid}`: `{ failures, attempts: [{ id, seq }], seq, lockedUntil, lockedBySeq, lockouts }`. Five consecutive wrong PINs lock that person's PIN on that tablet for 1 minute; each further lockout doubles (2, 4, 8) to a 15-minute cap. A correct PIN resets it.
- Every tablet-level lock writes a `pin.device_locked` activity entry (the tablet as actor, the person as target, `details.minutes`).
- Per person across tablets, `members/{uid}/private/pinGuard`: `{ recentFailures: [{ id, at }] (last hour, at most 20), dayFailures: [{ id, at }] (last 24 hours, at most 30), sinceSuccess: [{ id, seq }] (failures since the last correct PIN, at most 50), tabletLocks: [{ id, at }] (this person's tablet locks in the last 24 hours), repeatAlertAt, seq, lockedAt, lockedByAttempt, lockedReason }`. Every PIN for that person is refused on every tablet until cleared when any limit is reached: **20 failures within an hour** (`lockedReason: 'hour'`), **30 failures within 24 hours** (`'day'`; `MEMBER_FAILURES_PER_DAY_LOCK`, a count that correct PINs never reset), or **50 failures since their last correct PIN**, however slowly (`'total'`; `MEMBER_FAILURES_SINCE_SUCCESS_LOCK`). A correct PIN withdraws only its own provisional entries and forgives, for the since-last-correct count only, the failures recorded at or before its own reservation.
- When one person's PIN locks **3 tablets within 24 hours** (`TABLET_LOCKS_ALERT_COUNT`), every active owner and admin gets one "Tablet PIN keeps locking" notice (`sourceType: 'pin-tablet-locks'`); no further notice for that person within the next 24 hours (`repeatAlertAt`). Each lock writes `pin.locked` (`details.reason`) and sends a "Tablet PIN locked" notice to each active owner and admin. Residual risk (JC-26): anyone at a tablet can hard-lock a PIN; it is visible and recoverable.
- Lock activity and notices are written only once the attempt that set the lock proved wrong (and only while that lock is still in place, and never for a household that is gone or being deleted); the tablet is recorded as the actor and the person as the target. An attempt that reached a limit but was right lifts the lock it set and announces nothing. A failed announcement is retried once, then logged as a structured error (`pin_lock_announcement_failed` with household id, device id and reason; no names); the lock itself stands either way.
- Clearing a lockout empties the guards but keeps their sequence numbers, so an attempt in flight during the clear stays correctly ordered.
- Lock checks run before any hash work, so a locked PIN is never evaluated.

**Verification** (`verifyDevicePinAction` → `verifyDevicePin`; 7.4, S7, re-review R2), online only:

1. Pre-auth limits, never keyed by what the token claims: first 30 a minute per trusted client address (`clientAddress`, rightmost trusted `X-Forwarded-For` hop, passed by the server action; IPv6 addresses by their /64, `addressBucket`); then the token's signature and expiry are checked locally (`verifyIdToken(token, false)`) and its device claims and household are checked (`not_a_device`, `wrong_household`), and only then 600 a minute per instance is charged (`PRE_AUTH_LIMITS`, `preAuthAddressLimit`, `preAuthInstanceLimit`); then the revocation check (`verifyIdToken(token, true)`).
2. Before any Firestore or hash work: the verified tablet's own budget (10 verifies a minute, keyed by the verified device id, so a forged token naming a tablet never spends it), admission (at most 8 verifications at once per instance), and a second verify for the same tablet and person while one runs: `busy`. Then household, registration and actor eligibility (as the gate).
3. Transaction A: no PIN → `no_pin_set`; person hard-locked → `pin_locked_member`; tablet lock active → `pin_locked` with `retryAfterSec`; a missing pepper → `pin_unavailable`. Otherwise the attempt (with a fresh attempt id) is **counted as a failure in advance** on both guards, so the limits are exact under concurrency and scrypt runs once, outside any transaction.
4. The compare (async scrypt).
5. Wrong → nothing more to count: `pin_wrong` with `attemptsLeft`, or `pin_locked` / `pin_locked_member` when this attempt set a lock (announced now, as above). Right → transaction B re-reads the PIN record and requires `pinVersion` and hash equal to A's (a PIN changed or cleared in between opens no session: `pin_session_invalid`), re-runs the token-free gate checks, removes **only this attempt's** provisional entries (failures recorded by concurrent attempts stay; a lock set by a later attempt stays), re-hashes with the current pepper if needed, and creates the session. The answer comes only after B commits; if B fails the answer is `failed` and no session exists.

**PIN sessions** (7.5): `devices/{d}/pinSessions/{sha256(secret)}`: `{ memberUid, generation, pinVersion, roleAtUnlock, createdAt, lastUsedAt, expiresAt, endedAt, endedReason }` (server clock). The tablet keeps the 32-byte secret in memory only. Sessions also store the `pinId` they were opened with. Valid when not ended, not expired, for this actor, at the tablet's current generation, at the person's current `pinVersion` **and `pinId`** with a PIN set (`pinVersion` restarts at 1 when someone leaves or is removed and rejoins; `pinId` is never reused, so an old session can never validate again), and with the role unchanged since the unlock. Transaction B of a verify also requires the `pinId` read in A. Every gated use that commits slides it (`expiresAt = now + 2 min`, written last in the action's transaction). Admin-PIN capabilities need a session at most 30 s old (`pin_fresh_required`, S9). `endPinSessionAction` ends it ("Done", idle). PIN change or clear, re-pair or removal, role change and member removal are all detected on the next use; nothing fans out. The daily sweep deletes sessions created more than a day ago. One session type serves the PIN level and the points PIN (JC-12).

### The device action gate (8)

**Policy** (`src/lib/devices/action-policy.ts`, pure, shared with the tablet UI): every device-reachable action is a capability with a section, a level class (`device`, `face`, `pin`, `admin-pin`, `not_on_tablets`, `never`), the permissions of which the actor needs one (`null` only for `device` and `admin-pin`; never an empty list), an optional actor rule (`original-actor`, `original-actor-or-delete-permission`, `author-or-permission` with `actorRulePermission`), `points`, `queueable`, `faceNeedsUndoProof` and `freshPinSec`. The table follows design 8.2 as revised: Pets feed/dose/care/note/weight and their Undo are `face*` (backdated feeds and doses older than 12 hours are separate `.old` PIN capabilities; `backdatedCapability` picks them from the intent's time on the server, JC-27); note pin/unpin/edit/delete, older log deletes, time corrections, legacy-medication confirmation, course edits and Finish, meal slots, profile edits, pet create and delete are PIN (lead decision JC-14); pet photos are not on tablets. Chore complete, take and their Undo are `face*` points actions; every other chore action is not on tablets. Household-notice dismissal is `face*`. Shopping, maintenance, AI flows, household administration and automation are not on tablets; Profile, push registration, targeted notifications and personal reminders are `never`. `UNDO_PROVEN` is **empty**: a `face*` capability enters it only in the PR that records its 10.4 proof in the tracker (F4). An action name not in the table is `unclassified`.

**Contract** (`src/lib/server/device-gate.ts`): `authorizeDeviceAction({ idToken, householdId, capability, actorUid?, pinSessionId?, opId?, queued? }, now?)` returns `{ deviceId, deviceName, generation, householdId, timeZone, actor, level, capability, opId, attribution, now, hooks }` or throws `DeviceActionError(code, retryAfterSec?, attemptsLeft?)`. Checks, in order (8.4):

1. Shape: request at most 16 KB (`invalid_input`), capability known (`unclassified`), class not `not_on_tablets`/`never` (`not_on_tablets`: a permanent answer, "That isn't available on wall tablets yet. Use your phone.") and the server flag on (`unavailable`), a UUID `opId` for every face/PIN capability (`invalid_input`).
2. Rate (`rate_limited`): limits keyed independently of the claimed identity: 240 a minute per trusted client address (passed by the server action as `options.clientAddress`; IPv6 by /64) before anything, and 6000 a minute per instance once the token's signature has been checked locally and it is a tablet token of this household; after step 3, 60 gated calls a minute per **verified** tablet. A forged token naming a tablet never spends that tablet's budget, and tokens that are not tablet tokens of this household never spend the per-instance bucket. Two bounded rate maps (`src/lib/devices/rate-window.ts`: emptied windows are swept, the least recently used keys dropped past 20,000 each): one for keys the server knows (a verified tablet, a person, the instance; `takeRateSlot`) and one for address buckets taken before anything about the caller is known (`takeAddressRateSlot`), so address keys never push out verified ones. Code redemption's per-address limit uses the same address buckets (IPv6 by /64).
3. Token: `verifyIdToken(token, true)`, read with F1's `classifyVerifyError` (revoked, disabled or deleted: `device_revoked`; invalid or expired: `unauthenticated`; a verifier outage: `unavailable`, which the tablet treats as "try again", never as removal: `endsTabletSession`); device claims (`not_a_device` for a personal token).
4. Household: the token's household (`wrong_household`); exists and not being deleted (`household_deleting`).
5. Registration: record `active` at the token's generation (`device_revoked`).
6. Section on (`section_off`; Home always on).
7. Actor (every class but `device`): present (`actor_required`); a member of this household and not a `device_` uid (`actor_not_member`); not a guest (`actor_guest`); active owner/admin/member/child (`actor_inactive`).
8. Capability: one of `permissions` in the actor's effective permissions (`forbidden`); `admin-pin` needs the owner or admin role (`admin_pin_required`). Actor rules apply against the target record inside the operation (`assertActorRule`).
9. Required level (`requiredLevel`): the class; `face*` → PIN until proven; points actions → PIN for Everyone, or Kids only and the Child role (D-T10).
10. PIN: the actor has a PIN (`no_pin_set`, WT-9c) and the request names a valid session for this actor (`pin_required` when absent, `pin_session_invalid`, `pin_fresh_required`). A valid session supplied with a face action records `pin`; an invalid one is ignored.
11. Queued replay (`queued.createdAt`): at most 24 h old and 5 min in the future (`stale_intent`, JC-18); only queueable capabilities (`invalid_input`); a PIN required now is refused (`pin_required`), never upgraded.

Nothing the client sends about role, level, permissions, names or the device is used. **Hooks** (S1): `precheck(tx)` (reads only) reads the clock again on every transaction attempt (the real time; tests inject `options.clock`), so a retried transaction never accepts a session that expired, or an admin-PIN session that went stale, in between; `finalize` stores and slides with that time. It re-reads the household, record, actor, PIN record and session inside the mutation's own transaction and re-runs steps 4-11, updating `actor`, `level` and `attribution`; with an `opId` it also reads the ledger entry and returns `{ replay }` (same capability, actor and generation: return the stored summary, write nothing), throws `conflict` (another capability, actor or generation) or `already_undone`; for `….undo` capabilities it returns `{ undo: 'tombstone' | 'already' | 'applied', original }`. `finalize(tx, { targetPath, summary, targetName?, undo? })` (writes only, last) writes the ledger entry (applied, undone or tombstone), a `device.action` activity entry for PIN-level actions, and slides the PIN session. Refusal copy for the tablet: `deviceRefusalResponse(code, { name, kid, retryAfterSec })` (8.5). Two codes are kept apart: `not_on_tablets` (the capability is not offered on tablets; permanent, "That isn't available on wall tablets yet. Use your phone.") and `unavailable` (F1's retryable code: the server flag is off or the verifier or backend is unreachable; "Can't reach HomeHub right now. Try again in a moment.", `retry: true`). Neither ends the tablet's session (`endsTabletSession`).

**Op ledger** (`src/lib/server/device-ops.ts`, B1): `devices/{d}/ops/{opId}`: `{ capability, actorUid, generation, targetPath, state: 'applied' | 'undone', appliedAt, undoneAt, tombstone, summary, deviceCreatedAt, expireAt }`, all times the server clock stored in the action's transaction (`expireAt` = 7 days later; the daily sweep deletes expired entries). Undo capabilities reverse only the actions listed for them in `UNDO_OF` (`src/lib/devices/action-policy.ts`; `undoAccepts`), backdated variants included (`pets.feed.undo`: `pets.feed`, `pets.feed.backdated`, `pets.feed.backdated.old`; `pets.dose.undo`: `pets.dose.give`, `pets.dose.give.old`; `pets.note.undo`: `pets.note.add` only, never a note pin, unpin, edit or delete); any other ledger entry is a `conflict`, never a prefix match. A tombstone stores the Undo capability, actor and credential generation that wrote it: the same Undo again is `already`; an action it reverses, by the same actor at the same generation, is `already_undone`; anything else under that opId is a `conflict`. Helpers: `classifyActionAttempt`, `classifyUndoAttempt`, `assertUndoable` (same generation, original actor or the actor rule, window `appliedAt + 10 s + 5 s grace`: `undo_expired`), `createdRecordUnchanged` (`updateTime == createTime`), `undoWindowOpen`. The per-capability reversal and its proof are F4's.

**Operations take an actor** (9, `src/lib/server/operation-context.ts`): `OperationActor = { uid, name, device? }`, `OperationContext = { actor, opId?, hooks?, now }`. Every `…As` operation opens exactly one transaction, runs `precheck` first (return a replay unchanged), then its own reads and writes, and `finalize` last; `ctx.actor.device` is stored as `deviceAttribution`. `deviceOperationContext(authority)` reads the actor through getters so the values `precheck` re-checked are the ones stored; personal callers use `personalOperationContext` with no hooks (unchanged behaviour).

**Comfort from the tablet** (`updateDeviceComfortAction`, capability `device.comfort`, no actor, no PIN): only the four comfort fields, validated by `validateDevicePatch(..., 'comfort')`, written as dotted paths with `updatedVia: 'tablet-comfort'` inside a transaction that runs the hooks; not logged.

### Attribution (12)

`deviceAttribution = { deviceId, deviceName (frozen), generation, actorUid, level: 'face' | 'pin' }` is stored next to a module's own actor fields by the device actions (F4). Personal clients can never add it (every content allow-list leaves it out: chores, feeding logs, feeding state, medication logs, care logs), change it or remove it (`deviceAttributionKept()` on updates of chores, feeding, medication and care logs); on chores it may be removed only by an update that clears the completion (`isCompleted` from true to false; S10). PIN-level device actions are logged as `device.action` (`via: 'device'`, `deviceId`, `deviceName`, `level`, `details.capability`, `targetName`); face actions are attributed on their records and the ledger only (JC-19).

### Points PIN (WT-9d, WT-22, D-T10)

`households/{h}.devicePolicy = { pointsPin: 'off' | 'kids' | 'everyone', updatedAt, updatedByUid }` (absent: Off), set by owners and admins (role) through `updatePointsPinAction` (activity `device.policy_changed`). The gate raises points capabilities (chore complete, take, and their Undo) to PIN for everyone, or for the Child role (kid profiles included) under Kids only. Feeding and medication never ask (WT-22d). A tablet reads it from the household document it already reads.

## Authentication, Roles, and Security

**Server authority.** Codes, re-pair, settings, removal and the Devices-list reconcile authenticate a personal caller with `verifyCaller` (a verified ID token with an email, so a device token is refused) and require the **role** owner or admin, active, inside the transaction (a member granted `household.manageInvites` is refused; JC-22). Redemption is unauthenticated and guarded (below). The heartbeat takes the device's own token through `verifyDevice`. Every existing personal server action (household, chores, shopping, automation, AI flows) authenticates through `verifyCaller` or `authorizeHouseholdAction`, both of which require an email, so each refuses a device token; `tests/server/device-identity.test.ts` calls every exported action of those modules with a device token.

**Firestore rules** (`firestore.rules`, Identity section). A device token has no email, so `signedIn()`, `hasMemberDoc`, `hasHouseholdPermission`, `isOwnerOrAdmin` and everything built on them stay false for it; device access is only separate `||` clauses on reads. Helpers take the household from the **path** and require the token to name it:

- `isDevicePrincipal()`: `hh_kind == 'device'`, `sign_in_provider == 'custom'`, no `email` claim, string `hh_device`, `uid == 'device_' + hh_device`, numeric `hh_gen`.
- `isDevice(h)`: plus `hh_household == h` (no read).
- `deviceActive(h)`: plus the record `households/h/devices/<hh_device>` is `active` at `hh_gen`, and the household has no `deletingAt` (two lookups).
- `sectionEnabled(h, s)`: plus `sections[s] == true`.

| Path | Tablet read |
|---|---|
| `households/{h}` | get, when `deviceActive(h)` and the document has no `memberEmails`/`ownerEmail` |
| `members/{uid}` | get and list, `deviceActive(h)` |
| `members/{uid}/private/*` | never |
| `devices/{d}` | its own record only, in every status (`isDevice(h) && d == hh_device`); owners and admins get and list; no client writes |
| `devices/{d}/**` | never (catch-all) |
| `notifications/{id}` | `*` audience only, through `where('audience','array-contains','*')` + `where('category','==',c)`: `system` and `general` always, `chores`/`pets`/`shopping`/`maintenance` when that section is on (`deviceNotificationReadable`). Queries without the category filter, with `array-contains-any [uid,'*']` or `array-contains <uid>`, with a `category in [...]` filter that includes a category the tablet may not read, a `get` of a targeted notice, and the `automation` category are refused (tested) |
| `chores`, `chore-settings`, `chore-templates`, `rooms`, `stats` | `sectionEnabled(h,'chores')` |
| `shopping-lists` (+ `items`, `config`), `pantry-inventory`, `barcode-library`, `stores`, `shopping-settings`, `trips`, `shopping-usuals` | `sectionEnabled(h,'shopping')` |
| `pets`, `feeding-logs`, `feeding-state`, `medication-logs`, `care-logs` | `sectionEnabled(h,'pets')` (every new Pets path must get the clause in the PR that adds it) |
| `home-assets`, `vehicles`, `maintenance`, `maintenance-attachments` | `sectionEnabled(h,'maintenance')` |
| `auditLogs`, `home-automation`, unknown paths, `inviteCodes`, `deviceCodes`, `users/**`, `aiUsage` | never |

`deviceCodes/{code}`: owners and admins (role) of the code's household read it; no client writes. **No device client writes anywhere**: no write rule has a device clause.

**F2 rules.** `members/{uid}/private/pin` and `pinGuard` keep the existing rule (a client `get` of `contact` only, no writes) and the device subcollections the catch-all deny; both are tested for the owner, the member and a tablet. Membership records, kid profiles included, stay server-written. `deviceAttributionKept()` / `choreDeviceAttributionKept()` guard updates (section 12). Kid profile photos: `households/{h}/members/{memberUid}/avatar/{file}` is readable with `household.view` or by an active tablet of that household, and uploaded (image, at most 5 MB) or deleted only by an active owner or admin, only under a `kid_` uid.

**Storage rules** (`storage.rules`): `deviceActiveForStorage(h)` (claims as above, `hh_household == h`, the record under the path's household `active` at `hh_gen`; one Firestore lookup, Storage allows two) and `deviceSectionForStorage(h, s)`. Tablets read `households/{h}/pets/**` (pets on), `households/{h}/barcode-library/**` (shopping on), `households/{h}/maintenance/**` (maintenance on), and profile photos in account-ID folders `users/{uid}/avatars/**` only (never an email-named folder). No device uploads or deletes. Household A's tablet never reads household B's files, even when B has a record with its id (tested per clause).

**Release gate (JC-8, B3).** Tablet reads expose whatever fields shared documents hold. No rules release containing a device read clause deploys until `scripts/ops/scrub-shared-emails.mjs`, `scrub-member-emails.mjs`, `scrub-remaining-emails.mjs` and `migrate-avatars-to-uid.mjs` all report zero remaining work in a production dry run, recorded in the tracker with date and counts. Pairing also refuses a household still carrying `memberEmails`/`ownerEmail`.

**Redemption guards (3.4).** Server flag; in-memory windows of 10 attempts per minute per client address and 300 per minute per instance (`takeRateSlot`); a limited-use App Check token verified with `consume: true`, failing closed outside emulator mode (missing, invalid, over-long or already consumed tokens are `app_check_failed`). The client address is never the first `X-Forwarded-For` entry: `clientAddress(headers, hops)` takes the entry `hops` places left of the rightmost one (default 1: next-to-last, the App Hosting / Cloud Run shape), and validates only that entry: whatever a caller puts left of it is never parsed, so garbage there cannot remove the address. When the header is absent, too short, or the trusted entry is not a bare IP, the request is limited in one shared `unknown` bucket (`UNKNOWN_CLIENT`); the per-address limit is never skipped. **Pending live check:** the hop count must be confirmed on a deployment (set `HOMEHUB_LOG_FORWARDED_SHAPE=true` to log the entry count of each redemption, no addresses) and `HOMEHUB_TRUSTED_PROXY_HOPS` set if it differs.

**Privacy.** Codes store no email; activity entries store no email, code, nonce or token; the creator's notification names the tablet, not a person. The redemption result returns only `{ customToken, householdId, deviceId }`.

## Invariants and Failure Behavior

- A selected member is attribution, never proof: the server re-reads the member on every action and inside the mutation's transaction; the level comes from server-held session state, never a client flag (WT-5e, WT-7d).
- PIN material never leaves the server; a PIN changed, cleared, or a role changed ends its sessions on every tablet at their next use; a correct PIN never forgives failures recorded by concurrent attempts.
- Kid profiles cannot sign in, never receive targeted notices, have a fixed Child role and are never offered as chore assignees yet.
- A device principal is never a member: no membership record, never in member lists, pickers, audiences or push recipients; it holds no push subscription (cleared before sign-in and at every tablet start).
- Every credential is bound to one household and one generation; a bumped generation or a non-active status refuses new requests in the rules and on the server at once, whatever the ID token's expiry.
- Codes are single use, expire 15 minutes after the server stored them, and are redeemed only in their own flow; member invites never pair a tablet, and device codes never join a person.
- Redemption is idempotent per nonce and has exactly one winner per code; a re-pair has exactly one winner per generation.
- If the Auth calls after a removal fail, the action still succeeds (`authCleanup: 'pending'`), the record already refuses everything, and a retry, the Devices list or the daily sweep finish it.
- With the flags off: Devices tab hidden, setup button hidden, `/setup` not found, every device server function refuses with `unavailable`.
- The minimal tablet screen ends the session (Firestore cache cleared, push cleared, signed out, back to `/setup` with a one-shot note) when, from the server, its record is missing, not active, at another generation, unreadable, or when the heartbeat answers `device_revoked`, `household_deleting` or `unauthenticated` (`endsTabletSession`). `unavailable` (a verifier outage), `rate_limited`, `failed` and network errors keep the session and the next beat tries again. Cached snapshots never decide.
