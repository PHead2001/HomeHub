## Purpose and Scope

This module owns the **device principal**: a wall tablet that joins one household with a single-use device code instead of a Google account, has no permissions of its own, and acts as whoever is standing at it (the selected member, checked by the server on every action). Built today:

- the device credential (Firebase Auth custom tokens for uid `device_<deviceId>`), its verification, and ending it (removal, re-pair, household deletion);
- pairing (device codes, QR setup link with the code in the URL fragment, the `/setup` screen with typed entry and camera scan, redemption) and re-pairing the same record;
- the device record (`households/{h}/devices/{deviceId}`): settings that live with the household, edited from the Devices tab; the heartbeat (truthful last seen and app version);
- the Firestore and Storage **read** rules for tablets (no device client writes anywhere);
- the principal switch: `AuthProvider` tells a tablet session from a personal one before any profile work, and a tablet session renders the **tablet shell** instead of the app;
- the tablet shell (rail, top bar, household resting view, read-only section views, "Who's here?", PIN pad, state machine and timers, ambient, night dimming, keep-awake, idle reload, Tablet settings and the protected exits), revocation observation and clearing on the tablet, the offline face-action queue and the Undo journal;
- household quiet hours (the setting, its server action and the Devices-tab card; tablets dim during them);
- actors: who may act at a tablet (active owners, admins, members and children, including **kid profiles**: `members/kid_<id>` records with `kind: 'identity'`, no sign-in);
- tablet **PINs**: server-held salted scrypt hashes with a versioned server pepper, the WT-17 authority matrix, verification with lockouts per tablet and per person, and PIN sessions;
- the **device action gate** (`authorizeDeviceAction`) with the capability policy (`src/lib/devices/action-policy.ts`), the transaction hooks every device mutation runs, the server **op ledger** helpers, and the `OperationActor` / `OperationContext` types feature operations take;
- attribution of device writes (`deviceAttribution`) and their activity entries; the household **points-PIN** setting.

It does not own the feature data tablets read (chores, pets, shopping, maintenance keep their own modules and rules; this module adds only the separate device read clauses) nor the feature operations themselves: each feature keeps one server operation that takes an actor and runs this module's hooks (F4 adds the Pets and Chores device actions).

**Not on tablets (recorded, GT-2):** dismissing household notices (`notifications.dismiss` and its Undo; WT-10d: the notices view is read-only, members dismiss notices in the personal app); creating a pet (`pets.pet.create`) and pet photos (`pets.photo.upload`); the separate confirmation of a parsed meal-plan suggestion (`pets.slots.confirm`: on a tablet the meal-times editor saves as `pets.slots.edit`, which confirms a first plan too). Personal accounts are unaffected by all of it.

## Architecture and Data Flow

### Device identity

A tablet's Firebase uid is `device_<deviceId>` (`deviceId` is the record's 20-character auto id; Google uids never contain `_`). Its ID token carries four developer claims and nothing personal: `hh_kind: 'device'`, `hh_household`, `hh_device` (equals the uid suffix), `hh_gen` (the credential generation, an integer). No email, name or picture; `firebase.sign_in_provider == 'custom'`. `mintDeviceCredential(deviceId, householdId, generation)` creates (or re-enables) the Auth user with no email, stores the claims with `setCustomUserClaims` (the copy every newly issued ID token carries) and returns `createCustomToken(uid, claims)`, used once for the sign-in. The server test proves all four claims are present after a refresh-token exchange at the emulator's `securetoken` endpoint and that `hh_gen` arrives as an integer. **Emulator limit:** the Auth emulator does not check `revokeRefreshTokens` on the refresh-token exchange (it refuses only deleted or disabled users), and re-stamps `auth_time` on it, so after a re-pair the tests prove that the device's refresh tokens were revoked (`tokensValidAfterTime` moved past the old sign-in) and that an ID token the emulator still issues from the old refresh token carries the old `hh_gen` and is refused by `verifyDevice` and the rules; refusal at the exchange itself is production Firebase behaviour, to be confirmed live. The session is Firebase Auth's refresh token in the browser's existing persistence (IndexedDB); nothing else credential-like is stored.

`verifyDevice(idToken, householdId)` runs `verifyIdToken(token, true)` and classifies a failure (`classifyVerifyError`, `src/lib/devices/verify-errors.ts`): a revoked token or a disabled or deleted user is `device_revoked`; an invalid or expired token is `unauthenticated`; anything else (network, `auth/internal-error`, quota, timeouts, unknown or missing codes) is a verifier outage, `unavailable`, which the tablet treats as "try again later" and never as the end of its session, checks the claims (`readDeviceClaims`; a personal token is `not_a_device`), that the token's household is the requested one (`wrong_household`), that the household exists without `deletingAt` (`household_deleting`), and that the record is `active` at the token's generation (`device_revoked`).

**Revocation.** New requests are refused as soon as the record's `status` leaves `active` or its `generation` moves past the token's `hh_gen`: the rules compare them on every read, query or listener start, and `verifyDevice` on every server call. After the record's transaction commits, the Auth side follows (`finishRevocationForRecord`): refresh tokens revoked, then the user deleted (`removed`) or disabled (`unpaired`); an `active` record whose Auth user still carries an older `hh_gen` gets its refresh tokens revoked. It is idempotent and re-run by a retry of Remove, by opening the Devices list (`reconcileDeviceSessions`, at most once a minute per household per instance) and by the daily sweep. **Already-open listeners (JC-25):** Firestore does not document re-evaluating an open listener when a document its rules `get()` changes; `tests/server/device-identity.test.ts` holds a listener across a removal and records what it receives: on the Firestore emulator (2026-11-14) the listener got `permission-denied` when the next change to the document arrived after the removal, instead of the new data. That is the emulator; production behaviour is not documented and still needs the live check. Without it, a tampered tablet could keep an open listener until its ID token expires (at most an hour), after which the refresh fails. An honest tablet tears its listeners down as soon as it sees its record change (the tablet shell, `tablet-shell.tsx`; section "Revocation on the tablet").

### Pairing and redemption

1. An owner or admin (role) creates a code (`createDeviceCode`): name and room (1–40 characters after trimming), optional sections. One transaction checks the caller's role and the household (not being deleted), refuses an 11th live code (`too_many_codes`), reserves a code never used by a device code or a member invite (`INVITE_CHARS`, `XXXX-XXXX-XX`, about 50 bits, `randomInt`), writes `deviceCodes/{code}` and `device.code_created` (kind, name, room; never the code).
2. The dialog shows `https://<origin>/setup#code=ABCD-EFGH-JK` as a QR code. The code is in the fragment, so it never reaches a server, proxy or log.
3. The tablet (signed out) types or scans the code. `/setup` keeps `{ code, nonce }` in `sessionStorage` (`homehub.device-setup`; nonce = 32 random bytes, base64url) until the sign-in finishes, asks for a limited-use App Check token when App Check runs on the page (`appCheck` exported from `src/lib/firebase.ts`, `getLimitedUseToken`), and calls `redeemDeviceCodeAction` with the code in the request body.
4. The action takes the client address (`clientAddress`, below), then `redeemDeviceCodeGuarded`: server flag, rate limits, App Check (consumed), then `redeemDeviceCode`, one transaction:
   - read the code. Missing: `wrong_kind` when a member invite has that code, else `not_found`. `revokedAt`: `revoked`. Past `min(expiresAt, createTime + 15 min)`: `expired` (a stored `expiresAt` is never trusted further).
   - already used: if `redemptionNonceHash == sha256(nonce)` and the record it created is still `active` at the generation it created, this is the same tablet retrying after an uncertain answer and gets a fresh credential for that record; otherwise `used`.
   - the household exists (`not_found`), is not being deleted (`household_deleting`) and carries no legacy `memberEmails`/`ownerEmail` (`household_needs_upkeep`); the code's creator is still an active owner or admin (`creator_lost_access`, D-T14).
   - `pair`: creates the record (defaults plus the code's name, room and sections, `status: 'active'`, `generation: 1`). `repair`: the target record must not be `removed` (`not_repairable`) and its generation must still equal the code's `targetGeneration` (`superseded`); then `generation + 1`, `status: 'active'`, `pairedAt`, `pairedByUid`, the end fields cleared, settings untouched.
   - marks the code used (`usedAt`, `usedByDeviceId`, `usedDeviceName`, `usedGeneration`, `redemptionNonceHash`), writes `device.paired`/`device.repaired` (actor: the code's creator) and the creator's notification (`device-paired-<deviceId>-<generation>`).
5. After the commit the credential is issued under the device's **issuance lease** (`credentialLease: { holder, generation, until }` on the record, 30 s, taken and released in transactions): one redemption at a time per device, and only while the record is still `active` at the redemption's generation. A redemption superseded while it waited (a newer re-pair or a removal committed after it) gets `superseded` / `not_repairable` and changes nothing in Auth, so it never overwrites a newer generation's claims or ends its session. Under the lease every earlier credential is revoked and the new one minted; the record is then re-read: if it was removed meanwhile (removal does not take the lease) the credential just issued is ended (`not_repairable`); if a newer generation committed meanwhile the redemption is refused (`superseded`) without touching Auth, and that generation's issuance, which waits for the lease, revokes this credential and writes its own claims. A minting failure releases the lease and answers `failed`; the same code and nonce then recover the same record (retry path).
6. `/setup` keeps the pending code and nonce through every outcome a retry can still recover (`keepPendingAfter`, `src/lib/devices/setup-pending.ts`): `failed`, `rate_limited`, `app_check_failed`, `unavailable`, no answer, or a sign-in that did not finish. It drops them only after the sign-in or a refusal no retry can change (`used`, `expired`, `superseded`, …).
7. The tablet clears leftover push state (`clearPushState`: FCM `deleteToken`, then any push subscription of the service worker, then the stored push-device record; failures are logged and retried at the next start), calls `signInWithCustomToken`, and drops the pending nonce.

Two tablets redeeming one code race on the code document: Firestore serializes the transactions, exactly one commits and the others re-run, see `usedAt` with a different nonce hash and get `used`. The record is created inside the winning transaction, so no partial record exists. A re-pair racing a removal or another re-pair loses on the generation check (or on the re-pair code the removal revoked).

**Re-pair codes** (`createDeviceRepairCode`): same authority and limit; the target must be `active` or `unpaired`; older unused re-pair codes of that tablet are revoked (`superseded`) in the same transaction; the code stores `deviceId`, `targetGeneration`, and the record's name and room. **Cancel** (`revokeDeviceCode`): owners and admins, this household's codes only (another household's code is reported as not found), idempotent.

### Principal switch (S4)

`AuthProvider`'s Auth listener first asks `devicePrincipalOf(user)` (`src/lib/devices/principal.ts`): a user with an email is a person at once (no token read); otherwise the ID token's claims decide (`getIdTokenResult`, `readDeviceClaims`). A user with no email and a `device_` uid whose claims cannot be read (offline restore with an expired token) becomes `{ kind: 'device-unresolved', deviceId }`: never the personal flow, never a settled device with an empty household. While unresolved, `retryDeviceClaims` re-reads the claims on reconnect (`online`), on every ID-token change (`onIdTokenChanged`) and every 30 s, one read at a time, until they resolve; the tablet screen shows "HomeHub can't be reached right now" and opens no listener and sends no heartbeat meanwhile, then starts both once the principal resolves. For a tablet, `switchPrincipal` resets membership state, clears the previous person's household data on the device, sets `principal = { kind: 'device', deviceId, householdId, generation }` and returns before any profile work: no `users/{email}` read or creation, no profile listener, no membership listeners, no push sync (`currentUser` stays null, so the push manager never mounts), no member sync, no "No email address found" toast. The provider then renders the lazily loaded tablet shell (`tablet-shell.tsx`) instead of the page and the whole personal layout (header, tab bar, command palette, push manager), so a tablet never sees personal screens or `/setup`. `signInWithGoogle` refuses while the principal is a tablet. Personal sessions are unchanged (`principal = { kind: 'personal' }`).

### Settings, heartbeat, removal

- **Edits** (`updateDeviceSettings`, owners and admins by role): one transaction re-reads the household, the caller's membership and the record; a record not `active` refuses (`device_not_active`); `validateDevicePatch` (shared with the form) checks every named field and writes only fields whose value changes, as dotted paths, with `updatedAt`, `updatedByUid`, `updatedVia: 'devices-list'`. Two people editing different fields both keep their change. A start page in a section that is off is refused (`start_page_section_off`, D-T18); switching off the section that holds the start page resets it to Home in the same write. Admin-field edits write `device.settings_changed` (field names); comfort-only edits are not logged. The tablet listens to its own record, so edits reach it without a reload.
- **Heartbeat** (`recordDeviceHeartbeat`, device token): `verifyDevice`, at most 6 a minute per tablet, then a transaction that writes `lastSeenAt` (the server's clock) and `appVersion` (the running build id if it matches `^[0-9]{8}T[0-9]{9}Z$`, else `unknown`) only when the stored one is at least 60 s old or the version changed. The minimal tablet screen sends it at start, when it becomes visible, on reconnect and every 5 minutes while visible. The Devices list judges Online against the server's time (`reconcileDeviceSessions` returns `serverNow`; the list keeps the offset), never the viewer's clock.
- **Removal** (`removeDevice`, owners and admins): one transaction sets `status: 'removed'`, `generation + 1`, `removedAt`, `removedByUid`, `endedReason: 'removed'`, revokes the tablet's unused codes, writes `device.removed` and one notification per active owner and admin (`device-removed-<deviceId>-<generation>-<uid>`). After the commit, `finishDeviceRevocation` revokes and deletes the Auth user; if that fails the result says `authCleanup: 'pending'` and the record already refuses everything. A retry of Remove on a removed record changes nothing in Firestore and finishes the Auth side. Removed records stay (history) and can never be re-paired. Nobody's account is touched.

### Household deletion (B2)

`deleteHousehold` (`src/lib/server/household-membership.ts`): its first transaction also reads every device record and every device code of the household, marks each device `removed` (`generation + 1`, `endedReason: 'household-deleted'`) and revokes each unused code (`household-deleted`). Immediately after it commits, before any file or data deletion, every tablet of the household has its refresh tokens revoked and its Auth user deleted (3 tries each; failures are logged and left to the daily sweep). Data deletion then removes `devices/**` with the other subcollections, and the final batch deletes the household's `deviceCodes` with its invites. The rules refuse every device read once `deletingAt` is set, even if a later step fails and the household stays frozen.

### Daily sweep

`householdUpkeep` (hourly) calls `sweepDeviceRevocations(db, getAuth(), now)`, which runs in the hour `DEVICE_SWEEP_UTC_HOUR` (03 UTC) only: for every household's device records it runs `finishRevocationForRecord`, then it lists Auth users and deletes every `device_` user whose `hh_household` was not in its household list. The household list is read first, so before deleting such a user it re-reads the household and the device record the user names, and spares the user when either exists now or when the user was created after the sweep started (a household created and a tablet paired during the sweep). A failure counts as a failed household in the upkeep totals; it never blocks household upkeep.

### Actors and kid profiles (6.1, 6.2)

**Who may act at a tablet.** Membership records with `role` owner, admin, member or child and `status: 'active'` (a record without `status` counts as active, as everywhere else; the tablet's roster, `rosterFrom`, applies the same default): adults with accounts and kid profiles. Never pending people, departing households, removed people, guests (WT-21a) or devices. The F3 "Who's here?" row lists exactly these (adults by name, then children); the gate applies the same rule to every action (`checkActorEligible`), so a stale roster can never credit an ineligible person.

**Kid profiles** (`src/lib/server/child-identities.ts`, JC-9): `households/{h}/members/kid_<20-char auto id>` with `uid`, `kind: 'identity'`, `role: 'child'` (fixed), `status: 'active'`, `displayName` (1-40, never an email), `avatarUrl` (null or a Storage download URL under `households/{h}/members/{kid}/avatar/`), `permissions` (overrides, editable as for any child), `joinedAt`, `createdAt`, `createdByUid`. ### PINs (7)

**Storage (server only).** `households/{h}/members/{uid}/private/pin`: `{ pinId, hash, salt, params: { alg: 'scrypt', N: 32768, r: 8, p: 1, keyLen: 32, maxmem: 67108864 }, pepperId, pinVersion, setAt, setByUid, setHow: 'self' | 'admin-for-child' }` (`pinId`: a random UUID written with every set, never reused); a clear writes `pinId`, `hash`, `salt`, `params`, `pepperId` null with `clearedAt`, `clearedByUid` and keeps `pinVersion` (bumped). `hash = scrypt(HMAC-SHA256(pepper, pin), salt, 32, { N, r, p, maxmem: 64 MiB })` with the async `crypto.scrypt` (never `scryptSync`), a 16-byte random salt and `timingSafeEqual`. Hashing uses two pools per server instance, so changing PINs can never starve verification: verification has 4 scrypt slots (at most 8 verifications admitted at once, waiting included; `busy` beyond), PIN sets have 2; a slot is held only around the scrypt call itself, never across a transaction. PIN sets (`setMyPin`, `setChildPin`) are limited to 10 a minute per person and to 6 admitted at once per instance, running and waiting together (`PIN_SET_ADMISSION`; `busy` beyond). The PIN value is never logged, returned, put in activity details or kept after hashing. The existing rule on `members/{uid}/private/{docId}` allows a client `get` of `contact` only and no writes, so `pin` and `pinGuard` are unreadable and unwritable by every client (tested for the owner, the member and a tablet).

**Pepper** (JC-10): server secrets `HOMEHUB_PIN_PEPPER_<id>` (at least 32 characters; ids are letters and digits) and `HOMEHUB_PIN_PEPPER_CURRENT` naming the id new hashes use. Rotation: add a new id and make it current, keep the old ones configured; a successful verify against an older `pepperId` re-hashes with the current one in the settle transaction (same `pinVersion`, so sessions survive). Without the needed pepper, setting a PIN and verifying one both **fail closed** (`pin_unavailable`), and a verify fails before anything is counted. Losing a pepper forces every PIN hashed with it to be reset. Production: `HOMEHUB_PIN_PEPPER_CURRENT=V1` and `HOMEHUB_PIN_PEPPER_V1` from secret `homehubPinPepperV1` (`apphosting.yaml`; see [Firebase Platform](../firebase-platform/README.md)).

**Format** (JC-11): 4-6 digits; not the same digit throughout, not a straight run up or down (`1234`, `987654`).

**Authority** (WT-9a/b, WT-17; every action uses `verifyCaller`, so a tablet token is refused):

| Action | Who |
|---|---|
| Set or change your own PIN | Yourself (owner, admin, member, or a child with an account), from your own signed-in session; no old PIN needed. Guests: refused |
| Clear your own PIN | Yourself |
| Clear another person's PIN | An owner or admin (role) for someone of strictly lower rank (`rank()`); never set. Nobody but the owner touches the owner's PIN (WT-17c) |
| Set, change or clear a kid profile's PIN | An owner or admin (role) (WT-17d). Setting a PIN for any account is refused (no known-value reset, WT-17a) |
| Clear a lockout | Yourself, or an owner or admin above your rank |

Each set or clear bumps `pinVersion`, which ends that person's PIN sessions on every tablet at once (WT-17e). Activity: `pin.set` (`details.how`), `pin.cleared`, `pin.lockout_cleared` (actor and target, never the value). `pinStatusAction` tells owners and admins whether each person has a PIN and whether it is hard-locked, and everyone else only about themselves.

**Lockouts** (D-T11, WT-9f; arithmetic in `src/lib/devices/pins.ts`):

- Per tablet and person, `devices/{d}/pinGuards/{memberUid}`: `{ failures, attempts: [{ id, seq }], seq, lockedUntil, lockedBySeq, lockouts }`. Five consecutive wrong PINs lock that person's PIN on that tablet for 1 minute; each further lockout doubles (2, 4, 8) to a 15-minute cap. A correct PIN resets it.
- Every tablet-level lock writes a `pin.device_locked` activity entry (the tablet as actor, the person as target, `details.minutes`).
- Per person across tablets, `members/{uid}/private/pinGuard`: `{ recentFailures: [{ id, at }] (last hour, at most 20), dayFailures: [{ id, at }] (last 24 hours, at most 30), sinceSuccess: [{ id, seq }] (failures since the last correct PIN, at most 50), tabletLocks: [{ id, at, confirmed, deviceId }] (this person's tablet locks in the last 24 hours), repeatAlertAt, seq, lockedAt, lockedByAttempt, lockedReason }`. Every PIN for that person is refused on every tablet until cleared when any limit is reached: **20 failures within an hour** (`lockedReason: 'hour'`), **30 failures within 24 hours** (`'day'`; `MEMBER_FAILURES_PER_DAY_LOCK`, a count that correct PINs never reset), or **50 failures since their last correct PIN**, however slowly (`'total'`; `MEMBER_FAILURES_SINCE_SUCCESS_LOCK`). A correct PIN withdraws only its own provisional entries and forgives, for the since-last-correct count only, the failures recorded at or before its own reservation.
- When one person's PIN locks **3 different tablets within 24 hours** (`TABLET_LOCKS_ALERT_COUNT`; each lock records its tablet and the tablets are counted once each, so repeated locks of one tablet never add up; only locks whose attempt proved wrong count, never a lock set by an attempt still being checked, which may turn out right and lift it), every active owner and admin gets one "Tablet PIN keeps locking" notice (`sourceType: 'pin-tablet-locks'`); no further notice for that person within the next 24 hours (`repeatAlertAt`). Each lock writes `pin.locked` (`details.reason`) and sends a "Tablet PIN locked" notice to each active owner and admin. Residual risk (JC-26): anyone at a tablet can hard-lock a PIN; it is visible and recoverable.
- Lock activity and notices are written only once the attempt that set the lock proved wrong (and only while that lock is still in place, and never for a household that is gone or being deleted); the tablet is recorded as the actor and the person as the target. An attempt that reached a limit but was right lifts the lock it set and announces nothing. A failed announcement is retried once, then logged as a structured error (`pin_lock_announcement_failed` with household id, device id and reason; no names); the lock itself stands either way.
- Clearing a lockout empties the guards but keeps their sequence numbers, so an attempt in flight during the clear stays correctly ordered.
- Lock checks run before any hash work, so a locked PIN is never evaluated.

**Verification** (`verifyDevicePinAction` → `verifyDevicePin`; 7.4, S7, re-review R2), online only:

1. Pre-auth limits, never keyed by what the token claims: first 30 a minute per trusted client address (`clientAddress`, rightmost trusted `X-Forwarded-For` hop, passed by the server action; IPv6 addresses by their /64, `addressBucket`); then the token's signature and expiry are checked locally (`verifyIdToken(token, false)`) and its device claims and household are checked (`not_a_device`, `wrong_household`), and only then 600 a minute per instance is charged (`PRE_AUTH_LIMITS`, `preAuthAddressLimit`, `preAuthInstanceLimit`); then the revocation check (`verifyIdToken(token, true)`).
2. Before any Firestore or hash work: the verified tablet's own budget (10 verifies a minute, keyed by the verified device id, so a forged token naming a tablet never spends it), admission (at most 8 verifications at once per instance), and a second verify for the same tablet and person while one runs: `busy`. Then household, registration and actor eligibility (as the gate).
3. Transaction A: no PIN → `no_pin_set`; person hard-locked → `pin_locked_member`; tablet lock active → `pin_locked` with `retryAfterSec`; a missing pepper → `pin_unavailable`. Otherwise the attempt (with a fresh attempt id) is **counted as a failure in advance** on both guards, so the limits are exact under concurrency and scrypt runs once, outside any transaction.
4. The compare (async scrypt).
5. Wrong → nothing more to count: `pin_wrong` with `attemptsLeft`, or `pin_locked` / `pin_locked_member` when this attempt set a lock (announced now, as above). Right → transaction B re-reads the PIN record and requires `pinVersion` and hash equal to A's (a PIN changed or cleared in between opens no session: `pin_session_invalid`), re-runs the token-free gate checks, removes **only this attempt's** provisional entries (failures recorded by concurrent attempts stay; a lock set by a later attempt stays), re-hashes with the current pepper if needed, and creates the session. The answer comes only after B commits; if B fails the answer is `failed` and no session exists.

**PIN sessions** (7.5): `devices/{d}/pinSessions/{sha256(secret)}`: `{ memberUid, generation, pinVersion, roleAtUnlock, createdAt, lastUsedAt, expiresAt, endedAt, endedReason }` (server clock). The tablet keeps the 32-byte secret in memory only. Sessions also store the `pinId` they were opened with. Valid when not ended, not expired, for this actor, at the tablet's current generation, at the person's current `pinVersion` **and `pinId`** with a PIN set (`pinVersion` restarts at 1 when someone leaves or is removed and rejoins; `pinId` is never reused, so an old session can never validate again), and with the role unchanged since the unlock. Transaction B of a verify also requires the `pinId` read in A. Every gated use that commits slides it (`expiresAt = now + 2 min`, written last in the action's transaction). Admin-PIN capabilities need a session at most 30 s old (`pin_fresh_required`, S9). `endPinSessionAction` ends it ("Done", idle). PIN change or clear, re-pair or removal, role change and member removal are all detected on the next use; nothing fans out. The daily sweep deletes sessions created more than a day ago. One session type serves the PIN level and the points PIN (JC-12).

### The device action gate (8)

**Policy** (`src/lib/devices/action-policy.ts`, pure, shared with the tablet UI): every device-reachable action is a capability with a section, a level class (`device`, `face`, `pin`, `admin-pin`, `not_on_tablets`, `never`), the permissions of which the actor needs one (`null` only for `device` and `admin-pin`; never an empty list), an optional actor rule (`original-actor`, `original-actor-or-delete-permission`, `author-or-permission` with `actorRulePermission`), `points`, `queueable`, `faceNeedsUndoProof` and `freshPinSec`. The table follows design 8.2 as revised: Pets feed/dose/care/note/weight and their Undo are `face*` (backdated feeds and doses older than 12 hours are separate `.old` PIN capabilities; `feedCapability` and `doseCapability` pick them once per press from the effective time on the server: the chosen earlier time, else a queued replay's queue time capped at the server clock (`queuedLineTime`); JC-27); note pin/unpin/edit/delete, older log deletes, time corrections, legacy-medication confirmation, course create/edit, Finish and resume (`pets.course.resume`), meal slots, profile edits, pet create and delete are PIN (lead decision JC-14); pet photos are not on tablets. Chore complete, take and their Undo are `face*` points actions; every other chore action is not on tablets. Household-notice dismissal and its Undo are not on tablets (lead decision, WT-10d: the tablet's notices view is read-only and members dismiss notices in the personal app). Shopping, maintenance, AI flows, household administration and automation are not on tablets; Profile, push registration, targeted notifications and personal reminders are `never`. `UNDO_PROVEN` holds the four chore capabilities (F4a, proof in `tests/server/device-chores-undo.test.ts`) and `pets.feed`, `pets.feed.backdated`, `pets.feed.undo`, `pets.care.add`, `pets.care.undo` (F4b-1, proof in `tests/server/device-pets-undo.test.ts`) and `pets.dose.give`, `pets.dose.undo`, `pets.note.add`, `pets.note.undo`, `pets.weight.add`, `pets.weight.undo` (F4b-2, proof in `tests/server/device-pets-records.test.ts`); any other `face*` capability enters it only in the PR that records its 10.4 proof in the tracker. The Pets permissions come from the Pets module's own tables (R5): `PET_PERMISSIONS` (`src/lib/permissions.ts`) for feeding and care, `MEDICATION_ACTION_PERMISSIONS` for doses and courses (so course create/edit, Finish, resume and legacy confirmation need `pets.addLogs`, as the rules' `courseCreated`/`courseEdited` do), `PET_ACTION_PERMISSIONS` for notes, weights, the profile, meal times and pet delete; note edits list the author's `pets.addLogs` and `pets.editProfiles`, and the operation applies the record-level author rules the Firestore rules apply (`mayEditNote`, `mayDeleteNote`, `mayDeleteWeight`, the 10-minute author windows). An action name not in the table is `unclassified`.

**Contract** (`src/lib/server/device-gate.ts`): `authorizeDeviceAction({ idToken, householdId, capability, actorUid?, pinSessionId?, opId?, queued? }, { clock?, clientAddress?, undoProven?, replayFamily? })` returns `{ deviceId, deviceName, generation, householdId, timeZone, actor, level, capability, opId, attribution, now, hooks }` or throws `DeviceActionError(code, retryAfterSec?, attemptsLeft?)`. Checks, in order (8.4):

1. Shape: request at most 16 KB (`invalid_input`), capability known (`unclassified`), class not `not_on_tablets`/`never` (`not_on_tablets`: a permanent answer, "That isn't available on wall tablets yet. Use your phone.") and the server flag on (`unavailable`), a UUID `opId` for every face/PIN capability (`invalid_input`).
2. Rate (`rate_limited`): limits keyed independently of the claimed identity: 240 a minute per trusted client address (passed by the server action as `options.clientAddress`; IPv6 by /64) before anything, and 6000 a minute per instance once the token's signature has been checked locally and it is a tablet token of this household; after step 3, 60 gated calls a minute per **verified** tablet. A forged token naming a tablet never spends that tablet's budget, and tokens that are not tablet tokens of this household never spend the per-instance bucket. Two bounded rate maps (`src/lib/devices/rate-window.ts`: emptied windows are swept, the least recently used keys dropped past 20,000 each): one for keys the server knows (a verified tablet, a person, the instance; `takeRateSlot`) and one for address buckets taken before anything about the caller is known (`takeAddressRateSlot`), so address keys never push out verified ones. Code redemption's per-address limit uses the same address buckets (IPv6 by /64).
3. Token: `verifyIdToken(token, true)`, read with F1's `classifyVerifyError` (revoked, disabled or deleted: `device_revoked`; invalid or expired: `unauthenticated`; a verifier outage: `unavailable`, which the tablet treats as "try again", never as removal: `endsTabletSession`); device claims (`not_a_device` for a personal token).
4. Household: the token's household (`wrong_household`); exists and not being deleted (`household_deleting`).
5. Registration: record `active` at the token's generation (`device_revoked`).
6. Section on (`section_off`; Home always on).
7. Actor (every class but `device`): present (`actor_required`); a member of this household and not a `device_` uid (`actor_not_member`); not a guest (`actor_guest`); active owner/admin/member/child (`actor_inactive`).
8. Capability: one of `permissions` in the actor's effective permissions (`forbidden`); `admin-pin` needs the owner or admin role (`admin_pin_required`). Actor rules apply against the target record inside the operation (`assertActorRule`).
9. Required level (`requiredLevel`): the class; `face*` → PIN until proven; points actions → PIN for Everyone, or Kids only and the Child role (D-T10).
10. PIN: the actor has a PIN (`no_pin_set`, WT-9c) and the request names a valid session for this actor (`pin_required` when absent, `pin_session_invalid`, `pin_fresh_required`). A valid session supplied with a face action records `pin`; an invalid one is ignored.
11. Queued replay (`queued.createdAt`): at most 24 h old and 5 min in the future (`stale_intent`, JC-18); only queueable capabilities (`invalid_input`); a PIN required now is refused (`pin_required`), never upgraded.

Nothing the client sends about role, level, permissions, names or the device is used. **Hooks** (S1): `precheck(tx)` (reads only) reads the clock again on every transaction attempt (the real time; tests inject `options.clock`), so a retried transaction never accepts a session that expired, or an admin-PIN session that went stale, in between; `finalize` stores and slides with that time. It re-reads the household, record, actor, PIN record and session inside the mutation's own transaction and re-runs steps 4-11, updating `actor`, `level` and `attribution`; with an `opId` it also reads the ledger entry and returns `{ replay }` (same capability, actor and generation: return the stored summary, write nothing), throws `conflict` (another capability, actor or generation) or `already_undone`; for `….undo` capabilities it returns `{ undo: 'tombstone' | 'already' | 'applied', original }`. `replayFamily` (feeds: `FEED_CAPABILITIES`) names capabilities that are one action for replay: when the opId is already applied under one of them, the gate (before its first evaluation, and again inside `precheck`) uses the recorded capability for the level, queue checks, replay and `authority.capability`. `finalize(tx, { targetPath, summary, targetName?, undo? })` (writes only, last) writes the ledger entry (applied, undone or tombstone), a `device.action` activity entry for PIN-level actions, and slides the PIN session. Refusal copy for the tablet: `deviceRefusalResponse(code, { name, kid, retryAfterSec })` (8.5). Two codes are kept apart: `not_on_tablets` (the capability is not offered on tablets; permanent, "That isn't available on wall tablets yet. Use your phone.") and `unavailable` (F1's retryable code: the server flag is off or the verifier or backend is unreachable; "Can't reach HomeHub right now. Try again in a moment.", `retry: true`). Neither ends the tablet's session (`endsTabletSession`).

**Op ledger** (`src/lib/server/device-ops.ts`, B1): `devices/{d}/ops/{opId}`: `{ capability, actorUid, generation, targetPath, state: 'applied' | 'undone', appliedAt, undoneAt, tombstone, summary, deviceCreatedAt, expireAt }`, all times the server clock stored in the action's transaction (`expireAt` = 7 days later; the daily sweep deletes expired entries). Undo capabilities reverse only the actions listed for them in `UNDO_OF` (`src/lib/devices/action-policy.ts`; `undoAccepts`), backdated variants included (`pets.feed.undo`: `pets.feed`, `pets.feed.backdated`, `pets.feed.backdated.old`; `pets.dose.undo`: `pets.dose.give`, `pets.dose.give.old`; `pets.note.undo`: `pets.note.add` only, never a note pin, unpin, edit or delete); any other ledger entry is a `conflict`, never a prefix match. A tombstone stores the Undo capability, actor and credential generation that wrote it: the same Undo again is `already`; an action it reverses, by the same actor at the same generation, is `already_undone`; anything else under that opId is a `conflict`. Helpers: `classifyActionAttempt`, `classifyUndoAttempt`, `assertUndoable` (same generation, original actor or the actor rule, window `appliedAt + 10 s + 5 s grace`: `undo_expired`), `createdRecordUnchanged` (`updateTime == createTime`), `undoWindowOpen`. The per-capability reversal and its proof are F4's. Every summary is stored through `withoutEmails` (`src/lib/devices/without-emails.ts`, in the gate's finalize): no `…Email` field and only public names, so a no-op answer that carries a stored record (a chore someone completed under a legacy email) keeps no email in the ledger (design 10.1).

**Operations take an actor** (9, `src/lib/server/operation-context.ts`): `OperationActor = { uid, name, device? }`, `OperationContext = { actor, opId?, hooks?, now }`. Every `…As` operation opens exactly one transaction, runs `precheck` first (return a replay unchanged), then its own reads and writes, and `finalize` last; `ctx.actor.device` is stored as `deviceAttribution`. `deviceOperationContext(authority)` reads the actor through getters so the values `precheck` re-checked are the ones stored; personal callers use `personalOperationContext` with no hooks (unchanged behaviour).

**Comfort from the tablet** (`updateDeviceComfortAction`, capability `device.comfort`, no actor, no PIN): only the four comfort fields, validated by `validateDevicePatch(..., 'comfort')`, written as dotted paths with `updatedVia: 'tablet-comfort'` inside a transaction that runs the hooks; not logged.

### Attribution (12)

`deviceAttribution = { deviceId, deviceName (frozen), generation, actorUid, level: 'face' | 'pin' }` is stored next to a module's own actor fields by the device actions (chore completions since F4a; it is one of `COMPLETION_FIELDS`, so every un-completion removes it). Personal clients can never add it (every content allow-list leaves it out: chores, feeding logs, feeding state, medication logs, care logs), change it or remove it (`deviceAttributionKept()` on updates of chores, feeding, medication and care logs); on chores it may be removed only by an update that clears the completion (and a `chores.complete` holder's reopen may include that removal: the reopen allow-list names `deviceAttribution`) (`isCompleted` from true to false; S10). PIN-level device actions are logged as `device.action` (`via: 'device'`, `deviceId`, `deviceName`, `level`, `details.capability`, `targetName`); face actions are attributed on their records and the ledger only (JC-19).

### Points PIN (WT-9d, WT-22, D-T10)

`households/{h}.devicePolicy = { pointsPin: 'off' | 'kids' | 'everyone', updatedAt, updatedByUid }` (absent: Off), set by owners and admins (role) through `updatePointsPinAction` (activity `device.policy_changed`). The gate raises points capabilities (chore complete, take, and their Undo) to PIN for everyone, or for the Child role (kid profiles included) under Kids only. ### Tablet shell (F3; design 14, WT-14)

`AuthProvider` renders `TabletShell` instead of the whole app for a device principal (14.1), so nothing personal ever mounts on a tablet: no header, tab bar, account menu, Log out, Profile, command palette, push manager or personal reminders (WT-10, WT-14k). An unresolved principal (claims not readable yet) shows "HomeHub can't be reached right now" and reads nothing.

**TabletRuntime** (server state, section 13; keyed by household, device record and generation, so a different session starts from nothing). Listeners, only while a device session exists: the tablet's own record (`includeMetadataChanges`), the household document and `members` (the "Who's here?" roster, `rosterFrom`), plus the six household-wide notification listeners of 5.6 (`deviceNotificationCategories`: one per enabled source, `system` and `general` always, each exactly `audience array-contains '*'`, `category == c`, `orderBy(createdAt desc)`, `limit(50)`; expired notices are dropped, and anything email-shaped in a title or message is replaced: `parseDeviceNotice`, `redactEmails`; the ownership-transfer notice itself carries only the public name). Live settings (WT-4i): every record change from the server applies without a reload. The heartbeat (start, visible, reconnect, every 5 minutes) and push clearing at every start (S5) run here. Until the record and the household have answered, the screen says "Connecting to your household…".

**Dashboard scope.** The resting view is the existing dashboard drawn with a device scope (`DashboardScopeProvider`, `src/lib/dashboard/dashboard-scope.tsx`): the household id, name and zone from the household document, no viewer (`uid ''`, so nothing is "yours" and the brief uses household totals), view permissions from the record's sections only and **no write permission** (so no one-tap Done/Fed/Tick and no quick-add buttons appear), `notifications.view` off (notices come from the six device queries instead), and `kind: 'device'`, which makes `Dashboard` pass `household` to the brief (`buildMorningBrief(..., { household: true })`: household phrases only, no name, "Nothing needs doing right now."; no AI rewrite button) and hide Home Wrapped and the keyboard hint (D-T15). Weather comes from the record (`setDeviceWeather` in `use-weather.ts`: `display.weather`, `display.weatherPlace`, `display.temperatureUnit`); the tablet never reads a person's weather preference. Comfort from the record drives the existing `AppearanceProvider` (theme to mode, text scale, `motion: 'reduced'` to reduce motion, sounds; the local copy is a cache). The shell sets `data-kiosk` on `<html>`: no pull-to-refresh, no grain or drifting background (WT-14h/i); the shell root has no text selection or callouts outside inputs and no double-tap zoom (`touch-action: manipulation`), pinch zoom kept.

**State machine** (`shell-state.ts`, pure; 14.2). `ShellState = { face, pin, lastInputAt, idleReturned, ambient, revoked }`. Events: `input` (a pointer or key anywhere, except a tap on the ambient screen, which wakes it there), `pick` (someone chosen in "Who's here?"; another person ends the previous PIN unlock), `credit` (an action credited to a person slides face memory), `pin-verified`, `pin-used` (a gated use that passed), `pin-invalid` (the server said the session is gone), `done`, `tick(now, busy)`, `revoked`. Timers (14.3): face memory 2 minutes from the last credited action (D-T3, `face-memory.ts`); a PIN unlock 2 idle minutes from the unlock or the last gated use (the server slides its own session the same way); idle return after `idle.homeAfterSec` without input (once per idle period: closes dialogs and prompts, goes to the start page, forgets the person and ends the PIN session best effort); ambient after `idle.ambientAfterSec` (never sooner than the idle return). **Every expiry waits while the shell is busy** (`isShellBusy()`: a save in flight, an open Undo toast, unsaved input such as the admin settings form, the quiet-hours form or a typed quick add): a busy tick changes nothing and the shell ticks again the moment it becomes idle. `nextShellDeadline` gives the one timer the frame sets.

**Listeners never stay abandoned.** Every Firestore listener a tablet opens (its record, the household, the roster, the six notice queries, a shopping list's items) goes through `tabletListener` (`src/lib/devices/tablet-listener.ts`), and the section facts' listeners use the same recovery in the device scope: `resilientListener` retries with backoff and on `online`/visible, and after its permission-denied retries a tablet subscribes again every minute (`recoverUnauthorizedAfterMs`, `TABLET_DENIED_RECOVERY_MS`) instead of staying quiet; a settled denial of the record or household also asks the server through the heartbeat (removal ends the session through the revocation flow). Tablet components never call `onSnapshot` outside `tabletListener` (a unit test reads their sources).

**Every record setting is applied from the record** (`src/lib/devices/tablet-settings-apply.ts`, `tabletApplication`): name and room in the top bar; sections in the view permissions, rail and notice queries; the start page; comfort in the appearance provider (`appearanceFromRecord`: theme, text size, reduced motion, sounds, with the default colour presets and no haptics, so a previous personal session's preset or haptics on the browser never carry over); weather, place and unit in the weather client (`weatherFromRecord`); **seasonal touches** in the dashboard scope (`seasonal`: the house follows the record and hides its own "Seasonal touches" toggle, never the personal `homehub.dashboard.seasonal` key); idle and ambient times in the state machine's timers. The scanning camera is not used by the shell yet. Quiet hours come from the household document. `tests/unit/devices-round3.test.ts` maps every record setting to where it is applied and fails when a setting is added without a mapping.

**Section views read uncapped facts.** The dashboard's facts hold short previews (`PREVIEW_LIMITS` in `src/lib/dashboard/facts.ts`: 20 of today's work, 5 per room, 5 next up, 6 maintenance items, 6 shopping items). The tablet frame asks `useDashboardData(true, { sections: true })` for `sectionFacts`, the same documents assembled with `SECTION_LIMITS` (no caps; chores also get `upcoming`, every open chore due within the week). Every section view and quick add read only `sectionFacts`, through the pure selectors in `src/lib/devices/tablet-sections.ts` (`choresSection`, `petsSection`, `maintenanceSection`, `shoppingListsSection`, `calendarSection`, `quickAddTargets`); a list's items come from its own live listener (`neededListItems`). `tests/unit/devices-sections.test.ts` feeds every selector more entries than any preview cap and also fails if the tablet views read the preview facts.

**Navigation and start page** (`start-page.ts`; 14.5, D-T18). The frame reads the address (path and query) and `resolveTabletPath` decides the view: Home, a section (`/chores?room=`, `/shopping?list=`) when that section is on, or household notices; anything else (an off section, Profile, Household, Automation, Library, Setup, a room or list that no longer exists) goes to the start page, waiting until the shell is idle. A start page in an off section, or whose room or list is gone, falls back to Home on the tablet (the record is not rewritten). A start page changed on the record navigates there once idle. Both deferrals are state, not scheduled callbacks (`navigationReducer` in `shell-state.ts`): the owed navigation (`start-page` or `leave-page`) survives data updates while the shell is busy, runs once as soon as it is idle, and a start-page change counts as applied only when its navigation runs; a section switched back on, or a start page changed back, before then cancels it. Idle return and ambient are ticks of the state machine and the build reload waits on the busy flag, so no tablet navigation is a cancellable "when idle" callback. The rail and More list only enabled sections.

**Action pipeline** (`runAction`, for F4). A request names its capability, a label and the device server action that executes it. Classes `not_on_tablets`/`never`, and any capability without an executor (all of them until F4), are refused at once with "That isn't available on wall tablets yet. Use your phone." `admin-pin` asks "Who's here?" for an owner or admin and always a fresh PIN (reused only within 25 s of the unlock; the server allows 30 s). Face and PIN classes use the remembered person or ask; `requiredLevel` (with the household's points-PIN setting and the person's role) decides whether the PIN pad comes first; the call runs under the busy mark; success credits the person (and slides the PIN unlock); refusals map through `deviceRefusalResponse` (revocation codes end the session, `actor_*` clears the face, `pin_*` clears the unlock).

**No PIN yet** (D6): before the pad opens for a PIN-level action, an admin unlock or a PIN-level Undo, the shell asks `devicePinStatusAction` (the tablet's own token; its own pre-auth rate buckets, `PRE_AUTH_LIMITS.pinStatus`, so asking never spends a PIN entry's slots; the answer is only whether that person has a PIN and whether it is locked); a person without one is told at once "<Name> has no tablet PIN. An adult can set one in Household > Members." (`noTabletPinMessage`), is no longer remembered, and "Who's here?" opens again so someone else may do it (up to twice). A status that can't be read falls back to the pad. **PIN pad** (`pin-pad.tsx`): online only; digits stay in the dialog; `verifyDevicePinAction` runs under the busy mark; the answer's session secret lives only in the shell's memory (a reload ends a PIN unlock). Refusal copy: `pinRefusalMessage` (8.5 plus the tries left). **Who's here?** (`who-is-here.tsx`): the live roster; for admin-PIN purposes choosing someone who is not an owner or admin says "An owner or admin PIN is needed." and keeps the row open.

**Keep-awake, night dimming, idle reload.** A Screen Wake Lock while the shell is shown and visible, requested again on `visibilitychange` (`watchKeepAwake`, generalized from Shopping's controller). Night dimming: `isQuietAt(household.quietHours, household.timeZone, now)` re-evaluated every 30 s, in the household's zone (D-T1); the overlay never takes a touch. New builds: `TabletUpdateWatcher` registers the service worker on the tablet (registration only: no push subscription or token is requested; the push manager never mounts) and `TabletUpdateWatcher` asks it for its build; `decideTabletReload` reloads only when the worker build is newer, the shell is idle, resting (nobody chosen, no prompt or dialog open) and online, at most once per build per tab (`sessionStorage['homehub.shell.tablet-reloaded']`; without storage it never reloads by itself), and never once the crash guard counted repeated crashes in the last 10 minutes (the error boundary's plain error with the time and a manual retry stands, as in 2.1).

**Toasts, Done and Back on the tablet** (Android-emulator verification, D1-D5): the shell renders the shared `Toaster` with `tablet`: at most two toasts (`TABLET_TOAST_LIMIT`, newest first, chosen by the shared store's policy `capToasts`, so a notice never hides an open Undo) at the bottom right; the viewport takes no tap outside a toast card; a toast without an action (a notice, a refusal such as "Too late to undo.") leaves after at most 4 s (`TABLET_INFO_TOAST_MS`), an Undo after the time its window has left, timed by the shell itself from an absolute expiry per toast (`toastExpiries`, kept for every open toast whether the two-toast limit shows it or not, so a hidden toast never comes back with a full duration; Radix's own timer pauses while a pointer rests over, or focus sits in, the toast region, and after a tap on Undo the pointer rests where "Undone." appears); section views keep a scroll clearance at their end (`pb-40`) so their last controls can be scrolled above the toasts (Home has none and keeps its no-scroll layout). The Undo button is 48 px. When the tablet comes back from the background (`visibilitychange`, `pageshow`), every offered Undo is measured again from its journal entry (`resumedUndo`): one past its window is removed, another offered for the time it really has left. The acting person's **Done** sits above an open dialog's overlay and takes taps through its modal lock (the pill is portalled to the body at z-60 over an invisible copy that keeps its place in the bar: the `position: fixed` shell is its own stacking context, so nothing inside it can rise above an overlay), so it ends the remembered person even with a pet sheet open; an action still on its way when Done is tapped never brings the person back when it finishes (its credit only extends a memory of that same person). A touch pick in "Who's here?", the PIN pad or "Feed again?" never closes the pet sheet or settings under it (the shared dialog ignores an outside tap whose target has left the page or sits in another dialog; see Application shell). Once the page has started a full navigation (the tablet's session end loads `/setup` or `/` with `location.replace`), the back stack never takes an entry back again (`leave()`, called before that navigation and, where the Navigation API exists, on any cross-document `navigate`; `stay()` undoes it when the page stays after all: `navigateerror`, a stopped load, or a `pageshow` from the back-forward cache): on Android a closing dialog's `history.go(-1)` 18 ms after `location.replace('/setup')` cancelled the load and left a protected exit on the public landing page instead of the setup screen with its note (emulator against production, 2026-11-23). **Back** (Android or the browser) closes the topmost open dialog instead of leaving the page (`useBackCloses`, `src/hooks/use-back-closes.ts`, over the pure `createBackStack` in `src/lib/shell/back-stack.ts`: a dialog pushes one same-URL history entry when it opens, Back closes only the topmost, a dialog that refuses to close (a save in flight; its close returns false) gets its entry pushed again and stays registered, a dialog closed any other way takes its entry back off once (the traversal is asynchronous, so a dialog that opens before its popstate, such as Tablet settings handing over to its admin picker, is pushed only once that popstate has arrived), and nested dialogs, the prompt queue's "Who's here?", PIN pad and "Feed again?"/"Already given?", Tablet settings and its confirmations, quick add, the care dialog, the pet sheet and Give dose each hold their own entry). The second tap of a double tap on Save therefore never credits whoever's face was under it. The prompt carries `data-tap-ready` once the guard has passed. The resting screen has no face row (people are chosen only in "Who's here?").

### Revocation on the tablet (F3; design 13, WT-19b-d, S3)

`decideSessionEnd` (pure, `device-session.ts`) ends the session only on a **server** signal: the record missing, not `active` (an `unpaired` record whose `endedReason` is `new-code` or `personal-sign-in` ends as that exit; anything else, such as a removal from the Devices list, as `removed`), or at another generation (`repaired`); the household missing or carrying `deletingAt`; the Auth user signed out; an action or heartbeat answering `device_revoked`, `unauthenticated`, `wrong_household`, `not_a_device` (removed) or `household_deleting`. Cached snapshots never decide; `unavailable`, `rate_limited`, `failed` and network errors never end it. A **denied read** of the record or the household is confirmed with the server first: the shell sends a heartbeat and ends the session only on a revocation answer (App Check or a token refresh can deny one read for a moment); otherwise the listeners start again after 15-20 s. Clearing (`clearTabletSession`, every step best effort, run in order and limited to 2.5 s (`CLEAR_STEP_TIMEOUT_MS`): a step that hangs counts as failed and the rest still run; navigation always last): stop every listener; drop the PIN secret and face memory (memory only, gone with the hard navigation); delete IndexedDB `homehub-device` (queue and Undo journal; when another tab still has it open the delete is left to finish when that tab closes, and clearing goes on); `forgetHouseholdOnDevice(null)`; terminate Firestore and clear its cache (with another tab open, clearing the persisted cache can fail: Firestore is terminated first, the failure is recorded and clearing goes on); clear push state; remove the "this browser was a tablet" marker; sign out; leave the one-shot note (`sessionStorage['homehub.device-ended']`: `removed`, `repaired`, `household-deleted`, `new-code`); hard-navigate to `/setup` (or `/` after a personal-sign-in exit). **A tablet whose session ended while the shell was not running** (removed while switched off: at the next start its sign-in is refused, so the app starts signed out and the shell never mounts): the shell keeps a marker in `localStorage` (`homehub.tablet-browser`) while it runs, and its own clearing removes it. When the app starts signed out, or the setup screen opens, with the marker still present, `recoverFormerTabletHere` (`src/lib/devices/former-tablet.ts`) finishes the clearing, only while nobody is signed in (both entry points check, and recovery checks again before every step that clears data: a person who signs in meanwhile stops it before the next step, nothing of theirs is cleared, and the cleanup stays owed for the next signed-out start). Before clearing anything it checks that storage can write and remove a key (a probe); if not, nothing is cleared and nothing reloads, so no page reloads in a loop. The steps run in order, each time-boxed and best effort: delete `homehub-device`, forget the household's local data, clear push state, and last shut Firestore down and clear its cache. The cleanup owed is durable: the marker stays until every step has run, and `localStorage` `homehub.tablet-cleanup` counts the steps done, so a refresh or a closed page mid-cleanup resumes at the unfinished step on the next signed-out start (steps already done are not repeated; a tablet session starting again resets the count). Once Firestore has been shut down the page always reloads the setup screen, also if someone signed in meanwhile (they reload into a working app; nothing of theirs was cleared after the check). The marker and the count are removed after the last step; a marker that still cannot be removed keeps every step recorded as done, so the next start runs nothing and never reloads again. A setup link's code survives this: both entry points read it from the fragment before the asynchronous clearing, the reload goes to `/setup#code=…` (`formerTabletReloadUrl`), and the setup screen strips the fragment only once no recovery is owed (`shouldStripSetupFragment`), so a new QR link opened on a former tablet still prefills its code. Offline, nothing claims instant knowledge: the last synced view stays with the Offline pill until a listener or the first answer after reconnecting says otherwise.

### Protected exit and Tablet settings (F3; design 4.2, 14.6, WT-16, D-T2, D-T5, S9)

- **Comfort** (anyone, no PIN, WT-16d): `updateDeviceComfortAction` (F2), applied live from the record.
- Both tablet admin actions pass the trusted client address from the request (`options.clientAddress`, as every tablet action does) to the gate's pre-auth limits, and use the server clock the in-transaction `precheck` re-read (`authority.now`) for what they write.
- **Admin settings** (`updateDeviceSettingsFromTablet`, capability `device.settings`, `admin-pin`): owner or admin role with a PIN session at most 30 s old; one transaction runs the gate's `precheck`, validates the patch with `validateDevicePatch(..., 'admin')` (the Devices-list rules: start page vs sections, field allow-list; a refusal is `invalid_input`) and writes only the named fields with `updatedVia: 'tablet-admin-pin'`, `updatedByUid` = the person. Admin-field changes write `device.settings_changed` (`via: 'device'`, `level: 'pin'`, the person and the tablet). The form asks for a fresh PIN at the moment of saving.
- **Exits** (`exitTablet`, capabilities `device.exit.remove`, `device.exit.personal`, `device.exit.newCode`, `admin-pin`, fresh PIN): one transaction runs `precheck`, then sets `status` (`removed` for Remove, `unpaired` for the other two), `generation + 1` (the old credential and every PIN session are refused at once), `removedAt`, `removedByUid`, `endedReason` (`removed`, `personal-sign-in`, `new-code`), cancels the tablet's unused codes (except, for "Use a different code", a live re-pair code made for this record at the generation being ended: that is the code about to be typed, so it moves to the new generation, `carriedFromGeneration`, instead of being cancelled; emulator evidence D8; the `device.exited` entry then carries `codeKept: true` (never the code) and the owners' notice says "The re-pair code made for it still works until <time>. Cancel it in Devices if you didn't expect this." (`keptCodeNotice`); redemption then bumps the generation again, so the old credential stays refused), writes `device.removed` or `device.exited` (`details.reason`; `via: 'device'`) and notifies every active owner and admin (`device-removed-<deviceId>-<generation>-<uid>`, "Wall tablet removed" / "Wall tablet signed out"). After the commit `finishDeviceRevocation` deletes (removed) or disables (unpaired) the Auth user; a failure answers `authCleanup: 'pending'` and is finished by the Devices list or the daily sweep. Two exits racing: the second fails the gate (`device_revoked` or `pin_session_invalid`); exactly one is logged. An unpaired record is re-paired from the Devices list (settings kept). D-T5: a personal sign-in ends the device credential and keeps the record.
- **The note after this tablet's own exit** is decided by the exit, not by the revocation signal that races it (the record changing, the credential ending): `runExit` holds every session end that arrives while the exit is in flight (`exitGateSignal`; at most 30 s, `EXIT_TIMEOUT_MS`: an exit call that has not answered by then counts as failed), then ends the session as the exit's own end on success (`exitSessionEnd`: Remove is `removed`, "This tablet was removed."; Use a different code is `new-code`, "This tablet was signed out. Enter a new code to set it up again."; Sign in with a personal account is `personal-sign-in`, landing on the signed-out home page) or, on failure, as whatever signal arrived meanwhile (`exitGateSettle`).
- **Prompt queue** (`src/lib/devices/prompt-queue.ts`, pure; PR #185 review): "Who's here?", the PIN pad and "Feed again?" are questions in one queue (`createPromptQueue`, read with `useSyncExternalStore`): the oldest is shown, each dialog keyed by its question, and every question is answered or cancelled. Two actions asking at once (two pets fed before the first answer) wait their turn; a newer question never replaces an older one, so no action is left awaiting an answer with its save spinner and busy mark. The idle return cancels every waiting question (`cancelAll`: no one, no PIN, not again).
- **Dialog layering:** while "Who's here?" or the PIN pad runs (the whole admin unlock, `prompting` in the tablet context), the Tablet settings and exit-confirm dialogs are not rendered (`settingsLayer`), so the picker or the pad is the only dialog: focus is trapped there and Escape or Cancel brings settings back. The admin settings form stays mounted while its save asks for a fresh PIN (its draft survives); the pad mounts after it and sits on top.
- These admin-PIN actions carry no opId and do not call `finalize` (no op ledger, no generic `device.action` entry: each writes its own activity entry).

### Offline queue and Undo journal (F3 infrastructure; design 10.3, 11, re-review R1)

IndexedDB database `homehub-device` (`device-store.ts`) with stores `queue` and `undo`, keyed by `opId`; `memoryStore` is the same interface for tests and browsers without IndexedDB (then nothing survives a reload). Every queue read and write holds the Web Lock `homehub-device-queue` (`withQueueLock`; one sync owner across tabs; a page-local chain where Web Locks are missing).

- **What may queue** (`queueAllowed`): only `queueable` capabilities whose required level right now is `face` (the same policy, points PIN and role the server uses; the server decides again at sync), plus Undo intents. Never PIN-level actions, PIN verification, settings or exits (WT-19f).
- **Entries** (`createQueuedAction`): `{ opId, kind: 'action' | 'undo', householdId, deviceId, generation, capability, actorUid, actorName, level: 'face', intent, original: { opId, queued } | null, createdAt (device clock), attempts, sendState: 'pending' | 'inflight' | 'uncertain', lastError, nextAttemptAt }`. The intent is a frozen copy: the original actor, level, capability and payload never change; `withSendFields` changes only the four send fields. `enqueue` resolves only once stored (the UI may then say "Saved on this tablet, will sync"); a duplicate opId is refused.
- **Sync** (`syncQueue`): oldest first; entries of another session are discarded unsent (`belongsToSession`: household, device record **and** credential generation must all match, since every pairing starts at generation 1); each entry is marked in flight (`attempts + 1`) durably before it is sent through the same device action as a live call (`queued: { createdAt }`, same opId: the server replays an action it already applied); a success (including the server's idempotent replay of an action it already applied, and an Undo it answers as already done or never applied) and `already_undone` delete it; revocation codes stop sync and report `revoked` (the shell then clears everything); actor, permission, section, level, staleness and Undo refusals drop it with one plain notice (`dropNotice`: "1 change from this tablet couldn't be saved: Mia can no longer feed pets here."); outages keep it as `uncertain` with backoff (5 s doubling to 5 min) and stop the pass so nothing overtakes it. The sender gets data only: sync never opens a dialog, never asks "Feed again?", never shows an Undo toast and never counts as a new face choice or consent (WT-19g). Face memory is not re-checked: a confirmed action keeps its actor even after the 2 minutes.
- **Undo** (`undoRoute` in `undo-journal.ts`, run by `runUndo`; `removeIfNeverSent`): an entry that has never been sent (`attempts 0`, `pending`) is removed locally together with its Undo, and `removeIfNeverSent` (under the queue lock) has the last word: when it finds the entry was sent meanwhile, the Undo goes to the server instead. Anything that may have reached the server is undone by an Undo intent sent (or queued) by opId. R1: an Undo may arrive late only when the original was itself a queued replay; for an action sent live the device clock never extends the 10 s window (the server bounds queued Undos against its stored `appliedAt`).
- **Undo journal** (`undo-journal.ts`, pure, one state machine per action): `{ opId, householdId, deviceId, generation, capability, actorUid, label, toastGroup?, state, createdAt, windowFrom, viaQueue, undo }`. States: `attempting` (a live send in flight, written before sending), `unknown-outcome` (a send with no answer that could not wait in the queue: the server may hold it), `applied` (the server answered), `queued-unsent`, `queued-sent` (the queue sent it at least once without a confirmation), `undo-pending` (an Undo on its way, sent or queued), and the final `undone`, `refused` (refused by the server, or answered with nothing to take back) and `expired` (the server refused the Undo for good). Every change is one event through `journalStep` (answered, refused, no answer, sync sending, sync confirmed, sync retry, Undo sent, undone, Undo refused, Undo back, discarded); a final state never moves. `undoOffer` says whether the button is shown and for how long: from the server's answer (`applied`, a confirmed sync included), from the end of a send without an answer (`unknown-outcome`, `queued-sent`: the latest the server could have applied it), or a local cancellation window from the queuing (`queued-unsent`); a queued action takes the server's window once sync confirms it. `undoRoute` decides what a tap does: remove locally (never sent), send by opId, queue the Undo intent (offline), or "needs a connection" (a PIN is needed, or the queue isn't durable; the entry stays offered). After a reload `restoreJournal` stores every entry of this session as restored (a send the page lost becomes an unknown outcome, its window counted from when it could last have applied; an Undo lost mid-send is offered again, the server answering a second one `already`) and returns the toasts that still have time; only this session's entries are restored and another session's are pruned, as are final ones and those past their window (queued ones stay while the queue may send them). The server's window is the authority.
- F4a wires it in (`src/components/devices/use-device-actions.tsx`, through `performAction` and `runUndo` in `undo-flow.ts`): chore actions are queued when the tablet is offline or got no answer (face level, durable queue); a send with no answer that can't wait keeps its opId as an unknown outcome and its Undo is offered for the window left ("No answer from HomeHub. It may have been saved; Undo takes it back if it was."); the queue syncs at start, on reconnect and every 30 s and moves each entry's journal state (`syncQueue`'s `onSending` and `onResult`); Undo toasts come back after a reload from the journal. Revocation deletes the whole database.

### Device actions: chores (F4a; design 9, 10, 20 R1/R3/R4/R5; WT-6a, WT-20, WT-22, CH-12b, HP-33e)

**Server** (`src/lib/server/chore-completion.ts`, `src/lib/server/device-chores.ts`, actions in `src/app/chores/device-actions.ts`). Each tablet action passes `authorizeDeviceAction` (tablet, household, generation, the person chosen in "Who's here?", the section, the level), then runs the Chores operation with the gate's hooks inside the operation's own transaction: `precheck` first (a replay of the same opId returns the stored outcome and writes nothing), the operation's reads and writes, `finalize` last (op ledger entry with server time, PIN-session slide, a `device.action` activity entry for PIN-level actions).

- `chores.complete` (`completeChoresAs(db, householdId, input, ctx)`): one chore per call, `completionId == opId`, credited to the chosen person (`completedByUid`/`completedByName`, kid profiles included; CH-12b), `deviceAttribution` stored with the completion. A chore due after the household day is refused as for everyone (CH-2b); one someone already completed answers who did it. Every device answer is recorded in the op ledger, a no-op too (already done, not due, gone: `summary.noop`), so a retry with the same opId replays that answer even if the chore was reopened meanwhile; the operation reads the time of its latest gate check (`ctx.now` is a getter over the authority). Answers to a tablet carry no email: every `…Email` field is removed and names are public names (`withoutEmails`), replays included. The personal server action uses the same function with `{ actor }` and no hooks (its older `(db, caller, householdId, input, now)` form still works); behaviour unchanged.
- `chores.complete.undo` (`undoChoreCompletionAs(..., ctx)`): by the original's opId. No ledger entry yet: a tombstone, `not_applied` (the original, if it arrives, is refused `already_undone`); already undone: `already`; a no-op original: `already`, whatever the time (it never reverses a completion it did not make); applied: the same tablet generation (`not_undoable`), the same person (`forbidden`), inside the window (10 s + 5 s grace from the stored `appliedAt`, `undo_expired`), and the chore's completion still this one (`changed_since` otherwise; a later completion by anyone is never reverted). It clears only the completion fields (`deviceAttribution` included) and puts back the steps it ticked when they are unchanged, from the outcome stored in the ledger.
- `chores.take` (`takeChoreAs`): only an unassigned chore (no uid and no legacy email); one already the person's is a no-op (`already_yours`); someone else's is a reassignment, which tablets don't offer (`not_on_tablets`); a completed chore is refused. It writes only `assignedToUid` and `assignedToDisplayName`; the previous values go into the ledger's summary.
- `chores.take.undo` (`undoTakeChoreAs`): a no-op take answers `already` and changes nothing, also after the window (R3); otherwise, while the chore still holds exactly what the take wrote (the person and the name, both stored in the ledger's summary), the previous assignment comes back exactly (`changed_since` when anyone changed the assignment since).
- **Levels and permissions (R5):** the policy's permissions are the personal ones: `chores.complete` for completing and its Undo, `chores.assign` for taking (the personal reassignment rule). With the Undo proven these are face-level; the household points-PIN setting raises them to PIN (Everyone, or Kids only and the Child role; WT-22, D-T10).
- **R1, late queued Undo:** an Undo sent from the tablet's queue for an action that was itself a queued replay (its ledger entry carries `deviceCreatedAt`) is accepted up to 10 minutes after the stored `appliedAt` (`QUEUED_UNDO_WINDOW_MS`) when the Undo was also made within 15 s of the action on the same device clock (`queuedUndoInTime`, JC-17); every other Undo has the 10 s window. Device clocks never extend a window on their own. A queued request names the credential generation it was made under, and the gate refuses one that is missing or not the token's (`stale_intent`). Residual (recorded): the server cannot verify that a request really came from the tablet's queue; the device-clock check and the server's `appliedAt` bound limit what such a claim can extend.
- **R4, where take attribution lives:** in the op ledger entry (who, which tablet and generation) and, for a PIN-level take, the `device.action` activity entry; not on the chore. D-T17 asks for attribution fields on every device-written record; a take writes no `deviceAttribution` on the chore (a deliberate deviation, JC-29): the chore's attribution belongs to its completion (S10), and a take must never overwrite or outlive it. The chore still records who it is assigned to.

**Tablet** (`src/components/devices/use-device-actions.tsx`, `src/lib/devices/device-action-answers.ts`). `runAction` sends a capability the tablet can send (the four chore capabilities and the six Pets feeding and care capabilities; everything else is refused at once with "That isn't available on wall tablets yet. Use your phone.") after "Who's here?" (face memory) and the PIN pad when the policy says so. The opId is made before the first attempt and every retry reuses it; the Undo journal entry is written when the action is first attempted. Offline, or with no answer, a face-level queueable action waits in the queue ("Saved on this tablet. It syncs when the connection is back."), with an Undo that removes it locally while it has never been sent. A send with no answer that can't wait (PIN level, or no durable queue) keeps its opId: the server may hold it, so its Undo is offered for the window left; an explicit refusal ends it (one state machine, see **Offline queue and Undo journal**). Nothing that needs a PIN is ever queued (queued sends carry no PIN session): a PIN-level action offline, or a PIN-level Undo (points PIN), says it needs a connection, and the Undo stays offered for the time left, re-running the PIN flow when tapped online. Nothing is called saved unless the queue is durable here (`durable`: IndexedDB); without it the tablet says "Couldn't save offline on this tablet. Try again when connected." and the action counts as not done (`queueRefusal`, `QUEUE_REFUSAL_COPY`). A completed or taken chore shows a 10 s toast with **Undo**, sent to the server by opId (queued when offline: "Undo saved on this tablet. It's sent when the connection is back, if it's still in time."); after a reload the journal brings the toast back for the time left. The Undo runs `runUndo` (`src/lib/devices/undo-flow.ts`): local storage is best effort (a queue or journal that can't be read or written never stops the Undo reaching the server by opId); the original actor is authorized through the shell (`authorizeUndo`: their PIN pad when the Undo's level needs a PIN, also for a restored toast), and a PIN refusal asks once more and retries. Tapping the toast dismisses it, so an Undo that doesn't go through for a passing reason (the PIN pad closed, the retry after a PIN refusal cancelled, no connection, an outage) is offered again for the time left in its window (`undoReoffer`, from the journal entry as it is now); a cancelled one says nothing once the window has passed. When an action is taken back, the caller's `onReverted` runs once, so the dashboard's **Done** works again. The journal reports it: every step that moves an entry into `undone` (`journalTransition`, and `stepJournal`'s callback) says so exactly once, whichever way it got there (a never-sent queued entry removed, a live Undo answered, a queued Undo answered at sync as undone, already or not applied, or the queued original answered already undone at sync), and the runtime's journal step is the one place that runs the callback for it. A queued replay that is dropped (it never reaches `undone`) also runs it; `runAction` also reports `queued`. Queued replays read the answer per capability (`queuedSendResult`): a domain refusal answered successfully (not due yet, gone, already done by someone) is dropped with a notice that says why, never deleted as if applied. The Chores section's rows, today's and a room's alike, have **Done** and, for unassigned chores, **Take** (48 px; a room's entries carry the same assignment identity as today's work); the dashboard's **Done** and quick add's chore matches go through the same path on a tablet.

**Tablet.** The Pets board's rows show each pet's medication chips (a live read of its courses; a chip opens Give dose) and **More**, which opens the pet sheet (`src/components/devices/tablet-pet-sheet.tsx`: Medication, Notes, Weight, History, Profile; reads through the personal Pets readers, keyed on the tablet's own access (`useSettledPetAccess` returns the tablet while its shell is present, and a refused Pets listener keeps recovering every minute, `setPetListenerRecovery`): `useMedicationState` (courses with their offline doses, the legacy countdowns), `usePinnedNotes`/`useBehaviourEntries`, `usePetWeights`, `usePetLogs` (both date shapes merged; History reads every time shape, feedings' Dates included, through Pets' shared `toDate`), the shared `useNow` clock; only the pet document goes through `tabletListener`; a legacy medication is listed with **Confirm schedule** (the shared prefill `legacyCourseFormValues`, PIN level, `pets.medication.confirmLegacy`; finishing or merging it stays on phones); every form and button holds one pending action (`useTabletSubmit`, a ref) and a form keeps one opId (`TabletActionRequest.opId`) until an attempt is applied or saved (`formOpAfter`); a dose refusal is shown in Give dose whatever the runtime's `ok`; every write `runAction`; authors shown through `publicDisplayName`, as the server's answers, so no email ever shows on the wall). Give dose is the shared `GiveDoseDialog`: with the tablet shell present it sends `pets.dose.give` (or `.old`) through `runAction`, its intent carrying the occurrence it showed (identity and instant) and the medication and dosage it showed. A dose queued offline is recorded as follows (security review S1, D1). "Changed after queueing" means the course's `updatedAt` or `finishedAt` (server time) is later than the queue entry's `createdAt` (the tablet's clock, bounded by the gate). The occurrence is the current schedule's own when it still has that key (inside the course's start and end days), and a shown instant must then equal it; the shown occurrence is used only when the schedule no longer has the key and the course changed after queueing (a schedule or days edit, or a finish, while the tablet was offline), so a dose that was given is never dropped, even outside the course's days as they are now; otherwise it is refused (`occurrence`, or `finished` without a schedule). Either way the occurrence must lie within the dose's own given time (`givenAt`, else the queue time): at most 24 hours early and at most 7 days late (`DOSE_BACKDATE_MAX_MS`), so a queued dose can never mark later occurrences covered. The shown instant must also be the key's household wall time, whole milliseconds, less than 92 days ahead (else `invalid_input`); an older queued entry without it is looked up in the schedule. The shown medication and dosage (strings of at most 200 characters, a name never empty) are recorded only when the course changed after queueing; otherwise the course's own values are, the shell asks "Already given?" with the server's check and sends the answer with the same opId, and the toast offers Undo for 10 s; Finish in the dialog is `pets.course.finish`. Each course's doses, and each pet's notes and weighings, keep their own Undo toast (`toastGroup`: `petDoseToastGroup`, `pet-note:<pet>`, `pet-weight:<pet>`), and "Already given?" is asked through the shell's prompt queue like "Feed again?". The tablet builds every request from the shell's own fields after the intent's (`intentFields` drops any intent key named like a request field). A reminder's or Calendar's `/pets/<id>?tab=medication&dose=<courseId>` link opens the sheet and Give dose for an active course once the courses have loaded, then leaves the address; quick add's "Give Maple a dose" opens the pet's medication list. Notes and weighings are face-level with Undo and wait in the offline queue like feeds; PIN-level actions show the PIN pad (never queued). The sheet is a dialog that scrolls inside (48 px controls), so the board itself never scrolls the page at 1263x818, 1263x722 or 1264x843.

### Night dimming (F3; design 14.4, D-T1, JC-20)

`households/{h}.quietHours = { start: 'HH:mm', end: 'HH:mm', updatedAt, updatedByUid }` or null/absent (no dimming), in the household's time zone; a range may cross midnight (start inside, end outside); the wall-clock minute in the zone decides, so DST needs no special case (`isQuietAt`). Set by `updateQuietHours` (server, owners and admins by role, active, household not being deleted; `validateQuietHours`: two different `HH:mm` times or null; unchanged is a no-op; activity `device.quiet_hours_changed` with the old and new range). The client cannot write it: the household update rule allows only `timeZone` and `updatedAt`. Push muting by these hours is not part of this goal.

### Flags (how the devices feature is turned on)

Two independent switches; both default off in code. **Production has both on** (`apphosting.yaml`, the devices release after F4b-2 and the JC-8 gate); every other environment stays dark unless it sets them:

- `HOMEHUB_DEVICES_ENABLED=true` (server runtime; read on every call, no rebuild): every device, PIN, kid-profile, tablet-settings, exit and quiet-hours server action answers instead of `unavailable`.
- `NEXT_PUBLIC_HOMEHUB_DEVICES=true` (build time, inlined): shows the Devices tab and its quiet-hours and points-PIN cards, the sign-in dialog's **Set up a wall tablet** button, `/setup`, the Profile **Tablet PIN** card and the kid-profile controls.
- Also needed in production before PINs work: `HOMEHUB_PIN_PEPPER_CURRENT` and `HOMEHUB_PIN_PEPPER_<id>` (already declared in `apphosting.yaml`).

To turn them on in production, after the JC-8 release gate is recorded: add to `apphosting.yaml` `- variable: HOMEHUB_DEVICES_ENABLED / value: "true" / availability: [RUNTIME]` and `- variable: NEXT_PUBLIC_HOMEHUB_DEVICES / value: "true" / availability: [BUILD, RUNTIME]`, then roll out (the public flag needs a new build). To turn tablets off again, set `HOMEHUB_DEVICES_ENABLED=false` (immediate: every tablet action refuses with the retryable `unavailable`; paired tablets keep their session and their read rules). The emulator e2e suite turns both on (`playwright.config.ts` webServer env, with a test-only pepper).

## Authentication, Roles, and Security

**Server authority.** Codes, re-pair, settings, removal and the Devices-list reconcile authenticate a personal caller with `verifyCaller` (a verified ID token with an email, so a device token is refused) and require the **role** owner or admin, active, inside the transaction (a member granted `household.manageInvites` is refused; JC-22). Redemption is unauthenticated and guarded (below). The heartbeat takes the device's own token through `verifyDevice`. Every existing personal server action (household, chores, shopping, automation, AI flows) authenticates through `verifyCaller` or `authorizeHouseholdAction`, both of which require an email, so each refuses a device token; `tests/server/device-identity.test.ts` calls every exported action of those modules with a device token. F3: quiet hours (`updateQuietHoursAction`) authenticate a person with `verifyCaller` (owner or admin role); the tablet's admin settings and exits take the tablet's own token through the gate (`admin-pin`: owner or admin role with a PIN session at most 30 s old, re-checked inside the write's transaction); the tablet UI hiding a control is never the check.

**Firestore rules** (`firestore.rules`, Identity section). A device token has no email, so `signedIn()`, `hasMemberDoc`, `hasHouseholdPermission`, `isOwnerOrAdmin` and everything built on them stay false for it; device access is only separate `||` clauses on reads. Helpers take the household from the **path** and require the token to name it:

- `isDevicePrincipal()`: `hh_kind == 'device'`, `sign_in_provider == 'custom'`, no `email` claim, string `hh_device`, `uid == 'device_' + hh_device`, numeric `hh_gen`.
- `isDevice(h)`: plus `hh_household == h` (no read).
- `deviceActive(h)`: plus the record `households/h/devices/<hh_device>` is `active` at `hh_gen`, and the household has no `deletingAt` (two lookups).
- `sectionEnabled(h, s)`: plus `sections[s] == true`.

| Path | Tablet read |
|---|---|
| `households/{h}` | get, when `deviceActive(h)` and the document has no `memberEmails`/`ownerEmail` |
| `members/{uid}` | get and list, `deviceActive(h)` |
| `members/{uid}/private/*` | never |
| `devices/{d}` | its own record only, in every status (`isDevice(h) && d == hh_device`); owners and admins get and list; no client writes |
| `devices/{d}/**` | never (catch-all) |
| `notifications/{id}` | `*` audience only, through `where('audience','array-contains','*')` + `where('category','==',c)`: `system` and `general` always, `chores`/`pets`/`shopping`/`maintenance` when that section is on (`deviceNotificationReadable`). Queries without the category filter, with `array-contains-any [uid,'*']` or `array-contains <uid>`, with a `category in [...]` filter that includes a category the tablet may not read, a `get` of a targeted notice, and the `automation` category are refused (tested) |
| `chores`, `chore-settings`, `chore-templates`, `rooms`, `stats` | `sectionEnabled(h,'chores')` |
| `shopping-lists` (+ `items`, `config`), `pantry-inventory`, `barcode-library`, `stores`, `shopping-settings`, `trips`, `shopping-usuals` | `sectionEnabled(h,'shopping')` |
| `pets`, `feeding-logs`, `feeding-state`, `medication-logs`, `care-logs` | `sectionEnabled(h,'pets')` (every new Pets path must get the clause in the PR that adds it) |
| `home-assets`, `vehicles`, `maintenance`, `maintenance-attachments` | `sectionEnabled(h,'maintenance')` |
| `auditLogs`, `home-automation`, unknown paths, `inviteCodes`, `deviceCodes`, `users/**`, `aiUsage` | never |

`deviceCodes/{code}`: owners and admins (role) of the code's household read it; no client writes. **No device client writes anywhere**: no write rule has a device clause.

**F2 rules.** `members/{uid}/private/pin` and `pinGuard` keep the existing rule (a client `get` of `contact` only, no writes) and the device subcollections the catch-all deny; both are tested for the owner, the member and a tablet. Membership records, kid profiles included, stay server-written. `deviceAttributionKept()` / `choreDeviceAttributionKept()` guard updates (section 12). Kid profile photos: `households/{h}/members/{memberUid}/avatar/{file}` is readable with `household.view` or by an active tablet of that household, and uploaded (image, at most 5 MB) or deleted only by an active owner or admin, only under a `kid_` uid.

**Storage rules** (`storage.rules`): `deviceActiveForStorage(h)` (claims as above, `hh_household == h`, the record under the path's household `active` at `hh_gen`; one Firestore lookup, Storage allows two) and `deviceSectionForStorage(h, s)`. Tablets read `households/{h}/pets/**` (pets on), `households/{h}/barcode-library/**` (shopping on), `households/{h}/maintenance/**` (maintenance on), and profile photos in account-ID folders `users/{uid}/avatars/**` only (never an email-named folder). No device uploads or deletes. Household A's tablet never reads household B's files, even when B has a record with its id (tested per clause).

**Release gate (JC-8, B3).** Tablet reads expose whatever fields shared documents hold. No rules release containing a device read clause deploys until `scripts/ops/scrub-shared-emails.mjs`, `scrub-member-emails.mjs`, `scrub-remaining-emails.mjs` and `migrate-avatars-to-uid.mjs` all report zero remaining work in a production dry run, recorded in the tracker with date and counts. Pairing also refuses a household still carrying `memberEmails`/`ownerEmail`.

**Redemption guards (3.4).** Server flag; in-memory windows of 10 attempts per minute per client address and 300 per minute per instance (`takeRateSlot`); a limited-use App Check token verified with `consume: true`, failing closed outside emulator mode (missing, invalid, over-long or already consumed tokens are `app_check_failed`). The client address is never the first `X-Forwarded-For` entry: `clientAddress(headers, hops)` takes the entry `hops` places left of the rightmost one (default 1: next-to-last, the App Hosting / Cloud Run shape), and validates only that entry: whatever a caller puts left of it is never parsed, so garbage there cannot remove the address. When the header is absent, too short, or the trusted entry is not a bare IP, the request is limited in one shared `unknown` bucket (`UNKNOWN_CLIENT`); the per-address limit is never skipped. **Hop count on App Hosting (measured 2026-11-23):** with `HOMEHUB_LOG_FORWARDED_SHAPE=true`, redemptions from two different clients that send no header of their own both arrived with 3 `X-Forwarded-For` entries, so the client is two places left of the rightmost entry; production sets `HOMEHUB_TRUSTED_PROXY_HOPS=2` in `apphosting.yaml` (with the default of 1 every client would have shared one bucket: still limited, never bypassed). Set `HOMEHUB_LOG_FORWARDED_SHAPE=true` to log the entry count again (no addresses).

**Custom-token signing (production IAM).** `mintDeviceCredential` calls `createCustomToken`, which on App Hosting signs through the IAM Credentials `signBlob` API as the backend's runtime service account. That account needs `roles/iam.serviceAccountTokenCreator` on itself (and the IAM Service Account Credentials API enabled); without it every redemption commits the device record, then fails with `failed` ("Something went wrong on our side") and logs `Device credential could not be issued … iam.serviceAccounts.signBlob denied`. The record stays paired and the tablet retries with the same code and nonce once the role is granted.

**Privacy.** Codes store no email; activity entries store no email, code, nonce or token; the creator's notification names the tablet, not a person. The redemption result returns only `{ customToken, householdId, deviceId }`.

## Invariants and Failure Behavior

- A selected member is attribution, never proof: the server re-reads the member on every action and inside the mutation's transaction; the level comes from server-held session state, never a client flag (WT-5e, WT-7d).
- PIN material never leaves the server; a PIN changed, cleared, or a role changed ends its sessions on every tablet at their next use; a correct PIN never forgives failures recorded by concurrent attempts.
- Kid profiles cannot sign in, never receive targeted notices, have a fixed Child role and are never offered as chore assignees yet.
- A device principal is never a member: no membership record, never in member lists, pickers, audiences or push recipients; it holds no push subscription (cleared before sign-in and at every tablet start).
- Every credential is bound to one household and one generation; a bumped generation or a non-active status refuses new requests in the rules and on the server at once, whatever the ID token's expiry.
- Codes are single use, expire 15 minutes after the server stored them, and are redeemed only in their own flow; member invites never pair a tablet, and device codes never join a person.
- Redemption is idempotent per nonce and has exactly one winner per code; a re-pair has exactly one winner per generation.
- If the Auth calls after a removal fail, the action still succeeds (`authCleanup: 'pending'`), the record already refuses everything, and a retry, the Devices list or the daily sweep finish it.
- With the flags off: Devices tab hidden, setup button hidden, `/setup` not found, every device server function refuses with `unavailable`.
- The tablet shell ends the session (listeners stopped, PIN and face dropped, `homehub-device` deleted, household data forgotten, Firestore cache cleared, push cleared, signed out, back to `/setup` with a one-shot note) only on a server signal (section "Revocation on the tablet"); a denied read is confirmed by the heartbeat first. `unavailable` (a verifier outage), `rate_limited`, `failed` and network errors keep the session. Cached snapshots never decide.
- A tablet's face memory and PIN unlock carry no authority; every action re-checks the person, level and session on the server. Timers never fire during a save, an open Undo or unsaved input.
- Every write on a tablet is a device action through the gate (a capability the tablet can send; anything else the UI refuses before asking anyone); tablet code never writes with the client SDK (guarded by `tests/unit/devices-pets-care.test.ts` for Pets) and the rules have no device write clause.
- A queued entry's intent never changes; it is removed locally only while it has never been sent; sync never replays UI callbacks.
- Admin settings and every exit need an owner or admin PIN session at most 30 s old; a member's or child's PIN is never enough.
