# Household Governance

## Purpose and Scope

This module owns household creation and recovery, membership, roles, permission presets/overrides, temporary invites, pending approval, member departure/removal, ownership transfer, and audit activity. It does not own feature records except compatibility cleanup such as unassigning chores when a member leaves.

## User-Facing Capabilities

- Create or join a household from the global onboarding overlay. Enter submits either form; an empty or over-long name and an incomplete invite code are explained inline under the field (`FieldError`). Invite codes are re-formatted as `XXXX-XXXX-XX` while typing or pasting, with or without dashes. The pending-approval overlay names the household the person asked to join.
- Manage Overview, Invite Codes, Members, Roles, Activity, and Danger Zone at `/household`. Tabs a viewer cannot use are not shown: Invite Codes needs `household.manageInvites`, Activity is for owners and admins (the rules let only them read audit entries). Signed-out visitors get a Sign in prompt. What a person may do on this page comes from the management policy below (their effective permissions and rank), not from their role name.
- All Household Manager data is live (Firestore listeners); there is no Refresh button.
- Overview: four stat cards (2x2 on phones, four across from `md`); long household names, even without spaces, wrap inside their card (at most three lines; `tests/e2e/shell-wave4.spec.ts` checks that the longest allowed name (80 characters) with no spaces stays inside its card and never overlaps the next one). The member and active-invite counts tick in with `NumberTicker` (the card's title keeps the plain text). Rename the household inline (Enter saves; errors inline). The household ID is plain small text, not an input.
- Generate, copy, revoke, and use temporary invite codes. An empty invite list shows an `EmptyState` with a Create invite code action. Create invite code (both the button and the empty-state action) stays disabled until the household, the signed-in member and `household.manageInvites` have loaded, so a tap is never silently ignored; `EmptyState` actions accept `disabled` for this. The list stays a live client read (`inviteCodes` where `householdId ==`). The rules still let only owners and admins list invite codes, so a member who was granted `household.manageInvites` sees (and can revoke) only the codes they created during the current visit; the rules release will let `household.manageInvites` holders list them instead (see Not yet closed in the rules).
- Members (D13/H25): the member cards enter staggered (`Stagger`; instant under reduced motion). Each member is a card with `MemberAvatar` (photo or gradient) in a collision-free member color (`memberColorMap`), a color stripe, a role chip, "(you)", the email only on your own card and for viewers who may manage members (`canSeeMemberEmails`: owner and `household.manageMembers`), join time, a custom-permission count and, with `chores.view`, chores done this week and still open. Role changes, Customize permissions, Make owner and Remove live in a "..." menu that lists only actions the policy lets the viewer perform on that person (the role list holds only roles below the viewer's own); with none, no menu is rendered. Choosing a role asks for confirmation and says that custom permissions are reset. A household with only you shows an `EmptyState` inviting others.
- Pending people (`newuser`, shown as "Pending"; the internal name never appears) appear to people with `household.manageMembers` as an "Approve Jamie?" banner at the top of Members (slides in; instant under reduced motion) with a role picker (default Member; only roles below the viewer's own), Approve (the role-change server action) and Deny (the remove server action, after confirmation). A badge on the Members tab counts pending people.
- Roles (D12/H25): a permission matrix with permissions as rows (grouped by module) and the five role presets as columns; the viewer's role column is highlighted. Choosing a member in "Show" (or Customize permissions from their card) shows that member's role default beside their own permissions. When the policy lets the viewer edit that member (`household.manageRoles`, not themselves, not someone at or above their own rank; otherwise the description says why), the member column is editable: each cell is a real `role="checkbox"` button (Tab to move, Space/Enter to toggle), checkmarks draw in within 150 ms (instant under reduced motion), cells that differ from the default carry a dot, and a bar shows unsaved changes with Use role defaults, Discard and Save permissions. Locked cells (lock icon, reason as tooltip and for screen readers, and a short note under the matrix): the owner-only permissions (`household.delete`, `household.transferOwnership`), and any permission the viewer does not hold that the member does not already have. A permission the member already has can always be taken away. If a draft would grant something the viewer does not hold (for example through Use role defaults), the bar says so and Save is disabled. Save permissions asks for confirmation. Only differences from the role default are stored.
- Activity: plain-language entries ("Created an invite code", "Changed a role to Admin") with relative times; an empty log shows an `EmptyState`.
- Remove, Deny, Make owner, Leave, role changes and permission saves ask for confirmation in an alert dialog (no `window.confirm`). Approve does not: it is already a deliberate choice of role plus a button.
- Owners can permanently delete the household from Danger Zone after typing its name to confirm; the delete control is shown only to the owner, and Leave only to non-owners.
- Failures use `toastError` (plain language via `friendlyError`); raw Firebase text is never shown. Successful outcomes use short toasts.

## Architecture and Data Flow

`AuthProvider.createHousehold` checks for an empty name, then calls the `createHouseholdAction` server action with a fresh ID token and the browser's time zone (see Household Creation); it shows the returned message as a "Creation Failed" toast when one is refused, and a `friendlyError` toast when the server cannot be reached. `AuthProvider` also loads the caller's own membership record (a profile pointing at a household without a record, or one the rules deny, is cleared; there is no legacy recovery. Offline or other transient failures keep the reference and show a "Couldn't load your household" screen with Try again). Joining calls the `joinHouseholdWithInvite` server action (`src/app/household/actions.ts` → `src/lib/server/household-membership.ts`), which verifies the ID token and, in one Admin SDK transaction, checks the invite (exists, not revoked, not expired, uses left), refuses existing members and people still in another household, creates the pending record (no email; with `householdName`, the household's name at that moment, and a display name only when the token's name is not an email; photo by the same rule as creation, `membershipAvatarUrl`), increments `useCount`, records the redemption, writes the person's contact document (`members/{uid}/private/contact`, see Member contact), updates the profile cache (including `uid`), writes an audit entry, and sends a targeted approval notification to each active owner/admin. It writes no email to the household document or the record (see Email copies). Codes are accepted in any case, with or without dashes or spaces. The action returns only `{ household: { id, name }, member: { uid, role, status, joinedAt, householdName } }` (`JoinResult`): never the household document, which only approved members may read. While pending, `AuthProvider` shows the waiting screen from that result and, on later loads, from `householdName` on the person's own record (`pendingHouseholdView`, `src/lib/member-directory.ts`); it never reads the household document for a pending person. An older pending record without `householdName` gets an empty name, so the waiting screen shows its generic text ("An owner or admin will choose your role...") and Profile shows the role without a household name. Leaving and deleting also run through server actions (`leaveHouseholdAction` and `deleteHouseholdAction` in the same files), each verifying the ID token first. Leaving (any non-owner) runs in one transaction that re-reads the caller's membership, so a concurrent ownership transfer makes it retry and be refused; it deletes the caller's member record and contact document, removes their email from a legacy `memberEmails` list when the household still has one (and writes no list otherwise), clears their profile cache, unassigns their incomplete chores and recurring templates, writes a `member.left` audit entry, and sends a targeted notification to each other active owner/admin. Deleting requires an active `owner` member record and an exact (trimmed) household-name match; it first, in one transaction, marks the household `deletingAt`, sets every membership to status `deleting` (rules grant nothing to non-active members, so all client reads, writes and uploads stop) and revokes every invite; joining and leaving are refused from then on. It then deletes Storage objects under `households/{householdId}/` (when a bucket is configured) and recursively deletes every subcollection except `members`; then, in one batch, it clears the profile cache of every member whose profile still points at the household, deletes the household's `inviteCodes`, the member records with their contact documents, and the household document. If cleanup fails partway, the household stays frozen: members see that it is being deleted, and the owner gets a Finish deleting action that resumes it. `HouseholdManager` chooses the onboarding or pending-approval overlay. `HouseholdManagementClient` performs no management writes itself: rename, invite create/revoke/revoke-all, approve and role change, permission edits, removal and ownership transfer each call a server action (see Management Operations) with a fresh ID token and show the returned plain-language message when one is refused. The daily pending-member reminder is a server action too (`remindPendingMembersAction`), so the component writes nothing to Firestore. `useHouseholdLiveData` opens `onSnapshot` listeners on the household document (live name) and `members`; for holders of `household.manageMembers` (`canSeeMemberEmails`) one listener per member on their contact document (see Member contact); and, only when the viewer's role may read them, on `inviteCodes` (`householdId ==`), `auditLogs`, and two single-field chore queries for member stats (`isCompleted == false`, and `completedAt >=` the start of this week, Monday local time). Each listener fails independently, so a denied invite or audit read never blanks the member list.

`households/{householdId}/members/{uid}` is the only authority for household access in Firestore rules, Storage rules and server actions. `households.memberEmails`, `households.ownerEmail` and `users/{email}.{householdId,role,permissions}` are display/compatibility data and never grant access; a user listed only in `memberEmails` has no access and cannot create their own membership record. `households.ownerUid` must always point at an active `owner` membership record (enforced by rules); legacy households without `ownerUid` must be backfilled from their verified owner record before owner edits work.

### Member privacy (public member data)

What housemates see of each other is the membership record's public fields: `uid`, `displayName`, `avatarUrl`, `role`, `status`, `joinedAt` (and the record's permissions, used by the policy). `src/lib/member-directory.ts` turns records into `HouseholdPerson` values (`approvedPeople`, `personFromMemberRecord`); `publicDisplayName` never returns an email (an empty or email-like name becomes "Member"). The Chores page, the calendar, the command palette, the streaks tile and the member cards use only these fields; no screen reads a housemate's `users/{email}` profile, and the rules let only the person read it. Membership records carry no email (older records keep one until `scripts/ops/scrub-member-emails.mjs` removes it; the app uses such a leftover only as a matching key for chores written before `assignedToUid` existed). Emails are shown only to the person themself (their own card uses the email of their sign-in) and to member managers, from the protected contact document (member cards, the approval banner, which only managers see, and invite/activity lists, which only owners and admins can read). The untargeted pending-member reminder and the household-wide ownership-transfer notice name people by display name only ("A member" when there is none).

### Member contact

Each member's email has a document of its own, `households/{householdId}/members/{uid}/private/contact` (`{ email, updatedAt }`, ISO time). Only the server writes it (Admin SDK, in the same transaction as the membership change): joining (`redeemInvite`) and household creation (`createHousehold`, the owner's). Approval and role changes leave it as it is. Leaving, removal (including denying a request) and household deletion delete it. Members who joined before it existed get it from `scripts/ops/backfill-member-contact.mjs` (dry run by default; `--apply`, `--project`, `--firebase-tools-login`; counts only; creates a missing document, updates one that holds another email, skips records without an email; each write in its own transaction that re-reads the record, so it is safe to stop and re-run; pure planner `scripts/ops/member-contact.mjs`).

The rules let the person (`request.auth.uid == uid`, also while pending) and holders of `household.manageMembers` (`hasHouseholdPermission`, so an override counts both ways) `get` it; nobody lists the `private` collection, reads any other document in it, or writes from a client.

It is the only place the household keeps a member's email. Every reader uses it and nothing else (`functions/src/shared/member-contact.ts`: `memberEmailOf`, `withContactEmails`, which drops any legacy `email` from a record): the server actions read it inside their transactions for the profile cache (`users/{email}`), removal's assignee queries, activity-log `targetEmail` and household deletion; the push trigger and the hourly upkeep read it with the Admin SDK (Notifications and Chores modules). A member without one has no email for these purposes (no profile-cache update, no push, no reminder) until `scripts/ops/backfill-member-contact.mjs` creates it. In the Household Manager only member managers subscribe to the contact documents (`useHouseholdLiveData`, `canManageMembers`); a missing or unreadable document is simply absent, so the card shows no email. Everyone else never requests it.

### Email copies

No email is written into a document housemates can read. Household creation writes no `ownerEmail` or `memberEmails`, joining adds nothing to `memberEmails`, leaving and removal only remove the departing person's email from a legacy list that still exists (`legacyMemberEmailRemoval`), and an ownership transfer deletes a legacy `ownerEmail` instead of rewriting it. Membership records are written without `email` (creation, joining). Chores and templates are assigned by uid only and completions record `completedByUid` and `completedByName`, never `completedByEmail` (see [Chores](../chores/README.md), "Assignee identity"); yearly chore stats are keyed by uid; notifications are targeted by uid only (see [Notifications](../notifications/README.md)). The rules refuse client writes that would add an email to a household document, a membership record or a notification (see Authentication, Roles, and Security).

`scripts/ops/scrub-shared-emails.mjs` (dry run by default; `--apply`, `--project`, `--firebase-tools-login`; counts only; update-time preconditions; re-runnable; pure decisions in `scripts/ops/shared-email-scrub.mjs`) removes the stored copies: `memberEmails` and `ownerEmail` from households (`ownerEmail` is kept on a household without `ownerUid`), assignee emails from chores and templates, `targetUserEmail` and action-entry emails from live notifications, and email labels from the yearly chore stats' `names`. Members' emails come from their contact documents, then their records. `scripts/ops/rekey-chore-stats.mjs` then moves the yearly chore stats from email-derived keys to uid keys (see [Chores](../chores/README.md), "Yearly stats"), and `scripts/ops/scrub-member-emails.mjs` (same conventions; pure decisions in `scripts/ops/member-email-scrub.mjs`) removes what is left: `email` from each membership record whose contact document holds the same email (decided and written in one transaction that re-reads both; a record without a contact document, or with a different email in it, keeps its email and is counted), `memberEmails`/`ownerEmail` from households, every assignee email from chores and templates (completed ones included, after setting `assignedToUid` where missing or stale) and `completedByEmail` from chores (after setting `completedByUid` where missing). A completion credited to someone who has left and named only by that email gets their opaque former-member key instead, from a per-household secret in `households/{id}/ops/former-members` that only the server can read (see [Chores](../chores/README.md), "Assignee identity"); the count is reported. Run the re-key and then the scrub after the app, functions and rules of that release are live.

Invites keep `createdByEmail` and activity-log entries keep `actorEmail`/`targetEmail`; both are readable only by people who manage invites or members (owners and admins by role).

Members cannot write their own record under the rules, so a change of name or photo reaches it through `syncMyMemberProfileAction` (below): `updateUser` calls it after a profile save that touches `displayName` or `avatarUrl`, and `AuthProvider` calls it whenever a confirmed load finds the record's name or photo differing from the profile (`memberProfileDiffers`), which heals older drift. Both are best effort: a failure is logged and retried on the next load.

## Management Policy

`src/lib/household-policy.ts` is a pure module (no Firebase, no React). The server actions enforce it inside their transactions and the Household Manager uses the same functions to decide what to show.

- Rank: owner > admin > member > child = guest > pending (`newuser`). Unknown or legacy role names rank lowest and grant nothing.
- Effective permission: the role preset merged with the member's overrides (`getMemberPermissions`); the owner always has the full preset; pending or non-active people have nothing; `household.delete` and `household.transferOwnership` are forced off for everyone but the owner, whatever an override says.
- `household.view` and `household.manageInvites` work as ticked. A member granted `household.manageInvites` can create and revoke invite codes; an admin with it unticked cannot.
- `household.manageMembers`: approve pending people, change roles, remove members and rename the household. Member operations apply only to people whose rank is strictly lower than the actor's (never the owner, never an equal, never yourself), and the assigned role must be strictly below the actor's own rank (`owner` and `newuser` are never assignable).
- `household.manageRoles`: edit another member's permission overrides, with three guards: not your own; not someone at or above your rank; no granting (setting to true) a permission you do not effectively hold. Revoking is allowed under the same rank guard. Pending people have no permissions to edit.
- `household.delete` and `household.transferOwnership`: the owner only, always. They cannot be granted through overrides (the server refuses the save; the rules' `noOwnerOnlyOverrides` rejects the write too).
- Each refusal has a typed reason (`PolicyRefusal`: `not_member`, `missing_permission`, `self`, `rank`, `role_not_assignable`, `role_too_high`, `owner_only`, `grant_unheld`, `target_pending`) and a plain-language sentence (`refusalMessage`).

## Household Creation

`createHouseholdAction` (`src/app/household/actions.ts` → `createHousehold` in `src/lib/server/household-membership.ts`) verifies the ID token, then runs one Admin SDK transaction:

- the name is trimmed and must be 1-80 characters (`readHouseholdName`: "Give your household a name." / "Keep it under 80 characters.", code `invalid_input`); the time zone is kept only when it is a valid IANA name of at most 64 characters (`normalizeTimeZone`), otherwise left out so upkeep uses its default;
- refused with `conflict` ("Leave your current household before creating a new one.") when the caller's profile points at a household where they have a membership record (active or pending); a stale pointer without a record does not block;
- the ID is the slugified name plus a four-character suffix from a cryptographic random source (`householdIdFor`); up to 8 candidates are read and the first free one is used, and the household and membership are written with `create`, so an existing household can never be overwritten;
- writes the household (`name`, `ownerUid`, `createdAt`, `updatedAt`, `timeZone`; no emails since release C), the owner membership (no email; `role: owner`, `status: active`, `approvedAt`, `approvedByUid`, and the name and photo from the HomeHub profile, falling back to the token, with an email-like name left out (`publicMemberName`); a photo removed in Profile (`avatarUrl: null`) stays removed, and the token photo is used only when the profile has no `avatarUrl` field; `membershipAvatarUrl`), the profile pointer (`householdId`, `role: owner`, `permissions: {}`) the owner's contact document (`{ email, updatedAt }`) and the `household.created` activity entry (`details.householdName`) together.

Identity comes only from the token. Two creations at once by the same person both read the profile, so one is retried and then refused; the person ends up in exactly one household. The action returns the household and membership, which `AuthProvider` puts into context without another read.

## Management Operations

All are server actions in `src/app/household/actions.ts` backed by `src/lib/server/household-membership.ts`. Each verifies the ID token (identity never comes from caller-supplied fields), then runs one Admin SDK transaction that re-reads the household and the actor's membership (and the target's), refuses when the household is being deleted or the policy says no, performs the writes and adds the activity-log entry in the same transaction. Results are `{ ok: true, data }` or `{ ok: false, code, message }`, where `code` is a policy reason or one of `unauthenticated`, `invalid_input`, `not_found`, `household_deleting`, `conflict`, `failed`.

| Action | Policy | Writes | Activity-log action |
|---|---|---|---|
| `renameHouseholdAction` | `household.manageMembers` | household `name`, `updatedAt` (name trimmed, 1-80 characters; an unchanged name writes nothing) | `household.renamed` (`householdName`, `previousName`) |
| `createInviteAction` | `household.manageInvites` | `inviteCodes/{code}`: code generated on the server (never reusing an existing document), 30 minutes, one use | `invite.generated` (`code`) |
| `revokeInviteAction` | `household.manageInvites` | `revokedAt` on a code of this household (another household's code is reported as not found; an already revoked code is a no-op) | `invite.revoked` (`code`) |
| `revokeAllInvitesAction` | `household.manageInvites` | `revokedAt` on every code that could still be used | `invite.revoked_all` (`count`) |
| `changeMemberRoleAction` | `canAssignRole` | member `role`, `status: active`, `permissions: {}`, `approvedAt`, `approvedByUid`; profile cache `role`, `permissions` (profile found by the email in the member's contact document) | `member.approved` for a pending person, else `member.role_changed` (`role`, `previousRole`) |
| `updateMemberPermissionsAction` | `canEditPermissions` on the effective differences | member `permissions` (only differences from the role default); profile cache `permissions` (replaced). Refused with `conflict` when the member's role is no longer the one the editor showed | `member.permissions_changed` (`granted`, `revoked`) |
| `removeMemberAction` | `canManageMember` | deletes the member record and its contact document; removes their email from a legacy `memberEmails` list when there is one; clears the profile cache if it still points at this household; unassigns their open chores and their recurring templates (found by `assignedToUid`, and by `assignedToEmail` using the email in their contact document) | `member.removed` (`pending: true` when a request was denied) |
| `remindPendingMembersAction` | `household.manageMembers` (`canRemindPendingMembers`) | for each pending person not reminded in the last 24 hours (`pendingReminderDue`): member `lastNewUserReminderAt`; one household-wide `system` notification "Pending member approval" naming the person by display name only ("A member" when they have none, never the email) whose ID is fixed per person and UTC day (`getDeterministicNotificationId`, `stateKey` `pending\|<date>`, the same ID older browsers wrote), with `audience: ['*']`. Returns how many were due | none |
| `transferOwnershipAction` | owner only | household `ownerUid` (a legacy `ownerEmail` is deleted); new owner `role: owner`, previous owner `role: admin`, both with `permissions: {}`; both profile caches; one household-wide notification (display name only) | `ownership.transferred` |
| `syncMyMemberProfileAction` | your own record (active or pending) | your member `displayName` (removed when the profile's is empty or email-like; at most 80 characters) and `avatarUrl` (`https://` URLs up to 2048 characters, else `null`), copied from your `users/{email}` profile read on the server; nothing when they already match; refused while the household is being deleted | none |

Activity-log entries written by these actions take `actorUid` and `actorEmail` from the verified token, `actorName` from the actor's membership record (falling back to the token), `targetUid`/`targetName` from the target's membership record and `targetEmail` from their contact document (`null` when there is none), both read in the transaction, and `createdAt` from the server clock (an ISO string, as before). Joining, leaving, creation and these operations are therefore all authored by the server; the current app writes no activity-log entry from the browser.

Removal keeps completed chores assigned to the person who did them (the earlier client batch unassigned those too, erasing history) and clears recurring templates the same way leaving does. Leaving and removal find assigned chores and templates by email (older records) and by uid; a record found by uid whose email now names someone else (an older build reassigned it by email only) is left alone. Open chores become `assignedToUid: ''`, `assignedToDisplayName: 'Unassigned'` (`unassignedChoreFields`) and lose `assignedToEmail`; templates lose `assignedToUid`, `assignedToEmail` and `recurrence.assignedToEmail`.

### Not yet closed in the rules

`firestore.rules` did not change with the move to server actions, so that browsers still running an older build keep working. The current app no longer makes any of the client writes listed below: household creation, the pending-member reminder, invites, renaming, role and permission changes, removal, transfer, leaving and deletion all run on the server. Until the follow-up release, the rules still accept the old role-based client writes from older builds. The follow-up (rules-only) release must:

- deny client `create` of households and of the creator's `owner` membership record (`ownerCreatesHousehold` and the members `create` rule);
- deny client `update` and `delete` on `households/{id}/members/{uid}`;
- deny client `create` and `update` on `inviteCodes`, and let `household.manageInvites` holders (rather than owners/admins by role) list their household's codes, since the list stays a client read;
- deny client updates of household `name`, `ownerUid`, `ownerEmail` and `memberEmails` (the one household-document write the current app still makes is the owner's removal of the legacy permanent `inviteCode` field in `AuthProvider`; keep that allowed or move it to the server first);
- deny client `create` on `auditLogs` (`validNewAuditEntry`);
- deny the owner/admin updates of other people's `users/{email}` household fields, now written only by the server, and the self-update that points one's own profile at a household (`updatesOwnMembershipCache` with a household ID); clearing one's own stale pointer is still done by `AuthProvider` and must stay allowed;
- decide who may read `auditLogs` (still owner/admin by role) and gate reads on `household.view`.

The emulator E2E seed creates Household A and Household B, matching fake identities, a limited member, and a legacy profile-elevation fixture. Cross-household and conservative fallback checks complement the primary owner/admin/member/pending membership path.

## Data Model and Persistence

- Household: `households/{householdId}` with `name`, `ownerUid`, timestamps, and `timeZone` (older households may still carry the legacy `ownerEmail` and `memberEmails` until the scrub removes them). `timeZone` is captured from the creator's browser when the household is created (owners/admins may change it; the rules bound it to a 64-character string). Server-side upkeep uses it for recurring-chore dates and maintenance due days; households without one use `America/Chicago`.
- Membership: `households/{householdId}/members/{uid}`: `uid`, `displayName`, `avatarUrl`, `role`, `status`, `permissions`, `joinedAt`, approval fields, and for people who joined by invite `inviteCode` and `householdName` (server-written; read by the person while pending). No `email` (older records keep one until the scrub removes it).
- Member contact: `households/{householdId}/members/{uid}/private/contact`: `email`, `updatedAt` (server-written; see Member contact).
- Temporary invite: `inviteCodes/{code}`.
- Audit: `households/{householdId}/auditLogs/{auditId}`.
- System events: `households/{householdId}/notifications/{notificationId}`.
- Legacy compatibility: `users/{email}.{householdId,role,permissions}`, and on older households `households.memberEmails` and `households.ownerEmail` (no longer written; scrubbed by `scripts/ops/scrub-shared-emails.mjs` and `scripts/ops/scrub-member-emails.mjs`).

Household IDs are slugified names plus a four-character suffix. Invite codes use readable `XXXX-XXXX-XX` values, expire after 30 minutes, and default to one use. The legacy optional `Household.inviteCode` field remains in the type for compatibility but is no longer generated for joining.

## Authentication, Roles, and Security

Roles are `owner`, `admin`, `member`, `child`, `guest`, and system-only `newuser`. Legacy `super-admin` normalizes to owner and `user` to member. Permission presets and per-member overrides are defined in `src/lib/permissions.ts`.

Who may manage what is decided by the management policy above and enforced by the server actions. The rules are a second, older layer that is still role-based (see Not yet closed in the rules): they let approved members list memberships, let owners manage every membership and admins manage non-owner memberships, and block `uid` rewrites; `email` is not among the fields a client update may change, so no client can add one to a record. The rules' only client-created membership is the creator's `owner` record written in the same batch as a brand-new household (kept for older builds; the current app creates households on the server), and it must not carry `email`; that household must not carry `ownerEmail` or `memberEmails`, and no client update of a household may add, change or remove either field. Joining an existing household is a server operation. Only approved members can read the household document; pending users can read their own membership and their own contact document but not the household document or any household subcollection. A `users/{email}` profile is readable only by that person (the server reads profiles with the Admin SDK). A member's contact document is readable only by that person and by holders of `household.manageMembers`, and never writable from a client. Deleting your own record removes access; it never grants it.

Ownership invariants are enforced by rules: a membership has role `owner` exactly when `households.ownerUid` points at it, so the last owner cannot demote or remove themselves, and ownership moves only through a single batch that updates `ownerUid` and both membership records.

In the rules, invite codes are created, listed and revoked by owners/admins (`useCount` must start at 0, `maxUses` 1–10); the app itself creates and revokes them only through the server actions, for anyone holding `household.manageInvites`. Clients can no longer read or redeem invites; redemption (expiry, revocation, use count) is a server operation. Owners/admins may update only the role/permissions of profiles that already point at their household, or clear that household; they cannot point another user's profile at a household.

## Integrations and Background Processing

- Governance events create system notifications and therefore can trigger FCM delivery.
- Pending-member reminders run on the server (`remindPendingMembersAction`) when someone with `household.manageMembers` opens Household Manager and a pending person is due; the page checks `pendingReminderDue` first so it calls the action only when there is something to send. Each person's daily state uses a deterministic notification identity, so overlapping visits, and an older browser doing the same, write one document. It is a page-triggered server action rather than part of the hourly `householdUpkeep` function so the reminder keeps its existing timing (a manager visiting), ships with the web app instead of a separate Functions deploy, and reuses the household transaction, policy and tests. No daily scheduled function exists.
- Household deletion is a server action (`deleteHouseholdAction`) that uses the Admin SDK's recursive delete; there is no Cloud Function or scheduled cleanup for it.

## Invariants and Failure Behavior

- `newuser` is not manually assignable and has no preset permissions.
- Owners cannot leave before transferring ownership or deleting the household; only the owner can delete, and the delete dialog stays disabled until the typed name matches. The server rechecks ownership and the name.
- Nobody but the owner can act on the owner; the owner's role changes only through an ownership transfer, and the owner cannot be removed.
- Every management operation re-reads the actor and the target inside its transaction, so a concurrent demotion, role change or removal is seen before anything is written.
- A role change resets the member's permission overrides.
- Household creation picks a free candidate ID inside its transaction and writes with `create`, so it never overwrites an existing household.
- Manager listeners fail independently, so denied invite/audit/chore queries never blank member data; a failed members listener shows a notice and the caller's own record.
- Member chore stats count chores assigned to the member (chores do not record who ticked them), keyed by member uid (`choreStatsByMember`: the chore's `assignedToUid`, or for older chores the member with that email). This week's completions are read with two single-field queries, the same pair of timestamps the Chores module's `completionInstant` reads: `completedAtServer >= weekStart` (the authoritative server stamp, a Timestamp) and the legacy `completedAt >= weekStart` (ISO string); documents missing one field are covered by the other. Open chores come from `isCompleted == false`. The three results are merged by document id (`mergeChoresById`), so a chore found twice counts once, and bucketed with `completionInstant` (`choreStatsByEmail`). Counts are shown only once all three listeners have answered for the current household and week and none failed (`choreStatsReady`); before that, or after a failure, member cards show no chore counts rather than 0. The week boundary moves at local Monday midnight (and is re-checked when the tab regains focus or visibility), which re-subscribes all three queries.
- An unsaved permission draft is tied to the member, their role and their stored overrides; a live role or permission change discards it.
- The permission editor never sends owner-only overrides; the server refuses them (`owner_only`) and the rules reject them.
- `/household?tab=<tab>` opens that tab, including when the page is already open (`overview`, `invites`, `members`, `roles`, `activity`, or `danger`); unknown values, and tabs the viewer cannot see, fall back to Overview. Choosing a tab replaces the URL with `?tab=<tab>` (Overview has no parameter), so refresh and Back keep it. Approval notifications deep-link to `/household?tab=members`.
- Join-request and member-left notifications are written server-side with one notification per event and active owner/admin (a rejoin creates new documents, so push fires again), each targeted by `targetUserUid`. The daily pending-member reminder, written by the `remindPendingMembersAction` server action, is household-wide (`audience: ['*']`), so it is shown and pushed to every approved member with `notifications.view` and names the person by display name only (never the email); push recipients come only from approved member records, never from `memberEmails`.
