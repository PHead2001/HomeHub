# Pantry Inventory and Recipes

## Purpose and Scope

This module owns household pantry, refrigerator, and freezer inventory plus recipe suggestions generated from that inventory. It does not own shopping-list records, barcode mappings, or the shared OpenAI configuration.

## User-Facing Capabilities

- Use the Pantry Inventory tab on `/shopping` (linkable as `/shopping?tab=pantry`). The tab stays mounted while the Shopping Lists tab is shown, so switching back re-reads nothing.
- The pantry is live (SH-1c): another member's additions, edits, moves and deletions show without a reload.
- See the pantry as shelves (default): Pantry, Fridge and Freezer are shelves of product tiles showing a product photo from the barcode library (matched by exact name) or a food emoji. A tile is one product (one name on one shelf) and lists its batches, soonest expiry first: "2 × 450 g · next Fri, 1 × 450 g", "3 cans · tomorrow". Products whose soonest batch expires within three days glow amber, expired ones fade and tilt, freezer tiles have a frost edge, and the header counts products expiring soon or expired. Expiry is counted from today in the household's time zone (D-6) and the page re-keys "today" just after household midnight (and when the page is shown again), so an always-on tablet rolls over on time (SH-10b).
- **Used one** (−) on a tile removes ONE package from the product's soonest-expiring batch (an atomic `increment(-1)`); it never subtracts 1 from a measured amount (17.3, SH-22a). **One more** (+) adds one package to that batch (`planAddOne`); when that batch already holds 10,000 packages (the rules' limit), the package goes to a batch with the same merge key that has room, or else to a new one-package batch of the same name, shelf, size, unit and expiry (saved through the add-merge path, which re-checks the full batch online), so the tap is never a refused write. **Out of this** in the tile's ⋯ menu uses every package up (SH-29). The package changes of one tap, across all of a product's batches, commit together in one Firestore write batch (`changePackagesTogether`), so a refused change leaves nothing used up; only once the server has acknowledged that write does the page show a 10-second **Undo** toast, which adds back exactly what was removed (`increment(+n)`, again in one write batch, SH-29c). Offline the tap is queued as one unit and the toast says **Saved on this device** with no Undo (`packageChangeToast`): a queued write cannot be cancelled, and a queued Undo would be an independent `increment(+n)` that the server could accept on reconnect even though it refused the queued decrement (the count was already 0), creating a package nobody added; **One more** corrects a mistaken offline tap once it has synced. The Add-to-list question still follows an offline tap that reached zero. When the product's total reaches zero the page asks **Add {name} to the list?** with **Add** and **Not now** (D-8): Add puts it on a Grocery list by the same rule as "Put on a shopping list" (one tap when there is a single Grocery list) through the Shopping merge path; Not now adds nothing, and nothing is ever added without that tap (SH-22b, SH-29b). Undo withdraws the question. If the Pantry tab is hidden while a tap's write is still pending, its question is dropped (a request counter bumped on tab deactivation), and the question only shows while the tab is shown, so it never opens or traps focus over Shopping Lists.
- A legacy batch (no `packages` yet) changes only online: its first change is computed inside a transaction that re-reads the document (`changePackagesTogether`, routed by `packageChangeRoute`), so two members tapping **Used one** on the same older item both count (the second retry re-reads the now-v2 document and takes the increment) and nothing written from the screen overwrites newer stock. Offline such a tap writes nothing and says **Connect to update this older item.**; v2 batches still queue their increments offline. A legacy count above 10,000 (the rules' limit per batch) is read in full and its first change splits it in that transaction (`planLegacyUpgrade`): the document keeps the remainder (1 to 10,000, so undoing a Used one still fits) and new batches of the same product hold full 10,000s, so nothing is lost. When undoing would not fit one batch (an older count above 10,000 emptied by **Out of this**), the toast offers no Undo (`undoFits`).
- A legacy measured document whose amount is above 100,000 (one package's limit) **needs repair** (`needsRepair`, `repairAmount`): it is not empty stock. Its tile shows the stored amount with "too large for one package: edit to fix", it adds nothing to the product's count, **Used one**, **One more**, **Out of this** and merges never pick it (a change aimed at it is refused with a message), and the idle cleanup never deletes it (`shouldDeleteEmptyBatch`). Editing it with a valid package size fixes it: the edit dialog starts it at 1 package (never 0) with a suggested size where the amount converts cleanly to a larger unit within the limit (150,000 g as 150 kg, 150,000 ml as 150 L; `repairEditPrefill`), otherwise with the stored unit and an empty size, and refuses to save it with an inline message below 1 package or without a valid size for a weight or volume (`repairEditError`), so correcting the size never stores zero stock; the migration also leaves it for a person (below).
- A batch at zero packages is hidden at once. A member with `shopping.delete` deletes it later, online, with a transaction that deletes only if it still has no packages and nobody touched it in the last 60 seconds (`updatedAt`), so an Undo, a +1 or a hand-off in between keeps it. Until then (and for good when no member online has `shopping.delete`) the used-up batch stays stored with `packages: 0`; the dashboard's pantry facts and the AI overview's pantry facts leave such v2 batches out (the AI overview compares expiry days in the household's time zone, see [AI](../ai-genkit/README.md)) (`isUsedUpPantryDoc`: a numeric `packages` of 0 or less), while legacy documents without `packages` are counted as before.
- Move a product (all its batches) to another shelf by dragging its handle (mouse or touch), by keyboard (focus the handle, Enter or Space to pick up, arrow keys to choose a shelf, Enter or Space to drop, Escape to cancel), by tapping the handle and then **Move here** on a shelf, or from the tile's ⋯ menu.
- Switch to the list view (the previous table on wider screens and stacked rows on phones); the choice is remembered per device in `localStorage["homehub.pantry.view"]`.
- Add, edit, delete, and bulk-delete inventory (bulk delete is in the list view, which shows one row per batch). The form asks for the unit, how many packages, for weights and volumes the optional size of one package, the shelf and an optional expiration date with quick chips **+3 d**, **+1 w**, **+1 mo** and **Freezer +3 mo** (which also moves it to the Freezer), counted from the household's today. Adding stock that matches an existing batch exactly (same name, shelf, unit, package size and expiry) adds packages to it; anything else is a new batch. The match is made from what is on screen, so online the save re-reads that batch in a transaction and adds the packages only while its merge key still matches (`decidePantryMerge`); if another member changed or deleted it meanwhile, a separate batch is created instead. A batch holds at most 10,000 packages (the rules' limit), so the combined count is checked in that transaction (`planMergeAdd`, built on `fillBatch`): the target is topped up to 10,000 and the rest becomes a new batch of the same product (a full target takes nothing and the whole add is a new batch), never a refused write; `findPantryMergeTarget` prefers a matching batch with stock and room, then an empty one, and only then a full one. Offline, or when the server cannot be reached to check (`unavailable`), the save never queues an increment to the matched batch: it creates a separate batch (shown on the same tile), so a queued add can never credit a batch that became something else. The toast says "added to" only when the packages really merged. A tile with several batches offers **Edit** per batch in its menu; tapping the tile edits its soonest batch. The form's package limit is 10,000, except when editing a legacy count stored above 10,000: then it is that stored count (`editPackagesLimit`), so the − stepper steps down from it (`stepPackages`) and the save splits the edited total like a legacy upgrade (`planBatchEdit`: the document keeps the remainder, new batches of the same product hold full 10,000s, in one write batch), never cutting it to 10,000.
- Start an inventory item from a barcode scan (`pantryScanPrefill`, `src/lib/shopping/pantry-scan.ts`): the name is the Barcode Library's name (else the looked-up product name), cut to the pantry's 120 characters (`clampPantryName`) so a long product name never blocks Save; a weight or volume ("450 g") fills in one package of that size, never 450 packages (BL-1), and a size above 100000 is left out; a counted amount ("12 eggs") fills in how many there are (at least 1, at most 10000); an amount without a known pantry unit is not filled in, and nothing typed in the name or amount fields is overwritten. The barcode is kept on the batch. An unknown code offers "Save to library" inside the item dialog (to members with `shopping.edit`), and a lookup that cannot answer says "Lookup unavailable" instead of "not found" (shared `useLookupFeedback`, see [Barcode Library](../barcode-library/README.md)); a lookup that answers after the item dialog closed or opened for another item is dropped instead of filling that form.
- **Put on a shopping list** (tile menu) and **Delete & Add to List** put the product on a Grocery list (`groceryListChoice`): with exactly one Grocery list it goes straight there; with several, a picker (list, name, quantity) opens on the Grocery list this device last used from the pantry (`localStorage["homehub.pantry.recentList.<householdId>"]`, a per-device convenience, removed when this device stops showing that household and at sign-out; see [Household Governance](../household-governance/README.md), "Live membership"), else the household's default (a list named "Groceries", else the first Grocery list by name); with none, a "Groceries" list is created. The write goes through Shopping's shared save path (`addToGroceryList` → `addItemsToList`, given the list's needed items): online, an item already needed on the chosen list with the same name gets that many more in a transaction (`findMergeTarget` + `mergeIntoNeededItem`), so no duplicate is added (SH-6); otherwise, and always offline, a new needed item is saved at once with a local category (`addedByUid` the member) and sorted later by one batched AI call. Once the server has confirmed the write (at once, or when a pending one settles) it is announced with `notifyDataChanged({ module: 'shopping', householdId, listId })` (`shoppingWriteNotice`, only for `saved`), so the Lists tab's fallback counts (`useLiveListCounts`, for lists beyond the first 20 live ones) refresh. The toast says only what is known (`trackWrite`, SH-4): "On the list" naming the list (or that the needed item now needs that many more), "Saved, will sync" only when the durable cache shows the write, or "Still sending…"; a failed write shows a `toastError`. When the AI call fails, `categorizationNotice` says the item stays under Other (or was not sorted, if its write was not yet confirmed), with no promise of a later edit (SH-8c).
- Generate a recipe suggestion from usable stock only (SH-27e, SH-31a): batches with packages left, leaving out used-up batches, batches that need repair and expired batches (expiry before the household's today; a batch expiring today is still offered, expired stock is never offered as usable). Each stock line carries its soonest expiry as a date-only household day (`expiresOn`) and the days left until it (`expiresInDays`, 0 = today); lines are sent soonest expiry first (undated last) and cut to the flow's 60 lines, so stock about to go off is always included, and the model is asked to build the recipe around the items with the fewest days left. Amounts keep their precision: a measured total below 1 kg or 1 L is restated in g or ml (joined with any g/ml line of the same product) and then rounded to two decimals from 1 up, or three significant digits below 1 (`roundAmount`), so a 0.004 kg yeast packet is sent as 4 g and a 0.002 L vanilla bottle as 2 ml, never 0; tile labels use the same rounding ("1 × 0.004 kg"); the button needs at least two usable items, as the server does (H08 recipe reveal). It is requested once when the dialog opens (and again only with Try again), from the pantry as it is at that moment; live pantry updates while the dialog is open neither clear the recipe nor make another AI request. The dialog opens with a loading state; when the recipe arrives in the shelves view and it uses tiles, the dialog and its scrim fade out (150 ms) so the shelves are visible, the used tiles lift off their shelves (the tile card and picture rise 8 px in 200 ms; the controls' hit areas stay put) with an "In the recipe" marker, the first lifted tile is scrolled into view, and after 450 ms (or at once on any key or pointer press) the dialog returns and the recipe card flips in (220 ms). In the list view, with no matching tiles, or under reduced motion, the tiles are marked and the card shows at once with no flip. Screen readers hear a short "Lifting the items…" status, and focus stays in the dialog throughout. The marker stays until the next generation.
- The recipe card separates **From Your Pantry** from **You Might Need** (SH-31a). Each pantry ingredient shows the recipe's line and, below it, what the household has from HomeHub's own live data ("You have 3 items · Tue (Fridge)", every shelf of that name), never an amount from the model; if it has since been used up, it says it is no longer in the pantry. Each missing ingredient has a **+** (44 px, 48 px on coarse pointers) that puts it on a Grocery list (SH-22c), and **Add all missing** adds every missing ingredient not yet added from this recipe in one action (SH-22d, SH-31b; a failed one is tried again). The destination follows `groceryListChoice`: the only Grocery list ("Adds to Weekly Groceries."), a **Add to** picker preselecting the list this device last used from the pantry (else the default) when there are several, or a new "Groceries" list (created once, on the first add) when there is none. The lists are read when a recipe with missing ingredients is shown; a failed read says so with **Retry**. Each add goes through the same Shopping save path as "Put on a shopping list" with quantity 1 (`addToGroceryList`; **Add all missing** uses `addAllToGroceryList`, which reads the list's needed items and categories once, saves every entry through one `addItemsToList` call, so each one merges into a still-needed item of the same name online and new items share one batched AI categorization call). Each row shows its own honest state (Adding…, On the list, Saved, will sync, Sending…, Not added) and stays added for this recipe; a late failure turns the row back to Not added with a `toastError`. Row states are kept per destination list (`withMissingAddState`, `missingAddStatesOn`): with several Grocery lists, choosing another list in **Add to** shows that list's own states, so an ingredient added to one list is still offered (and included by **Add all missing**) for another, and **Add all missing** is busy only for the list it is adding to. Each add writes to the list selected when it started, and its state, including a pending write that settles later, stays on that list even if the picker has changed since. A single **+** shows the same toast as "Put on a shopping list"; **Add all missing** shows one summary toast (`summarizeMissingAdds`): how many are on the list, which raised an item already needed there, which are saved on this device or still sending, and which failed, by name. There is no Undo. Without `shopping.edit` the buttons are disabled and the card says why. The add states belong to the shown recipe: a new recipe (Regenerate, Try again, or reopening the dialog) starts fresh.
- Shelf item counts, the expiring/expired header counts and the list view's shelf counts tick with the shared `NumberTicker` (`animateOnMount={false}`; one text node holding the final value, so "Pantry (3)" always reads exactly that), and each shelf's tiles enter with the shared `Stagger` (instant under reduced motion).
- Receive purchased grocery items in one batch from the shopping trip (see [Shopping](../shopping/README.md)); there is no longer a per-item pantry form after ticking.

## Architecture and Data Flow

`ShoppingCenterClient` hosts the inventory tab and holds the pantry listener; `PantryInventoryClient` receives it (`pantryState`) together with `focusItemId`/`onFocusHandled`: an expiring chip on the Shopping overview (SH-11c) carries the id of its product's soonest-expiring batch with packages left, switches to this tab and, once the tab is shown and the pantry has loaded, opens that batch's edit dialog (the batch a tile tap opens) for members with `shopping.edit` (the tab alone for viewers, or when the batch is gone or used up). The inventory client reads and writes household-scoped Firestore documents. Recipe generation sends only usable `{name, quantity, unit, expiresOn, expiresInDays}` values (`usableRecipeItems`, soonest expiry first, at most 60: the package count for counted units, packages × size summed per unit for measured ones with a known size; packages of a measured batch with no size are sent as their own line, `quantity` = packages and `unit` "packs of unknown size (g)", never as grams or litres and never added to a known-size total) plus a Firebase ID token to the AI server action and keeps the result only in component state. The server verifies household membership and `shopping.view` before requesting OpenAI.

The dashboard overview uses the same verified `shopping.view` boundary to calculate inventory and expiration counts server-side. It sends only bounded labels/dates and counts to the optional narrative, not full inventory documents.

The inventory is one `onSnapshot` listener ordered by name, shared by this tab and the Shopping overview's expiring chips (`useLivePantry` in `ShoppingCenterClient`, with metadata changes, bounded-backoff retry reset only by a server-confirmed snapshot, one toast per failure code, and resubscribe on `online`/visibility; see [Shopping](../shopping/README.md) for `keepListening`). It serves the cache offline. Firestore applies this device's writes to the listener at once and rolls a rejected one back there, so saves, moves and deletes never re-read the pantry. Every document is read through `readPantryBatch` and grouped with `groupPantryBatches`. The shelves view renders `PantryShelves`; moving a tile updates `location` (plus `updatedByUid`/`updatedAt`) on each of its batches in one batch write (shown at once through the listener and Firestore's queue; a rejected write shows a `toastError` and the tile moves back). The shopping lists for "Put on a shopping list" and the zero prompt's Add are read on demand when chosen. If the Pantry tab is hidden before that read finishes, the request is dropped, and the list picker only shows while the tab is shown. Product photos come from a live listener on `barcode-library` (`useLibraryPhotos`, the same source as shopping rows), so a photo replaced or removed in the library changes the tiles at once; a failed read only drops photos, and a photo that fails to load falls back to the tile's food emoji (`TilePhoto` in `pantry-shelves.tsx`). The recipe dialog composes the shared dialog parts (`DialogPortal`, `DialogOverlay`, Radix `Content`) itself, only so the scrim can step aside during the lift; it keeps the standard dialog markup, focus trap, Escape and close button. The recipe's output is normalised on the server against the stock that was sent (`normalizeRecipeIngredients`, see [AI](../ai-genkit/README.md)): each "from your pantry" entry names a supplied item exactly, in HomeHub's spelling. The tiles a recipe lifts are the products with exactly those names, on every shelf (`recipeProductKeys`).

In the list view, inventory uses compact table rows from `sm` upward and stacked item rows on narrower screens. Location filters and inventory actions wrap into a two-column mobile control grid; long item names wrap instead of widening the document.

Deleting a product (all its visible batches) and adding it back to a shopping list are separate operations: the inventory document is deleted before the shopping write begins. The shopping write is refused by the rules if that list was deleted meanwhile (items may only be written to a list document that exists).

## Data Model and Persistence

- Firestore: `households/{householdId}/pantry-inventory/{itemId}`, **one document per batch** (Pantry v2, audit 17.3).
- New batch IDs are `slugify(name)` (a slug plus a random suffix).
- v2 fields: `name`, `nameKey` (`itemNameKey(name)`), `location` (Pantry, Fridge, Freezer), `unit` (`PantryItemUnit`), `packages` (0 to 10000), `packageSize` (null, or above 0 and at most 100000: the size of one package in `unit`; always null for counted units), `expiryDate` (`yyyy-MM-dd` in the household zone, or null; SH-10a), `barcode` (optional), `addedByUid` (creator, set on create only), `updatedByUid` (last writer), `updatedAt` (server time) and `schemaVersion: 2`. v2 clients also **dual-write** the legacy `quantity` (packages for counted units, the package size for measured ones) so an older page still open shows something sensible; counted-unit package changes increment it too.
- **Legacy documents** (`name`, `quantity`, `unit`, `location`, ISO `expiryDate` of local midnight) are read by `readPantryBatch`: a counted unit's `quantity` is the package count (`packageSize` null); a measured unit's `quantity` is one package of that size (`packages` 1, or 0 when the quantity was 0); the ISO expiry becomes its day in the household zone. A legacy counted `quantity` is not clamped (a count above 10,000 reads in full); a legacy measured `quantity` above 100,000 reads as `needsRepair` (0 packages, never cleaned up). The first v2 write to a legacy document writes absolute upgraded values computed from a re-read inside a transaction (`planLegacyUpgrade`, online only; above 10,000 it splits into extra batches in the same transaction), since it has no `packages` to increment; afterwards changes are increments. The add-merge and the shopping handoff upgrade a legacy target the same way from their own transaction's read. An older page that later edits a v2 document changes only `quantity` (and may write an ISO expiry), which v2 pages ignore in favour of `packages` until the next v2 edit; the migration rewrites such expiries.
- **Merge key** `nameKey + location + packageSize + unit + expiryDate` (`pantryMergeKey`): batches that differ on any of these stay separate documents, so incompatible units never merge (SH-23a). The tile groups a product's batches.
- `PantryItem` in `src/lib/types.ts` is the stored shape (v2 fields optional, legacy `quantity` optional).
- `PantryItemUnit`, `pantryItemUnitCategories`, and `PantryItemLocation` define supported units and locations.
- Recipe results are not persisted.
- Purchases reach the pantry only through Shopping's **Put away** (S5, the `putAwayAndClear` server action, `applyTrip` in `src/lib/server/shopping-trips.ts`): one Admin SDK transaction, idempotent by a client-generated trip id, that re-reads every chosen shopping item and credits only those still exactly the purchase the member confirmed (same name, quantity and `purchaseOpId`, still purchased, and not already credited: `pantryCreditedAt` newer than `purchasedAt`, or its `purchaseOpId` credited by an earlier trip that is not undone). A purchase is a batch counted in `items` with no package size, on the chosen shelf and with the chosen date-only expiry (or none), named as the pantry stores it (a shopping name over 120 characters is cut by `clampPantryName`, and the merge key and the trip's recorded effect use that stored name, so its Undo recognises the batch), so it merges only into an existing batch with that merge key (same name, case-insensitive, same shelf, unit `items`, no size, same expiry, a legacy ISO expiry compared as its day in the household's zone, which the server reads from the household document in the same transaction, as does the trip's Undo); same-name purchases with the same shelf and expiry are combined. Merge targets are planned from a pantry read made just before the transaction and re-read and re-checked inside it (`tripTargetStillValid`); an entry deleted, moved, renamed, re-dated or re-unitted meanwhile gets a new batch instead. A v2 target has `packages` and `quantity` raised with `increment()`s; a legacy target is upgraded with absolute values from the transaction's own read (`planLegacyUpgrade`). A target is topped up to 10,000 packages and the rest, or a new purchase above 10,000, is split across new batches of at most 10,000 each (`tripPlanWrites`, using `fillBatch`/`splitPackages`); nothing is clamped. New batches carry `addedByUid`/`updatedByUid` (the member who put the trip away) and `updatedAt` (server time). A trip whose items need more than 450 document writes (`MAX_TRIP_WRITES`: pantry, shopping items, usuals and the trip itself) applies the longest run of its items that fits and leaves the rest on the list for another trip (`deferred`); nothing is written beyond the limit. Each pantry change is recorded on the trip (`pantryEffects`: document id, created / incremented / upgraded, packages added) for its Undo, which subtracts exactly those packages from the batch as re-read then (never below zero), leaves a batch someone renamed, moved, re-dated or removed since, and deletes a batch the trip created when it would be empty and nobody has touched it since (same `updatedAt` and writer as the trip); a batch left at zero is hidden and cleaned up like any used-up batch. Shelves are guessed from the shopping category (Dairy, Meat, Produce, Deli, Seafood, Eggs to Fridge; Frozen to Freezer; everything else to Pantry), except shelf-stable produce (onions, shallots, garlic, potatoes, sweet potatoes, yams, bananas, plantains, squash, pumpkins), which stays in the Pantry (SH-23c); the put-away dialog sets each item's expiry from its shelf (Fridge +7 days, Freezer +3 months, Pantry none; chips +3 d, +1 w, +3 mo, No date; SH-30, SH-23b) and every batch's expiry stays editable in the pantry's edit dialog.

**Migration M2** (`scripts/ops/migrate-pantry-v2.mjs --project <id>`; dry run by default with counts only, `--apply` to write, `--firebase-tools-login` for auth as in `./credentials.mjs`): converts legacy documents to v2 (derived values, `nameKey`, the ISO expiry as a household-zone day using `households/{id}.timeZone`, default America/Chicago, the dual-written `quantity`, `schemaVersion: 2`) and rewrites ISO expiries on v2 documents. Each write is an update with the document's last update time as a precondition, so a member's concurrent edit is never overwritten: the document is re-read and the mapping recomputed (up to three tries; the rest is counted and left for a re-run). Deleted documents are skipped, converted ones are left alone, so it is resumable. It does not set `updatedAt` or attribution. Stock is never truncated: a legacy counted document above 10,000 (the rules' limit per batch) is split with `splitPackages` (the script's twin of the app's), the document keeping the first 10,000 and new batch documents `<id>-v2-<n>` (the legacy fields copied with the v2 values and their own count) taking the rest, all in one atomic batch with the guarded update, so a retry never splits twice; a legacy measured document above 100,000 (one package's limit) is not converted and is counted as "left unconverted" for a person to fix before a re-run. The mapping is the JavaScript twin of `readPantryBatch` (`tests/unit/pantry-v2-migration.test.ts` checks they agree).

Edits are `updateDoc` of the batch's full v2 fields; package changes are increments (one tap's changes in one write batch, or in one transaction when a legacy batch is involved); an add that merges is a transaction (re-read, then the increment, or a new batch); new batches are `setDoc` (or `transaction.set`) with `addedByUid`. Every one of these writes stamps `updatedByUid` (the writer) and `updatedAt` (server time), as the S4a rules require. Editing a batch's name does not rename its Firestore document ID. Offline, writes are queued (`awaitWriteUnlessOffline`); the empty-batch cleanup, the list merge and any change to a legacy batch need a connection.

## Authentication, Roles, and Security

The UI requires an authenticated user and derives `householdId` from `useAuth`. Firestore access is covered by the approved-household-member fallback rule in `firestore.rules`; pending `newuser` members are excluded and legacy `households.memberEmails` membership is supported.

Firestore rules require `shopping.view` to read, `shopping.edit` to create or update and `shopping.delete` to delete `pantry-inventory` documents.

**Rules stage S4a (this release, compatible with older pages):** `validPantryFields` allowlists `name` (1 to 120 characters, the recipe flow's limit, required on create; an older, longer name stays on its document and is refused only when rewritten), `nameKey` (≤500), `location` (Pantry, Fridge, Freezer), `unit` (the twelve `PantryItemUnit` values), `packages` (number 0 to 10000, checked after `increment()`, so a "used one" can never go below zero: a second tap on a batch someone just emptied is refused and rolled back with a `toastError`), `packageSize` (null or above 0 and at most 100000), legacy `quantity` (number 0 to 100000), `expiryDate` (null, `yyyy-MM-dd`, or a legacy ISO string of at most 40 characters), `barcode` (≤128 or null), `addedByUid` (only on create, and only the writer's uid; `pantryAdderUnchanged` keeps it fixed and not removable on update), `updatedByUid` (the writer) and `updatedAt` (`request.time`), and `schemaVersion` (2). On every update the resulting batch is checked (`pantryUpdateAttributed`), not only the changed keys: an update that changes any v2 field (such as `packages`) or removes a field must leave `updatedByUid` equal to the writer and `updatedAt` equal to the request time, so nobody can change a count under another member's `updatedByUid` or an old `updatedAt`, or strip the attribution. The one exception in stage S4a is an older page's update (`pantryLegacyOnlyUpdate`): it changes only `name`, `quantity`, `unit`, `location` or `expiryDate` and removes nothing, and is allowed on legacy and v2 batches alike, leaving `packages` and the v2 attribution as they were (v2 pages read `packages`, not `quantity`); stage S4b removes this exception. Only written keys are checked (`writtenKeys()`), so legacy documents and older pages keep working. **Stage S4b (a later release, after M2 has run and one update cycle has passed):** accept only a date-only or null `expiryDate` (drop the ISO branch of `validPantryExpiry`), so no ISO expiry can be written again. Release order: S4a rules → this client → M2 (`--apply`) → S4b rules.

Pantry item names are at most 120 characters (`PANTRY_NAME_MAX` in `src/lib/shopping/pantry-batches.ts`, the recipe flow's limit). The item form says "Keep the name to 120 characters.", and every pantry writer stores names through `clampPantryName` (whitespace collapsed, cut to 120 without splitting a character), so a longer shopping item name still saves when it moves to the pantry.

The UI follows the same permissions and hides what a member cannot do: Add Item, Edit, Used one, One more, Out of this, the move handles and "Put on a shopping list" need `shopping.edit`; Delete, bulk selection and Delete Selected need `shopping.delete`; "Delete & Add to List" needs both. Members without `shopping.view` see an explanation on `/shopping` instead of the tabs.

## Invariants and Failure Behavior

- Recipe generation rejects fewer than two items; the button is disabled until two usable stock lines exist (SH-10e, the same count the server checks).
- Adding a missing ingredient never adds a second needed item of the same name online (it gets one more); offline nothing merges and a new item is saved, as for every Shopping add.
- Invalid or missing Firestore dates are handled defensively for display.
- A failed, timed-out, rate-limited, refused, or malformed recipe request leaves inventory unchanged, keeps the dialog open, reports a sanitized error (the AI action's public message for `AiClientError`, otherwise `friendlyError`), and offers retry.
- Delete-and-return-to-shopping is not atomic; a shopping failure can occur after inventory deletion.
- Slug-derived IDs can collide for names that normalize to the same slug.
- Pantry, fridge, and freezer mobile lists must keep item actions and long names within the document bounds at 360 px and wider supported viewports.
- Expiry styling (tilt, glow, frost, lift) is applied to a decorative layer or the whole tile as a state change, never as a hover effect; nothing moves on hover. Expiry states use household-zone calendar days (`daysUntilDay` from `useHouseholdToday`): `soon` is today through three days out.
- Every move has a non-pointer path (keyboard, tap-then-Move here, menu) and is announced through a polite live region.
- A tile's expiry pill ("Expires tomorrow", "Expired yesterday", "In the recipe") is 12 px text in its status colour on a 10% tint of that colour, a pair checked at 4.5:1 in every theme (`tests/unit/theme-contrast.test.ts`, `tests/unit/shopping-trip-mode.test.ts`; SH-26f). The recipe dialog's decorative icons are hidden from assistive technology (SH-26e).
- Errors use `toastError`, so raw Firebase text never reaches users.
