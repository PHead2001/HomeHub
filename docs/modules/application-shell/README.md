# Application Shell and Dashboard

## Purpose and Scope

This module owns the root layout, global providers and overlays, primary navigation, dashboard, the shared visual shell and design foundation (color tokens and theme presets, surfaces, focus ring, motion system, route loading skeletons, ambient background, sound/haptic feedback API), and global error/toast placement. It does not own feature data or feature-specific authorization rules.

## User-Facing Capabilities

- Signed out, `/` is a landing page: a sample "living house" that assembles as you scroll while each module's tile flies into its room, what HomeHub does, and one "Sign in with Google" button at the end. No module navigation and no data reads.
- Signed in, `/` is the dashboard: the household name and date, the living house hero (rooms with overdue, due and finished chores; pets fed or waiting by the bowl; fridge stock and expiring food; HVAC and car service), a one-line morning brief, and a bento grid of live tiles (today's chores progress ring, shopping with the first three items, pets' fed status, next maintenance countdown, food expiring soon, unread notifications, household streaks, and the weather when the member turned live weather on). Clicking a room opens Chores filtered to that room. An optional, per-user live weather switch on the house draws rain, snow or a sun glint over the house and the shell. Everything comes from exact household data the member can view and is shown by default; nothing needs a "Generate" click.
- Hover or keyboard-focus a room, a tile, a linked phrase in the morning brief or a notification for 400 ms to see a peek card with its details (pointer devices only). `PeekLink` makes any link peekable.
- Time-of-day lighting tints the shell and the house (dawn, day, dusk, night; the attic window lights up in the evening). Seasonal touches (snow, a pumpkin, a lit tree) can be switched off on the house. Easter eggs: the Konami code starts a 10 s disco on the house, long-pressing a pet makes it hop, and the roof turns gold after 100 completed chores.
- Open Home Wrapped from the dashboard: a swipeable story of the household's year (chores done, chore champion, most-bought item, pet meals logged, upkeep spend) that can be shared as an image with first names only.
- Ask AI to rewrite the morning brief with the small sparkle button next to it (H04). The rewrite comes from the overview flow's exact, permission-filtered facts, shows with an "AI-written" marker, HomeHub's exact counts and its suggested priorities, and "Show plain brief" goes back. The deterministic brief is always the default; there is no separate AI Overview section or "Generate Overview" button any more.
- Press Ctrl/Cmd+K (or "/", or the header search button) for the command palette: search pages, chores, lists, items, pets and maintenance records, or type a sentence ("milk and eggs to groceries", "fed Maple", "vacuum Friday for Sam", "trash every Tuesday for Sam", "oil change 48,200 miles") to quick-add with a preview and a Confirm step: it adds items, logs feedings, creates one-time and repeating chores (assignee and room) and logs maintenance (odometer reading, for the chosen vehicle). A sentence the parser cannot read can be read by AI on request ("Read … with AI"), with the same preview and Confirm. A mic button adds by voice where the browser supports speech recognition.
- Keyboard shortcuts: `N` new chore, `A` add shopping item, `F` log feeding, `G` then `H`/`C`/`S`/`P`/`M`/`K`/`N` to jump to Home, Chores, Shopping, Pets, Maintenance, Calendar or Notifications, and `?` for the cheat sheet. They never fire while typing. Tooltips on the header search, the header links and the dashboard's quick-add buttons (Add a chore `N`, Add a shopping item `A`, Log a feeding `F`) show the keys from the same map.
- Navigate through permission-filtered desktop header links and avatar actions. The current page's header link is shown in the foreground color with an accent underline that slides between links.
- On phones, navigate with a fixed bottom tab bar (Home, Chores, a raised quick-add button, Shopping, Pets, More) and a More sheet (Maintenance, Calendar, Automation, Household, Barcode Library, Profile). The quick-add button fans out Chore, Item, Feeding and Maintenance; long-press opens voice add.
- The desktop header lists Calendar next to Chores (gated by `chores.view`, like Chores).
- Open profile, household management, barcode library, notifications, and logout controls.
- Receive create/join-household and pending-approval overlays.
- See the chosen theme (Dark, Light or System mode with curated presets) from the first paint, without a flash of the default theme.
- Route changes crossfade page content with an 8 px settle through the View Transitions API (a CSS fade where it is missing), and shared elements morph between pages; the header and tab bar stay put. Tab switches fade the new panel in (opacity only), and lists and tiles enter staggered; every route shows a layout-matched skeleton while it loads, and navigations slower than 150 ms show a thin top progress bar.
- With Reduce motion (system setting or the in-app switch), every transition renders its end state instantly.
- See the HomeHub brand mark in the header, browser tab, and installed app icon; the header mark plays a one-time intro on the first load of a browser session.
- Install HomeHub to a phone or desktop home screen (standalone window, splash from the manifest colors and icon), with long-press shortcuts for "Add to shopping", "Log feeding" and "My chores".
- Share links or text into the installed app (handled by [Shopping Lists](../shopping/README.md)).
- Open the dashboard and shopping lists offline; other routes show a friendly offline page.

## Architecture and Data Flow

The root layout renders the color tokens for every theme preset and an inline theme script in `<head>`, the ambient background, then installs `AuthProvider`, `AppearanceProvider` (theme, motion preference and feedback settings, wrapping everything in motion's `MotionConfig`), the navigation progress bar, the glow pointer tracker, the cross-route morph listener, foreground push handling (`DeferredPushNotificationManager` loads `PushNotificationManager`, with Messaging and the service worker registration, after `load` and idle; `DeferredToaster` mounts the toast viewport the same way, and toasts raised earlier wait in the toast store), Firebase error reporting, password-change handling, household-state overlays, the header, and global toasts around every route. `src/app/template.tsx` wraps page content in `PageTransition`; because templates remount on navigation and layouts do not, only page content animates. The dashboard (see "Dashboard" below) reads live household facts in the browser and keeps the on-demand `HomeAiOverview`; it makes no overview request on page load and does not persist results. The module carousel (and its arrow that overlapped the first card's title) was replaced by the living house and the tile grid. `CommandCenter` (palette, shortcuts, help) is mounted once after the tab bar and loads `CommandPalette` as its own chunk only for members who can use it; the header loads `NotificationBell` and the motion-driven nav underline the same way (a same-size placeholder first). Signed-out pages therefore load only the app, Auth and the shell, with no Firestore, Storage, Messaging, App Check or animation library before first paint (see [Firebase Platform](../firebase-platform/README.md), "Split initialization"), and `TimeOfDayTint` sits behind the shell next to the ambient background.

Below the `md` breakpoint, `MobileTabBar` renders a fixed bottom navigation bar inside `HouseholdManager`, after `<main>`; at `md` and wider it is hidden. Primary tabs are Home, Chores, Shopping, and Pets; a More tab opens a bottom sheet with Maintenance, Calendar, Automation, Household, Barcode Library, and Profile. A raised "Quick add" button sits in the middle of the bar (`aria-haspopup="menu"`, `aria-expanded`). Tapping it fans out a menu (`role="menu"`, named "Quick add") of the actions the member may use: Add chore (`chores.create`), Add shopping item (`shopping.edit`), Log feeding (`pets.addLogs`) and Log maintenance (`maintenance.createLogs`, opens `/maintenance`). The first three open the command palette pre-filled ("chore ", "add ", "fed "). Escape or a tap outside closes the fan; a 500 ms long-press opens the palette and starts voice input. The active tab icon fills and bounces once. The active tab or sheet item is marked with `aria-current="page"`, and More is highlighted when the current route is one of its items. The bar is not rendered for users without a household, without a loaded member record, or with role `newuser`.

The root `viewport` export sets `viewportFit: 'cover'`. The tab bar pads its bottom by `env(safe-area-inset-bottom)` and the More sheet adds the same inset to its bottom padding, so content clears the home indicator. On phones `<main>` reserves `calc(4rem + env(safe-area-inset-bottom))` of bottom padding (the 4rem bar height plus the inset) so page content is not hidden behind the bar; `md:pb-0` removes it on larger screens. This padding applies whenever `<main>` renders on a phone, including when the bar itself is hidden.

### Brand mark

`Logo` renders the HomeHub mark as inline SVG: a house whose roof is two connection edges meeting at a hub node, with smaller nodes at the eaves, plus two windows. It uses `currentColor`, defaulting to `hsl(var(--primary))`, and fixed `width`/`height` from its `size` prop so it never shifts layout. `variant="wordmark"` adds the HomeHub name; the mark is decorative (`aria-hidden`) unless a `title` is passed. The header renders `<Logo size={24} animated />` next to its own HomeHub text.

With `animated`, CSS keyframes in `logo.module.css` play once: the roof draws on with `stroke-dashoffset` (0-560 ms), the nodes pop in (380-680 ms), and the windows light up (620-900 ms), 900 ms in total. The base styles are the finished mark, so skipping the animation always shows the end state. An inline script rendered right after the SVG records `homehub:logo-intro-played` in `sessionStorage` and, on later loads in the same tab session, marks the SVG `data-intro-played` before it paints, so the intro never replays. The animation is also disabled by `@media (prefers-reduced-motion: reduce)` and by `html[data-motion="reduce"]` (the in-app motion setting contract). Nothing waits on the animation.

All static brand assets come from the same artwork constants in `logo-artwork.ts`. `scripts/brand/render-icons.mjs` rasterizes them with `sharp` into `src/app/icon.svg` and `src/app/favicon.ico` (16/32/48 px, rounded navy tile), `src/app/apple-icon.png` (180 px, full bleed), `public/icons/icon-192.png` and `icon-512.png` (purpose `any`), `public/icons/maskable-512.png` (full bleed, mark inside the 80% safe zone) and `public/icons/shortcut-96.png`. `public/icons/badge-96.png` (the push notification badge: the house glyph alone in white on transparency, used by Android as a monochrome mask) is not produced by that script; it was derived from `icon-192.png` by keeping the accent-colored pixels, so regenerate it the same way if the mark changes (see [Notifications](../notifications/README.md)). Raster icons use the static hex values `BRAND_BACKGROUND_HEX` (`#020817`, the dark `--background`) and `BRAND_ACCENT_HEX` (`#4bb9ae`, the current `--primary`); regenerate and commit them if either token changes. Next's file conventions emit the favicon, SVG icon and apple-touch-icon links.

### Installable app (PWA)

`src/app/manifest.ts` is served at `/manifest.webmanifest` (Next adds the link tag): `id`/`start_url`/`scope` `/`, `display: standalone`, `background_color` and `theme_color` `#020817` (matching the dark default and the `viewport.themeColor`, so the splash blends into the first frame), the icons above, three shortcuts (`/shopping?quickAdd=1`, `/pets?feed=1` (opens the Pets feeding picker, see [Pets](../pets/README.md)), `/chores`), and a GET `share_target` to `/share` with `title`, `text` and `url`. The root `metadata` adds `applicationName` and `appleWebApp` (capable, title, `black-translucent` status bar) for iOS home-screen launches.

### Service worker contract

HomeHub has exactly one service worker, `/api/sw` with scope `/` (`src/lib/service-worker.ts` holds the URL and scope). It combines Firebase Messaging push handling (see [Notifications](../notifications/README.md)) with the offline app shell. Production builds register it from `PushNotificationManager` after the window `load` event; development builds and the Playwright suite (which runs the dev server) do not auto-register, so cached pages never mask code changes or intercept test traffic, though enabling push still registers it.

- Install precaches the page shells for `/`, `/shopping` and `/offline`, every `/_next/static/` asset those pages reference, and the manifest and icons, then calls `skipWaiting`. Activate deletes `homehub-*` caches from other versions and claims open pages. The cache names carry `SHELL_VERSION` in `route.ts`; bump it when the caching logic or precache list changes.
- Navigations are network first. A successful same-origin response for a shell route refreshes its cached copy. If the network fails, the cached shell for that path is returned (query strings are ignored, so `/shopping?quickAdd=1` works offline), otherwise the cached `/offline` page, otherwise a small inline offline page.
- `/_next/static/` assets are cache first (they are content-hashed); the unhashed manifest and icons are served from cache and refreshed in the background. The static cache is trimmed to 300 entries.
- The worker ignores non-GET requests, other origins (Firebase, Google APIs, CDNs), `/api/*` and `/__/*`. React Server Component fetches go to the network; when they fail offline, Next falls back to a full navigation, which the worker serves.
- Cached shells are client-rendered and contain no household data. Offline data comes from Firestore's persistent cache ([Firebase Platform](../firebase-platform/README.md)).

`/offline` is a static page with links to Shopping and Home.

### Navigation

The desktop header (`<nav aria-label="Main">`) marks the current link with `aria-current="page"`, the foreground color and an accent underline (a motion `layoutId="header-nav-underline"` element) that slides to the new link on navigation. Header and phone tab bar share `isActiveRoute` from `src/lib/navigation.ts`.

Header and phone tab bar navigation derive visibility from effective permissions. The header also has a "Search or quick add" button (opens the palette), the notification bell named "Notifications" (plus the unread count when there is one, which ticks to new values) and the "Account menu" button with the member's shared gradient `MemberAvatar` (photo when there is one; decorative, the button carries the name). The search button and the header links with a `G` shortcut carry `ShortcutHint` tooltips through `LazyShortcutHint` (`src/components/ui/lazy-shortcut-hint.tsx`): the tooltip code loads only once a signed-in header renders them, so the signed-out landing never downloads it before first paint, and until then the control already has its `aria-keyshortcuts`. `ShortcutKeys` lives in its own tooltip-free file (`shortcut-keys.tsx`) for the same reason (the cheat sheet in the first-paint command center uses it).

`tailwind.config.ts` sets `future.hoverOnlyWhenSupported`, so every `hover:` style applies only on devices with a hovering, fine pointer. On phones a tapped button no longer keeps a stuck hover fill (the audit's "Refresh button keeps a filled look after click").

### Dashboard

`src/app/page.tsx` renders, while auth loads, both `Landing` and `DashboardSkeleton` in the server HTML; an inline script picks one before first paint from the device hint `localStorage["homehub.session"]` (`"1"` only, written by `TimeOfDayTint` on every route once auth resolves, removed on sign-out; `src/lib/dashboard/session-hint.ts`). Without the hint the landing hero paints at once instead of waiting for Firebase Auth; a signed-in member on a device without the hint (first visit) sees the landing until auth resolves. It shows `Landing` when signed out (the same element, so nothing remounts), and the dashboard (`src/components/dashboard/dashboard.tsx`, loaded with `next/dynamic` as its own chunk so the landing page never downloads it) otherwise. `useDashboardData` (`src/lib/dashboard/use-dashboard-data.ts`) subscribes read-only, with `onSnapshot`, to the sections the member can view: `chores.view` (rooms, chore templates, completed chores, the household's membership records and the `chore-settings/preferences` leaderboard setting for streaks, open chores, chores with today's `originalDueDate`, and chores completed today found by both completion timestamps: `completedAtServer >=` local midnight as a Timestamp, and the legacy `completedAt >=` its ISO string; single-field range queries, merged by document id, with readiness and failure tracked for each), `shopping.view` (lists, each list's items, pantry), `maintenance.view` (home assets, vehicles, and maintenance logs dated within the last 92 days for the home health score), `pets.view` (pets, and each pet's 12 most recent feedings per date shape) and `notifications.view` (the bell's query, built by `notificationWindowQuery` in `src/app/notifications/notification-query.ts`: the last 7 days, newest 30; for a member who lacks any module view permission it adds `where('category', 'in', ...)` with the categories they may see plus `system` and `general`, so the 30 are counted after that filter). The notification query therefore also depends on `automation.view`. State is keyed by household, member, day and the view permissions (`chores`, `shopping`, `maintenance`, `pets`, `notifications`, `automation`), so a change never shows old data. No model is called and the AI quota is not used.

Pure functions in `facts.ts` turn the documents into exact facts by reusing each module's own rules, so the dashboard always agrees with the module's screen:
- Chores: `choreDueKey`, `completionInstant` and local day keys from `src/lib/chores/dates.ts`, and missed instances of a repeating series fold into the latest one with `collapseMissedRecurring` (templates with a valid recurrence), exactly as the Chores To Do list counts them. "Open for you" on the Today tile counts the viewer's chores that are overdue or due today, and a room's "coming up" counts the next 7 days (`UPCOMING_DAYS`). The hourly job generates 30 occurrences of each repeating chore ahead of time, and those are not today's work.
- Maintenance: `buildMaintenanceReminders` (shared with the Maintenance page, the calendar and the hourly reminders) in the household's time zone. Retired assets and retired or sold vehicles are excluded, "due soon" is 14 days or 500 miles, an expired warranty is not a task, and each item links to the module's own deep link (`?asset=…&schedule=…`, `?vehicle=…`). Each item keeps the reminder's own status and its trigger (`reminderTrigger`: the due date, or the mileage threshold when mileage made it due), and every status shown on the dashboard (the Next maintenance tile, its peek, the HVAC and car names, the brief) uses Maintenance's copy helpers: `reminderStatusLabel` ("Overdue", "Due today", "Expires soon") and `reminderDueDetail` ("Due Aug 1, 2026 · 2 weeks ago", "At 49,000 mi · 1,200 mi over"). Nothing recomputes a status from dates, so a service overdue by mileage with a future date never reads as a negative number of days.
- Pets: feedings are read in both date shapes (Timestamps and older ISO strings, which Firestore orders separately), merged with the Pets module's `newestFirst`, and judged with its `feedingPlan` and `feedingStatus`. A pet is fed when today's target is met ("2 of 2 today"); the house and tile use its `feedingCountLabel` and `feedingHeadline` wording.
- Pantry: Shopping's `daysUntilExpiry`.
- Notifications: `deduplicateNotifications`, then `activeBellNotifications` with the same category check as the bell (`canView` from the member's view permissions; a module's notifications need that module's view permission, `system` and `general` need none) and its 10-item cap, so the tile and the bell badge always match.

Loading, failed and empty are kept apart (`assembleDashboardFacts` in `src/lib/dashboard/assemble.ts`). A section's facts exist only once every listener it needs has answered: all six chore listeners, every list's items, pantry, both maintenance collections, pets, notifications. A section whose listener failed is listed in `facts.unavailable`; its tile reads "Unavailable right now" (a dashed card that links to the module), the house says "Rooms are unavailable right now" for chores, and nothing shows a failed read as "nothing due", "all fed" or 0. A pet's feeding claim needs both date-shape queries to have answered without error; otherwise its `fed` is null, the house shows no bowl and no wandering, and the tile and its link name use the Pets module's "Feeding status is unavailable right now." The brief never says "Nothing needs you" when anything is unavailable, and adds "Some sections could not be loaded." to an otherwise normal brief. Home Wrapped loads each section on its own; a failed one is left out and named on the last card, never counted as zero.

Links use each module's URL scheme (`src/lib/dashboard/links.ts`): Shopping `?list=<id>` and `?tab=pantry`, Maintenance `?tab=reminders` and `?tab=logs`, Pets `/pets/<id>?tab=feeding`.

- **Living house** (H01): an isometric-style cutaway in inline SVG and CSS (no WebGL, no library). `layoutHouse` (`src/lib/dashboard/house-layout.ts`) places up to six rooms on a grid of floors (one floor up to three rooms, 2x2 for four, three wide for five or six; empty cells are plain wall), with a receding side wall, a roof prism and each room's inner walls and floor for depth. The SVG is `aria-hidden`; each room is an HTML link laid exactly over its rectangle (`house-room-<id>`, `data-room-status`, name "Room: summary"), so the click target never moves while the SVG room lifts on hover or focus. Rooms are sorted by name, then "+N more"; chores without a room go to "Around the house" (id `general`). Chores whose room no longer exists go to an "Unknown Room" tile (the Chores page's label), so their work is never dropped; a chore counts once per tile. When there are more than six rooms, the ones needing attention (overdue, then due today) are shown first. Chores of someone who is no longer a member still count in household totals. A room is `overdue` (amber glow and a count badge), `due` (a dot) or `clear` (a one-time sparkle when something there was finished today). Keyboard: Tab, or the arrow keys, Home and End, move room by room (`roomNeighbor`); an `sr-only` sentence summarizes the scene.
  - Clicking a room links to `/chores?room=<roomId>` (`choresRoomHref`; `general` included, the Unknown Room bucket opens `/chores`). The stage zooms toward the room for 420 ms, the room's visual takes the view-transition name `room-<roomId>` (`roomMorphName`: sanitized like `sharedId`, no suffix, matching the Chores page's `roomSharedId`) and `useMorphNavigation` runs the route morph. Modified clicks, and every click under reduced motion, are plain navigations with no zoom.
  - Pets (`placePets`): a pet that met today's feeding target walks between rooms on its floor (three waypoints, a 24 s CSS transform loop); a pet not fed on schedule sits by its bowl, in the room named Kitchen when there is one, else a ground-floor room; a pet whose feeding history is unavailable rests in a room with no bowl and no walking. Their links are fixed chips in the yard strip (`house-pet-<id>`, `data-fed`), because clickable targets must not move.
  - The fridge fills by the number of Fridge items (10 is full) and pulses when food expires within 7 days. HVAC (assets whose category or name matches HVAC, furnace, AC, heat pump or boiler) and the car (any vehicle item due, or a vehicle that needs attention) show a wrench.
  - Home health (H10 mirrored): a small ring and score next to the title from Maintenance's own `computeHomeHealth` (household time zone), named with `healthSummaryText` and linked to `/maintenance?tab=overview`. Hidden when there is nothing to score or the logs could not be read.
  - First paint does only pure layout math: no images, fonts or extra requests.
- **Time of day** (H02): `phaseWeights` blends dawn, day, dusk and night with raised-cosine weights that sum to 1 and change continuously; they are recomputed every minute. The weights become `--tod-*` properties that tint token colors (`--member-5` rose, `--primary`, `--warning` amber, `--member-3` indigo). The shell tint is scaled by `--ambient-intensity` and is not rendered under reduced motion. The attic and room windows light from dusk.
- **Live weather** (H02, opt-in): the "Live weather" switch on the house is per user, saved to the member's own profile as `users/{email}.preferences.weather = { enabled, city }` (`preferences` is already on the profile self-update allowlist, so no rules change). Households have no city, so a "City for weather (optional)" field next to the switch is saved per user with it. `src/lib/dashboard/weather.ts` calls Open-Meteo (free, no key): the geocoding endpoint with only the city name, then the forecast endpoint with only the returned coordinates (`credentials: 'omit'`, no referrer). No other household data is sent. Reports are cached per device in `localStorage["homehub.dashboard.weather"]` for 30 minutes (one city) and shared by every consumer (`useLiveWeather`). Any failure hides the weather with no error UI. WMO codes map to rain streaks (drizzle, rain, showers, storms), snow, or a sun glint (clear or partly cloudy by day), drawn by `WeatherLayer` over the house and behind the shell: CSS only, loops of 20 s or more, very low contrast, paused while the tab is hidden, not rendered under reduced motion.
- **Seasons and easter eggs** (H27, H29): an October pumpkin on the lawn, a December lit tree, January and February snow; the switch on the house is stored in `localStorage["homehub.dashboard.seasonal"]`. The Konami code (captured before the shortcut listener, so its final "a" does not open quick add) runs a 10 s hue drift. A long-press on a pet chip, or Space while it has focus, plays a short synthesized bark, meow or chirp (`playPetSound` in `src/lib/dashboard/pet-sound.ts`, Web Audio, no files) only when the member's Sound setting is on (the same `getFeedbackSettings` switch as `playFeedback`), a haptic tick when Haptics is on, and a hop of the pet in the house (not under reduced motion). A count query of completed chores turns the roof gold at 100.
- **Morning brief** (H04): `buildMorningBrief` builds one sentence with links: your chores today or overdue, a pet waiting to be fed, food expiring within 2 days or already expired, overdue or due-today maintenance, otherwise shopping items, otherwise a calm line. It types out once per day (`localStorage["homehub.dashboard.briefTyped"]`, at most 1.2 s, any key or tap skips) over an invisible copy that reserves its space; screen readers get the whole sentence. Each linked phrase is a `PeekLink` whose card lists the same facts (your next chores, the pet's meals today, the nearest expiring food, the maintenance items, list counts; `BriefSegment.peek`). ### Command palette and shortcuts

`CommandCenter` renders only for approved household members. No key handler acts while an input method editor is composing (`isComposingKey`: `isComposing` or `keyCode` 229): the palette input ignores Enter and the arrows, the palette does not close on that Escape, and shortcuts, the Konami listener, peek cards, the tab-bar fan and Wrapped's arrow keys do the same. It handles Ctrl/Cmd+K anywhere, and other shortcut keys only when focus is not in a text field and no dialog or menu is visibly open; closed overlays that stay in the DOM (the tab bar's aria-hidden quick-add fan, or the whole tab bar on desktop) don't count (`matchShortcut` and `isTypingTarget` in `src/lib/dashboard/shortcuts.ts`); `G` waits 1.2 s for its second key. Shortcuts for modules the member cannot use are neither handled nor listed. Other components open the palette or the cheat sheet through window events (`openCommandPalette`, `openShortcutHelp` in `src/components/command/events.ts`).

`CommandPalette` is a dialog titled "Search or quick add" with a combobox input and a listbox (the project has no cmdk dependency). Each open remounts it and loads a read-only index (members, lists, needed items, open chores, pets, assets, vehicles) for permitted sections. Results are grouped: Quick add, Chores, Shopping, Pets, Maintenance, then Go to (pages filtered by permission, with `G` hints), and enter staggered when the palette opens. The index also loads rooms (`chores.view`), active vehicles (not retired or sold) and home assets (not retired) for the parser. A shopping list or item result opens its list (`/shopping?list=<id>`).

`parseQuickAdd` (`src/lib/dashboard/quick-add.ts`) is deterministic and matches whole words only (pet names, list names, service words, "and"). Feedings name a known pet ("fed Maple", "Pixel ate 1 can"); the amount is read with the Pets module's `parsePortion` (".5 cups", "1/2 cup", "1 1/2 cups", "one can"), and a unit with an unreadable amount is rejected rather than guessed; "fed …" that matches no pet falls back to search. Explicit shopping verbs ("add", "buy", "need") and "to <list>" pick items and a list by name or type (default: the Grocery list); items are split on commas and the words "and", "&" and "+", then parsed by Shopping's own quick-add parser (counts, name casing, repeated names). Maintenance needs a service word or a mileage; a vehicle (nickname, make, model or "make model") or, without a mileage, a home asset named in whole words becomes its target ("for the Civic" is removed from the title). A name that fits more than one record (two Hondas, two "Furnace" assets) selects nothing: the intent keeps the name (`targetQuery`), the preview says "which Honda?" and keeps Confirm disabled until the member picks one. Chores need "chore" or "remind me to", a date ("tomorrow", weekdays, "next friday", "in 3 days", "Aug 20", "8/20"), a repeat ("every Tuesday", "daily", "monthly") or an assignee ("for Sam", "for me", "@sam": first name, full name or email name, case-insensitively; the phrase is removed from the task, and a name that fits several members leaves the assignee empty in the preview, which asks who it is for and keeps Confirm disabled until someone is chosen), and may name a room in whole words ("in the kitchen" is removed from the task, a bare "kitchen" stays). Bare words ("milk and eggs") are offered as a shopping suggestion only when search finds nothing. Anything else falls back to search.

AI fallback (H13): when the parser finds nothing, or only a bare-words shopping guess, for something that reads like a sentence (`shouldOfferAiParse`), the palette offers "Read “…” with AI" (first when nothing else matches, otherwise last, so Enter never spends an AI request by surprise). Choosing it calls `parseCommand` (`src/ai/flows/parse-command-flow.ts`) with the sentence, today's date and display names paired with opaque references (`m1`, `r1`, `p1`, `l1`, `v1`; `buildAiParseRequest`), never emails or ids. A name that is or contains an email, or equals the member's email name (display names fall back to emails for members without one), is sent as a neutral label such as "Member 2" (`modelSafeName`, `src/ai/redact.ts`); the reference still maps the answer back. The answer is mapped back to the same intents (`intentFromAiParse`), filtered by the same permissions, and shown in the same preview card with "Read by AI. Check the details before you confirm."; "AI could not read that" otherwise. Each AI read belongs to one input revision (`createRevisionGuard`): editing the sentence (typed or spoken), opening another preview or going back makes it stale, and a stale read's answer, error and status are ignored, so an older, slower answer never replaces what the member is reviewing. Nothing is written until Confirm.

Choosing a quick-add result shows a preview; nothing is written until Confirm. Writes use the owning modules' contracts (`src/components/command/quick-add-actions.ts`): shopping items merge into a still-needed item of the same name with Shopping's `findMergeTarget` and `mergeIntoNeededItem` transaction (online only, as on the list), otherwise they are created with `buildShoppingListItem` and the share target's category resolution (the guarded, quota-counted categorizer; `Other` offline); feedings go through the Pets module's `addFeedingLog` (with who logged them), using the sentence's amount or else the pet's usual portion from `feedingPlan`, and the food type of the pet's latest feeding (`knownFoodType` of the newest entry across both date shapes, read offline-aware; Dry only without history) with no comment, the same fields as the Pets one-tap feed; one-time chores are a temporary task (`sourceType: 'temporary'`, no room) with a deterministic targeted "New chore assigned" notification, skipped when you assign yourself. The assignee follows the Chores rule (`choreCapabilities(...).canAssign`, i.e. `chores.assign`): with it you may pick any approved member; without it the chore is always yours, and a requested other member is replaced by you with a note in the preview. The preview card lets the member change the assignee and the room (one-time and repeating chores) and the vehicle or asset (maintenance); a mileage needs a vehicle, so with vehicles but none named, Confirm waits for one (the vehicle named in the sentence, else the household's only vehicle, is preselected from the loaded records (`defaultMaintenanceTarget`), even if they arrive after the card opens), and a reading below the vehicle's recorded odometer gets a note. Every preview waits for the palette index: no quick-add suggestion is offered until members, rooms, lists, pets, vehicles and assets have loaded, and the preview keeps Confirm disabled with a loading note while they load (`quickAddConfirmBlocker`), so no choice is made against half the records. Created documents always get a new id, a readable slug plus a Firestore auto-id (`quickCreateId`), so a create (even one queued offline, when the cached list of existing ids may be incomplete) never overwrites an existing template or log. Repeating chores (`chores.create`) are a `chore-templates` document shaped like the Chores "Add Chore" dialog's (`repeatingChoreTemplate`, with Chores' own `buildRecurrence`; monthly days follow the dialog's 1-28 rule: `normalizeRepeat` moves a day after the 28th to the 28th before the preview, which then says so, so the confirmed schedule is exactly the saved one, and `recurrenceFromRepeat` refuses any other day rather than changing it), plus the "new repeating chore" notification for someone else; the household upkeep (`syncHouseholdUpkeep`) then runs so the first instance appears at once. Maintenance logs (`maintenance.createLogs`) are a routine log dated today shaped like the Maintenance "Add log" form's (`quickMaintenanceLog`): `targetType` vehicle/home_asset/general, `vehicleId`/`assetId`, `title`/`item`, the mileage on vehicle logs only (without a vehicle it goes in the notes). The modules keep these writes inline in their screens and export no write helper, so quick add builds the same documents from the modules' own builders; Firestore rules check the same permissions. Shopping items follow Shopping's quick-add contract: every entry is its own write, settled independently and split with `splitSettled` (`shoppingAddOutcome`). Saved entries are confirmed with a toast; failed ones stay in the preview with an inline message (`quickAddRetryMessage` plus the `friendlyError` reason), so Confirm retries only those and never adds the saved ones twice. Each retry re-reads the list's needed items before merging. Chores (one batch with its notification) and feedings (one document) are single atomic writes. Every quick-add write goes through `awaitWriteUnlessOffline`: offline it is queued (it syncs on reconnect), the palette closes with "Saved offline" instead of waiting for a server acknowledgement, and a later rejection is reported with `toastError`; reads use the offline-aware helpers; the tab-bar fan only opens the palette or a page. After every confirmed write the palette dispatches the `homehub:data-changed` window event (`notifyDataChanged` in `src/lib/data-changed.ts`, detail `{ module, householdId, listId?, petId?, choreId? }`). Screens that load with one-time reads subscribe with `onDataChanged` and refresh silently: the Shopping list re-reads the open list (if it is the one changed) and the card counts with its offline-aware reads, and the Chores page re-runs its load. Pets uses live listeners, so it does not need it; maintenance logs dispatch `{ module: 'maintenance' }` for the Maintenance screen to refresh. Saves confirm with a toast and `playFeedback('add')`; failures use `toastError`.

Voice add (H14) uses the Web Speech API (`useVoiceInput`). The mic button is hidden where the API is missing, starts only on a tap, fills the input with the transcript and never submits by itself.

### Design foundation

**Color tokens.** Every color is an HSL channel token defined once per theme preset in `src/lib/theme/tokens.ts` (`PRESETS`) and emitted by `themeCss()` into `<head>` as `:root[data-theme="<preset>"]` rules (Midnight doubles as the `:root` fallback). Tailwind maps them to classes: surfaces `background`/`card`/`popover` (aliases `surface-base`/`surface-raised`/`surface-overlay`), `foreground`, `muted(-foreground)`, `secondary`, `primary` (brand accent for fills, links, selection), `accent` (a subtle hover/selected surface, not the brand color), status `destructive`/`success`/`warning`/`info` (each usable as text on any surface and as a fill with its `-foreground`), `border` (component boundaries, at least 3:1), `border-subtle` (decorative dividers), `input`, `ring`, `scrim` (dialog backdrops), `chart-1..5`, and `member-1..8` with `member-foreground`. Code outside the token files uses these classes or `hsl(var(--token))`, never raw color literals (the Google logo in the login dialog keeps Google's mandated colors). Non-color tokens live in `src/app/globals.css`: one radius scale (`--radius`, Tailwind `rounded-sm` to `rounded-2xl`), elevation shadows (`shadow-raised` for cards, `shadow-overlay` for dialogs, popovers, menus, sheets and toasts, each with a soft shadow and a 1 px inner highlight), the focus ring, and motion durations/easings.

**Presets and contrast.** Dark presets: Midnight (default), Hearth, Forest. Light presets: Light, Sunrise. Each preset sets its own foreground on filled colors (bright accents carry dark text in dark presets; deep accents carry white text in light presets), so filled buttons are AA (D01). In dark presets each elevation level is lighter than the one below. `tests/unit/theme-contrast.test.ts` (`npm run test:unit`) asserts at least 4.5:1 for every text pair (including accent, status and member colors as text on base/raised/overlay/muted surfaces and on their 10-15% tints) and at least 3:1 for borders, inputs, the focus ring and filled controls.

**Theme application.** `<html>` is server-rendered with `data-theme="midnight"` and class `dark` (`suppressHydrationWarning`). The inline script from `themeBootstrapScript()` (every embedded value goes through `scriptLiteral`, which escapes `<`, `>`, U+2028 and U+2029 so nothing can close the `<script>` tag) runs before first paint and before hydration: it reads `localStorage["homehub.appearance"]`, resolves System mode with `prefers-color-scheme`, sets `data-theme`, the `dark`/`light` class (for Tailwind `dark:` variants) and the `theme-color` meta, and sets `data-motion="reduce"` when reduced motion applies. It never throws; invalid stored values fall back to defaults. After hydration `AppearanceProvider` keeps `<html>` in sync (OS theme changes in System mode, other tabs via the `storage` event, profile sync). Switching themes uses the View Transitions API: the new theme is revealed in an expanding circle (`clip-path`, 520 ms) from the control that changed it; where the API is missing or motion is reduced the switch is instant.

**Focus.** One ring for every interactive element: a base `:focus-visible` rule draws a 2 px `--ring` outline with a 2 px offset (`--focus-ring-width`, `--focus-ring-offset`). Components do not add their own focus rings; menu items keep their highlight and inset the ring (`-outline-offset-2`).

**Surfaces and effects.** The header, phone tab bar and sheets use `surface-glass` (frosted overlay surface, mostly opaque so text keeps its contrast). `AmbientBackground` paints two slow aurora blobs (`--ambient-1`/`--ambient-2`) and a faint grain behind the shell at the preset's single intensity token `--ambient-intensity` (5-7%); loops are 32 s and 41 s, paused while the tab is hidden (`<html data-visibility="hidden">`) and static under reduced motion. Any element with the `glow-card` class (or `<GlowCard>`) gets a pointer-following spotlight and brightening border from the single delegated `GlowPointerTracker`; it runs only for `(hover: hover) and (pointer: fine)` and changes only pseudo-element layers, never the element's position. Dashboard cards and Maintenance asset/vehicle cards use it; `hover:bg-accent` is now a subtle surface lift instead of a solid teal fill (D10).

**Per-member colors.** `memberColor(uid)` (`src/lib/member-colors.ts`) returns a deterministic slot 1-8 (FNV-1a hash of the id) with `color`, `foreground`, `soft` tint and static Tailwind classes (`text-member-N`, `bg-member-N`, `ring-member-N`, `chip`, `softChip`). `memberColorMap(uids)` assigns collision-free colors for up to eight members regardless of input order. Member colors are AA as text on every surface and as chip fills in every preset.

**Motion system.** `motion` (pinned `14.3.1`, React 18 compatible) is the only animation library; import from `motion/react`. Budgets and helpers live in `src/lib/motion.ts` (`DURATION`, `EASE`, `SPRING_UI`, `SPRING_SNAPPY`, `STAGGER`, `staggerDelay`, `PAGE_ENTER`). Contract for all motion: when reduced motion is on (system `prefers-reduced-motion` or the in-app switch), `<html>` carries `data-motion="reduce"`; `useReducedMotion()` from `src/hooks/use-reduced-motion.ts` returns the combined value; `MotionConfig` disables transform/layout animation and zeroes default transitions; and global CSS collapses every CSS animation and transition under both `@media (prefers-reduced-motion: reduce)` and `:root[data-motion="reduce"]`. New CSS animations must honor both selectors.

- Route transitions (H12): one engine, `runRouteTransition` in `src/components/motion/route-transition.ts` (no `motion` import, so it is first-paint safe). `MorphRouteListener` (root layout) turns plain internal link clicks into View Transitions: it listens on `window` in the bubble phase, after `next/link` has started the navigation, so it never changes where a link goes; it skips modified clicks, other origins, query-only changes, links inside `data-route-transition="manual"` (use it when a click handler delays navigation, like the house's room zoom) and clicks a handler already turned into a morph. While a transition runs `<html>` carries `data-route-transition`, which names the page wrapper (`[data-page-transition]`, from `PageTransition`) `page-content` (in `globals.css`, not a CSS module, which would rename the ident so the `::view-transition-*(page-content)` rules never matched), the header `site-header` and the phone tab bar `site-tab-bar`: page content fades out in 120 ms and the new page fades in with an 8 px settle over `--duration-ui` (`globals.css`), and the header and tab bar are shown live so they never re-animate. Nothing is named otherwise, so the theme reveal still clips one whole-page snapshot. The old page is held until the URL (path and query) has committed, at most 500 ms after a link click (`ROUTE_TRANSITION`). The 8 px settle moves only the transition's snapshot, which takes no input; the real page never moves. Where the API is missing, and for back/forward, `PageTransition` plays an opacity-only fade in CSS (`page-transition.module.css`, `PAGE_ENTER` values) instead; during a view transition it adds no animation of its own. The first page of a session is not animated, and under reduced motion (system or in-app) nothing is held or animated.
- Tabs (D09): `TabsContent` (`src/components/ui/tabs.tsx`, used by every tab set) fades a panel in, opacity only, in 150 ms (`tabs.module.css`, `TAB_ENTER`) each time it goes from inactive to active. Radix keeps every panel element rendered (inactive ones are `hidden`), so the trigger is activation, not mounting: a MutationObserver on the panel's own `data-state` sets `data-tab-enter` before paint (`tabEnterChange`), which also works for uncontrolled tab sets whose wrapper does not re-render. The panel shown on first render does not animate, it is focusable at once, only opacity changes (its buttons are clickable at once and never move), and reduced motion shows it at once.
- Loading: every route has a `loading.tsx` built from `src/components/route-skeletons.tsx` that mirrors the page's container, header and first content block; skeletons expose a polite `role="status"` label. `NavigationProgress` shows a 2 px top bar only when an internal link navigation has not committed after 150 ms (it gives up after 10 s).
- Overlays: dialogs, alert dialogs, sheets, popovers, dropdown/menubar menus, selects and tooltips enter on a spring curve (`.ease-spring-enter`, `--ease-spring` is motion's `spring(0.25, 0.2)` as a CSS `linear()` easing, 220 ms; kept in sync by a unit test). Sheets open in 220 ms (previously 500 ms).
- `transition-ui` is the one scoped transition utility (color, background, border, opacity, shadow, transform at 150 ms); `transition-all` is no longer used.
- `Stagger` (`import { Stagger } from '@/components/motion/stagger'`) staggers its direct children with CSS keyed by position (`stagger.module.css`): the first at once, then 30 ms apart, items from the 12th on sharing the last delay (330 ms, `staggerItemDelayMs`), each an opacity-only fade-in over `--duration-ui` (items are often click targets, and clickable targets never move, so nothing translates the item box; `tests/e2e/shell-wave4.spec.ts` checks a staggered button's box is identical at the start and end of its entrance). Children keep their own classes (grid spans) and semantics (`as="ul"` with `li` children), the entrance needs no animation library, and children that mount more than `STAGGER_WINDOW_MS` (1.2 s) after it just appear (`data-stagger="settled"`); reduced motion shows everything at once. `StaggerItem` is an optional wrapper: a plain element, or a motion element when given motion props (`layout`, `exit`, `transition`, ...), so rows inside `AnimatePresence` keep their exit and layout animations (Chores' rows); `data-*` and DOM props pass through. `count` from the earlier motion-based API is accepted and ignored (deprecated). Used for the bento tiles, Notification Center rows, palette results and the household member list; `NumberTicker` ticks numbers in 400-700 ms and is safe inside any label: its element is one inline span whose only text node is the final value at every moment, so the surrounding `textContent`, `innerText` and accessible name read exactly ("To Do (1)", "1 of 2 today"), with no screen-reader copy, no hidden width copy and no grid or block box in the label. While a change counts, that text is drawn transparent and an inline `::after` (`content: attr(data-display) / ""`, alt text empty) paints the moving digits over it, padded to the final width with figure and punctuation spaces (`tickerFrame`), so it adds no text, no name and no width; a count that would be wider than the final value (12 → 9) changes at once. `animateOnMount` (default true, for stat tiles) counts up from 0 on first show; labels pass false and tick only on change. Reduced motion, SSR and pre-hydration show the final value. `tests/e2e/shell-wave4.spec.ts` renders the real component in a button, an accordion trigger and running text and checks exact text, `innerText` and accessible names mid-count and after.
- Shared-element morphs between any two elements (card → detail), through the same engine as route transitions. Contract: (1) name both ends with `sharedId(kind, id, part)` from `@/lib/motion` and spread `morphProps(name)` (or `style={morphStyle(name)}`) on each; names must be unique on the page at both ends, so a card that stays mounted beside its open detail passes `null` while the detail is open. (2) In the click handler, `e.preventDefault()` and `useMorphNavigation().navigate(href, { waitFor?, replace? })` (`@/hooks/use-morph-navigation`). It works across routes and for query changes on one route (`/shopping?list=…`, `/maintenance?asset=…`); `waitFor` (a `data-morph` name from `morphProps`, or a predicate) holds the old snapshot until the destination element has rendered, at most 800 ms in total. The page content crossfades around the morph; plain `router.push`/`replace` where the API is missing or motion is reduced. Within one route without a URL change, motion `layoutId={sharedId(...)}` still works. The dashboard room → Chores morph uses this path.

**Feedback.** `playFeedback('complete' | 'add' | 'celebrate')` from `src/lib/feedback.ts` plays a short Web Audio tone (at most 400 ms, no audio files) and/or a `navigator.vibrate` pattern, only when the member enabled Sound or Haptics in Profile > Appearance; it is a silent no-op otherwise and never throws. Overview metrics and generated sections are filtered by verified server-side effective permissions.

**Empty states.** `EmptyState` (`src/components/empty-state.tsx`) is the one empty-state pattern (H24): an inline-SVG illustration, a title, a one-line invitation and an optional primary and secondary action. Props: `kind` (`chores`, `lists`, `pets`, `assets`, `notifications`, `generic`; default `generic`), `title`, `description`, `action` and `secondaryAction` (`{ label, icon?, onClick }` renders a real `<button>`, `{ label, icon?, href }` a real Next `<Link>`; the primary uses the filled button, the secondary the ghost button), `headingLevel` (2-4, default 2, so it fits the page outline), `compact` (smaller art and spacing for cards and popovers), plus any `div` attribute. The illustrations share one style (primary-tinted backdrop, muted line drawing in `currentColor`, one primary accent, a sparkle), use token classes only so every preset recolors them, and are `aria-hidden`; `EmptyStateIllustration` exports the art alone. The content fades in with a 6 px settle (a 200 ms CSS animation, opacity/transform only, fixed illustration size, so nothing shifts). It starts at first paint, so server-rendered empty states never wait for hydration, and the global reduced-motion rules show the end state instantly. Modules adopt it in their own pages.

**Member avatars.** `MemberAvatar` (`src/components/member-avatar.tsx`) takes `uid`, `name`, `photoUrl?`, `size` (`sm` 24 px, `md` 36 px default, `lg` 56 px), `ring?` (a ring in the member color with a background-colored offset), `color?` (override, e.g. from `memberColorMap`), `decorative?` and `className`. It shows the photo once it has loaded; without a photo, or when the photo fails to load, it shows a generated diagonal gradient between the member's color token and a partner member token (`avatarGradientPartner`, three slots around the hue wheel) with one or two initials (`memberInitials`: first and last word, email local part, `?` when there is no letter) in `member-foreground`, which is AA on every member fill. The avatar is announced as the member's name (`role="img"`, `aria-label`); pass `decorative` when the name is printed next to it. `MemberAvatarStack` takes `members` (`{ uid, name, photoUrl? }[]`), `max` (circles including the `+k` chip, default 4), `size`, `ring`, `label?` and `className`; it colors members with `memberColorMap` so no two share a color, overlaps them with a background ring, and is one image to assistive tech named after the members ("Sam, Alex and 3 others"). Pure helpers live in `src/lib/member-avatar.ts`.

**Toasts.** The toast viewport sits at the top: top-center (at most 420 px wide) on phones and top-right from the `md` breakpoint, below the status bar/notch (`env(safe-area-inset-top)`) and inside the left/right safe areas. Dialogs, alert dialogs and sheets keep their primary buttons in a bottom footer and the phone tab bar is at the bottom, so a toast never covers them (previously toasts sat bottom-right on top of dialog buttons). Toasts slide in from the top and can be swiped right; the viewport ignores pointer events so its empty padding never blocks the header, and it stays above dialogs (`z-[100]`). Radix renders the viewport as a dismissable-layer branch, so pressing a toast does not close an open dialog. Toasts are compact on phones (16 px padding).

**Validation and errors.** One rule for every form: a problem with a field is shown inline under that field and never as a toast; toasts are only for outcomes (saved, deleted, could not reach the server). Use `FieldError` (`src/components/field-error.tsx`; props `id` of the field and the message as children, renders nothing when empty, `role="alert"`) with `fieldErrorProps(fieldId, error)` on the input (`aria-invalid` and `aria-describedby` to `${id}-error`), or `FormMessage` inside react-hook-form forms, which now has the same look (destructive text with an alert icon). `friendlyError(error)` (`src/lib/friendly-error.ts`) turns any thrown value into a plain-language message so raw Firebase or network text never reaches users: Firestore/Functions/Storage/Auth codes with or without a service prefix, HTTP statuses, `FirestorePermissionError`, fetch failures and timeouts map to `permission-denied`, `unavailable`, `deadline-exceeded`, `not-found`, `resource-exhausted`, `unauthenticated`, `offline` (network-shaped or unknown errors while `navigator.onLine` is false) or `unknown`; `friendlyErrorKind` returns the kind and `FRIENDLY_ERROR_TITLES` a short title. `toastError(error, title?, options?)` from `src/hooks/use-toast.ts` (also returned by `useToast()`) shows a destructive toast whose description always comes from `friendlyError`; the global `FirebaseErrorListener` uses it for permission errors. Existing call sites that build their own error toasts are migrated by their modules.

## Data Model and Persistence

The shell owns no Firestore documents. It consumes `User`, `Household`, `HouseholdMember`, and permission data supplied by auth/household context. Overview facts are transient and the optional model narrative remains component state. Dashboard facts are derived in memory from live listeners and never written. Quick add writes only documents owned by Shopping, Pets and Chores, in their existing shapes (no new fields). Device-local keys: `homehub.session` (`1` while someone is signed in on this device; a pre-paint hint only, never used for access), `homehub.dashboard.seasonal` (`on`/`off`), `homehub.dashboard.briefTyped` (the last day the brief typed itself) and `homehub.dashboard.weather` (the last weather report, 30 minutes). The dashboard writes one profile field: `users/{email}.preferences.weather` (`{ enabled: boolean, city: string }`, the member's own profile, allowed by the existing self-update allowlist; written with `awaitWriteUnlessOffline`). Missing or malformed means off.

Appearance preferences are stored in `localStorage["homehub.appearance"]` (mode, dark and light preset, reduce motion, sound, haptics) for pre-paint use, and the synced part is persisted by the identity/profile module in the existing `users/{email}.theme` field (see [Identity and Profile](../identity-profile/README.md)). Sound and haptics stay device-local.

## Authentication, Roles, and Security

- Logged-out users see the landing page at `/` (no module navigation, no data reads) and normal route content plus login controls elsewhere.
- Signed-in users without a household receive the create/join overlay.
- Members with role `newuser` receive a waiting-for-approval overlay on routes other than `/profile`.
- Desktop navigation uses `hasPermission`. The phone tab bar and More sheet omit (rather than disable) items whose view permission the member lacks: `chores.view`, `shopping.view`, `pets.view`, `maintenance.view`, `automation.view`, and `household.view`; Home, Barcode Library, and Profile are always listed. Calendar is gated by `chores.view` in both. Dashboard tiles, house sections, palette results and pages, shortcut keys and quick-add actions are each filtered by the matching view or write permission (`chores.create`, `shopping.edit`, `pets.addLogs`, `maintenance.createLogs`); Firestore rules remain the authority for every read and write. Direct routes still depend on feature code and Firebase rules.

While either overlay is shown, `HouseholdManager` renders only the overlay: the header and child routes are not mounted, so their effects do not run. Children do render while household state is still loading and for logged-out users. Security must be enforced by rules and module code, not by the overlay alone.

## Integrations and Background Processing

The shell mounts foreground Firebase Cloud Messaging handling and links to the notification bell. The overview calls the authenticated AI server module only after the brief's "Rewrite the brief with AI" sparkle is pressed; provider failure leaves the plain brief and the exact facts visible. The dashboard makes no AI calls on its own. Live weather (opt-in) calls Open-Meteo from the browser with only the member's city name and the coordinates it returns; it has no key and no proxy. Quick add calls the `parseCommand` AI action only when the member picks "Read … with AI" (one daily AI request), and otherwise an AI action only when confirming shopping items, through the existing guarded, quota-counted `categorizeGroceryItem` (as the share target does), falling back to `Other` on any failure, timeout or when offline. Fonts (Inter for body text, Space Grotesk for headings, exposed as `--font-inter` and `--font-space-grotesk`) are bundled at build time from the `@fontsource-variable/inter` and `@fontsource-variable/space-grotesk` packages (Latin subset, variable weights) through `next/font/local` in `src/app/layout.tsx`; builds never download fonts, so a Google Fonts outage cannot fail a build or a deploy. No shell-owned Cloud Function or scheduled job exists.

Authenticated emulator tests enter through `/e2e-login`; that route is rendered only for an explicit demo-project emulator configuration and delegates custom-token sign-in to the identity module.

## Invariants and Failure Behavior

- Global providers must remain ordered so all consumers are inside `AuthProvider`.
- Dashboard tiles and house links appear only for sections the member can view; destination security is authoritative.
- The dashboard never calls a model on load; exact counts come from HomeHub data. The brief's AI rewrite stays on demand, and the plain brief is the default. The palette calls the AI reader only when the member picks "Read … with AI", and never writes before Confirm.
- Quick add never writes without an explicit Confirm and never writes repeating chores or maintenance logs.
- Under reduced motion the living house, brief, bell and tab bar render end states (no wandering, glow, typing, disco, ring or fan animation, no room zoom, no tile tilt), the shell tint and weather are not rendered, and the landing shows the finished house.
- Live weather never sends anything but the city name (and the coordinates geocoded from it) and never shows an error.
- Firebase permission errors are converted to global toasts through the error emitter/listener pair, using `toastError`, so the text is the plain-language `friendlyError` message.
- Toasts never cover dialog or sheet footers or the phone tab bar: the viewport stays at the top of the screen inside the safe areas.
- The household overlays replace child routes, but shell loading does not: children mount while household state is resolving, so loading must not be treated as proof that route effects did not run.
- At 360 px and wider supported mobile viewports, the dashboard (house yard strip, tiles, peeks) must not make the document scroll horizontally.
- The theme script must stay dependency-free and must not throw; if storage is blocked the default dark theme applies and in-session changes still work.
- No animation delays content, errors or focus: the first page is not animated, loading skeletons match page layout, overlays remain interactive during their enter animation, and the progress bar is decorative (`aria-hidden`).
- `html { scrollbar-gutter: stable }` keeps pages from shifting sideways when a scrollbar appears.
- Ambient and glow effects are decorative (`aria-hidden`, `pointer-events: none`) and must keep text contrast; new ambient effects get one intensity token per preset.
- Only one service worker may control the origin. Any new worker behavior goes into `/api/sw`; registering a different script at scope `/` would replace it and break push or offline support.
- The logo intro must stay at or under 900 ms, show the finished mark under reduced motion (system or `data-motion="reduce"`), and never replay within a tab session.
- The manifest, favicon and app icons must be regenerated from `logo-artwork.ts` with `npm run brand:icons`, never edited by hand.
