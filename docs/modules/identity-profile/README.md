# Identity and Profile

## Purpose and Scope

This module owns Firebase Authentication session handling, Google sign-in, email-keyed user profiles, personal settings, avatars, and logout. Household creation, membership, roles, and invites belong to Household Governance.

## User-Facing Capabilities

- Sign in with Google from the header login dialog ("Sign in to HomeHub"). Signed-out visitors to every signed-in-only page (`/chores`, `/calendar`, `/shopping`, `/library`, `/pets`, `/pets/[id]`, `/maintenance`, `/household`, `/profile`, `/automation`) see a `SignInPrompt` (`src/components/profile/sign-in-prompt.tsx`) with a real Sign in button that opens the same dialog, never a dead-end "Please log in" line (covered by `tests/e2e/dashboard-shell.spec.ts`).
- Cancel sign-in and return to an idle login state.
- With `NEXT_PUBLIC_HOMEHUB_DEVICES=true`, the login dialog also offers **Set up a wall tablet** (links to `/setup`; see [Registered Wall Tablets](../devices/README.md)).
- View and edit personal profile fields at `/profile`.
- See your current avatar at the top of Personal Information: your photo, or the generated gradient avatar in your member color (`MemberAvatar`), with your name, role and household. Add, change or remove the photo (preview before saving, Undo / Keep photo). Unsupported types and files over 5 MB are explained inline (`FieldError`); the display name (2-60 characters) is validated inline.
- Choose appearance in Profile > Appearance: theme mode (Dark, Light, System), a dark preset (Midnight, Hearth, Forest) and a light preset (Light, Sunrise), Text size (Default 100%, Large 115%, Larger 130%; this device only, with a live preview sample, and the whole page changes at once), Reduce motion, Sound effects (with a sample button) and Haptics (shown only where `navigator.vibrate` exists). Changes apply immediately; there is no save button. The profile page shows two columns only when both fit at their rem-based minimum widths (32rem and 20rem, flex-wrap), so at 130% text a 768-1023 px tablet stacks them; the Theme and Text size option tiles wrap below 5.5rem each.
- Configure chore reminder time/enabled state.
- Manage browser push-notification subscription.
- Log out.

- **Tablet PIN** card on Profile (only with the wall-tablet flag on; active owners, admins, members and children with an account, never guests): set, change or remove your own PIN for wall tablets and unlock it after too many wrong tries, from your own signed-in session (`src/components/profile/tablet-pin-card.tsx`, server actions in `src/app/household/pin-actions.ts`). The card never sees a stored PIN, only whether one is set or locked. See [Devices](../devices/README.md), "PINs".

## Architecture and Data Flow

`AuthProvider` listens to Firebase Auth state, loads or creates the email-keyed Firestore profile, then resolves household membership. It imports only the app and Auth (`@/lib/firebase-app`) statically; Firestore and `@/lib/firebase` (which starts App Check first) load with a dynamic `import()` inside each profile, membership, household or logout call, so signed-out visitors never download them. `loading` stays true until the profile is known. Repeat visits take a fast path (H01): once Auth restores the session on the device, the provider reads that user's profile from Firestore's local cache only (`getDocFromCache`: no network, no App Check) and renders with it, then reads the server profile as before. The cached profile is provisional: `profileConfirmed` stays false until the server profile arrives, and until then an ended or stale membership shows as loading and the stale-pointer cleanup does not run, `AppearanceProvider` doesn't sync theme or Reduce motion from it, and `/profile` shows its card skeleton instead of the forms (their starting values are taken once, so saving could otherwise write an outdated name or reminder back). The server profile replaces the cached one only when it differs (`sameProfile`, `src/lib/auth/cached-session.ts`). Once the server has confirmed the profile, the provider keeps one live listener on `users/{email}` for the rest of the session, so a household pointer changed by the server (a removal, or a household joined or created on another device) reaches the open page. Membership, role and household are live too (listeners on the person's own membership record and, for approved members, the household document; see [Household Governance](../household-governance/README.md), "Live membership"); the household pointer, `role` and `permissions` on `currentUser` follow the membership record, never the profile's cached copies, and `currentUser` keeps the same object while its data is unchanged. Firestore serves those listeners from the local cache first, so a repeat visit still renders at once. The cache holds only what this user has read on this device and is cleared on sign-out; on a first visit, or with the emulator's memory cache, nothing is cached and the server answers alone. On a device with the signed-in hint (`homehub.session`), the provider also starts loading the data layer at mount, alongside the session restore; signed-out visitors never load it. Google sign-in calls `signInWithPopup(auth, provider)` with Firebase's standard popup resolver, configured once in `src/lib/firebase-app.ts` and kept on purpose so the popup is not blocked on mobile and Safari (see [Firebase Platform](../firebase-platform/README.md)); `tests/e2e/dashboard-house.spec.ts` signs in through the Auth emulator's popup from the landing page. The force-password-change dialog (react-hook-form and zod) loads as its own chunk only for members who must change their password. The Google provider requests only Firebase's default scopes (`openid`, `email`, `profile`) with no forced consent prompt. A new profile takes its name and photo from the ID-token claims Firebase Auth already returns (`getAdditionalUserInfo(result).profile`: `name`, `given_name`, `family_name`, `picture`), falling back to the Auth user's `displayName` and `photoURL`; there is no Google People API call and no birthday or gender is requested or stored. Profile edits merge into the current user's document and refresh context state. When an edit changes `displayName` or `avatarUrl` and the person is in a household, `updateUser` then calls `syncMyMemberProfileAction`, which copies the two fields from the stored profile onto their membership record, the public member data housemates see (see [Household Governance](../household-governance/README.md), "Member privacy"); it is also called, once per change, whenever the confirmed profile and the live membership record are out of step. Housemates never read each other's profiles, and the rules allow only the person to: every screen shows other people from membership records.

Popup cancellation produces `Login canceled.` and clears loading in `finally`.

`updateUser(data, newPassword?, { silent: true })` skips the global loading state and the success toast; it is used for background preference sync (a failed write still shows the error toast).

Appearance: `AppearanceSettings` calls `useAppearance().setPreferences(...)`. The provider writes all preferences to `localStorage["homehub.appearance"]` (read by the pre-paint theme script) and, for a signed-in member, writes the synced part to the profile with a silent `updateUser({ theme })` when the mode, a preset or Reduce motion changes. On each sign-in the profile's synced values (when present) replace this device's copy once; Sound, Haptics and Text size never leave the device (a wall tablet and a phone want different sizes). Text size (`textScale`: 100, 115 or 130, default 100) is applied to `<html>` as `data-text-scale` before first paint by the theme script and kept in sync by the provider afterwards; see [Application Shell](../application-shell/README.md), "Text size". Theme changes reveal in a circle from the chosen option (instant under reduced motion). The Reduce motion switch shows as on and disabled when the device already requests reduced motion.

For local E2E only, `/api/e2e/auth-token` returns an emulator custom token for an allowlisted fake test identity and `/e2e-login` exchanges it with `signInWithCustomToken`. The default remains `e2e-owner-uid`; limited, legacy, and Household B identities support isolation tests, and `e2e-live-member-uid` is created and removed by `tests/e2e/live-membership.spec.ts`. Both paths are guarded by explicit emulator mode, the exact demo project, loopback Auth/Firestore hosts, and non-production runtime; normal and production authentication remain Google-only.

## Data Model and Persistence

- Profile: `users/{email}`.
- Avatar objects (see Profile photos): new uploads `users/{uid}/avatars/{uuid}.{extension}`; older uploads `users/{email}/avatars/{uuid}.{extension}`.
- `User` includes Auth `uid`, email/name fields, avatar, role and permission compatibility fields, `householdId`, theme, chore settings, force-password-change state, and the legacy `fcmTokens` field (see below).
- Birthday and gender are no longer collected. Older profiles may still hold `birthday` and `gender` until `scripts/ops/purge-profile-demographics.mjs` removes them (owner-approved; dry run by default, prints counts only, `--apply` deletes just those two fields; authenticates with Application Default Credentials, or with `--firebase-tools-login` the `firebase login` account, loading firebase-tools from `--firebase-tools-from <dir>`, `HOMEHUB_FIREBASE_TOOLS_FROM` or this checkout, via `scripts/ops/credentials.mjs`). No feature reads them.
- Push tokens: `users/{email}/private/push` `{ fcmTokens: string[] (at most 20), updatedAt }`, readable and writable only by the profile owner (see [Notifications](../notifications/README.md)). The legacy `users/{email}.fcmTokens` field, which housemates could read with the rest of the profile, is no longer written; it may only shrink or be removed, and `scripts/ops/migrate-push-tokens.mjs` moves what is left into the private document.
- `theme` (an existing allow-listed field) holds `{ version: 2, mode: 'dark' | 'light' | 'system', darkPreset: 'midnight' | 'hearth' | 'forest', lightPreset: 'light' | 'sunrise', reduceMotion: boolean }`. Older profiles may still hold the legacy free-color shape `{ background, accent, backgroundHex, accentHex }`; it is ignored (curated presets replace free colors) and overwritten the next time the member changes appearance. No new profile keys or rules changes were needed.
- `preferences` (an existing allow-listed field) may hold `weather: { enabled: boolean, city: string }`, the dashboard's opt-in live weather and its city (see [Application Shell](../application-shell/README.md), "Live weather"). The member writes it with a merge, so other keys are kept; missing means off. No rules change was needed.
- New profiles default to `role: member` and `householdId: null`.
- `timeZone` (IANA name, at most 64 characters) is taken from the browser: whenever the profile loads and the browser's zone differs from the stored one, `AuthProvider` overwrites it (best effort; a failed write is ignored). Server-side upkeep uses it to decide when this person's overdue alert (after 07:00) and daily chore reminder fire; if it is missing or invalid, the household timezone is used.

Household compatibility fields are maintained by Household Governance: its server actions (Admin SDK) write `role`, `permissions` and `householdId` when a household is created or joined, a role or permission set changes, or a member leaves, is removed or the household is deleted. The rules deny every client write of those fields except one: a person clearing their own stale pointer (`householdId: null`, `role: 'member'`, `permissions` empty), which `AuthProvider` does when the profile points at a household without a membership record. Nobody, owners included, can point a profile at a household or change another person's profile from a client.

## Authentication, Roles, and Security

Firestore rules allow a user to read/write their own email-keyed profile and nobody else's: `canReadProfile` is the person only (housemates, member managers, pending people and other households are denied; the server reads profiles with the Admin SDK), and listing the `users` collection is prohibited. Self-service updates are limited to an explicit profile-field allowlist. `birthday` and `gender` may not be added or changed by any write (a new profile cannot carry them either); a profile that still holds them stays readable and updatable, and its owner may delete them. A new profile cannot carry `fcmTokens`, and an update may only shrink or remove that legacy field. `users/{email}/private/{docId}` allows only `docId == 'push'`, only for the profile owner, with only `fcmTokens` (a list of at most 20) and a server-time `updatedAt`; housemates, managers and outsiders are denied. Covered by `tests/rules/firestore.rules.test.ts` ("profiles", "profile demographics", "push tokens", and "member privacy: closed reads", which checks a profile read per role).

Avatar Storage folders (`users/{owner}/avatars/**`) are readable by any signed-in person. Uploads and replacements go only to the account-ID folder (`request.auth.uid == owner`) and must be images of at most 5 MB (`isImage(5 * 1024 * 1024)`); the profile form checks the same limits before uploading. The older email folder (`users/{email}/avatars/**`) stays readable until its files are deleted, and its owner (token email, `ownsAvatarFolder` in `storage.rules`) may delete them, but nothing new can be written there. Covered by `tests/rules/storage.rules.test.ts` ("avatars").

### Profile photos

The Profile form uploads a new photo to `users/{uid}/avatars/{uuid}.{extension}` (`uploadAvatar` in `src/components/profile-client.tsx`), so its download URL, which is saved as `avatarUrl` on the profile and copied to the membership record, no longer contains the email. Photos uploaded before sit under `users/{email}/avatars/`; `scripts/ops/migrate-avatars-to-uid.mjs` (dry run by default; `--apply`, `--project`, `--firebase-tools-login`; counts only) copies each to the same file name under the uid with a download token of its own, then points `users/{email}.avatarUrl` and every membership record's `avatarUrl` that showed it at the copy (each update guarded by the document's update time; a changed document is skipped and picked up by the next run). The uid comes from the profile's `uid` and from membership records; an email that maps to no single uid, a photo whose file is gone, and photos that are not uploads in this project (the Google account photo) are left alone. A re-run reuses copies made before. The original files are kept for now. A photo URL that still points into an email-named folder (`isEmailFolderPhotoUrl` in `src/lib/member-directory.ts`) is never copied to a membership record: `syncMemberProfile`, joining and household creation leave the record without a photo, and `memberProfileDiffers` ignores it, so it causes no repeated syncs; `scripts/ops/scrub-remaining-emails.mjs` removes such URLs from membership records (see [Household Governance](../household-governance/README.md), "Email copies"). Pure planner: `scripts/ops/avatar-path.mjs` (`tests/unit/identity-avatar-path.test.ts`); Storage credentials: `opsStorage` in `scripts/ops/credentials.mjs`.

## Integrations and Background Processing

- Firebase Authentication uses Google popup sign-in with default scopes only; no other Google API is called.
- Authenticated Playwright setup uses Firebase Auth Emulator custom-token sign-in and persists browser Auth IndexedDB under ignored `playwright/.auth/`.
- Firebase Cloud Messaging tokens are stored in the owner-only `users/{email}/private/push` document (legacy: `users/{email}.fcmTokens`). Sign-out removes this device's token from it; the next sign-in on a device whose browser permission is still granted registers a token for the account that signed in, without a prompt ([Notifications](../notifications/README.md)).
- Firebase web configuration comes from the `NEXT_PUBLIC_FIREBASE_*` variables documented in `.env.example`.
- No identity-owned Cloud Function or scheduled job exists.

## Invariants and Failure Behavior

- Firestore user document IDs are email addresses; a personal sign-in requires an Auth email.
- **Principal switch (wall tablets).** `AuthProvider` exposes `principal`: `{ kind: 'personal' }`, `{ kind: 'device', deviceId, householdId, generation }` for a registered wall tablet, or `{ kind: 'device-unresolved', deviceId }` for a tablet whose claims could not be read yet (offline restore; retried on reconnect, on ID-token change and every 30 s until resolved). The Auth listener decides it first (`devicePrincipalOf` in `src/lib/devices/principal.ts`: a user with an email is a person without a token read; otherwise `getIdTokenResult` + `readDeviceClaims`). For a tablet (`switchPrincipal`) it resets membership state, forgets the previous person's household data on the device and returns before any profile work: no `users/{email}` read or creation, no profile or membership listener, no push or member sync, no "No email address found" toast; `currentUser` stays null and the provider renders the lazily loaded tablet shell (`src/components/devices/tablet-shell.tsx`) instead of the page and the personal layout. `signInWithGoogle` refuses while the principal is a tablet ("This browser is a wall tablet. An owner or admin can switch it from Tablet settings."). Personal sessions are unchanged. See [Registered Wall Tablets](../devices/README.md).
- Profile listing is intentionally denied.
- While the Profile form has an edited name, a chosen or removed photo, or a save in progress, it holds the shell busy (`useUnsavedInput`, see [Application Shell](../application-shell/README.md)), so no automatic recovery reloads the page over it.
- Signed-in-only routes (Profile included) show their skeleton, not the sign-in prompt, until Auth has first answered (`useSessionKnown`).
- Sign-in failures surface a specific toast and reset the spinner; tokens and credentials are not logged.
- Profile save and profile update failures show `friendlyError` text (via `toastError` or the auth context); household creation (a Household Governance server action called from the auth context) shows the server's plain-language refusal, or `friendlyError` text when the server cannot be reached; raw Firebase messages are never shown. Saving chore reminders shows one "Reminder saved" toast (the profile write is silent on success).
- The emulator E2E endpoint returns 404 unless every safety condition is active and never uses a production service-account key.
- Avatar replacement does not establish a general cleanup contract for older avatar objects.
- Household resolution is asynchronous and has a separate loading state from Auth (`householdLoading`, derived from the live membership: true while the watched household's record or household document has not answered).
- Logout (`logout` in `src/contexts/auth-context.tsx`) ignores further calls while one sign-out is in progress (a second tap during the flush does nothing; the menu itself is unchanged). It first forgets every household's data kept on the device (`forgetHouseholdOnDevice(null)`, `src/lib/auth/household-scope.ts`: the dashboard's last-known house rooms `localStorage["homehub.house-rooms"]`, see [Application Shell](../application-shell/README.md), the shopping Undo journal, and in-memory household memories), in every mode and before anything that can fail or reload. Before that it closes the push sign-out gate (a synchronous flag), so a push registration still in flight cannot complete for this account. After the house rooms, in every mode, it removes this device's push registration while the member is still signed in (`runPushSignOut`: module loading and cleanup share one 2 s budget, failures only logged, nothing loaded when the device has no token, no registration in flight and no push subscription; see [Notifications](../notifications/README.md)), so a shared browser stops receiving the previous person's notifications. Outside emulator mode it then calls `clearLocalFirestoreCache()` ([Firebase Platform](../firebase-platform/README.md)) while the member is still signed in, because the rules would reject queued writes after sign-out. That waits up to 3 s for queued writes, such as offline shopping ticks, to reach the server, terminates Firestore, and deletes the device's IndexedDB cache. Only then does it sign out of Firebase Auth. Once Firestore has been terminated the page always reloads to `/` (no toast), even if deleting the cache failed because another HomeHub tab still has it open; that failure is logged and the cache is cleared on a later sign-out. Writes still queued after 3 s are discarded with the cache. If Firestore could not be terminated, the member is signed out in place and sees the usual "Logged Out" toast. Emulator runs use the memory cache, skip the Firestore cleanup and show the toast. Whenever Auth resolves with nobody signed in (after a sign-out here or elsewhere, or an expired session), `AuthProvider` forgets the same device data too, and when a different account signs in on an open page the previous account's membership state is reset first.

## Validation

- Run `npm.cmd run lint` and `npm.cmd run typecheck` after identity/profile changes.
- `tests/e2e/tablet-pages.spec.ts` checks `/profile` on the wall tablet (1263 × 818, touch): no sideways scroll, every control's hit area at least 48 × 48 and none overlapping (see [Application Shell](../application-shell/README.md)).
- Run `npm.cmd run test:e2e:local` to verify emulator custom-token sign-in and persisted authenticated state.
- Manually test successful Google sign-in, popup cancellation, provider failure, profile creation, profile editing, avatar upload, Profile > Appearance (mode, presets, Text size at 115% and 130%, Reduce motion, Sound, Haptics; reload without a flash of the wrong theme or text size; sync to a second browser after sign-in), push subscription, and logout (in a production build, confirm the page reloads to `/` and DevTools > Application shows no `firestore/` IndexedDB database afterwards).
- Verify self-profile updates reject membership-field spoofing and unrelated users cannot list profiles.
