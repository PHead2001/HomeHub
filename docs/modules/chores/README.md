# Chores

## Purpose and Scope

This module owns rooms, chore templates (the chore library), one-time and recurring assignments, generated chore instances, reassignment, subtasks, completion/history, the household leaderboard (points, streaks, fair share), the household calendar at `/calendar`, and chore notification creation. It does not own household membership, push transport, or the maintenance and pet data the calendar reads.

## User-Facing Capabilities

- Manage chores at `/chores`. The page header is left-aligned with its actions in the header row, like the other modules: **Add Chore** (primary), **Calendar** (link to `/calendar`) and **Chore Manager** (Chore library, Repeating chores, Rooms, and for owners/admins a **Show leaderboard** switch).
- **Add Chore** is the one-dialog way to add a chore: name, who (defaults to you), one time (due date, default today) or repeats (daily/weekdays, weekly or every 2 weeks on chosen days, monthly by day or nth weekday), an optional room and notes. One-time chores are direct chore documents (`sourceType: 'temporary'`); repeating chores create a library template with a recurrence, and server upkeep generates the instances. With no rooms yet the room field says so and offers **Create a room** (when the member may edit rooms).
- The chore library still holds reusable chores: create, edit, delete (with confirmation) and tick several to assign them together. The assign dialog is titled after the chore ("Assign Reset the kitchen" or "Assign 3 chores"), defaults the assignee to you, and shows one-time or repeating controls, never both. Weekday toggles show a filled selected state.
- **One tap completes** (H05): the round checkbox next to a chore marks it done. The box fills and a check draws itself, the row slides out of To Do, confetti bursts from the checkbox (bigger for chores with more steps), a `complete` sound/haptic plays (`playFeedback`, only if the member enabled it), and a toast offers **Undo** for 5 s. Undo restores exactly what was there (`isCompleted`, `completedAt`, `completedSubTasks`, and removes the server stamp). Completing a chore with open steps ticks the steps too; Undo un-ticks them. Ticking a completed chore's box reopens it. Confetti fires at most once per chore per visit. If a write fails, only that write's chores roll back (other completions made meanwhile are kept).
- **House is clean** (H05): when the last chore due today (or overdue) is completed, a short full-screen card says "House is clean" over a small house drawn from the household's rooms (up to 8; rooms worked in today first, a single "Home" room when none are set up), and the rooms sparkle one by one (a tile flash and stars; opacity and transform only). It shows at most once per household per day on a device (`localStorage` key `homehub.houseClean.<householdId>.<day>`, plus an in-memory flag when storage is blocked), lasts at most 1.5 s, ignores the pointer (`pointer-events: none`), never takes focus, and disappears at the first key, click, touch or scroll. Screen readers hear one polite "House is clean" status. It is drawn by `house-clean-moment.tsx`, not by the dashboard's `LivingHouse`: that component is an interactive page hero (links, peeks, a seasonal toggle, a global key listener) that needs the dashboard's full facts and has no room-by-room sparkle, so it does not belong in a non-interactive overlay.
- **Room filter in the URL**: `/chores?room=<roomId>` opens the page filtered to that room (`?room=general` for chores without a room); the **All Rooms** filter button shows the room. Choosing another room or All Rooms updates the URL in place (`history.replaceState`; All Rooms removes the param). The filter is read from `useSearchParams()` on every render, so Next.js links, Back/Forward and the dashboard's room links all keep it in step. An unknown room id (a deleted room, a stale link) falls back to All Rooms once rooms have loaded. The page container, and the route skeleton, carry `view-transition-name: room-<roomId>` (`roomSharedId()` in `src/lib/chores/url-state.ts`) while a room is requested, as the landing target of the living house's room → Chores morph (H01, H12).
- **Select mode**: **Select** switches the checkboxes to selection checkboxes ("Select …") for bulk completion ("1 chore selected", "3 chores selected"); **Complete selected** confirms first when selected chores have open steps ("1 selected chore still has open steps", each listed with "2 unfinished steps"). Plurals use the shared `pluralize`.
- **Motion and hints** (H12, H28): chore rows in every room group enter with the shared `Stagger`/`StaggerItem` (at most 30 ms apart, 400 ms in all; none under reduced motion; rows are interactive from the first frame), and the To Do, Future, Completed and room-group counts are `NumberTicker`s (screen readers and accessible names get the final number). **Add Chore** shows "New chore from anywhere  N" in a tooltip on hover or keyboard focus and carries `aria-keyshortcuts="N"`, through the shared `ShortcutHint` (`src/components/ui/shortcut-hint.tsx`, keys read from the `SHORTCUTS` map).
- **Missed repeating chores fold**: for each repeating series (generated instances of a template that currently repeats, with the same rooms and assignee; one-time library assignments, marked `sourceType: 'template'`, and temporary chores never fold) only the latest instance due today or earlier is listed; older missed ones show as "+N earlier missed" on that row (instances due on the same day are never folded into each other), and members who may delete chores can **Clear** them from that row.
- Rows show the chore name on up to two lines (no single-line truncation on phones), the due day ("Today", "Yesterday", "Tue, Aug 4"), an **Overdue** badge, step progress, and the assignee as a `MemberAvatar` (name beside it from the `sm` breakpoint). Overdue rows keep the normal surface with a destructive left border and badge (no red-on-red text); the badge (destructive text on a 10% destructive tint over the card) meets WCAG AA in all five presets (unit-tested). Reassign is a menu on the avatar (for members who may edit and assign); the delete icon shows for members who may delete. Tapping the name (with its small chevron) shows notes and steps.
- Empty states use `EmptyState`: a household with no chores invites you to **Add your first chore**; an empty To Do says "Nothing due today" (or "All done for today" when you finished something) and names the next chore.
- **Leaderboard** (H06, beside the chart on wide screens, below it on phones): this Monday-Sunday week's points per member (10 per chore, +2 per step, +5 when done on or before its due day), a daily streak flame (consecutive days with at least one completed chore, ending today or yesterday), and a fair-share ring (each member's slice of the chores due this week, in their member color). Child accounts collect stickers (one per chore this week) instead of points. On Sundays a podium rises with a crown for the week's MVP. Owners and admins can turn the leaderboard off for the household.
- **Calendar** at `/calendar` (H19, replaces the old calendar dialog, D11): Day (agenda), Week and Month views of chores (colored by assignee with `memberColor`), maintenance due dates and expirations, and pet medication (doses given, and upcoming doses), for the whole visible range: future occurrences of repeating chores that the server has not generated yet (it makes the next 30) appear as dashed "planned" items (not movable), and warranty, registration and inspection expirations show on their date however far ahead (an expired warranty is shown but never counted as overdue). Today glows (it rolls over at midnight and when the tab becomes visible again, together with overdue flags and maintenance statuses; a view that was showing today moves with it, and the Chores page's To Do, overdue, empty-state copy, leaderboard week, streaks and Sunday podium roll over the same way); overdue chores and maintenance stack in a red **Overdue** rail; a legend lists members. Month cells show up to three items (dots on phones) and selecting a day lists everything for it below the grid. Week view stacks days vertically on phones. **Day** is the agenda for one day: the default on phones (below 768 px when the page opens; Week elsewhere), it lists that day's items (staggered in, sliding 16 px from the side you moved toward, ≤ 250 ms, nothing under reduced motion), and today's card glows with a **Today** badge. Swiping left/right changes the day in Day view (week or month in the others); the keyboard equivalents are **Previous day**/**Next day** (or week/month) and, with the agenda focused, the Left/Right arrow keys (ignored while focus is on an item inside it or with a modifier). Switching views keeps the selected day in view. Upcoming medication doses come from the Pets module's own countdown rule (`currentMedications`, which the pet card chips and the server reminders mirror): one per current medication on its due day, amber and dashed ("Medication due", "Due in 2 days"), red and in the Overdue rail when overdue, linking to `/pets/<petId>?tab=medication`; logged doses stay green ("Medication given"). The Overdue count is a `NumberTicker`. Each item opens a details popover with a link to its module, and hovering (mouse) or keyboard-focusing it for 400 ms shows the shared `PeekCard` (H26) with its kind, title, who or what, date and status (not while its popover is open).
- **Reschedule** (calendar): members with `chores.edit` can drag an open chore to another day, or open it and use **Move to date** (keyboard-accessible date field). The chip springs into its new day and a toast offers **Undo** for 5 s. Maintenance and medication items are read-only.

## Architecture and Data Flow

`ChoreChartClient` loads rooms, templates, chore instances, and assignees from approved membership records (enriched with readable `users/{email}` profiles; the membership role is kept for sticker mode). It does not expand recurring templates itself: before reading chores, each load calls the `syncHouseholdUpkeep` server action, which runs the same idempotent upkeep as the hourly `householdUpkeep` Cloud Function. That step creates any missing instances for the next 30 occurrences of each recurring template, starting at today in the household time zone, with deterministic IDs derived from template, room, date, and assignee. If the action fails, the page logs a warning and shows whatever instances already exist.

Completion writes go through `completionUpdate()` (`src/lib/chores/completion.ts`): `isCompleted: true`, `completedAt` (client ISO time, kept for older readers and retention) and `completedAtServer: serverTimestamp()`. The page updates optimistically and rolls back with `toastError` on failure. Undo and reopen write back the previous fields and delete `completedAtServer`.

Points, streaks, stickers, fair share and the podium are computed in the browser by `computeChoreStats()` from the chore documents already loaded (completion history is kept 90 days). Nothing is stored, so there is no score a client could write. Completion times come from `completedAtServer` when present (cannot be backdated, see Security) and fall back to `completedAt` for chores completed before the stamp existed. Points go to the chore's assignee; chores of former members are ignored.

Editing or canceling a recurrence deletes the template's incomplete instances in the browser; the reload that follows runs server upkeep, which regenerates instances for an edited recurrence. Completed history remains.

Add Chore (one time) validates name, assignee and due date inline, then atomically writes one auto-ID chore instance and, when the assignee is someone else, one deterministic assignee notification. It does not write `chore-templates`. Add Chore (repeating) writes one template with its recurrence. New chore templates (Add Chore repeating, new library chores) and new rooms get an ID that cannot collide: a readable slug of the name (up to 60 characters) plus a Firestore auto-id (`newChoreDocId` in `src/lib/chores/list.ts`, mirroring the shell's `quickCreateId`), for example `take-out-trash-AbCd…`. IDs are never picked from the page's loaded list, which can be a stale offline cache or miss documents another member just created, so a create can never overwrite or merge into an existing document; the library create also runs in a transaction that refuses an existing ID and writes without merge. Nothing depends on readable IDs: chores link to templates by `templateId`, generated instance IDs are derived from whatever the template and room IDs are, and `?room=<id>` links, the room filter, the living house and its room links all read the stored ID (the house picks the pet bowl's room by name). Existing templates and rooms keep their IDs. One-time library assignments use auto IDs, so they never share (and overwrite) the deterministic ID of a generated occurrence or an earlier assignment; older one-time assignments keep their deterministic IDs.

The calendar (`HouseholdCalendar`) runs upkeep, then reads chores and chore templates (`chores.view`), `home-assets` and `vehicles` (`maintenance.view`, turned into due dates with the shared `buildMaintenanceReminders` used by Maintenance and the reminder function), and `pets/{petId}/medication-logs` (`pets.view`), each only when the member may read it. Maintenance items are built by `maintenanceCalendarItems()`: scheduled services from the shared builder (every status) plus expiration fields read directly, recomputed whenever today changes. Repeating chores are projected over the visible range with the server's own recurrence rules (`occursOn`) and occurrence identity (`recurringChoreId`, via `occurrenceIds()`): an occurrence is planned only while its document does not exist, so a generated chore that was moved or completed never reappears on its original day. A source that fails shows an inline alert; the others still render. Medication entries are read with both date shapes (ISO strings and legacy timestamps, via `toDate`) and their `nextDueDate`; `medicationDueEvents` groups them per pet and calls `currentMedications`. Moving a chore writes `originalDueDate` (the day) and `dueDate` (local noon ISO) to the chore document only.

## Data Model and Persistence

- Templates: `households/{householdId}/chore-templates/{templateId}`.
- Instances: `households/{householdId}/chores/{choreId}`.
- Rooms: `households/{householdId}/rooms/{roomId}`.
- Chore preferences: `households/{householdId}/chore-settings/preferences`, shape `{ leaderboardEnabled: boolean, updatedAt?: string }`. A missing document means the defaults (leaderboard on).
- Notifications: `households/{householdId}/notifications/{notificationId}`.
- Read-only for the calendar: `chore-templates`, `home-assets`, `vehicles`, `pets` and `pets/{petId}/medication-logs`.

Important types are `Recurrence`, `RecurrenceFrequency`, `MonthlyRecurrenceMode`, `MonthlyNthWeekday`, `ChoreTemplate`, `Chore`, and `Room`; `ChoreRecord` (`src/lib/chores/dates.ts`) is `Chore` plus the optional `completedAtServer` timestamp.

`Chore.templateId` is optional for backward-compatible direct instances. `Chore.sourceType` may explicitly distinguish `template` and `temporary`; existing documents without `sourceType` continue through the established template/instance behavior. `completedAtServer` is optional and additive: existing completed chores without it keep working (their `completedAt` is used), and no migration is needed.

Biweekly schedules use `startDate` as an anchor. Monthly day-of-month is limited to 1-28. Nth-weekday supports first through fourth; last-weekday recurrence is not implemented. Pets have no medication schedule beyond each dose's optional `nextDueDate`, so the calendar's upcoming doses are exactly the pending countdowns (one next dose per medication), not a recurring series.

## Authentication, Roles, and Security

The page requires an authenticated user and uses that user's household ID. Assignee discovery uses approved, active `households/{householdId}/members/{uid}` records; an unreadable profile falls back to the member record's display name.

Navigation uses `chores.view`. Firestore rules enforce granular permissions: `chores.view` to read chores, templates, rooms and chore preferences; `chores.create` to create chores and templates; `chores.complete` for updates limited to `isCompleted`, `completedAt`, `completedSubTasks` and `completedAtServer`; `chores.edit` for other chore and template updates and room create/update; and `chores.delete` for deletes. `chores.assign` is enforced on assignment: creating a chore whose `assignedToEmail` is someone other than the caller (by token email) needs it, while `chores.create` alone still covers a chore for yourself or an unassigned one (`''` or null); any change of a chore's `assignedToEmail` on update needs it, including to yourself (Reassign already requires it in the UI). On templates, setting or changing `assignedToEmail` or `recurrence.assignedToEmail` to someone other than the caller needs it; keeping the current assignee, switching to yourself or clearing it does not (the Edit repeating chore dialog offers exactly those choices without `chores.assign`).

Shape validation (QA-8): chore writes may only set `task` (1 to 500 characters, required on create), `notes` (up to 5000), `assignedToEmail`, `assignedToDisplayName`, `dueDate`, `originalDueDate`, `roomIds` (list, at most 50), `isCompleted` (bool), `completedAt`, `completedAtServer` (timestamp), `completedSubTasks` and `subTasks` (lists, at most 100), `templateId` and `sourceType` (`temporary` or `template`). Templates may only set `task` (required on create), `notes`, `roomIds`, `subTasks`, `assignedToEmail` and `recurrence`; `recurrence` is null or a map of `frequency` (`daily`, `weekly`, `biweekly`, `monthly`, required), `interval` (1 to 52), `assignedToEmail`, `startDate`, `dailyOptions` (`excludeWeekends`), `weeklyOptions` (`daysOfWeek`, at most 7) and `monthlyOptions` (`mode`, `dayOfMonth` 1 to 31, `nthWeekday` with `week`/`dayOfWeek`). On update only added or changed keys are checked, so chores and templates holding legacy fields stay editable. A recurring assignment merged into a template that was deleted meanwhile (no `task`) is now refused instead of creating a nameless template. On-demand upkeep requires `chores.view`. Pending `newuser` members are denied by rules.

Uid assignee: chores and templates also accept `assignedToUid` (a string up to 128 characters; empty or null when unassigned), written next to `assignedToEmail` by member privacy release A. It is guarded like the email: without `chores.assign`, a uid is accepted only when it verifiably belongs to the email beside it (your own uid with your own email, or a member whose member document carries that email), so filling in the existing assignee's uid is allowed but pointing it at anyone else is not; every other assignee change needs `chores.assign`.

Completion stamp rule (every chore write): a chore that becomes completed must carry `completedAtServer == request.time`. A completion with no stamp, or a client-chosen one, is denied. A chore that stays completed must keep its stamp unchanged, and a chore can be created already completed only with a server stamp. So completion times, which points and streaks read, can't be backdated or forged. Chores completed before the stamp existed (phase 1, 2026-11-06) remain editable and can be reopened, and stats fall back to `completedAt` for them. Chore preferences may be written only by owners and admins (role, not overrides), only at `preferences`, only with `leaderboardEnabled` (bool) and `updatedAt` (string); nobody may delete them.

The UI never shows an action the member cannot perform, mirroring the rules through `choreCapabilities(permissions)`: the completion checkbox is disabled without `chores.complete`; Add Chore and the library's create need `chores.create`; reassign, room add/edit and library edit need `chores.edit`; delete (rows, library, rooms, clearing missed instances) needs `chores.delete`; editing or stopping a repeating chore needs both `chores.edit` and `chores.delete` (it removes the old open instances); removing a room from a library chore without `chores.delete` is refused inline; picking someone other than yourself as assignee needs `chores.assign`; calendar rescheduling needs `chores.edit`; the leaderboard switch is shown to owners and admins.

## Integrations and Background Processing

- Assignment notifications go only to someone other than the person assigning (no "New chore assigned" for chores you give yourself). Template assignment notifications are best-effort household notification writes. One-time Add Chore batches its direct chore and deterministic assignment notification together so a successful creation cannot omit its initial notification.
- Overdue alerts (after 7:00 local time) and each person's daily reminder (at their chosen time, in their own `users.timeZone`, falling back to the household's) are created on the server. The hourly `householdUpkeep` Cloud Function (`functions/src/index.ts` → `functions/src/reminders.ts`) runs the same idempotent step for every household; the Chores page and the calendar also run it on demand through `syncHouseholdUpkeep` (`src/app/chores/actions.ts`, authorized by `chores.view`) so a new recurring assignment appears immediately.
- Deterministic per-user/day notification IDs suppress same-day duplicates.
- New records can trigger the shared FCM Cloud Function.
- Recurring instances for the next 30 occurrences are generated on the server from `functions/src/shared/recurrence.ts`, using the household `timeZone` (default `America/Chicago`). Chore IDs are `stableSlugify(templateId-roomId-day-email)`, identical to the previous browser-generated IDs. Nothing is generated for someone who is not an approved member. A rescheduled instance keeps its ID, so upkeep never recreates it on its old day.
- Feedback: `playFeedback('complete')` on completion, `'celebrate'` for "House is clean", `'add'` after adding or moving a chore.

The homepage AI Overview includes only incomplete chores assigned to the verified token email, with exact overdue/today/seven-day counts and at most five bounded urgent labels. It does not expose another member's assignment list to the model.

- [Household Governance](../household-governance/README.md) supplies members and unassigns chores when members leave.
- [Notifications](../notifications/README.md) owns read/dismiss history and push delivery.
- [Firebase Platform](../firebase-platform/README.md) owns persistence and rules.
- [Application Shell and Dashboard](../application-shell/README.md) exposes route navigation and the design foundation used here (`EmptyState`, `MemberAvatar`, `FieldError`, `toastError`/`friendlyError`, `memberColor`, `playFeedback`, motion and the reduced-motion contract). `/calendar` is linked from the Chores page, the desktop header (next to Chores) and the phone More sheet, all gated by `chores.view`. The dashboard and the command palette also read chores: the dashboard counts them with this module's `choreDueKey`, `completionInstant` and `collapseMissedRecurring` (missed instances fold as on To Do), and palette quick add writes chores in this module's shapes after the member confirms a preview card, gated by `chores.create` and, for anyone but yourself, `chores.assign` (the preview lets them change the assignee and the room):
  - One-time chores ("vacuum Friday for Sam") are a temporary chore (`sourceType: 'temporary'`, `roomIds` from the chosen room) plus, for someone else, the deterministic "New chore assigned" notification, in one batch (`createOneTimeChore` in `src/components/command/quick-add-actions.ts`).
  - Repeating chores ("trash every Tuesday for Sam", or the same read by the palette's AI fallback) are a `chore-templates` document shaped like the Add Chore dialog's Repeats option (`repeatingChoreTemplate` in `src/lib/dashboard/quick-add-writes.ts`): task, empty notes and sub-tasks, `roomIds`, the recurrence built with this module's own `buildRecurrence` (weekly and every-other-week on the named weekday, the biweekly anchor at the first occurrence, daily, or monthly on a day 1-28) plus `assignedToEmail`, under an id that is always new: a readable slug plus a Firestore auto-id (`quickCreateId`). Quick add never picks a free readable id from the template list, because offline (or from cache) that list can be incomplete and a queued write onto a taken id would overwrite that template on reconnect. A monthly day after the 28th is moved to the 28th before the preview, with a note, so the confirmed schedule is the saved one. For someone else the "You have a new repeating chore" notification follows (best effort, as in the dialog: a failure is logged and never undoes the template). The palette then calls `syncHouseholdUpkeep` (the same server action the Chores page runs on load, needing `chores.view`) so the first instance is generated at once; if that call fails it is only logged and the hourly upkeep creates the instance.
  - Writes go through `awaitWriteUnlessOffline`: offline they are queued and the palette says "Saved offline" (upkeep is skipped until the next load or hourly run), a rejected write is reported with `toastError` and the preview stays open, and Firestore rules (`chores.create` for chores and templates) still decide.
  After such a write the palette dispatches `homehub:data-changed` (`src/lib/data-changed.ts`), and the Chores page re-runs its load silently, so the new chore or repeating chore appears without a reload.
- [Maintenance Center](../maintenance-center/README.md) owns assets, vehicles and their schedules; the calendar reads them read-only and shares `buildMaintenanceReminders` for due dates.
- [Pets](../pets/README.md) owns pets and medication logs; the calendar reads them read-only.

## Invariants and Failure Behavior

- Defensive normalization supplies defaults for old recurrence records missing interval, weekdays, anchors, monthly mode, or day.
- Retention: completed chores older than 90 days (household-local) are deleted by the server step, so leaderboard totals cover at most 90 days. Before deleting, upkeep adds each removed chore to `households/{householdId}/stats/chores-{year}` (the year, in the household timezone, of its authoritative completion instant: `completedAtServer` when present, else `completedAt`, from `choreCompletionInstant` in `functions/src/shared/completion.ts`, which `completionInstant` in `src/lib/chores/dates.ts` also uses; retention itself still keys off `completedAt`) in the same transaction as the delete: `{ year, completed, byAssignee: { <key>: count }, names: { <key>: displayName }, updatedAt }`, where the key is `choreStatsAssigneeKey(email)` (a slug of the email's local part plus a hash of the lower-cased email, because emails cannot be map keys). Totals are read, added to and written inside the transaction (`addPurgedChores` in `functions/src/shared/chore-stats.ts`), and a chore is counted only when it is actually deleted, so repeated or overlapping runs never count it twice. Clients can read the document with `chores.view` and can never write it. Home Wrapped adds these yearly totals to the retained completions.
- Room deletion (confirmed) updates templates but not existing chore instances; unresolved room IDs show under "Unknown Room".
- Generation and reminders no longer depend on anyone opening the app.
- Generation is create-only and retention re-checks: inside each upkeep transaction a generated instance is written only if it is still absent, and a completed chore is purged only if it is still completed with the same `completedAt`, so overlapping hourly and on-demand runs never reset or remove work done in between. Instances are also created only if their source template is unchanged since the run read it (same update time), so editing or cancelling a recurrence while a run is in flight is never undone.
- Best-effort notification failures do not roll back chore writes.
- Every client that completes a chore must use `completionUpdate()`; the rules deny unstamped completions.
- Field problems in every chore dialog are shown inline with `FieldError` (with `aria-invalid`/`aria-describedby`), never as toasts; failures use `toastError`, so raw Firebase text never reaches users.
- Motion follows the shared contract: under reduced motion (system or in-app) the checkbox, row entrance and exit, count tickers, podium, agenda slide and calendar moves show their end state instantly and confetti does not render; "House is clean" shows its finished, sparkling house at once. Hover effects are not used for meaning, and no animation delays content, focus or errors.
- Assignment forms show one-time date controls or recurring controls, never both.
- Active and completed chore instances use the same confirmation contract before permanent deletion.
- Future/completed view switches use the shared control dimensions; their thumbs must remain inside the track at desktop and mobile widths.
