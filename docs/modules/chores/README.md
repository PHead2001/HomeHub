# Chores

## Purpose and Scope

This module owns rooms, chore templates (the chore library), one-time and recurring assignments, generated chore instances, reassignment, subtasks, completion/history, the household leaderboard (points, streaks, fair share), the household calendar at `/calendar`, and chore notification creation. It does not own household membership, push transport, or the maintenance and pet data the calendar reads.

## User-Facing Capabilities

- Manage chores at `/chores`. The page header is left-aligned with its actions in the header row, like the other modules: **Add Chore** (primary), **Calendar** (link to `/calendar`) and **Chore Manager** (Chore library, Repeating chores, Rooms, and for owners/admins a **Show leaderboard** switch).
- **Add Chore** is the one-dialog way to add a chore: name, who (defaults to you), one time (due date, default today) or repeats (daily/weekdays, weekly or every 2 weeks on chosen days, monthly by day or nth weekday), an optional room and notes. One-time chores are direct chore documents (`sourceType: 'temporary'`); repeating chores create a library template with a recurrence, and server upkeep generates the instances. With no rooms yet the room field says so and offers **Create a room** (when the member may edit rooms).
- The chore library still holds reusable chores: create, edit, delete (with confirmation) and tick several to assign them together. The assign dialog is titled after the chore ("Assign Reset the kitchen" or "Assign 3 chores"), defaults the assignee to you, and shows one-time or repeating controls, never both. Weekday toggles show a filled selected state.
- **One tap completes** (H05): the round checkbox next to a chore marks it done. The box fills and a check draws itself, the row slides out of To Do, confetti bursts from the checkbox (bigger for chores with more steps), a `complete` sound/haptic plays (`playFeedback`, only if the member enabled it), and a toast offers **Undo** for the shared 10-second Undo window (`CHORE_UNDO_MS` = `UNDO_WINDOW_MS`, `src/lib/undo-window.ts`; toast group `chore-complete`, so a newer completion toast replaces it). Completion runs on the server (H3, see Architecture): a chore due after today (household timezone) cannot be completed, so its box is disabled (also in Select mode); the page judges this on the household's day (`useHouseholdToday`, `isDueAfterHouseholdDay`), the same day the server uses, not the device's, so a member in another timezone can complete a chore exactly when the server accepts it and a refused one says "Not due yet: … is due Tue, Nov 11. It can be completed from that day."; a chore someone else already completed shows as done with "… was already done by Sam."; offline nothing is queued: "You're offline. Not completed." and the row stays open. Undo reverts only that completion: if someone else already reopened it the chore simply stays open; if someone reopened and completed it again, or deleted it, meanwhile (`stale`, `missing`), it says "Already changed" and re-reads the chore so the page shows what is stored (removing a deleted one) rather than the completion it saved; only a request that never reached the server (offline, failed) puts that saved completion back (`settleUndo`, `applyUndoSettlement`, `applyRefreshedChores` in `src/lib/chores/patch.ts`), clears the completion fields and puts the steps back only if they are unchanged since; the page then shows the steps the server stored (restored, or kept because someone changed them meanwhile), so a later step toggle starts from them. Completing a chore with open steps ticks the steps too. Ticking a completed chore's box reopens it (on the server; its points go away). Confetti fires at most once per chore per visit, and only after the server confirmed. While a completed row slides out of To Do it is `aria-hidden`, inert and ignores the pointer, so a chore has exactly one actionable row across To Do, Future and Completed. If a request fails, only its chores roll back (other completions made meanwhile are kept).
- **House is clean** (H05): when the last chore due today (or overdue) is completed, a short full-screen card says "House is clean" over a small house drawn from the household's rooms (up to 8; rooms worked in today first, a single "Home" room when none are set up), and the rooms sparkle one by one (a tile flash and stars; opacity and transform only). It shows at most once per household per day on a device (`localStorage` key `homehub.houseClean.<householdId>.<day>`, plus an in-memory flag when storage is blocked; `houseCleanShown` / `markHouseCleanShown` in `house-clean.ts`, which the dashboard's HP-34 celebration uses too, so the moment never repeats between the two), lasts at most 1.5 s, ignores the pointer (`pointer-events: none`), never takes focus, and disappears at the first key, click, touch or scroll. Screen readers hear one polite "House is clean" status. It is drawn by `house-clean-moment.tsx`, not by the dashboard's `LivingHouse`: that component is an interactive page hero (links, peeks, a seasonal toggle, a global key listener) that needs the dashboard's full facts and has no room-by-room sparkle, so it does not belong in a non-interactive overlay.
- **Overdue and Mine filters in the URL** (GOAL-filters, HP-25): `/chores?due=overdue` keeps only overdue chores in To Do (a row whose earlier missed instances were folded into it stays, since that work is overdue; Future and Completed are unchanged) and `/chores?who=me` shows only the reader's chores everywhere on the page (`matchesWhoFilter` in `src/lib/chores/list.ts`, which uses `isAssignedTo` from `functions/src/shared/assignee.ts`: a uid-only chore by uid, an older one by email). The **Overdue** and **Mine** toggle buttons beside the room filter have static labels with `aria-pressed` and write the URL in place (`history.replaceState`) through `choresFiltersHref`, which keeps the other filters and always orders them `room`, `due`, `who`; reload, Back and the dashboard brief's links (`/chores?due=overdue&who=me`) open the same view. With the overdue filter and nothing overdue, To Do says "Nothing overdue". The To Do room groups remount on every filter change (`choresFiltersKey`), so a room that a change brings in (turning Mine off lists housemates' rooms) opens like the others instead of arriving collapsed.
- **Room filter in the URL**: `/chores?room=<roomId>` opens the page filtered to that room (`?room=general` for chores without a room); the **All Rooms** filter button shows the room. Choosing another room or All Rooms updates the URL in place (`history.replaceState`; All Rooms removes the param). The filter is read from `useSearchParams()` on every render, so Next.js links, Back/Forward and the dashboard's room links all keep it in step. An unknown room id (a deleted room, a stale link) falls back to All Rooms once rooms have loaded. The page container, and the route skeleton, carry `view-transition-name: room-<roomId>` (`roomSharedId()` in `src/lib/chores/url-state.ts`) while a room is requested, as the landing target of the living house's room → Chores morph (H01, H12).
- **Select mode**: **Select** switches the checkboxes to selection checkboxes ("Select …") for bulk completion ("1 chore selected", "3 chores selected"); **Complete selected** confirms first when selected chores have open steps ("1 selected chore still has open steps", each listed with "2 unfinished steps"). Plurals use the shared `pluralize`.
- **Motion and hints** (H12, H28): chore rows in every room group enter with the shared `Stagger`/`StaggerItem` (at most 30 ms apart, 400 ms in all; none under reduced motion; rows are interactive from the first frame), and the To Do, Future, Completed and room-group counts are `NumberTicker`s (screen readers and accessible names get the final number). **Add Chore** shows "New chore from anywhere  N" in a tooltip on hover or keyboard focus and carries `aria-keyshortcuts="N"`, through the shared `ShortcutHint` (`src/components/ui/shortcut-hint.tsx`, keys read from the `SHORTCUTS` map).
- **Missed repeating chores fold**: for each repeating series (generated instances of a template that currently repeats, with the same rooms and assignee; one-time library assignments, marked `sourceType: 'template'`, and temporary chores never fold) only the latest instance due today or earlier is listed; older missed ones show as "+N earlier missed" on that row (instances due on the same day are never folded into each other), and members who may delete chores can **Clear** them from that row.
- Rows show the chore name on up to two lines (no single-line truncation on phones), the due day ("Today", "Yesterday", "Tue, Aug 4"), an **Overdue** badge, step progress, on completed rows who did it ("Done by Sam · Nov 4", D-7: `completerLabel` uses the current member name for `completedByUid`, else the stored `completedByName`, and never an email; older completions just "Done Nov 4"), and the assignee as a `MemberAvatar` (name beside it from the `sm` breakpoint). Overdue rows keep the normal surface with a destructive left border and badge (no red-on-red text); the badge (destructive text on a 10% destructive tint over the card) meets WCAG AA in all five presets (unit-tested). Reassign is a menu on the avatar (for members who may edit and assign); the delete icon shows for members who may delete. Tapping the name (with its small chevron) shows notes and steps.
- Empty states use `EmptyState`: a household with no chores invites you to **Add your first chore**; an empty To Do says "Nothing due today" (or "All done for today" when you finished something) and names the next chore.
- **Leaderboard** (H06, beside the chart on wide screens, below it on phones): this Monday-Sunday week's points per member (10 per chore, +2 per step, +5 when done on or before its due day; the points go to whoever completed the chore, D-7), a daily streak flame (consecutive days with at least one completed chore, ending today or yesterday), and a fair-share ring (each member's slice of the chores due this week, in their member color). Child accounts collect stickers (one per chore this week) instead of points. On Sundays a podium rises with a crown for the week's MVP. Owners and admins can turn the leaderboard off for the household.
- **Calendar** at `/calendar` (H19, replaces the old calendar dialog, D11): Day (agenda), Week and Month views of chores (colored by assignee with `memberColor`), maintenance due dates and expirations, and pet medication (doses given, and upcoming doses), for the whole visible range: future occurrences of repeating chores that the server has not generated yet (it makes the next 30) appear as dashed "planned" items (not movable), and warranty, registration and inspection expirations show on their date however far ahead (an expired warranty is shown but never counted as overdue). Today glows (it rolls over at midnight and when the tab becomes visible again, together with overdue flags and maintenance statuses; a view that was showing today moves with it, and the Chores page's To Do, overdue, empty-state copy, leaderboard week, streaks and Sunday podium roll over the same way); overdue chores and maintenance stack in a red **Overdue** rail; a legend lists members. Month cells show up to three items (dots on phones) and selecting a day lists everything for it below the grid. Week view stacks days vertically on phones. **Day** is the agenda for one day: the default on phones (below 768 px when the page opens; Week elsewhere), it lists that day's items (staggered in, sliding 16 px from the side you moved toward, ≤ 250 ms, nothing under reduced motion), and today's card glows with a **Today** badge. Swiping left/right changes the day in Day view (week or month in the others); the keyboard equivalents are **Previous day**/**Next day** (or week/month) and, with the agenda focused, the Left/Right arrow keys (ignored while focus is on an item inside it or with a modifier). Switching views keeps the selected day in view. Upcoming medication doses come from the Pets module's own countdown rule (`currentMedications`, which the pet card chips and the server reminders mirror): one per current medication on its due day, amber and dashed ("Medication due", "Due in 2 days"), red and in the Overdue rail when overdue, linking to `/pets/<petId>?tab=medication`; logged doses stay green ("Medication given"). The Overdue count is a `NumberTicker`. Each item opens a details popover with a link to its module, and hovering (mouse) or keyboard-focusing it for 400 ms shows the shared `PeekCard` (H26) with its kind, title, who or what, date and status (not while its popover is open).
- **Reschedule** (calendar): members with `chores.edit` can drag an open chore to another day, or open it and use **Move to date** (keyboard-accessible date field). The chip springs into its new day and a toast offers **Undo** for 10 s (`UNDO_WINDOW_MS`). Maintenance and medication items are read-only.

## Architecture and Data Flow

`ChoreChartClient` loads rooms, templates, chore instances, and assignees from approved membership records (`approvedPeople`, `src/lib/member-directory.ts`: display name, photo and role, kept for sticker mode; housemates' `users/{email}` profiles are not read).
Assignee identity: see the section below. It does not expand recurring templates itself: before reading chores, each load calls the `syncHouseholdUpkeep` server action, which runs the same idempotent upkeep as the hourly `householdUpkeep` Cloud Function. That step creates any missing instances for the next 30 occurrences of each recurring template, starting at today in the household time zone, with deterministic IDs derived from template, room, date, and assignee, and an `occurrenceKey` (`templateId|roomId|day`, no assignee). If the action fails, the page logs a warning and shows whatever instances already exist.

Completion (H3: CH-2, CH-12, D-7) goes through the server actions `completeChores({choreIds, completeSubTasks})`, `undoChoreCompletion({choreId, completionId, restoreSubTasks})` and `reopenChore({choreId})` in `src/app/chores/actions.ts`, each authorized with `authorizeHouseholdAction(ctx, 'chores.complete')` and run as one Admin SDK transaction (`src/lib/server/chore-completion.ts`, plans in `src/lib/chores/completion.ts`). The caller's identity comes only from the verified ID token. Chore IDs are checked with `isChoreDocId` (Firestore's own limits: one segment without '/', at most 1500 UTF-8 bytes, not `.`, `..` or `__…__`), because upkeep's recurring IDs (template ID, room ID, day and assignee email) can exceed 200 characters; the household ID still uses `isDocId`. Per chore, `completeChores` returns `completed`, `already` (idempotent: nothing written, and the result says who did it, so two people completing at once yield one completion) or `refused` (`early` when its due day, `originalDueDate` or `dueDate` read in the household timezone with `localDay`, is after the household's today, `householdToday`; `isDueAfterHouseholdDay` is the shared check; `missing`). A completion writes `isCompleted: true`, `completedAt` (server ISO time), `completedAtServer` (server timestamp), `completedByUid`, `completedByName` (no `completedByEmail`: every member with `chores.view` reads the chore; the name is the member record's display name, else the caller's token name, else "Member"; never an email, via `publicDisplayName`) and a random `completionId`, plus every step in `completedSubTasks` when steps were open. Undo reverts only while `completionId` still matches, clears only the completion fields (never restores a whole document) and restores `completedSubTasks` only if they are still exactly what the completion ticked; an `undone` result always carries the stored `completedSubTasks` afterwards, which the page applies. Reopen clears the completion fields (steps stay ticked). Every entry point calls these through `src/lib/chores/complete-client.ts` (`completeChoresOnServer` in batches of 50, `undoCompletionOnServer`, `reopenChoreOnServer`); today that is the Chores page's one tap, Select mode, Undo and reopen , and the dashboard's one-tap **Done** with its Undo (`useChoreDone` in `src/components/dashboard/one-tap.tsx`, HP-33b); the calendar has no completion. It refuses to run offline (`OFFLINE_COMPLETION_MESSAGE`), so a completion is never queued. The page updates optimistically and then applies what the server recorded, rolling back only chores that were not completed.

Points, streaks, stickers, fair share and the podium are computed in the browser by `computeChoreStats()` from the chore documents already loaded (completion history is kept 90 days). Nothing is stored, so there is no score a client could write. Completion times come from `completedAtServer` when present (cannot be backdated, see Security) and fall back to `completedAt` for chores completed before the stamp existed. Points, streak days and stickers go to whoever completed the chore (`creditedUid`: the member with `completedByUid`, else the member whose email is an older chore's `completedByEmail`, else, for completions recorded before attribution, the assignee resolved by uid or email with `resolveAssigneeUid`); fair share still counts assignments. Completions credited to former members are ignored (a recorded completer who left is not replaced by the assignee). The Chores page and the dashboard streaks tile build the stats members the same way (`statsMemberFrom` in `src/lib/chores/stats.ts`, applied to the approved member records; `streakMembersFrom` on the dashboard): each carries the record's email only while an older record still has one, purely as a matching key for `completedByEmail` and `assignedToEmail` on older chores; records written since member privacy release D have none, and such chores are scrubbed to uids. The email never reaches `MemberChoreStats` or any label, so both pages credit an older email-only completion by a current member identically (`tests/unit/chores-completion.test.ts`).

Editing or canceling a recurrence deletes the template's incomplete instances in the browser; the reload that follows runs server upkeep, which regenerates instances for an edited recurrence. Completed history remains, and a day that already has its chore (by `occurrenceKey`) is never regenerated, so reassigning a template or editing its schedule never brings back a completed day (CH-3).

Add Chore (one time) validates name, assignee and due date inline, then atomically writes one auto-ID chore instance and, when the assignee is someone else, one deterministic assignee notification. It does not write `chore-templates`. Add Chore (repeating) writes one template with its recurrence. New chore templates (Add Chore repeating, new library chores) and new rooms get an ID that cannot collide: a readable slug of the name (up to 60 characters) plus a Firestore auto-id (`newChoreDocId` in `src/lib/chores/list.ts`, mirroring the shell's `quickCreateId`), for example `take-out-trash-AbCd…`. IDs are never picked from the page's loaded list, which can be a stale offline cache or miss documents another member just created, so a create can never overwrite or merge into an existing document; the library create also runs in a transaction that refuses an existing ID and writes without merge. Nothing depends on readable IDs: chores link to templates by `templateId`, generated instance IDs are derived from whatever the template and room IDs are, and `?room=<id>` links, the room filter, the living house and its room links all read the stored ID (the house picks the pet bowl's room by name). Existing templates and rooms keep their IDs. One-time library assignments use auto IDs, so they never share (and overwrite) the deterministic ID of a generated occurrence or an earlier assignment; older one-time assignments keep their deterministic IDs.

The calendar (`HouseholdCalendar`) runs upkeep, then reads chores and chore templates (`chores.view`), `home-assets` and `vehicles` (`maintenance.view`, turned into due dates with the shared `buildMaintenanceReminders` used by Maintenance and the reminder function), and `pets/{petId}/medication-logs` (`pets.view`), each only when the member may read it. Maintenance items are built by `maintenanceCalendarItems()`: scheduled services from the shared builder (every status) plus expiration fields read directly, recomputed whenever today changes. Repeating chores are projected over the visible range with the server's own recurrence rules (`occursOn`) and occurrence identity (`occurrenceChoreId` and `choreOccurrenceKey`, via `occurrences()`; no assignee involved): an occurrence is planned only while neither its document nor a chore with its occurrence key exists, so a generated chore that was moved, completed or reassigned never reappears on its original day. A source that fails shows an inline alert; the others still render. Medication entries are read with both date shapes (ISO strings and legacy timestamps, via `toDate`) and their `nextDueDate`; `medicationDueEvents` groups them per pet and calls `currentMedications`. Moving a chore writes `originalDueDate` (the day) and `dueDate` (local noon ISO) to the chore document only.

### Assignee identity

Chores and templates moved from the assignee's email (`assignedToEmail`) to their Auth uid (`assignedToUid`). Member privacy release A dual-wrote both; since release C writers store the uid only. Every reader goes through `functions/src/shared/assignee.ts` (shared by the app, the household server actions and the upkeep function):

- Writers set `assignedToUid` only (`assigneeFields`): Add Chore (one time and repeating), library assignment, repeating-chore edits, reassignment, command-palette quick add (`createOneTimeChore`, `repeatingChoreTemplate`) and server generation. A writer that updates an existing record also deletes `assignedToEmail` (and, on templates, `recurrence.assignedToEmail`), because a leftover email of the previous assignee would win over the new uid: reassignment and repeating-chore edits delete the top-level field and replace `recurrence` whole; library assignment merges, so it deletes both copies explicitly. Stopping a repeating chore writes `recurrence: null`, `assignedToUid: null` and deletes `assignedToEmail`. Leaving and removal unassign open chores with `unassignedChoreFields` (`assignedToUid: ''`, "Unassigned") and delete their email (see [Household Governance](../household-governance/README.md)).
- Readers resolve the assignee with `resolveAssigneeUid` (a list of people) or `isAssignedTo` (one person). The email decides whenever the reader can match it to a member, because a browser still on an older build reassigns by rewriting only the email and leaves the previous uid behind. Otherwise the uid decides, but only when it cannot contradict the email: there is no stored email, or the reader does not know the uid's member email. A uid whose member's email differs from the stored email is stale and matches nobody, even when the email names a former member (so a departed member's completed chores never turn into the previous assignee's points, streaks or calendar label). The Chores page resolves once on load and keeps the result in memory as `assignedToUid`, so rows, the reassign menu, assignee pickers, the repeating-chores list and the leaderboard work by uid. The calendar, dashboard facts and streaks, member chore stats in Household Manager, server reminders and the AI overview use the same helpers. Pickers and menus use member uids as values and show display names only, never an email (`memberName`, "Unassigned" when nobody).
- Readers keep the email fallback (release F removes it) because browsers still on a build from before release A write the email alone; the minimum-build check (see [Application Shell](../application-shell/README.md), "Minimum build") reaches release C and later builds only (and only asks them to reload), so it cannot force those older builds off. Records without an email (every record written since release C, and every scrubbed one) resolve by uid for every reader.
- Generated instance ids name no one: `occurrenceChoreId` (`stableSlugify(templateId-roomId-day)`, member privacy release E), whoever the template is assigned to. Chores generated earlier carry the assignee after the day (`recurringChoreId`: the template's email, or its uid); upkeep and calendar planning skip every day whose new id exists or whose occurrence key (`templateId|roomId|day`, stored on the chore or recovered from either id shape by `storedOccurrenceKey`) a chore already holds, so a day that already has its chore, completed or open, is never generated again after the switch, a reassignment or a schedule edit. The key is not rebuilt from `originalDueDate`, which a move rewrites. Missed-instance folding (`collapseMissedRecurring`) keys each series on the member `resolveAssigneeUid` names among the household's people (the Chores page passes its members, the dashboard its member records when loaded), so instances with email and uid and newer uid-only ones form one series, and a chore an older build reassigned by email counts for the member the email names; without people it keys on the email, else the uid.
- One-time assignment notifications use the uid in their state key (`assigned|<day>|<uid>`); notification documents are readable by every member.
- `scripts/ops/backfill-chore-assignee-uid.mjs --project <id>` (dry run, counts only) and `--apply` add `assignedToUid` to chores and templates that only have the email, repair a uid that disagrees with the email (an older build's reassignment), and clear (`''`) a current member's uid that sits next to a former member's email, from the household's member records; pure decisions in `scripts/ops/chore-assignee.mjs` (`resolveAssigneeUidJs` is checked against the shared helper). Each update is guarded by the document's update time, so a document changed meanwhile is skipped and picked up by the next run; unassigned records and emails of former members are left alone. Run it after this release is live and again once older builds have aged out, before any release reads the uid alone.
- The upkeep function knows members' emails only from their protected contact documents (`withContactEmails`; see [Household Governance](../household-governance/README.md), "Member contact"), so email-keyed templates keep resolving without any email on the records. A template that still carries an assignee email is generated only for the member whose contact document holds that email, never by its stored uid (which an older build's email-only reassignment can leave stale): when the contact read fails, or the email names nobody, it generates nothing that run and is retried on the next one. Templates without an email generate as usual.
- Yearly stats: see "Retention" and "Yearly stats, legacy keys" under Invariants and Failure Behavior.
- `scripts/ops/scrub-shared-emails.mjs --project <id>` (dry run, counts only) and `--apply` (member privacy release C) remove `assignedToEmail` and `recurrence.assignedToEmail` from chores and templates, first setting `assignedToUid` to the member the email names when it is missing or stale (members' emails from their contact documents, then the records), and clearing a current member's uid next to a former member's email, so readers resolve the same member by uid afterwards. It kept the email on completed chores without a recorded completer; `scripts/ops/scrub-member-emails.mjs` (release D, same conventions) removes those too, the same way, and `completedByEmail` from every chore (setting `completedByUid` first where it was missing). A completed chore whose credited person (its completer, else its assignee) has left and is named only by the email being removed is credited to that person's identity instead (`completedByUid`, or `assignedToUid` when credited to the assignee, replacing any other uid there, also release C's clearing of a current member's leftover uid; an open chore is cleared as before), so the person keeps their yearly credit. A departed person's identity is their account uid when the household's chores and templates pair their email with exactly one uid that is not a current member's, and that uid with no other email; otherwise it is their former-member key: `former-` and 24 hex characters, an HMAC-SHA-256 of the lower-cased email under a random per-household secret, which cannot be recomputed or confirmed from a guessed email (`scripts/ops/former-member-key.mjs`). The secret and every decision (former-member key to identity, no email) are stored in `households/{householdId}/ops/former-members` (never readable or writable by a client) before anything is written with them and never change, so re-runs, interrupted runs and either script order use the same identity. Before changing any chore, the scrub moves the yearly stats' legacy keys of current members and of these people to the same identities (see "Yearly stats, legacy keys"), so a departed person's archived and retained completions are one score. Credit and stats treat the identity like any uid (`choreStatsMemberKey`), labelled by the stored display name; a chore whose departed person has no settled identity yet keeps its email and is counted. Both also scrub other documents (see [Household Governance](../household-governance/README.md), "Email copies"). Pure decisions in `scripts/ops/shared-email-scrub.mjs` and `scripts/ops/member-email-scrub.mjs`; updates are guarded by update time, and the scripts can be re-run at any time.
- `scripts/ops/rekey-chore-ids.mjs --project <id>` (dry run, counts only) and `--apply` (member privacy release E) move every generated chore whose id still carries an assignee part to its `occurrenceChoreId`: one transaction per chore re-reads the household (nothing is written while it is being deleted), the chore (skipped when changed or deleted since the run read it) and the target ids, creates the same document under the new id and deletes the old one. Every field is kept (assignee, completion attribution, `completionId`, `completedAtServer`, `occurrenceKey`); a chore without `occurrenceKey` gets the one its id names. A day that already has a chore under the new id (two chores for one day, from before upkeep checked occurrence keys) goes to `<id>-2` .. `<id>-9`. One-time chores (auto ids, or a `sourceType`) and ids that are not generated ids are left alone and counted. Without an occurrence key whose room still matches, the day is located from the template's slug forward (`legacyOccurrenceBase`), never from the end of the id, because the assignee part may contain date-shaped text: one date-shaped part after the room is the day; with several, the one whose room part is one of the household's rooms decides, and otherwise the chore is left alone and counted as ambiguous. Every target ends with its day (`assertOccurrenceBase`), followed at most by a `-2`..`-9` slot. Upkeep and the calendar recover keys only by the chore's own room and the ten characters after it (`storedOccurrenceKey`), so they never read into the assignee part. Nothing refers to a generated id: notifications name one-time chores, templates or days; a page that listed a chore just before it moved acts on the old id once, like on a deleted chore (completion, Undo and reopen report it missing and the page lists again; a calendar move or sub-task tick shows its error). Pure decisions in `scripts/ops/chore-id-rekey.mjs`, the transaction in `scripts/ops/chore-id-move.mjs`; re-runnable.
- `scripts/ops/scrub-remaining-emails.mjs` (release E; see [Household Governance](../household-governance/README.md), "Email copies") removes any assignee or completer email still stored the same way as release D's scrub (with the same stored identities of people who have left, so a completion credited to one of them keeps that credit), and replaces assignee or completer labels that are an email by the member's current name ("Member" when the uid names nobody, "Unassigned" without a uid).

## Data Model and Persistence

- Templates: `households/{householdId}/chore-templates/{templateId}`.
- Instances: `households/{householdId}/chores/{choreId}`.
- Rooms: `households/{householdId}/rooms/{roomId}`.
- Chore preferences: `households/{householdId}/chore-settings/preferences`, shape `{ leaderboardEnabled: boolean, updatedAt?: string }`. A missing document means the defaults (leaderboard on).
- Notifications: `households/{householdId}/notifications/{notificationId}`.
- Read-only for the calendar: `chore-templates`, `home-assets`, `vehicles`, `pets` and `pets/{petId}/medication-logs`.

Chores and templates carry `assignedToUid` (optional; older records have only `assignedToEmail`) next to `assignedToEmail` (see Assignee identity). Important types are `Recurrence`, `RecurrenceFrequency`, `MonthlyRecurrenceMode`, `MonthlyNthWeekday`, `ChoreTemplate`, `Chore`, and `Room`; `ChoreRecord` (`src/lib/chores/dates.ts`) is `Chore` plus the optional `completedAtServer` timestamp.

`Chore.templateId` is optional for backward-compatible direct instances. `Chore.sourceType` may explicitly distinguish `template` and `temporary`; existing documents without `sourceType` continue through the established template/instance behavior. `completedAtServer` is optional and additive: existing completed chores without it keep working (their `completedAt` is used), and no migration is needed.

Server-written chore fields (H3): `completedByUid`, `completedByName` (who completed it, D-7) and `completionId` (random id of the current completion) are written only by the completion actions and removed on undo or reopen; older completions have none and are credited to their assignee. Completions recorded before member privacy release D also carry `completedByEmail`, which the completion actions no longer write, undo and reopen remove, and `scripts/ops/scrub-member-emails.mjs` scrubs. `occurrenceKey` (`templateId|roomId|day`, `choreOccurrenceKey` in `functions/src/shared/ids.ts`) is written by upkeep on every generated chore and never changes, also when the chore is moved or reassigned. Generated chores from before the field are recognized by their deterministic id, which embeds the original day (`storedOccurrenceKey`), so upkeep and the calendar work without the backfill; `scripts/ops/backfill-occurrence-key.mjs` stores the key on them (dry run by default with counts only, `--apply` writes just that field, `--project`, `--firebase-tools-login` as the other ops scripts, resumable: chores that have a key are skipped).

Biweekly schedules use `startDate` as an anchor. Monthly day-of-month is limited to 1-28. Nth-weekday supports first through fourth; last-weekday recurrence is not implemented. Pets have no medication schedule beyond each dose's optional `nextDueDate`, so the calendar's upcoming doses are exactly the pending countdowns (one next dose per medication), not a recurring series.

## Authentication, Roles, and Security

The page requires an authenticated user and uses that user's household ID. Assignee discovery uses approved, active `households/{householdId}/members/{uid}` records and their public fields only (no profile reads); a member without a usable display name shows as "Member". The rules validate chore and template shapes (allowlisted fields, types, bounds) and guard the uid assignee (see Uid assignee below).

Navigation uses `chores.view`. Firestore rules enforce granular permissions: `chores.view` to read chores, templates, rooms and chore preferences; `chores.create` to create chores and templates; `chores.complete` for updates limited to `isCompleted`, `completedAt`, `completedSubTasks` and `completedAtServer`; `chores.edit` for other chore and template updates and room create/update; and `chores.delete` for deletes. `chores.assign` is enforced on assignment: creating a chore whose `assignedToEmail` is someone other than the caller (by token email) needs it, while `chores.create` alone still covers a chore for yourself or an unassigned one (`''` or null); any change of a chore's `assignedToEmail` on update needs it, including to yourself (Reassign already requires it in the UI). On templates, setting or changing `assignedToEmail` or `recurrence.assignedToEmail` to someone other than the caller needs it; keeping the current assignee, switching to yourself or clearing it does not (the Edit repeating chore dialog offers exactly those choices without `chores.assign`).

Shape validation (QA-8): chore writes may only set `task` (1 to 500 characters, required on create), `notes` (up to 5000), `assignedToEmail` (optional; no longer written), `assignedToUid`, `assignedToDisplayName`, `dueDate`, `originalDueDate`, `roomIds` (list, at most 50), `isCompleted` (bool), `completedAt`, `completedAtServer` (timestamp), `completedSubTasks` and `subTasks` (lists, at most 100), `templateId` and `sourceType` (`temporary` or `template`). Templates may only set `task` (required on create), `notes`, `roomIds`, `subTasks`, `assignedToUid`, `assignedToEmail` and `recurrence`; `recurrence` is null or a map of `frequency` (`daily`, `weekly`, `biweekly`, `monthly`, required), `interval` (1 to 52), `assignedToEmail` (optional), `startDate`, `dailyOptions` (`excludeWeekends`), `weeklyOptions` (`daysOfWeek`, at most 7) and `monthlyOptions` (`mode`, `dayOfMonth` 1 to 31, `nthWeekday` with `week`/`dayOfWeek`). On update only added or changed keys are checked, so chores and templates holding legacy fields stay editable. A recurring assignment merged into a template that was deleted meanwhile (no `task`) is now refused instead of creating a nameless template. On-demand upkeep requires `chores.view`. Pending `newuser` members are denied by rules.

Uid assignee: chores and templates also accept `assignedToUid` (a string up to 128 characters; empty or null when unassigned), dual-written with `assignedToEmail` by member privacy release A and written alone since release C. It is guarded like the email: without `chores.assign`, a uid is accepted only when it is empty, your own uid next to your own email (`choreAssigneeUidMatchesEmail`), or, when creating a chore or setting a template, your own uid with no email beside it (`choreAssigneeUidIsCallerOrMatches`). Membership records carry no email, so the rules never match a uid to someone else's email: filling in another member's uid next to their email needs `chores.assign`, like every other change of a chore's assignee (even to yourself, even once no email is left).

Completion attribution, rules stage R1 (this release, compatible with older clients): the chore allowlist includes `completedByUid`, `completedByEmail`, `completedByName`, `completionId` and `occurrenceKey`, but clients may not set them on create, nor set, change or remove them on update (only the Admin SDK writes them); and a client write that completes a chore is denied while the chore still carries attribution (an older release reopened a server completion with client writes and tries to complete it again), so points are never credited to a stale completer. Clients may still toggle `isCompleted` with stamped writes, which older releases need.

Rules stage R2 (next release, not deployed): clients may not change `isCompleted` at all, so every completion, undo and reopen goes through the server actions and eligibility (CH-2) can't be bypassed with a direct write. Order: deploy R1 rules, run the occurrence key backfill, deploy functions (upkeep writes and checks `occurrenceKey`), ship this client, wait one release window watching for denied chore writes, then deploy R2. Rollback is redeploying R1.

Completion stamp rule (every chore write): a chore that becomes completed must carry `completedAtServer == request.time`. A completion with no stamp, or a client-chosen one, is denied. A chore that stays completed must keep its stamp unchanged, and a chore can be created already completed only with a server stamp. So completion times, which points and streaks read, can't be backdated or forged. Chores completed before the stamp existed (phase 1, 2026-11-06) remain editable and can be reopened, and stats fall back to `completedAt` for them. Chore preferences may be written only by owners and admins (role, not overrides), only at `preferences`, only with `leaderboardEnabled` (bool) and `updatedAt` (string); nobody may delete them.

The UI never shows an action the member cannot perform, mirroring the rules through `choreCapabilities(permissions)`: the completion checkbox is disabled without `chores.complete`; Add Chore and the library's create need `chores.create`; reassign, room add/edit and library edit need `chores.edit`; delete (rows, library, rooms, clearing missed instances) needs `chores.delete`; editing or stopping a repeating chore needs both `chores.edit` and `chores.delete` (it removes the old open instances); removing a room from a library chore without `chores.delete` is refused inline; picking someone other than yourself as assignee needs `chores.assign`; calendar rescheduling needs `chores.edit`; the leaderboard switch is shown to owners and admins.

## Integrations and Background Processing

- Assignment notifications go only to someone other than the person assigning (no "New chore assigned" for chores you give yourself). Template assignment notifications are best-effort household notification writes. One-time Add Chore batches its direct chore and deterministic assignment notification together so a successful creation cannot omit its initial notification.
- Overdue alerts (after 7:00 local time) and each person's daily reminder (at their chosen time, in their own `users.timeZone`, falling back to the household's) are created on the server. The hourly `householdUpkeep` Cloud Function (`functions/src/index.ts` → `functions/src/reminders.ts`) runs the same idempotent step for every household; the Chores page and the calendar also run it on demand through `syncHouseholdUpkeep` (`src/app/chores/actions.ts`, authorized by `chores.view`) so a new recurring assignment appears immediately.
- Deterministic per-user/day notification IDs suppress same-day duplicates.
- New records can trigger the shared FCM Cloud Function.
- Recurring instances for the next 30 occurrences are generated on the server from `functions/src/shared/recurrence.ts`, using the household `timeZone` (default `America/Chicago`). Chore IDs are `stableSlugify(templateId-roomId-day)` (`occurrenceChoreId` in `functions/src/shared/ids.ts`); chores generated before member privacy release E have the template's assignee email or uid after the day until `scripts/ops/rekey-chore-ids.mjs` moves them. The template's assignee is resolved by uid (`resolveAssigneeUid`), or, for a template that still carries an email, only by that email matched against the members' contact documents (see Assignee identity); nothing is generated for someone who is not an approved member. Generated chores carry `assignedToUid` (no email since release C) and the member's display name ("Member" when none, never the email). Chore reminders match chores with `isAssignedTo` and are targeted by `targetUserUid` only. A rescheduled instance keeps its ID, so upkeep never recreates it on its old day.
- Feedback: `playFeedback('complete')` on completion, `'celebrate'` for "House is clean", `'add'` after adding or moving a chore.

## Invariants and Failure Behavior

- Defensive normalization supplies defaults for old recurrence records missing interval, weekdays, anchors, monthly mode, or day.
- Retention: completed chores older than 90 days (household-local) are deleted by the server step, so leaderboard totals cover at most 90 days. Before deleting, upkeep adds each removed chore to `households/{householdId}/stats/chores-{year}` (the year, in the household timezone, of its authoritative completion instant: `completedAtServer` when present, else `completedAt`, from `choreCompletionInstant` in `functions/src/shared/completion.ts`, which `completionInstant` in `src/lib/chores/dates.ts` also uses; retention itself still keys off `completedAt`) in the same transaction as the delete: `{ year, completed, byAssignee: { <key>: count }, names: { <key>: displayName }, updatedAt }`, where the key is `choreStatsMemberKey(uid)` (`uid-<uid>`, `functions/src/shared/ids.ts`). Totals are read, added to and written inside the transaction (`addPurgedChores` in `functions/src/shared/chore-stats.ts`), and a chore is counted only when it is actually deleted, so repeated or overlapping runs never count it twice. Clients can read the document with `chores.view` and can never write it. Each removed chore counts for its completer, else its assignee (`creditedPerson`: `completedByUid`; an older `completedByEmail` matched to a member; else the assignee: an `assignedToEmail` that names a member, else `assignedToUid` unless a known email of that uid's member contradicts the stored email). A recorded completer who left keeps the credit under their uid. `names` labels are never an email. A chore whose credit could depend on an email (`purgeNeedsMemberEmails`: no `completedByUid`, and a `completedByEmail` or `assignedToEmail`) is purged only when upkeep could read the members' contact documents (`readMemberContactsOrNull` returns `null` on failure, distinct from no contacts) and `creditedPerson` finds its person (`purgeMustWait`), also inside the purge transaction: a transient failure never deletes a chore without its credit, and a completion credited by email to someone who has left waits until `scripts/ops/scrub-member-emails.mjs` gives it a former-member key (see Assignee identity). Chores credited by uid are purged as usual. Home Wrapped credits retained completions with the same rule (it knows no emails but the viewer's own, and every chore stored since uids were written resolves by uid), so a completion keeps its member when it crosses the 90-day boundary, and adds these yearly totals to the retained completions.
- Yearly stats, legacy keys: documents written before member privacy release D keyed people by `choreStatsAssigneeKey(email)` (a slug of the email's local part plus a hash of the whole email), which let anyone who reads the stats see the local part and confirm a guessed address. Nothing writes those keys any more. Upkeep folds a current member's legacy key into their uid key whenever it adds to a document (`foldLegacyStatsKeys`, emails from the contact documents); Home Wrapped folds the viewer's own and counts any other legacy key on its own, labelled from the stats. `scripts/ops/rekey-chore-stats.mjs --project <id>` (dry run, counts only; `--apply`, `--firebase-tools-login`) re-keys every stats document in its own transaction: a current member's legacy key is folded into their uid key, a departed person still named on a chore or template goes to their identity, the one `scripts/ops/scrub-member-emails.mjs` gives their chores (see Assignee identity); any other (no chore names that email any more) goes to an opaque key of its own (`unknownLegacyKey`: an HMAC of the legacy key under the household's secret, the same in every run), with the same count and label; `completed` is unchanged and a re-run finds nothing to do (pure decisions and the keys' JavaScript twins in `scripts/ops/chore-stats-rekey.mjs`, the per-household steps both scripts share in `scripts/ops/member-privacy-household.mjs`). Run it once the release's functions are live, before or after `scripts/ops/scrub-member-emails.mjs` (which re-keys the stats of current members and of the departed people it scrubs, and leaves keys of nobody named to this script).
- Room deletion (confirmed) updates templates but not existing chore instances; unresolved room IDs show under "Unknown Room".
- Generation and reminders no longer depend on anyone opening the app.
- Generation is create-only and retention re-checks: inside each upkeep transaction a generated instance is written only if it is still absent, and a completed chore is purged only if it is still completed with the same `completedAt`, so overlapping hourly and on-demand runs never reset or remove work done in between. Instances are also created only if their source template is unchanged since the run read it (same update time), so editing or cancelling a recurrence while a run is in flight is never undone.
- Best-effort notification failures do not roll back chore writes.
- Every client that completes, undoes or reopens a chore must use `src/lib/chores/complete-client.ts` (the server actions); the rules deny unstamped client completions and any client write of the attribution fields. Completion needs a connection.
- A generated occurrence (`occurrenceKey`) gets at most one chore: upkeep skips a key that any chore already holds (read from the listing and re-checked inside the creating transaction), whoever it is assigned to.
- Field problems in every chore dialog are shown inline with `FieldError` (with `aria-invalid`/`aria-describedby`), never as toasts; failures use `toastError`, so raw Firebase text never reaches users.
- Motion follows the shared contract: under reduced motion (system or in-app) the checkbox, row entrance and exit, count tickers, podium, agenda slide and calendar moves show their end state instantly and confetti does not render; "House is clean" shows its finished, sparkling house at once. Hover effects are not used for meaning, and no animation delays content, focus or errors.
- Assignment forms show one-time date controls or recurring controls, never both.
- Active and completed chore instances use the same confirmation contract before permanent deletion.
- Future/completed view switches use the shared control dimensions; their thumbs must remain inside the track at desktop and mobile widths.

Completion rules, stage R1 (ahead of the shared completion operation): chore writes may carry `completedByUid`, `completedByEmail` (older completions only), `completedByName`, `completionId` and `occurrenceKey`, but only the server (Admin SDK) writes the first four; clients can never set, change or remove them, and a client completion is refused while the chore still carries someone's completion attribution. `occurrenceKey` is immutable for clients. Older clients can still toggle `isCompleted` with stamped writes until stage R2.
