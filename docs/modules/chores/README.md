# Chores

## Purpose and Scope

This module owns rooms, chore templates (the chore library), one-time and recurring assignments, generated chore instances, reassignment, subtasks, completion/history, the household leaderboard (points with the CH-20 limits, fair streaks, contribution, the closed-week podium and its allowance payout), the household calendar at `/calendar`, and chore notification creation. It does not own household membership, push transport, or the maintenance and pet data the calendar reads.

## User-Facing Capabilities

- Manage chores at `/chores`. The page header is left-aligned with its actions in the header row, like the other modules, and stays one row on phones (CH-18): **Add Chore** (primary; "Add" on phones), **Calendar** (link to `/calendar`) and **Chore Manager** (both icon buttons below the `sm` breakpoint, named by `aria-label`) (Chore library, Repeating chores, Rooms, and for owners/admins a **Show leaderboard** switch and **Allowance** (CH-29)).
- **Add Chore** is the one-dialog way to add a chore: name, who (defaults to you), one time (due date, default today) or repeats (daily/weekdays, weekly or every 2 weeks on chosen days, monthly by day or nth weekday), an optional room and notes. One-time chores are direct chore documents (`sourceType: 'temporary'`); repeating chores create a library template with a recurrence, and server upkeep generates the instances. With no rooms yet the room field says so and offers **Create a room** (when the member may edit rooms).
- The chore library still holds reusable chores: create, edit, delete (with confirmation) and tick several to assign them together. The assign dialog is titled after the chore ("Assign Reset the kitchen" or "Assign 3 chores"), defaults the assignee to you, and shows one-time or repeating controls, never both. Weekday toggles show a filled selected state.
- **One tap completes** (H05): the round checkbox next to a chore marks it done. The box fills and a check draws itself, the row slides out of To Do, confetti bursts from the checkbox (bigger for chores with more steps), a `complete` sound/haptic plays (`playFeedback`, only if the member enabled it), and a toast offers **Undo** for the shared 10-second Undo window (`CHORE_UNDO_MS` = `UNDO_WINDOW_MS`, `src/lib/undo-window.ts`). Each completion has its own Undo toast (up to the shared limit of 3), so a second completion never takes away the first one's Undo (CH-10). Completion runs on the server (H3, see Architecture): a chore due after today (household timezone) cannot be completed, so its box is disabled (also in Select mode); the page judges this on the household's day (`useHouseholdToday`, `isDueAfterHouseholdDay`), the same day the server uses, not the device's, so a member in another timezone can complete a chore exactly when the server accepts it and a refused one says "Not due yet: … is due Tue, Nov 11. It can be completed from that day."; a chore someone else already completed shows as done with "… was already done by Sam."; offline nothing is queued: "You're offline. Not completed." and the row stays open. Undo reverts only that completion: if someone else already reopened it the chore simply stays open; if someone reopened and completed it again, or deleted it, meanwhile (`stale`, `missing`), it says "Already changed" and re-reads the chore so the page shows what is stored (removing a deleted one) rather than the completion it saved; only a request that never reached the server (offline, failed) puts that saved completion back (`settleUndo`, `applyUndoSettlement`, `applyRefreshedChores` in `src/lib/chores/patch.ts`), clears the completion fields and puts the steps back only if they are unchanged since; the page then shows the steps the server stored (restored, or kept because someone changed them meanwhile), so a later step toggle starts from them. Completing a chore with open steps ticks the steps too. Ticking one step writes only that step (`arrayUnion` / `arrayRemove`), so two devices ticking different steps both count; editing a template's steps drops ticks of steps it no longer has from its open chores (CH-10). Ticking a completed chore's box asks "Reopen …? It goes back to To Do, and the points Sam got for it are removed. Its ticked steps stay ticked." (**Keep it done** / **Reopen**) and then reopens it on the server (CH-6). The completion's Undo follows the same rule on the server (`undoChoreCompletionAs` with the caller): knowing a completion id is not enough. Only the person who completed it, its assignee (a completion from before completer attribution counts as the assignee's) or a member with `chores.edit` may reopen it (`mayReopen` in `src/lib/chores/completion.ts`, checked by the page and enforced by `reopenChoreAs`, which returns `refused` otherwise and writes nothing); anyone else is told who can. Confetti fires at most once per chore per visit, and only after the server confirmed. While a completed row slides out of To Do it is `aria-hidden`, inert and ignores the pointer, so a chore has exactly one actionable row across To Do, Future and Completed. `inert` is set through `inertProps` (`src/lib/inert.ts`), which passes the value the running React writes as the attribute (`true` under the React 19 that Next's App Router bundles, an empty string under React 18), so the row's `inert` property is true in the browser and React logs no warning (`tests/unit/inert.test.ts`). If a request fails, only its chores roll back (other completions made meanwhile are kept).
- **House is clean** (H05): when the last chore due today (or overdue) is completed, a short full-screen card says "House is clean" over a small house drawn from the household's rooms (up to 8; rooms worked in today first, a single "Home" room when none are set up), and the rooms sparkle one by one (a tile flash and stars; opacity and transform only). It shows at most once per household per day on a device (`localStorage` key `homehub.houseClean.<householdId>.<day>`, plus an in-memory flag when storage is blocked; `houseCleanShown` / `markHouseCleanShown` in `house-clean.ts`, which the dashboard's HP-34 celebration uses too, so the moment never repeats between the two), lasts at most 1.5 s, ignores the pointer (`pointer-events: none`), never takes focus, and disappears at the first key, click, touch or scroll. Screen readers hear one polite "House is clean" status. It is drawn by `house-clean-moment.tsx`, not by the dashboard's `LivingHouse`: that component is an interactive page hero (links, peeks, a seasonal toggle, a global key listener) that needs the dashboard's full facts and has no room-by-room sparkle, so it does not belong in a non-interactive overlay.
- **Your chores are done** (CH-22): when your own To Do (open chores assigned to you, due today or overdue) clears through a completion on this page while the rest of the house still has work, a small pill says "Your chores are done, Sam!" (first name; `person-done-moment.tsx`, `ownListCleared` and `personDoneTitle` in `house-clean.ts`) and the `celebrate` feedback plays. It shows at most once per person per household per day on a device (`homehub.personDone.<householdId>.<uid>.<day>`, the same flag helpers as "House is clean"), stays 2.5 s, ignores the pointer, never takes focus, is one polite status for screen readers, shows without motion under reduced motion, and lives outside the toast stack, so the completion's Undo toast stays. When the whole house is clean, "House is clean" is the moment instead. The wall tablet shows the same pill (see Devices).
- **Overdue and Mine filters in the URL** (GOAL-filters, HP-25): `/chores?due=overdue` keeps only overdue chores in To Do (a row whose earlier missed instances were folded into it stays, since that work is overdue; Future and Completed are unchanged) and `/chores?who=me` shows only the reader's chores everywhere on the page (`matchesWhoFilter` in `src/lib/chores/list.ts`, which uses `isAssignedTo` from `functions/src/shared/assignee.ts`: a uid-only chore by uid, an older one by email). The **Overdue** and **Mine** toggle buttons beside the room filter have static labels with `aria-pressed` and write the URL in place (`history.replaceState`) through `choresFiltersHref`, which keeps the other filters and always orders them `room`, `due`, `who`; reload, Back and the dashboard brief's links (`/chores?due=overdue&who=me`) open the same view. With the overdue filter and nothing overdue, To Do says "Nothing overdue". The To Do room groups remount on every filter change (`choresFiltersKey`), so a room that a change brings in (turning Mine off lists housemates' rooms) opens like the others instead of arriving collapsed.
- **Room filter in the URL**: `/chores?room=<roomId>` opens the page filtered to that room (`?room=general` for chores without a room); the **All Rooms** filter button shows the room. Choosing another room or All Rooms updates the URL in place (`history.replaceState`; All Rooms removes the param). The filter is read from `useSearchParams()` on every render, so Next.js links, Back/Forward and the dashboard's room links all keep it in step. An unknown room id (a deleted room, a stale link) falls back to All Rooms once rooms have loaded. The page container, and the route skeleton, carry `view-transition-name: room-<roomId>` (`roomSharedId()` in `src/lib/chores/url-state.ts`) while a room is requested, as the landing target of the living house's room → Chores morph (H01, H12).
- **Select mode**: **Select** switches the checkboxes to selection checkboxes ("Select …") for bulk completion ("1 chore selected", "3 chores selected"); **Complete selected** confirms first when selected chores have open steps ("1 selected chore still has open steps", each listed with "2 unfinished steps"). Plurals use the shared `pluralize`.
- **Motion and hints** (H12, H28): chore rows in every room group enter with the shared `Stagger`/`StaggerItem` (at most 30 ms apart, 400 ms in all; none under reduced motion; rows are interactive from the first frame), and the To Do, Future, Completed and room-group counts are `NumberTicker`s (screen readers and accessible names get the final number). **Add Chore** shows "New chore from anywhere  N" in a tooltip on hover or keyboard focus and carries `aria-keyshortcuts="N"`, through the shared `ShortcutHint` (`src/components/ui/shortcut-hint.tsx`, keys read from the `SHORTCUTS` map).
- **Missed repeating chores fold**: for each repeating series (generated instances of a template that currently repeats, with the same rooms and assignee; one-time library assignments, marked `sourceType: 'template'`, and temporary chores never fold) only the latest instance due today or earlier is listed; older missed ones show as "+N earlier missed" on that row (instances due on the same day are never folded into each other), and members who may delete chores can **Clear** them from that row.
- Rows show the chore name on up to two lines (no single-line truncation on phones), the due day ("Today", "Yesterday", "Tue, Aug 4"), an **Overdue** badge, step progress, on completed rows who did it ("Done by Sam · Nov 4", D-7: `completerLabel` uses the current member name for `completedByUid`, else the stored `completedByName`, and never an email; older completions just "Done Nov 4"), and the assignee as a `MemberAvatar` (name beside it from the `sm` breakpoint). Overdue rows keep the normal surface with a destructive left border and badge (no red-on-red text); the badge (destructive text on a 10% destructive tint over the card) meets WCAG AA in all five presets (unit-tested). Reassign is a menu on the avatar (for members who may edit and assign); for members who may delete, delete sits behind the row's **More actions for …** menu (**Delete…**, which still confirms), never beside Done (CH-16). Tapping the name (with its small chevron) opens the chore's **detail sheet** (CH-15, `chore-detail-sheet.tsx`, a side sheet that follows the live chore): assignee, due day (or Done), rooms and whether it repeats; notes; steps (tickable by members who may complete chores, like the rows); **History**: this chore and the other days of its series (same library chore) done in the retained 90 days, newest first, at most 10, with who did each (`choreHistory` in `src/lib/chores/detail.ts`); and for members with `chores.edit` **Edit** (name and notes, and the due day for a chore that is not a generated day of a repeat, which moves on the calendar instead; validated like the rules, 1-500 and up to 5,000 characters) and, for a library chore, **Edit every day** (the library editor). Every control in a row (the done check, the selection checkbox's cell, the name button of a chore with details, the avatar menu, the More actions menu, **Clear**) is at least `--target-min` itself (44 px, 48 px on touch screens, D-2); in Select mode the whole cell is the checkbox's `<label>` (a 24 px box), so a tap anywhere in it selects; each step in the details is a `<label>` row of that height (`StepRow`, 20 px box, 24 px and 16 px text on touch screens) so the whole row ticks the step and the hit areas never overlap, and the filter buttons, room headers and the To Do, Future and Completed headers are at least that tall too. On a touch screen the assignee's name beside the avatar is 14 px. The section and room headers keep the label and its live count in one element, so the count sits against its brackets ("Kitchen (1)") at every size.
- **Focus after completing** (CH-16): completing a row with its check moves focus to the next open row's own done check in To Do (the one before when it was the last; `focusAfterCompleting` in `src/lib/chores/row-focus.ts`), never to the page body. Only a row's main check counts (`CompletionCheck` with `rowCheck`, `data-chore-row-check`): a step checkbox in an expanded row, even of the chore being completed, is never the target, and neither is another copy of the same chore in another room group (a chore in several rooms has a row in each, and they leave together; `pickFocusTarget`).
- **Rendering** (CH-26): rows are memoised (`MemoRow` in `chore-list.tsx`): the handlers they receive are stable (they read the latest props through a ref), each row gets its own booleans (selected, open), and a listener snapshot keeps the previous object for every chore whose content is unchanged (`keepUnchangedRows` in `src/lib/chores/live.ts`), so a tick re-renders only the rows that changed. A row measures layout only when its own group's rows change (`layoutDependency`), so only the changed group animates, and under reduced motion (system or in-app) rows have no layout animation at all, so the list is still from its first frame. `tests/e2e/tablet-pages.spec.ts` waits until the page has settled (animations finished and every control's box unchanged across 100 ms) before measuring hit areas. The route's loading state and the page while its listeners answer render the same skeleton (`chores-skeleton.tsx`), so one skeleton shows until the page is ready. The leaderboard's contribution ring is 48 px with a 12 px percentage.
- Empty states use `EmptyState`: a household with no chores invites you to **Add your first chore**; an empty To Do says "Nothing due today" (or "All done for today" when you finished something) and names the next chore.
- **Room view** (CH-13): with one room chosen (`?room=<roomId>`, or `?room=general` for Around the house) the page shows the room layout: a compact header (no subtitle), a room header (`room-hero.tsx`) with the room's icon and name as large as 36 px, "N to do" (or "Nothing left to do here today."), counted before the Overdue filter; with Overdue on it adds "· nothing overdue" or "· 2 overdue" (`roomSummary`), so the filter never makes today's work look finished, and a **Done today** strip of the room's chores completed on the household day, newest first, with the completer's avatar (`doneTodayEntries` in `src/lib/chores/room-view.ts`; never an email). Rows are large cards (18-20 px names, the assignee's 36 px avatar and name always shown; on a narrow phone the assignee's name is at most 80 px and shrinks and truncates before the chore's name does, so a long name never squeezes the chore out or overflows the row) and the leaderboard is the ribbon at the top at every width, with no side column.
- **Leaderboard ribbon** (CH-13, CH-18): below the `lg` breakpoint, and in the room view, the leaderboard is a one-row ribbon above the list (`leaderboard-ribbon.tsx`): each member's avatar, name, points (stars for child accounts) and streak, highest first, plus a **Leaderboard** button (`aria-expanded`) that opens the full card under it. The list scrolls sideways inside the ribbon and is its own positioned container, so the members' screen-reader labels (absolutely positioned) never widen the page on a phone (`tests/e2e/chores-ux.spec.ts`). Wide screens keep the full card beside the list.
- **Rotations** (CH-28): in **Repeating chores**, editing a chore offers **Take turns** to people who may assign chores (`chores.assign`) when at least two people can be assigned (kid profiles cannot yet, HO-15d). Tick who takes turns and set the order with the up and down buttons (rows and buttons 48 px on touch, D-2); the first person does the next occurrence. The table shows "Sam, Alex and Kim take turns". Saving replaces the open generated days, so the new order shows at once; changing only the schedule keeps the order counting from the same day. Stopping the schedule, or assigning the library chore to one person as Repeats, removes the rotation. Someone without `chores.assign` who edits a rotating chore sees the turns as text ("Ask someone who can assign chores to change the turns.") and saving keeps them unchanged.
- **Leaderboard** ("This week", H06, beside the chart on wide screens, behind the ribbon elsewhere): this week's points per member (the household's week, CA-16: Monday to Sunday, or Sunday to Saturday when the household's week starts on Sunday) (10 per chore, +2 per step, +5 when done on or before its due day; the points go to whoever completed the chore, D-7), at most 100 points per person per household day, and none for a one-time chore you added for yourself (CH-20); a fair streak flame (CH-19: consecutive days the member had chores due and every one of them was done by the end of that day, by anyone; days with nothing due neither break nor extend it, a late completion does not repair a missed day, a missed day that upkeep expired out of To Do (CH-7, an entry in `stats/missed-recent` for that member and day) still breaks it exactly as the open chore did, and an open chore due today does not break it until the day is over: "(keep it going today)"); "N done · X of Y assigned done"; and a contribution ring (CH-21: the member's share of the chores current members completed this week, so the rings add up to 100%). Chores assigned to someone who is no longer a member are left out of every count. A line under the list states the rules (points per chore, step and on time, the daily cap, self-added chores, streaks). Child accounts collect stickers (one per chore this week that earns points) instead of points. The podium shows the week that has closed, on the first two household days of the next week (Monday and Tuesday, or Sunday and Monday for a Sunday week; `PODIUM_DAYS`, `podiumWeekStart(today, weekStartsOn)`), with a crown for its MVP; it never shows before the week ends. Owners and admins can turn the leaderboard off for the household.
- **Allowance from points** (CH-29): owners and admins open **Chore Manager > Allowance** and set whole cents per point (0, the default, is off; at most 100; inline error otherwise; "100 points pay $5.00"). When a rate is set, the closed week's podium lists every member who earned points with their points and payout ("Allowance at 5¢ a point"), children included. The podium's results come from upkeep's snapshot of that week (`stats/week-{weekStart}`, read live by `useClosedWeekPodium`), so a later Undo, the 90-day retention or a new rate never change them; until upkeep has written it, the page computes the same results from the retained chores at the current rate. Money is shown in US dollars, as in Maintenance. Registered wall tablets have no allowance control (the setting is changed only from a personal device).
- **Calendar** at `/calendar` (H19, replaces the old calendar dialog, D11; audit section 6): Day (agenda), Week and Month views of chores (each chip shows its assignee's avatar and colour, CA-10; colours from `memberColorMap`, members placed in join order, so each has the same colour as on Household and Chores), maintenance due dates and expirations, projected later repeats of maintenance schedules (dashed, CA-23: `projectedMaintenanceEvents`, the next due days if each is done on its day, by the shared `nextDueDay`), pet medication (doses given and upcoming doses), logged pet care (CA-23, `careEvents`, on the household day) and pantry expiry dates (CA-23, `pantryExpiryEvents`, in-stock items only, never "overdue", linking to `/shopping?tab=pantry`), for the whole visible range: future occurrences of repeating chores that the server has not generated yet (it makes the next 30) appear as dashed "planned" items, and warranty, registration and inspection expirations show on their date however far ahead (an expired warranty is shown but never counted as overdue; a lifetime warranty, asset `warrantyLifetime: true`, never expires and is not shown). Everything is live (CA-1): changes from other devices, upkeep and this page arrive without a reload. **Today is the household's day** (D-6, CA-7: `useHouseholdToday(household.timeZone)`), the day completion is judged on; it rolls over at household midnight and when the tab becomes visible again, together with overdue flags and maintenance statuses, and a view that was showing today moves with it. Weeks and months start on the household's **Week starts on** day (CA-16, Monday unless set to Sunday; see Data Model). Overdue chores and maintenance stack in a red **Overdue** rail, where missed days of one repeating chore fold into one chip with "×9" (CA-2, `foldedOverdueRail`, the `collapseMissedRecurring` rule Chores and the dashboard use; the count counts that chip once). Below 1280 px the rail and the key are a slim strip above the calendar, so the week gets the full width on a wall tablet (CA-9). The key lists members (tap one for **only their chores**, again for everyone, CA-24), what dashed (planned) and a red edge (overdue) mean, and kind chips (Chores, Maintenance, Medication, Pet care, Pantry) that switch kinds on and off (`filterEvents`; a person filter keeps house items). Month cells show up to three items (dots on phones); the whole cell selects its day and the day's list below the grid scrolls into view (CA-13); moving to another month selects today when it is in that month, else the 1st (CA-18). The Month grid is a `role="grid"` with one tab stop and arrow keys (a day or a week; CA-19); its cells' chips are previews that are not tab stops (the day's list below holds them). Week view stacks days vertically on phones; on wider screens each day is an `h3` column whose items scroll inside it, with "+N more" (opening that day) after six (CA-14), "Nothing planned" on empty days at every size (CA-18), and a **Days / People** switch: **People** shows per-person lanes (CA-21, owns CH-14: a row per member with their chores and a **House** row for maintenance, pets, pantry and unassigned chores, `laneRows`). In the current week a **Fair share this week** strip lists, per member, how many of their chores due this week are done ("2 of 5 done") and their share of what the household completed this week (CH-21's contribution), from the leaderboard's own `computeChoreStats` (CA-26). **Day** is the agenda for one day: the default on phones (below 768 px when the page opens; Week elsewhere), it lists that day's items (staggered in, sliding 16 px from the side you moved toward, ≤ 250 ms, nothing under reduced motion), and today's card glows with a **Today** badge. Swiping changes the day in Day view, the month in Month view and the week on phones; never in Week view on wider screens, and never when the finger starts on an item (CA-11, CA-12). The keyboard equivalents are **Previous day**/**Next day** (or week/month) and, with the agenda focused, the Left/Right arrow keys (ignored while focus is on an item inside it or with a modifier). Switching views keeps the selected day in view. After 2 minutes without input the page shows Today again (CA-12, `useIdleReturn`; never under an open details panel or while an Undo is showing; registered tablets have their own idle return). Upcoming medication doses come from the Pets module's own model: each active medication course's next due dose (wherever it falls, for the Overdue rail) and every scheduled occurrence in the visible range after it, bounded by the range alone, so a dense schedule fills every visible day (`courseDueEvents` with `occurrencesBetween`, the shared schedule model of `functions/src/shared/medication-schedule.ts`, so a twice-daily course shows both doses each day with their times, PE-27d), linking to `/pets/<petId>?tab=medication&dose=<courseId>`, and one per legacy medication still counting down that no course has taken over (`currentMedicationsOn` for the household's day, which the pet card chips and the server reminders mirror, PE-7b), linking to `/pets/<petId>?tab=medication`; amber and dashed ("Medication due", "Due 8:00 PM", "Due in 2 days"), the next dose red and in the Overdue rail when overdue; a finished course shows none; logged doses stay green ("Medication given") on the household day they were given (`medicationEvents(entries, timeZone)`), not the viewer's device day. Events get unique ids (`withUniqueIds`), so two same-named medications never collide (CA-7). The Overdue count is a `NumberTicker` (in one element with its label, so it never drifts from the brackets). Every item chip, the month grid's day numbers, its "+N more", the view switches, **Today**, Previous/Next, filters and person buttons are at least `--target-min` (44 px, 48 px on touch screens, D-2); chip titles wrap to two lines, 15 px on touch screens, and the **Today** pill is 14 px (CA-9); the subtitle under the page title is hidden on landscape touch screens. Each item opens a details panel with a link to its module (a chore links to `/chores?room=<room>&chore=<id>`, which opens Chores on its room and marks that chore for a moment, CA-17), and hovering (mouse) or keyboard-focusing it for 400 ms shows the shared `PeekCard` (H26) with its kind, title, who or what, date and status (not while its panel is open). Chip names say ", planned" for planned items, "missed N times" for a folded rail chip, and the due date in the rail (CA-19).
- **Mark done** (calendar, CA-8): a chore's details panel has a large **Mark done**, and the Day agenda, the Month day list and the Overdue rail show a 48 px **Done** beside each open chore that is due (none for planned days). It is the Chores page's completion: `completeChoresOnServer` (`src/lib/chores/complete-client.ts`, the `completeChores` server action), so CH-2's rule (nothing before its day, household time zone) and D-7's credit (the person signed in) hold on the server; a chore due later shows **Mark done** disabled with "Not due yet: it can be completed from Tue, Nov 11." Done plays the `complete` feedback and confetti (none under reduced motion), and a toast offers **Undo** for 10 s (`undoCompletionOnServer`; "Already changed on another device." when it was changed meanwhile). Refusals ("already done by Sam", "Not due yet", offline) are toasts and the chip goes back. Needs `chores.complete`.
- **Move** (calendar): members with `chores.edit` can drag an open chore to another day with a mouse (the "Drag a chore…" hint shows only for fine pointers; a cancelled drag is reset on `dragend` and a drop moves only the chore that drag started with, CA-4; the drop highlight is a `data-drop` attribute, so a drag re-renders no chip, CA-20), or open it and pick **Today**, **Tomorrow** or one of the next weekdays, or type a date in **Move to date** (CA-11). A generated chore moves by writing `originalDueDate` (the day) and `dueDate` (local noon ISO); its Undo writes the previous values back, removing `originalDueDate` for an older chore that had none (CA-7). A **planned** day moves through the server (CA-15, see Architecture), which creates that occurrence now on the new day; its Undo (bound to that move by a server-only operation id) deletes it while untouched, so the day goes back to planned. Each move has its own Undo toast (group `chore-move:<id>`), so a second quick move keeps the first one's (CA-7; up to 3 toasts, SL-17). Maintenance, medication, care and pantry items are read-only.
- **Skip and "We're away"** (calendar, CA-27, the skip mechanism of CH-3): members with `chores.delete` get **Skip this day** in a repeating chore's details (generated or planned, today or later) and **We're away** in the header: pick the first and last day and every repeating chore on them (open or planned) is skipped through the `skipChoreDaysAction` server action (`chores.delete`; `src/lib/server/chore-day-skips.ts`): in one Admin SDK transaction the days' occurrence keys go into the templates' `skippedOccurrences` (`withSkippedOccurrences`, today or later, only keys of that template), and each chore that holds one of those days (the id the calendar saw, the occurrence's deterministic id, or any chore carrying its occurrence key, so a day sent as planned that upkeep generated meanwhile is found too) is re-read and deleted only while it is still that open occurrence (same template and occurrence key, not completed, no one-time `sourceType`), so a chore completed or changed meanwhile is kept ("1 changed meanwhile and stayed."). The deleted chores' fields are kept server-only, one document per chore under the operation record (`calendar-ops/{opId}/removed/{n}`), so a long range never nears Firestore's 1 MiB document limit; a skip names at most 120 days (`MAX_SKIP_ITEMS`; **We're away** says so and refuses a longer list) and is refused as too many past the 500-write transaction limit. The record keeps, for its Undo, only the keys this skip added (a day someone had already skipped stays skipped when this one is undone). The toast **Undo** (`undoSkipChoreDaysAction`, the same person, by that operation's id, within 10 minutes) removes those keys again and puts each deleted chore back exactly as it was (a moved day, its assignee, ticked steps) while its day is still free (no chore with its id or occurrence key); what could not be put back, and planned days, come from upkeep, which it runs. One-time chores and completed chores are never skipped.
- **Reschedule** (calendar): members with `chores.edit` can drag an open chore to another day, or open it and use **Move to date** (keyboard-accessible date field). The chip springs into its new day and a toast offers **Undo** for 10 s (`UNDO_WINDOW_MS`). Maintenance and medication items are read-only.

## Architecture and Data Flow

`ChoreChartClient` listens live (CH-1, `useChoreLiveData` in `src/components/chores/use-chore-live-data.ts`, state in `src/lib/chores/live.ts`) to rooms, templates, chore instances and the household's membership records, from which assignees come (`approvedPeople`, `src/lib/member-directory.ts`: display name, photo and role, kept for sticker mode; housemates' `users/{email}` profiles are not read). Each listener is a `resilientListener` (bounded backoff, retried at once on `online` and when the page is visible again), so completions, new chores and reassignments from other devices, quick add and upkeep appear without a reload, and the page never re-reads after its own writes. The leaderboard switch (`useChoreSettings`) is live too. A chore with a write in flight from this page (complete, Undo, reopen, a step, reassign, delete) keeps the page's version (`mergeLiveRows`) while the write runs and, after it settles, until the listener delivers a newer snapshot than the one current at that moment or 5 seconds pass (`SETTLE_WAIT_MS`), so neither an unrelated snapshot nor an older one flips it back for a moment, and another device's change is never hidden for long. Listeners take metadata changes, so a server confirmation of cached data resets their retry counts. **Try again** starts every listener over, also one that stopped after repeated refusals. The page shows its skeleton until every listener answered once; a listener that fails before that shows "Couldn't load chores" with **Try again** (CH-8), never the empty "No chores yet"; a failure after that keeps what loaded while the listener retries.
Assignee identity: see the section below. It does not expand recurring templates itself: on opening (in the background, never before the first render: CH-17), and 1.5 s after a change to repeats or a quick add (debounced, so several edits share one run), the page calls the `syncHouseholdUpkeep` server action, which runs the same idempotent upkeep as the hourly `householdUpkeep` Cloud Function; the chores it generates arrive through the listener. That step creates any missing instances for the next 30 occurrences of each recurring template, starting at today in the household time zone, with deterministic IDs derived from template, room, date, and assignee, and an `occurrenceKey` (`templateId|roomId|day`, no assignee). If the action fails, the page logs a warning and shows whatever instances already exist.

Completion (H3: CH-2, CH-12, D-7) goes through the server actions `completeChores({choreIds, completeSubTasks})`, `undoChoreCompletion({choreId, completionId, restoreSubTasks})` and `reopenChore({choreId})` in `src/app/chores/actions.ts`, each authorized with `authorizeHouseholdAction(ctx, 'chores.complete')` and run as one Admin SDK transaction (`src/lib/server/chore-completion.ts`, plans in `src/lib/chores/completion.ts`). A completion also deletes any `completedByEmail` an older client left on a chore it reopened, so a shared chore never pairs another person's email with the new completer's uid. The caller's identity comes only from the verified ID token. Chore IDs are checked with `isChoreDocId` (Firestore's own limits: one segment without '/', at most 1500 UTF-8 bytes, not `.`, `..` or `__…__`), because upkeep's recurring IDs (template ID, room ID, day and assignee email) can exceed 200 characters; the household ID still uses `isDocId`. Per chore, `completeChores` returns `completed`, `already` (idempotent: nothing written, and the result says who did it, so two people completing at once yield one completion) or `refused` (`early` when its due day, `originalDueDate` or `dueDate` read in the household timezone with `localDay`, is after the household's today, `householdToday`; `isDueAfterHouseholdDay` is the shared check; `missing`). A completion writes `isCompleted: true`, `completedAt` (server ISO time), `completedAtServer` (server timestamp), `completedByUid`, `completedByName` (no `completedByEmail`: every member with `chores.view` reads the chore; the name is the member record's display name, else the caller's token name, else "Member"; never an email, via `publicDisplayName`) and a random `completionId`, plus every step in `completedSubTasks` when steps were open. Undo reverts only while `completionId` still matches, clears only the completion fields (never restores a whole document) and restores `completedSubTasks` only if they are still exactly what the completion ticked; an `undone` result always carries the stored `completedSubTasks` afterwards, which the page applies. Reopen clears the completion fields (steps stay ticked); on the personal path it is allowed only for the completer, the assignee or a member with `chores.edit` (`refused` otherwise, CH-6). Every entry point calls these through `src/lib/chores/complete-client.ts` (`completeChoresOnServer` in batches of 50, `undoCompletionOnServer`, `reopenChoreOnServer`); today that is the Chores page's one tap, Select mode, Undo and reopen , and the dashboard's one-tap **Done** with its Undo (`useChoreDone` in `src/components/dashboard/one-tap.tsx`, HP-33b), and the calendar's **Mark done** and **Done** (CA-8). It refuses to run offline (`OFFLINE_COMPLETION_MESSAGE`), so a completion is never queued. The page updates optimistically and then applies what the server recorded, rolling back only chores that were not completed.

Points, streaks, stickers, contribution and the podium are computed in the browser by `computeChoreStats()` from the chore documents already loaded (completion history is kept 90 days), on household days (D-6: the Chores page passes the household day and zone, `householdDayZone`; the dashboard streaks tile does the same and passes the open chores too, since a fair streak needs the days that were missed). Nothing is stored, so there is no score a client could write. The point rules live in `functions/src/shared/chore-points.ts` (`POINTS`, `earnsPoints`, `DAILY_POINT_CAP` = 100, `pointsLedger`, `weekSummary`): a chore earns points unless it is a one-time chore (`sourceType: 'temporary'`) whose `createdByUid` is the person credited with it; generated days of a repeating chore and library chores (`sourceType: 'template'`) always earn, and chores written before `createdByUid` existed earn too. Points are summed per person per completion day and each day is capped at 100, so neither self-made chores nor long step lists can be farmed (CH-20). Completion times come from `completedAtServer` when present (cannot be backdated, see Security) and fall back to `completedAt` for chores completed before the stamp existed. Points and stickers go to whoever completed the chore (`creditedUid`: the member with `completedByUid`, else the member whose email is an older chore's `completedByEmail`, else, for completions recorded before attribution, the assignee resolved by uid or email with `resolveAssigneeUid`); streaks and "assigned" still count assignments (a chore someone else did keeps its assignee's streak day). Completions credited to former members are ignored (a recorded completer who left is not replaced by the assignee). The Chores page and the dashboard streaks tile build the stats members the same way (`statsMemberFrom` in `src/lib/chores/stats.ts`, applied to the approved member records; `streakMembersFrom` on the dashboard): each carries the record's email only while an older record still has one, purely as a matching key for `completedByEmail` and `assignedToEmail` on older chores; records written since member privacy release D have none, and such chores are scrubbed to uids. The email never reaches `MemberChoreStats` or any label, so both pages credit an older email-only completion by a current member identically (`tests/unit/chores-completion.test.ts`).

Editing or canceling a recurrence deletes the template's incomplete instances in the browser; the reload that follows runs server upkeep, which regenerates instances for an edited recurrence. Completed history remains, and a day that already has its chore (by `occurrenceKey`) is never regenerated, so reassigning a template or editing its schedule never brings back a completed day (CH-3).

Add Chore (one time) validates name, assignee and due date inline, then atomically writes one auto-ID chore instance and, when the assignee is someone else, one deterministic assignee notification. It does not write `chore-templates`. Add Chore (repeating) writes one template with its recurrence. New chore templates (Add Chore repeating, new library chores) and new rooms get an ID that cannot collide: a readable slug of the name (up to 60 characters) plus a Firestore auto-id (`newChoreDocId` in `src/lib/chores/list.ts`, mirroring the shell's `quickCreateId`), for example `take-out-trash-AbCd…`. IDs are never picked from the page's loaded list, which can be a stale offline cache or miss documents another member just created, so a create can never overwrite or merge into an existing document; the library create also runs in a transaction that refuses an existing ID and writes without merge. Nothing depends on readable IDs: chores link to templates by `templateId`, generated instance IDs are derived from whatever the template and room IDs are, and `?room=<id>` links, the room filter, the living house and its room links all read the stored ID (the house picks the pet bowl's room by name). Existing templates and rooms keep their IDs. One-time library assignments use auto IDs, so they never share (and overwrite) the deterministic ID of a generated occurrence or an earlier assignment; older one-time assignments keep their deterministic IDs.

The calendar (`HouseholdCalendar`, `src/components/chores/calendar/`) listens live (CA-1): chores, chore templates, rooms and members through the Chores page's own `useChoreLiveData` (with `chores.view`; without it only the members collection, for colours), and `home-assets`, `vehicles` (`maintenance.view`), `pets` with each pet's `medication-logs`, `medication-courses` and `care-logs` (`pets.view`) and `pantry-inventory` (`shopping.view`) through `useLiveDocs` (`use-live-docs.ts`: one `resilientListener` per collection, bounded backoff and an immediate retry on `online` or a visible page; when a pet is added or a permission changes only the listeners that changed start or stop), each only when the member may read it. Nothing re-reads after a write. The page draws as soon as chores (and the membership, so permissions are known) have answered; the other sources render as they arrive ("Loading maintenance…"), and upkeep (`syncHouseholdUpkeep`) runs in the background after the first render (CA-6). A source that fails before answering shows one alert naming it ("Members could not be loaded, so planned repeats and colours are missing." for the members listener, CA-3) with "Retrying automatically." and **Try again**, which restarts every listener (CA-18: kiosks may have no reload control); the others still render. A member without a household gets "No household yet" with a link to Household, and a household load failure a retry, never an endless skeleton (CA-7). Writes in flight (Mark done, a move) keep the page's version of that chore until a newer snapshot arrives or 5 s pass, as on Chores. Events are derived in separate memos per source (CA-20), only the visible range is grouped and sorted, and chips are memoised (`EventChip` in `event-chip.tsx`). Medication history is still read whole per pet (the legacy countdown and `withOfflineDoses` need every dose, and dose `date` fields mix ISO strings and timestamps, so a range query would drop doses). Maintenance items are built by `maintenanceCalendarItems()`: scheduled services from the shared builder (every status) plus expiration fields read directly (the builder reports expiries only inside its 30-day warning window), recomputed whenever today changes; assets with `warrantyLifetime: true` contribute no warranty expiration. Repeating chores are projected over the visible range with the server's own recurrence rules (`occursOn`) and occurrence identity (`occurrenceChoreId` and `choreOccurrenceKey`, via `occurrences()`; no assignee involved): an occurrence is planned only while neither its document nor a chore with its occurrence key exists, so a generated chore that was moved, completed or reassigned never reappears on its original day. Medication entries are read with both date shapes (ISO strings and timestamps, via `toDate`), their `nextDueDate`, `courseId` and `oneOff`; `medicationDueEvents` groups the legacy ones per pet and calls `currentMedicationsOn` without the names a course took over; courses are read with `readCourse` and expanded by `courseDueEvents`.

Moving a planned day (CA-15) calls the `movePlannedChore` server action (`src/app/chores/actions.ts`, `authorizeHouseholdAction(ctx, 'chores.edit')`, the permission a move of a generated chore needs under the rules; logic in `src/lib/server/planned-chore-move.ts`), one Admin SDK transaction that checks the template still repeats on that day, the day and the new day are today or later (household time zone), the day is not skipped, the room is one of the template's, and the assignee is upkeep's: the person whose turn it is for a rotating chore (CH-28, `rotationTurn` with the day's `occurrenceNumber`), else an approved member by uid (a template that still names its assignee by email waits for upkeep), then creates the occurrence with upkeep's own id, occurrence key and fields (`generatedOccurrence` in `functions/src/shared/occurrence-chore.ts`, which the generator in `functions/src/reminders.ts` uses too) due on the new day, or answers `conflict` when the day exists already. Upkeep never generates it again (its id exists). The move also writes a server-only operation record (`households/{h}/calendar-ops/{opId}`: `kind: 'move'`, the chore id, its new day, `createdByUid`, `createdAt`, `expiresAt`) and returns its `opId`. `undoPlannedChoreMove` takes only that `opId` (no chore id): it is refused (`invalid`) unless the record is a move by the same person made within `CALENDAR_OP_UNDO_MS` (10 minutes), so `chores.edit` can never delete an arbitrary open chore; then it deletes the chore only while nothing has written it since the move (its `updateTime` still equals the operation record's `createTime`, both from the move's transaction, so a reassignment counts) and it is still that move (open, no step ticked, still due on the new day); otherwise it answers `stale` and the chore stays. The record is used once (deleted by its Undo).

### Assignee identity

Chores and templates moved from the assignee's email (`assignedToEmail`) to their Auth uid (`assignedToUid`). Member privacy release A dual-wrote both; since release C writers store the uid only. Every reader goes through `functions/src/shared/assignee.ts` (shared by the app, the household server actions and the upkeep function):

- Writers set `assignedToUid` only (`assigneeFields`): Add Chore (one time and repeating), library assignment, repeating-chore edits, reassignment, command-palette quick add (`createOneTimeChore`, `repeatingChoreTemplate`) and server generation. A writer that updates an existing record also deletes `assignedToEmail` (and, on templates, `recurrence.assignedToEmail`), because a leftover email of the previous assignee would win over the new uid: reassignment and repeating-chore edits delete the top-level field and replace `recurrence` whole; library assignment merges, so it deletes both copies explicitly. Stopping a repeating chore writes `recurrence: null`, `assignedToUid: null` and deletes `assignedToEmail`. Leaving and removal unassign open chores with `unassignedChoreFields` (`assignedToUid: ''`, "Unassigned") and delete their email (see [Household Governance](../household-governance/README.md)).
- Readers resolve the assignee with `resolveAssigneeUid` (a list of people) or `isAssignedTo` (one person). The email decides whenever the reader can match it to a member, because a browser still on an older build reassigns by rewriting only the email and leaves the previous uid behind. Otherwise the uid decides, but only when it cannot contradict the email: there is no stored email, or the reader does not know the uid's member email. A uid whose member's email differs from the stored email is stale and matches nobody, even when the email names a former member (so a departed member's completed chores never turn into the previous assignee's points, streaks or calendar label). The Chores page resolves once on load and keeps the result in memory as `assignedToUid`, so rows, the reassign menu, assignee pickers, the repeating-chores list and the leaderboard work by uid. The calendar, dashboard facts and streaks, member chore stats in Household Manager, server reminders and the AI overview use the same helpers. Pickers and menus use member uids as values and show display names only, never an email (`memberName`, "Unassigned" when nobody).
- Readers keep the email fallback (release F removes it) because browsers still on a build from before release A write the email alone; the minimum-build check (see [Application Shell](../application-shell/README.md), "Minimum build") reaches release C and later builds only (and only asks them to reload), so it cannot force those older builds off. Records without an email (every record written since release C, and every scrubbed one) resolve by uid for every reader.
- Generated instance ids name no one: `occurrenceChoreId` (`stableSlugify(templateId-roomId-day)`, member privacy release E), whoever the template is assigned to. Chores generated earlier carry the assignee after the day (`recurringChoreId`: the template's email, or its uid); upkeep and calendar planning skip every day whose new id exists or whose occurrence key (`templateId|roomId|day`, stored on the chore or recovered from either id shape by `storedOccurrenceKey`) a chore already holds, so a day that already has its chore, completed or open, is never generated again after the switch, a reassignment or a schedule edit. The key is not rebuilt from `originalDueDate`, which a move rewrites. Missed-instance folding (`collapseMissedRecurring`) keys each series on the member `resolveAssigneeUid` names among the household's people (the Chores page passes its members, the dashboard its member records when loaded), so instances with email and uid and newer uid-only ones form one series, and a chore an older build reassigned by email counts for the member the email names; without people it keys on the email, else the uid.
- One-time assignment notifications use the uid in their state key (`assigned|<day>|<uid>`); notification documents are readable by every member.
- `scripts/ops/backfill-chore-assignee-uid.mjs --project <id>` (dry run, counts only) and `--apply` add `assignedToUid` to chores and templates that only have the email, repair a uid that disagrees with the email (an older build's reassignment), and clear (`''`) a current member's uid that sits next to a former member's email, from the household's member records; pure decisions in `scripts/ops/chore-assignee.mjs` (`resolveAssigneeUidJs` is checked against the shared helper). Each update is guarded by the document's update time, so a document changed meanwhile is skipped and picked up by the next run; unassigned records and emails of former members are left alone. Run it after this release is live and again once older builds have aged out, before any release reads the uid alone.
- The upkeep function knows members' emails only from their protected contact documents (`withContactEmails`; see [Household Governance](../household-governance/README.md), "Member contact"), so email-keyed templates keep resolving without any email on the records. A template that still carries an assignee email is generated only for the member whose contact document holds that email, never by its stored uid (which an older build's email-only reassignment can leave stale): when the contact read fails, or the email names nobody, it generates nothing that run and is retried on the next one. Templates without an email generate as usual.
- Yearly stats: see "Retention" and "Yearly stats, legacy keys" under Invariants and Failure Behavior.
- `scripts/ops/scrub-shared-emails.mjs --project <id>` (dry run, counts only) and `--apply` (member privacy release C) remove `assignedToEmail` and `recurrence.assignedToEmail` from chores and templates, first setting `assignedToUid` to the member the email names when it is missing or stale (members' emails from their contact documents, then the records), and clearing a current member's uid next to a former member's email, so readers resolve the same member by uid afterwards. It kept the email on completed chores without a recorded completer; `scripts/ops/scrub-member-emails.mjs` (release D, same conventions) removes those too, the same way, and `completedByEmail` from every chore (setting `completedByUid` first where it was missing). A completed chore whose credited person (its completer, else its assignee) has left and is named only by the email being removed is credited to that person's identity instead (`completedByUid`, or `assignedToUid` when credited to the assignee, replacing any other uid there, also release C's clearing of a current member's leftover uid; an open chore is cleared as before), so the person keeps their yearly credit. A departed person's identity is the uid their departure recorded (since release D, in `ops/former-members` itself; under release C, as a stats alias), else the uid of their recorded completions (`completedByEmail` with `completedByUid`, written together by the server) when those name exactly one uid that no other email uses (a stale assignee pairing never outweighs it), else their account uid when the household's chores and templates pair their email with exactly one uid that is not a current member's, and that uid with no other email; otherwise it is their former-member key: `former-` and 24 hex characters, an HMAC-SHA-256 of the lower-cased email under a random per-household secret, which cannot be recomputed or confirmed from a guessed email (`scripts/ops/former-member-key.mjs`). The secret and every decision (former-member key to identity, no email) are stored in `households/{householdId}/ops/former-members` (never readable or writable by a client) before anything is written with them and never change, so re-runs, interrupted runs and either script order use the same identity. Before changing any chore, the scrub moves the yearly stats' legacy keys of current members and of these people to the same identities (see "Yearly stats, legacy keys"), so a departed person's archived and retained completions are one score. Credit and stats treat the identity like any uid (`choreStatsMemberKey`), labelled by the stored display name; a chore whose departed person has no settled identity yet keeps its email and is counted. Both also scrub other documents (see [Household Governance](../household-governance/README.md), "Email copies"). Pure decisions in `scripts/ops/shared-email-scrub.mjs` and `scripts/ops/member-email-scrub.mjs`; updates are guarded by update time, and the scripts can be re-run at any time.
- `scripts/ops/rekey-chore-ids.mjs --project <id>` (dry run, counts only) and `--apply` (member privacy release E) move every generated chore whose id still carries an assignee part to its `occurrenceChoreId`: one transaction per chore re-reads the household (nothing is written while it is being deleted), the chore (skipped when changed or deleted since the run read it) and the target ids, creates the same document under the new id and deletes the old one. Every field is kept (assignee, completion attribution, `completionId`, `completedAtServer`, `occurrenceKey`); a chore without `occurrenceKey` gets the one its id names. A day that already has a chore under the new id (two chores for one day, from before upkeep checked occurrence keys) goes to `<id>-2` .. `<id>-9`. One-time chores (auto ids, or a `sourceType`) and ids that are not generated ids are left alone and counted, except one-time chores assigned from the library before upkeep matched occurrences by id (`sourceType: 'template'`, id `<template>-<room>-<day>-<assignee email>`): they move to `<template>-<room>-<day>-once` (or `-once-2`..`-once-9`), never the occurrence id itself, and keep no occurrence key, so they stay one-time and never stop upkeep generating that day. Without an occurrence key whose room still matches, the day is located from the template's slug forward (`legacyOccurrenceBase`), never from the end of the id, because the assignee part may contain date-shaped text: one date-shaped part after the room is the day; with several, the one whose room part is one of the household's rooms decides, and otherwise the chore is left alone and counted as ambiguous. Every target ends with its day (`assertOccurrenceBase`), followed at most by a `-2`..`-9` slot. Upkeep and the calendar recover keys only by the chore's own room and the ten characters after it (`storedOccurrenceKey`), so they never read into the assignee part. The overdue notifications list chore ids (`overdueChoreIds`, `notifiedChoreIds`): the move rewrites a moved chore's id to its new one in the same transaction (`overdueIdsAfterMove`; the dry run counts the references), so it is not news to its person again and read and dismissed state are kept. No other notification names a generated id (others name one-time chores, templates or days); a page that listed a chore just before it moved acts on the old id once, like on a deleted chore (completion, Undo and reopen report it missing and the page lists again; a calendar move or sub-task tick shows its error). Pure decisions in `scripts/ops/chore-id-rekey.mjs`, the transaction in `scripts/ops/chore-id-move.mjs`; re-runnable.
- `scripts/ops/scrub-remaining-emails.mjs` (release E; see [Household Governance](../household-governance/README.md), "Email copies") removes any assignee or completer email still stored the same way as release D's scrub (with the same stored identities of people who have left, so a completion credited to one of them keeps that credit), and replaces assignee or completer labels that are an email by the member's current name ("Member" when the uid names nobody, "Unassigned" without a uid).

## Data Model and Persistence

- Templates: `households/{householdId}/chore-templates/{templateId}`.
- Instances: `households/{householdId}/chores/{choreId}`.
- Rooms: `households/{householdId}/rooms/{roomId}`.
- Chore preferences: `households/{householdId}/chore-settings/preferences`, shape `{ leaderboardEnabled?: boolean, centsPerPoint?: int 0-100, updatedAt?: string }`. A missing document or field means the defaults (leaderboard on, no allowance). `useChoreSettings` writes each change as a merge, so the leaderboard switch keeps the rate and the other way round. Rules: owners and admins only, keys limited to those three, `centsPerPoint` an integer from 0 to 100.
- Closed-week snapshots (CH-29): `households/{householdId}/stats/week-{weekStart}` (the week's first household day: Monday, or Sunday when the household's week starts on Sunday, CA-16), `{ kind: 'week', weekStart, weekEnd, centsPerPoint, members: [{ uid, name, stickerMode, points, completed, payoutCents }], createdAt }`, written only by upkeep (`snapshotClosedWeek` in `functions/src/reminders.ts`, with `weekSummary` in `functions/src/shared/chore-points.ts`), read with `chores.view` (clients can never write `stats/`). Names are labels, never an email ("Member" when none).
- Notifications: `households/{householdId}/notifications/{notificationId}`.
- Calendar Undo records (CA-15, CA-27; server-only, the rules deny every client): `households/{householdId}/calendar-ops/{opId}` with `kind` (`move` or `skip`), `createdByUid`, `createdAt`, `expiresAt` (10 minutes later; a TTL policy on it may remove old ones), and for a move `choreId` and `toDay`, for a skip `keys` (`[{ templateId, keys }]`, only the keys it added) and `removedCount`, with each deleted chore's backup (`{ id, key, data }`) in its own document `calendar-ops/{opId}/removed/{n}`. An Undo deletes its record; a record whose Undo was never used stays (household deletion removes it with the other subcollections).
- Read-only for the calendar (live): `home-assets`, `vehicles`, `pets`, `pets/{petId}/medication-logs`, `pets/{petId}/medication-courses`, `pets/{petId}/care-logs` and `pantry-inventory`, and `households/{h}.weekStartsOn` (CA-16). The calendar writes chores only by moving them (`dueDate`, `originalDueDate`), creating a planned day through `movePlannedChore`, and skipping days through the server (a template's `skippedOccurrences` and deleting open generated chores, CA-27).

Chores and templates carry `assignedToUid` (optional; older records have only `assignedToEmail`) next to `assignedToEmail` (see Assignee identity). Important types are `Recurrence`, `RecurrenceFrequency`, `MonthlyRecurrenceMode`, `MonthlyNthWeekday`, `ChoreTemplate`, `Chore`, and `Room`; `ChoreRecord` (`src/lib/chores/dates.ts`) is `Chore` plus the optional `completedAtServer` timestamp.

`Chore.templateId` is optional for backward-compatible direct instances. `Chore.sourceType` may explicitly distinguish `template` and `temporary`; existing documents without `sourceType` continue through the established template/instance behavior. `completedAtServer` is optional and additive: existing completed chores without it keep working (their `completedAt` is used), and no migration is needed.

Server-written chore fields (H3): `completedByUid`, `completedByName` (who completed it, D-7) and `completionId` (random id of the current completion) are written only by the completion actions and removed on undo or reopen; older completions have none and are credited to their assignee. Completions recorded before member privacy release D also carry `completedByEmail`, which the completion actions no longer write, undo and reopen remove, and `scripts/ops/scrub-member-emails.mjs` scrubs. `occurrenceKey` (`templateId|roomId|day`, `choreOccurrenceKey` in `functions/src/shared/ids.ts`) is written by upkeep on every generated chore and never changes, also when the chore is moved or reassigned. Generated chores from before the field are recognized by their deterministic id, which embeds the original day (`storedOccurrenceKey`), so upkeep and the calendar work without the backfill; `scripts/ops/backfill-occurrence-key.mjs` stores the key on them (dry run by default with counts only, `--apply` writes just that field, `--project`, `--firebase-tools-login` as the other ops scripts, resumable: chores that have a key are skipped).

`ChoreTemplate.rotation` and `rotationStart` (CH-28): two to eight member uids in turn order, and the household day the turns count from (`rotationFieldsFor` in `src/lib/chores/rotation.ts`: a new or reordered rotation starts on the day it is saved; an unchanged one keeps its day; fewer than two people removes both fields). Occurrence number n of the schedule, counted from `rotationStart` (`occurrenceNumber` in `functions/src/shared/rotation.ts`, skipped days included), goes to `rotation[n mod k]` (`rotationTurn`), so every upkeep run and the calendar give each day the same person, a skipped day never shifts anyone's turn, and all rooms of one day go to the same person. A uid that is not an approved member, or is a kid profile, passes the turn to the next person in the list (everyone else keeps their days). The template's `assignedToUid` is the first person in the rotation. Occurrence ids and keys do not include the assignee, so the occurrence-key and skip invariants are unchanged: a completed day keeps its person and is never generated again.

`ChoreTemplate.skippedOccurrences` (CH-3, CA-5) lists the occurrence keys of days someone deleted on purpose ("we're away Saturday"): deleting a generated chore due today or later adds its key in the same transaction as the delete (`skipsForDeletion` in `src/lib/chores/recurrence-edits.ts`, `withSkippedOccurrences` in `functions/src/shared/skips.ts`, which drops past days, removes duplicates and keeps at most 400 keys, latest days first), and upkeep and the calendar's planned repeats never generate or plan a listed key (`skippedOccurrenceKeys`). Past days need no key, since upkeep never generates a day before today. A generated chore is one with a `templateId`, no `sourceType` and an occurrence (`storedOccurrenceKey`; `isGeneratedInstance`): older one-time library assignments without a `sourceType` have random ids, so they are never treated as a series' days.

Repeats (CH-10, CH-25): daily can be every N days (1–14 offered, counted from its start day) and weekly every N weeks (1–8 offered); every 2 weeks stays a choice of its own. Every schedule can have a **Starts on** day (stored only when it is later than today, or for a stepped schedule's anchor: a start of today means "from now", so a device whose day differs from the household's never moves today's occurrence; older templates have none and behave as before) and an optional **Ends** day (inclusive; "Never" by default). Both sit in a folded "Start and end" section (open when set), so Add Chore stays short; a stepped schedule shows its start outside it, since it needs one, stored as `recurrence.startDate` / `recurrence.endDate` and applied by the shared `occursOn` in `functions/src/shared/recurrence.ts` for upkeep, the calendar and the dashboard alike. A stepped weekly schedule (every 2 or every N weeks) is stored from the Monday of the picked week (`weekStartOf`), so a Mon and Fri pair always lands in the same week. Biweekly schedules use `startDate` as an anchor. Monthly day-of-month is limited to 1-28. Nth-weekday supports first through fourth; last-weekday recurrence is not implemented. Medication courses (Pets) carry their own schedule, so the calendar shows their recurring occurrences; legacy medications without a course have no schedule beyond each dose's optional `nextDueDate`, so for them the calendar shows exactly the pending countdown (one next dose per medication).

## Authentication, Roles, and Security

The page requires an authenticated user and uses that user's household ID. Assignee discovery uses approved, active `households/{householdId}/members/{uid}` records and their public fields only (no profile reads); a member without a usable display name shows as "Member". The rules validate chore and template shapes (allowlisted fields, types, bounds) and guard the uid assignee (see Uid assignee below).

Navigation uses `chores.view`. Firestore rules enforce granular permissions: `chores.view` to read chores, templates, rooms and chore preferences; `chores.create` to create chores and templates; `chores.complete` for updates limited to `isCompleted`, `completedAt`, `completedSubTasks` and `completedAtServer`; `chores.edit` for other chore and template updates and room create/update; and `chores.delete` for deletes. `chores.assign` is enforced on assignment: creating a chore whose `assignedToEmail` is someone other than the caller (by token email) needs it, while `chores.create` alone still covers a chore for yourself or an unassigned one (`''` or null); any change of a chore's `assignedToEmail` on update needs it, including to yourself (Reassign already requires it in the UI). On templates, setting or changing `assignedToEmail` or `recurrence.assignedToEmail` to someone other than the caller needs it; keeping the current assignee, switching to yourself or clearing it does not (the Edit repeating chore dialog offers exactly those choices without `chores.assign`).

Shape validation (QA-8): chore writes may only set `task` (1 to 500 characters, required on create), `notes` (up to 5000), `assignedToEmail` (optional; no longer written), `assignedToUid`, `assignedToDisplayName`, `dueDate`, `originalDueDate`, `roomIds` (list, at most 50), `isCompleted` (bool), `completedAt`, `completedAtServer` (timestamp), `completedSubTasks` and `subTasks` (lists, at most 100), `templateId` and `sourceType` (`temporary` or `template`), and `createdByUid` (CH-20: optional, so older clients' chores stay valid; when present it must be the writer's uid on create and can never be changed or removed afterwards). Add Chore (one time), library one-time assignments and command-palette quick add write it. Templates may only set `task` (required on create), `notes`, `roomIds`, `subTasks`, `assignedToUid`, `assignedToEmail`, `recurrence`, `skippedOccurrences`, `rotation` (null, or a list of 2 to 8) and `rotationStart` (null or a string of at most 10 characters); setting or changing `rotation` needs `chores.assign` (it names other people), removing it does not; `recurrence` is null or a map of `frequency` (`daily`, `weekly`, `biweekly`, `monthly`, required), `interval` (1 to 52), `assignedToEmail` (optional), `startDate`, `dailyOptions` (`excludeWeekends`), `weeklyOptions` (`daysOfWeek`, at most 7) and `monthlyOptions` (`mode`, `dayOfMonth` 1 to 31, `nthWeekday` with `week`/`dayOfWeek`). On update only added or changed keys are checked, so chores and templates holding legacy fields stay editable. A recurring assignment merged into a template that was deleted meanwhile (no `task`) is now refused instead of creating a nameless template. On-demand upkeep requires `chores.view`. Pending `newuser` members are denied by rules.

Uid assignee: chores and templates also accept `assignedToUid` (a string up to 128 characters; empty or null when unassigned), dual-written with `assignedToEmail` by member privacy release A and written alone since release C. It is guarded like the email: without `chores.assign`, a uid is accepted only when it is empty, your own uid next to your own email (`choreAssigneeUidMatchesEmail`), or, when creating a chore or setting a template, your own uid with no email beside it (`choreAssigneeUidIsCallerOrMatches`). Membership records carry no email, so the rules never match a uid to someone else's email on a record: filling in another member's uid next to their email needs `chores.assign`, like every other change of a chore's assignee (even to yourself, even once no email is left). One exception keeps the assignee: replacing a stored legacy assignee email by the uid of the member it names, removing the email (and a template's `recurrence.assignedToEmail`) in the same write, needs no `chores.assign` when that member's protected contact document holds the removed email (`legacyAssigneeKept`, compared case-insensitively; the rules read the contact document, the caller never does), so a schedule-only edit of a legacy email-assigned chore or template by an editor without `chores.assign` succeeds.

Completion attribution, rules stage R1 (this release, compatible with older clients): the chore allowlist includes `completedByUid`, `completedByEmail`, `completedByName`, `completionId` and `occurrenceKey`, but clients may not set them on create, nor set, change or remove them on update (only the Admin SDK writes them); and a client write that completes a chore is denied while the chore still carries attribution (an older release reopened a server completion with client writes and tries to complete it again), so points are never credited to a stale completer. Clients may still toggle `isCompleted` with stamped writes, which older releases need.

Rules stage R2 (next release, not deployed): clients may not change `isCompleted` at all, so every completion, undo and reopen goes through the server actions and eligibility (CH-2) can't be bypassed with a direct write. Order: deploy R1 rules, run the occurrence key backfill, deploy functions (upkeep writes and checks `occurrenceKey`), ship this client, wait one release window watching for denied chore writes, then deploy R2. Rollback is redeploying R1.

Completion stamp rule (every chore write): a chore that becomes completed must carry `completedAtServer == request.time`. A completion with no stamp, or a client-chosen one, is denied. A chore that stays completed must keep its stamp unchanged, and a chore can be created already completed only with a server stamp. So completion times, which points and streaks read, can't be backdated or forged. Chores completed before the stamp existed (phase 1, 2026-11-06) remain editable and can be reopened, and stats fall back to `completedAt` for them. Chore preferences may be written only by owners and admins (role, not overrides), only at `preferences`, only with `leaderboardEnabled` (bool) and `updatedAt` (string); nobody may delete them.

The UI never shows an action the member cannot perform, mirroring the rules through `choreCapabilities(permissions)`: the completion checkbox is disabled without `chores.complete`; Add Chore and the library's create need `chores.create`; reassign, room add/edit and library edit need `chores.edit`; delete (rows, library, rooms, clearing missed instances) needs `chores.delete` (deleting a day of a repeating chore also writes that template's `skippedOccurrences`, which the rules allow a `chores.delete` holder to change, and nothing else on the template); editing or stopping a repeating chore needs both `chores.edit` and `chores.delete` (it removes the old open instances); removing a room from a library chore without `chores.delete` is refused inline; picking someone other than yourself as assignee needs `chores.assign`; calendar rescheduling needs `chores.edit`; the leaderboard switch is shown to owners and admins.

## Integrations and Background Processing

- Assignment notifications go only to someone other than the person assigning (no "New chore assigned" for chores you give yourself). Template assignment notifications are best-effort household notification writes. One-time Add Chore batches its direct chore and deterministic assignment notification together so a successful creation cannot omit its initial notification.
- Overdue alerts (one notification per person, `${uid}-overdue`, updated in place: announced after 7:00 local time, pushed only when a chore the person was not told about becomes overdue and at most once a day, silent when their daily reminder carries the overdue count (the reminder counts as that day's push, at any hour), resolved when nothing is overdue; see [Notifications](../notifications/README.md)) and each person's daily reminder (at their chosen time, in their own `users.timeZone`, falling back to the household's) are created on the server. The hourly `householdUpkeep` Cloud Function (`functions/src/index.ts` → `functions/src/reminders.ts`) runs the same idempotent step for every household; the Chores page and the calendar also run it on demand through `syncHouseholdUpkeep` (`src/app/chores/actions.ts`, authorized by `chores.view`) so a new recurring assignment appears immediately.
- Deterministic per-user/day daily-reminder IDs suppress same-day duplicates; the overdue notification has one ID per person.
- New records can trigger the shared FCM Cloud Function.
- Recurring instances for the next 30 occurrences are generated on the server from `functions/src/shared/recurrence.ts`, using the household `timeZone` (default `America/Chicago`). Chore IDs are `stableSlugify(templateId-roomId-day)` (`occurrenceChoreId` in `functions/src/shared/ids.ts`); chores generated before member privacy release E have the template's assignee email or uid after the day until `scripts/ops/rekey-chore-ids.mjs` moves them. A template with a rotation (CH-28) gives each occurrence to whoever's turn it is (see Data Model); otherwise the template's assignee is resolved by uid (`resolveAssigneeUid`), or, for a template that still carries an email, only by that email matched against the members' contact documents (see Assignee identity); nothing is generated for someone who is not an approved member. Generated chores carry `assignedToUid` (no email since release C) and the member's display name ("Member" when none, never the email). Chore reminders match chores with `isAssignedTo` and are targeted by `targetUserUid` only. A rescheduled instance keeps its ID, so upkeep never recreates it on its old day.
- Feedback: `playFeedback('complete')` on completion, `'celebrate'` for "House is clean", `'add'` after adding or moving a chore.

## Invariants and Failure Behavior

- Defensive normalization supplies defaults for old recurrence records missing interval, weekdays, anchors, monthly mode, or day.
- Weekly snapshot (CH-29): every upkeep run checks the week that closed (the household's week before the current one: Monday to Sunday, or Sunday to Saturday with `weekStartsOn` 0, CA-16; `weekStartDay(today, weekStartsOn)`). If `stats/week-{weekStart}` does not exist yet, it computes each member's capped points, completions and payout at the current `centsPerPoint` from the chores it read and creates the document in a transaction that re-reads the household (nothing is written for a household being deleted) and never overwrites one that exists. A week where nobody earned points writes nothing. Writing one also deletes snapshots more than `WEEK_SNAPSHOT_KEEP_WEEKS` (26) weeks older; the yearly `chores-{year}` documents (no `weekStart`) are never touched, and the departure fold only reads `chores-{year}`.
- Retention: completed chores older than 90 days (household-local) are deleted by the server step, so leaderboard totals cover at most 90 days. Before deleting, upkeep adds each removed chore to `households/{householdId}/stats/chores-{year}` (the year, in the household timezone, of its authoritative completion instant: `completedAtServer` when present, else `completedAt`, from `choreCompletionInstant` in `functions/src/shared/completion.ts`, which `completionInstant` in `src/lib/chores/dates.ts` also uses; retention itself still keys off `completedAt`) in the same transaction as the delete: `{ year, completed, byAssignee: { <key>: count }, names: { <key>: displayName }, updatedAt }`, where the key is `choreStatsMemberKey(uid)` (`uid-<uid>`, `functions/src/shared/ids.ts`). Totals are read, added to and written inside the transaction (`addPurgedChores` in `functions/src/shared/chore-stats.ts`), and a chore is counted only when it is actually deleted, so repeated or overlapping runs never count it twice. Clients can read the document with `chores.view` and can never write it. Each removed chore counts for its completer, else its assignee (`creditedPerson`: `completedByUid`; an older `completedByEmail` matched to a member; else the assignee: an `assignedToEmail` that names a member, else `assignedToUid` unless a known email of that uid's member contradicts the stored email). A recorded completer who left keeps the credit under their uid. `names` labels are never an email. A chore whose credit could depend on an email (`purgeNeedsMemberEmails`: no `completedByUid`, and a `completedByEmail` or `assignedToEmail`) is purged only when upkeep could read the members' contact documents (`readMemberContactsOrNull` returns `null` on failure, distinct from no contacts) and that email (the completer's, else the assignee's) names a current member (`purgeMustWait`), also inside the purge transaction: a transient failure never deletes a chore without its credit, and a completion whose email names someone who has left waits, whatever uid is stored next to it (an older build's email-only reassignment can leave another person's uid there), until `scripts/ops/scrub-member-emails.mjs` replaces the email by that person's settled identity (see Assignee identity). A completion that records both `completedByEmail` and `completedByUid` of someone who has left waits too: that pair is the only evidence tying their archived email-derived stats key to their uid, and the scrub (or the re-key) settles it and moves the key before the email is removed. The scrub is a step of member privacy release D, so such chores wait until it runs; chores credited by uid alone, and current members' completions, are not affected. Chores credited by uid are purged as usual. Home Wrapped credits retained completions with the same rule (it knows no emails but the viewer's own, and every chore stored since uids were written resolves by uid), so a completion keeps its member when it crosses the 90-day boundary, and adds these yearly totals to the retained completions.
- Yearly stats, legacy keys: documents written before member privacy release D keyed people by `choreStatsAssigneeKey(email)` (a slug of the email's local part plus a hash of the whole email), which let anyone who reads the stats see the local part and confirm a guessed address. Nothing writes those keys any more. Keys release C wrote as `uid-<uid>` (someone who had left, known only by uid) are already uid keys and are kept as they are. Leaving and removal fold the departing person's legacy key into their uid key in every stats document of the household, in the departure transaction (`foldDepartingStatsKey` in `src/lib/server/household-membership.ts`), write nothing derived from their email into any document a client can read, and record their uid as the settled identity of their email in `ops/former-members` (`identities.<former-member key of the email>`, `recordDepartedIdentity`; the key is the HMAC of `functions/src/shared/former-member.ts`, twin of the scripts' `formerMemberKey`), so completions that still name them only by email are credited to that uid by the scrub, in either script order, so their completions archived before and after leaving are one score. Release C's departures wrote `aliases.<uid>` (the person's legacy key) instead: upkeep and Home Wrapped fold an aliased legacy key into that uid key (`foldLegacyStatsKeys`), the scrub takes that uid as the person's identity, and the re-key moves the key there and deletes the `aliases` field (an email-derived key, readable by everyone who sees chores); a document that still has the field is not clean for the re-key. Upkeep folds a current member's legacy key into their uid key whenever it adds to a document (`foldLegacyStatsKeys`, emails from the contact documents); Home Wrapped folds the viewer's own and counts any other legacy key on its own, labelled from the stats. `scripts/ops/rekey-chore-stats.mjs --project <id>` (dry run, counts only; `--apply`, `--firebase-tools-login`) re-keys every stats document in its own transaction: a current member's legacy key is folded into their uid key, a departed person still named on a chore or template goes to their identity, the one `scripts/ops/scrub-member-emails.mjs` gives their chores (see Assignee identity); any other (no chore names that email any more) goes to an opaque key of its own (`unknownLegacyKey`: an HMAC of the legacy key under the household's secret, the same in every run), with the same count and label; `completed` is unchanged and a re-run finds nothing to do (pure decisions and the keys' JavaScript twins in `scripts/ops/chore-stats-rekey.mjs`, the per-household steps both scripts share in `scripts/ops/member-privacy-household.mjs`). Run it once the release's app and functions are live (so no departure writes an alias any more), before or after `scripts/ops/scrub-member-emails.mjs` (which re-keys the stats of current members and of the departed people it scrubs, removes aliases with them, and leaves keys of nobody named to this script); if a departure was handled by release C's app after a run, run it again.
- Room deletion (confirmed; needs `chores.edit` and `chores.delete`) is one transaction (CH-4, `roomDeletionPlan`): an open generated day from today on whose template still repeats in other rooms is deleted (the series goes on there); every other chore in the room stays without it: overdue days (upkeep never regenerates them), one-time chores, completed history, days whose template is gone, and days of a template left with no rooms. Such a template then repeats around the house, so each kept day's around-the-house key goes into its `skippedOccurrences` and upkeep never adds a second chore that day. Templates drop the room. The confirmation says so. Every delete of open chores (room deletion, repeat edits and stops, Repeats assignment, library delete) lists its candidates first and re-reads each inside the transaction, so a chore completed meanwhile is never deleted (`stillOpen`).
- Repeat edits touch only the series' own generated days (CH-4): stopping or editing a repeating chore, and assigning a library chore as "Repeats", delete its open generated chores and never a one-time assignment of the same library chore. Assigning as "Repeats" (offered only with both `chores.edit` and `chores.delete`) writes the rooms chosen in the dialog (none chosen keeps the chore's own rooms) and replaces the old series' open days from today on (overdue days stay: upkeep never regenerates them; `isUpcomingInstance`), so reassigning A to B leaves one series. A completed day keeps its occurrence key, so changing the assignee mid-day never generates today's chore again.
- The calendar never shows an action the rules would refuse: **Mark done** needs `chores.complete`, moving `chores.edit` (a planned day: the server action checks it too), **Skip this day** and **We're away** `chores.delete` (checked by the skip server action, the permission the rules give for a template's `skippedOccurrences` and for deleting chores). Undo of a planned move or a skip is accepted only by the operation's server-only id, from the person who did it, within 10 minutes.
- Deleting a day of a repeating chore removes only that day (the confirmation says so): its key goes into `skippedOccurrences`, so upkeep and the calendar never bring it back. Clearing missed days needs no key (they are in the past).
- **Missed days expire (CH-7), the stated rule:** a day of a repeating chore that nobody completed stays in To Do (folded into its series' "+N earlier missed", and counted against "House is clean") for 7 days after the day it is due (`MISSED_EXPIRY_DAYS`; a moved chore counts from its new day, `effectiveDueDay`). After that, upkeep deletes it in the same guarded transaction as generation and retention (only if it is still open, still that occurrence, still a generated day and still due that long ago); a chore assigned by an older email waits for a run that knows the members' emails; a moved chore whose own occurrence day is still to come also gets that key in its template's `skippedOccurrences`, so generation never brings the day back; and the entry names the assignee resolved like every reader (email first) and records it in `households/{householdId}/stats/missed-recent` (`entries`: occurrence key, task, day, assignee uid and name; one per key, the last 90 days (`MISSED_KEEP_DAYS`, as far back as fair streaks look, so a pruned missed day never joins two streaks), at most 1000 (`MAX_MISSED_ENTRIES`), latest first; once the list is at that cap, days up to its oldest entry are unknown and a fair streak ends there, `missedHorizon` in `src/lib/chores/stats.ts`; `functions/src/shared/missed.ts`). One-time chores never expire. The page shows the last two weeks under To Do as a collapsed "3 missed in the last 2 weeks" list with what, whose and which day (`MissedRecently`, fed by the page's one live listener `useMissedEntries`, which also gives fair streaks the expired days, CH-19), so undone work stays visible after it leaves To Do. Upkeep results count them as `expiredChores`. Upkeep never regenerates a past day, so an expired day stays gone.
- Generation and reminders no longer depend on anyone opening the app.
- Generation is create-only and retention re-checks: inside each upkeep transaction a generated instance is written only if it is still absent, and a completed chore is purged only if it is still completed with the same `completedAt`, so overlapping hourly and on-demand runs never reset or remove work done in between. Instances are also created only if their source template is unchanged since the run read it (same update time), so editing or cancelling a recurrence while a run is in flight is never undone.
- Best-effort notification failures do not roll back chore writes.
- Every client that completes, undoes or reopens a chore must use `src/lib/chores/complete-client.ts` (the server actions); the rules deny unstamped client completions and any client write of the attribution fields. Completion needs a connection.
- A generated occurrence (`occurrenceKey`) gets at most one chore: upkeep skips a key that any chore already holds (read from the listing and re-checked inside the creating transaction), whoever it is assigned to.
- Field problems in every chore dialog are shown inline with `FieldError` (with `aria-invalid`/`aria-describedby`), never as toasts; failures use `toastError`, so raw Firebase text never reaches users.
- Motion follows the shared contract: under reduced motion (system or in-app) the checkbox, row entrance and exit, count tickers, podium, agenda slide and calendar moves show their end state instantly and confetti does not render; "House is clean" shows its finished, sparkling house at once. Hover effects are not used for meaning, and no animation delays content, focus or errors.
- Assignment forms show one-time date controls or recurring controls, never both.
- Active and completed chore instances use the same confirmation contract before permanent deletion.
- Future/completed view switches use the shared control dimensions; their thumbs must remain inside the track at desktop and mobile widths.

- Kid profiles (members with `kind: 'identity'`, docs/modules/devices/README.md) count wherever names, completions and the leaderboard appear, but are not offered as assignees yet (HO-15d): `assignablePeople` filters the assignee picker, the reassign menu and quick add (a current assignee stays listed). They get no chore reminders. `deviceAttribution` on a chore (written by tablet actions, F4) can never be added, changed or removed by a personal client, except removed together with the completion when a chore is reopened (`choreDeviceAttributionKept`).

- On a registered wall tablet (docs/modules/devices/README.md, "Device actions: chores"), Done, Undo and Take are device actions through the device action gate: the completion is credited to the person chosen in "Who's here?" (a kid profile included), with `completionId` equal to the action's opId and `deviceAttribution` on the completion; Take assigns only an unassigned chore (or is a no-op for one already the person's) and its Undo puts the previous assignment back while it is unchanged. The same eligibility (no completion before the household day), the same permissions (`chores.complete`, `chores.assign`) and the same Undo rules (only while the completion is still that one) apply. `completeChoresAs(db, householdId, input, ctx)` takes an operation context; the personal action passes `{ actor }` and behaves as before.

## Names and days (CH-10, CH-23)

- Chores without a room are called **Around the house** everywhere (the room filter, To Do groups, Add Chore, the library filter, the dashboard house and the House is clean moment); chores of a room that was removed are grouped under **Removed room** (the dashboard uses the same name). To Do groups by room id, never by name, so a room someone named "General" or "Around the house" stays its own group.
- The page's "today" (To Do, Future, overdue, streaks and the House is clean check) is the household's day, the same day the server generates and judges chores on (`useHouseholdToday`), not the device's; completion instants are read as household days too (Completed, completed today, and the stats via `computeChoreStats`'s `household` option, `{ today, timeZone, weekStartsOn }`, which also carries the household's week start, CA-16), so a device in another zone never drops or misdates a completion.
- Assigning a library chore as Repeats replaces its whole schedule: optional keys the new schedule leaves out (start, end, day options) are deleted, so an older end date never survives.
- With nothing left in To Do, the empty state says "All done for today" with the next chore, or "Nothing else is scheduled." when there is none; "Nothing is scheduled" shows only when nothing was done today either.
